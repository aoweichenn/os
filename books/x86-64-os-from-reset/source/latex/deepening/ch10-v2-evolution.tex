\section{从纵向原型走向长期系统}

v1.0 已经把 CPU 复位、ROM、磁盘加载、长模式、ELF64 Kernel、异常、分页、
中断、Ring 3、抢占、IPC、持久文件和交互式 Shell 串成一条真实路径。它证明
了一件重要的事：不借用现成固件、引导器和目标运行时，项目仍能让自己的程序
在 x86-64 硬件模型上运行。

但是，“能够运行”与“能够演进”是两个问题。v1.0 为了尽快贯通所有层，合理地
使用了四个 PCB、每进程八个描述符、一次性 ELF 装载、静态 Ring 0 栈和固定
布局文件系统。这些结构适合证明控制流，却不能自然回答下面的问题。进入 v1.1
后，静态 Ring 0 栈已经迁移为 KVA 动态双 guard 栈；此处保留 v1.0 名单，
是为了说明演进起点而非描述当前实现：

\begin{itemize}
  \item 第五个进程和第九个描述符从哪里得到空间，失败后怎样回滚？
  \item 一个 Process 有两个执行流时，PID、调度现场和退出状态分别属于谁？
  \item 一个虚拟区尚未被访问时，为什么必须立刻占用物理页？
  \item fork 后父子共享哪些对象，哪个写入动作才真正触发复制？
  \item 文件内容同时被 read、mmap、truncate 和 write 观察时，谁是权威副本？
  \item 磁盘更新在任意两个扇区之间断电时，重启后如何判断事务是否提交？
\end{itemize}

这些问题不能靠扩大数组解决。扩大数组只改变“什么时候耗尽”，不会建立身份、
所有权和失败原子性。第二周期的真正任务，是把第一周期为了闭环而合并的概念
重新拆开。

因此 v2 不是“继续增加系统调用”的清单。每一条新引用都必须能够回答四个问题：
谁创建，谁共享，谁最后释放，任一步失败后如何恢复调用前状态。

\subsection{所谓 Linux 对齐，是对象方法而不是源码数量}

现代 Linux 包含 SMP、网络、容器、权限、成百上千种设备和长期兼容接口。
教学内核若追逐这些表面数量，会迅速失去可解释性。本项目只对齐那些决定长期
正确性的结构：

\begin{itemize}
  \item Process 与 Thread 分离，调度器只选择 Thread；
  \item 地址空间、文件表、工作目录和信号处置通过显式引用共享；
  \item fd、FileDescription 与 Vnode 分属三层身份；
  \item VMA 与 PTE 分别表示软件策略和硬件驻留；
  \item CachePage、BlockRequest、journal transaction 和磁盘块各有状态；
  \item 容量由动态分配器与运行时 limit 决定，不由固定数组形状决定。
\end{itemize}

SMP、网络、USB、AHCI/NVMe、动态链接和完整 POSIX 不进入 v2.0。虚拟内存
也主动延后 writable \code{MAP_SHARED}、\code{msync}、swap、overcommit
和 OOM killer。这个边界使单核系统中的共享对象、阻塞点与故障恢复可以真正
完成，而不是留下大批只能成功一次的接口。

\subsection{CPU 特性也是平台契约}

“x86-64”不是单一、永远不变的特性集合。长模式、NX、SSE2 和
\code{SYSCALL/SYSRET} 都需要相应 CPUID 或 MSR 支持。若开发机、CI 和发布
机器让 QEMU 自动选择不同 CPU 型号，同一镜像可能走不同指令路径。

第二周期因此冻结正式 QEMU CPU 型号和必需 CPUID 摘要。Kernel 启动时验证
long mode、NX、SSE2 与 SYSCALL，缺少任一必需能力都必须在使用前明确拒绝。
v2.0 使用 \code{FXSAVE/FXRSTOR} 保存 x87、MMX、SSE 与 SSE2 现场；AVX
和 XSAVE 保持禁用。这样既完整保存现代 C++ 编译器可能使用的基础扩展现场，
又不提前引入可变长度 XSAVE area、XCR0 和更多 CPUID 叶。

\subsection{三类 RAM 配置回答不同问题}

要求 64 MiB 同时承担最大并发，会迫使实现为低内存重新引入狭窄固定表；
只运行 64 GiB，又会隐藏小内存下的分配失败。三种配置必须分工：

\begin{longtable}{L{0.16\textwidth}L{0.13\textwidth}L{0.18\textwidth}L{0.39\textwidth}}
\toprule
\textbf{配置} & \textbf{RAM} & \textbf{容量下限} & \textbf{提供的证据}\\
\midrule
bootstrap & 64 MiB & 不规定对象规模 & 复位、启动链、异常、基础分页和历史失败镜像\\
functional & 256 MiB & 64 Process、128 Thread、256 fd、128 pipe & PID1、VM、线程、信号、TTY 和持久化完整功能\\
capacity & 64 GiB & 256 Process、512 Thread、4096 fd、1024 pipe & 全 RAM、4 GiB 以上访问、规模压力与 soak\\
\bottomrule
\end{longtable}

functional 要求单 Process 至少 32 Thread，capacity 要求至少 64 Thread。
capacity 还要求 1 GiB 稀疏镜像、256 MiB rootfs、64 MiB 单文件、32 个
独立 ELF 和 16 级流水线。64 GiB 是验收规格，不是实现上限；真实上界仍由
E820、\code{CPUID.80000008H}、64 TiB direct-map 与资源限制共同决定。

\section{单 BSP 仍然需要严格的并发模型}

“只有一个 CPU，所以没有并发”是早期内核最危险的误解之一。Thread 在 Ring 0
执行时，PIT、键盘或 ATA IRQ 仍可打断它；系统调用检查条件之后、登记等待之前，
IRQ 也可能改变条件。即使任一时刻只有一条普通指令流，控制权仍会在不受 C++
调用图表达的位置切换。

\subsection{为什么选择中断可进入、内核不可抢占}

早期 Unix 内核常让进程在内核中主动睡眠，而不是在任意内核指令处被调度器
换走。这降低了锁和栈生命周期的组合数量。v2.0 采用同样适合教学的边界：

\begin{itemize}
  \item IRQ 可以打断允许中断的 Ring 0 代码；
  \item 普通 Thread 在 Kernel 中不会被时钟强制换走；
  \item 调度只发生在显式阻塞、让出、Thread 退出和返回用户态之前；
  \item IRQ handler 只提交有界状态、唤醒等待者并设置重调度标记；
  \item IRQ handler 永不睡眠、取得 sleep mutex 或访问可能 fault 的用户页；
  \item NMI 不进入通用锁、等待、日志和用户复制路径。
\end{itemize}

这个模型不是“没有抢占”。用户态仍会被 PIT 抢占；区别在于 Kernel 的普通
调用链不会突然消失。以后若引入内核抢占，必须把禁止抢占计数、锁语义和每个
临界区重新审计，那属于 v2.x 之后的独立工程。

\subsection{三类锁解决三种控制权关系}

\begin{longtable}{L{0.22\textwidth}L{0.29\textwidth}L{0.35\textwidth}}
\toprule
\textbf{原语} & \textbf{保护对象} & \textbf{绝对禁止}\\
\midrule
\code{SpinLock} & 只由 Thread 上下文访问的短提交区 & 睡眠、调度、用户复制、无界循环和日志\\
\code{IrqSaveSpinLock} & Thread 与当前 BSP IRQ 共享的短状态 & IRQ 递归取得、睡眠和长设备操作\\
\code{Mutex} & Thread 上下文中的长临界区 & IRQ/NMI 使用、持有 spinlock 后等待\\
\bottomrule
\end{longtable}

irq-save 锁必须保存进入前的 IF 并在释放时恢复原值，不能无条件 \code{STI}。
否则调用者原本处于关中断提交区时，内层释放会意外开放 IRQ。sleep mutex
竞争失败时把 Thread 放入 WaitQueue；它节省 CPU，但意味着临界区中的对象
必须允许当前 Thread 离开。

\subsection{WaitQueue 必须只有一个完成者}

一个读取动作可能同时遇到“数据到达、deadline 到期、signal 到达、fd 关闭”。
若四条路径各自把 Thread 变成 Ready，就会重复入队、重复发布引用，甚至让
同一个内核栈被两个调度实体使用。

WaitQueue 因而包含单赢家 WakeReason：

条件检查与登记等待必须处于同一个受保护提交区。唤醒只说明“条件曾经变化”，
Thread 恢复后仍要在对象锁下重新验证条件；这就是避免 lost wakeup 与错误
资源预留的共同基础。

\section{Process、Thread 与用户边界}

\subsection{资源容器和执行现场为什么必须分开}

\begin{longtable}{L{0.20\textwidth}L{0.30\textwidth}L{0.34\textwidth}}
\toprule
\textbf{对象} & \textbf{拥有的状态} & \textbf{生命周期终点}\\

Thread 状态中的 Exited 与 Process Zombie 不能共用一个枚举。前者说明执行流
不再调度，后者说明父 Process 尚未取得退出结果。把两者合并会让 join、wait
和“最后一个 Thread 退出”互相覆盖。

\subsection{原生系统调用入口为什么晚一个版本}

Process/Thread 是软件对象模型；SYSCALL 是体系结构入口。把两者塞进同一提交，
入口栈错误会表现成调度器损坏，调度引用错误又会表现成 SYSRET 故障。因此
v1.2 先在现有 \code{INT 0x80} 上证明新调度对象，v1.3 再加入原生入口。

SYSCALL 不自动切换到内核栈。入口必须先 \code{SWAPGS} 取得可信 CpuLocal，
保存用户 RSP，再加载 current Thread 的 Ring 0 栈。返回前要验证 RIP/RSP
canonical、RFLAGS 和段状态；只有安全快速路径使用 \code{SYSRETQ}，其余
合法现场使用 \code{IRETQ}。不能让用户构造的非 canonical RCX 在 SYSRET
处把故障带到错误特权上下文。

\subsection{多线程中的 fork、exec 与退出}

这些语义必须在开放用户线程之前冻结：

\begin{longtable}{L{0.17\textwidth}L{0.65\textwidth}}
\toprule
\textbf{操作} & \textbf{v2.0 语义}\\
\midrule
fork & 子 Process 只复制调用 fork 的 Thread；父 Process 的其他 Thread 不出现在子进程\\
exec & 先在候选 AddressSpace 中读取、验证和构造映像；成功后才汇合兄弟 Thread 并原子替换，失败保持原 Thread 组可运行\\
ThreadExit & 只发布当前 Thread 的栈、现场、TLS 与等待关系\\
ProcessExit & 终止整个 Thread 组，发布共享资源，并给父 Process 留下 Zombie\\
signal & disposition 属于 Process，mask 属于 Thread；交付时选择一个未屏蔽的 Thread\\
wait & 只观察子 Process，不暴露内部 Thread 对象\\
\bottomrule
\end{longtable}

exec 的参数环境合计至少 128 KiB。这个容量明显大于动态内核栈的合理预算，
所以字符串必须暂存在一组可回收页里，验证完成后再构造用户栈。失败时释放候选
页，原 AddressSpace、兄弟 Thread 与 fd 表保持不变。

\subsection{波次 A：先让资源和执行实体有真实生命周期}

\paragraph{v1.1：资源地基不提前拆除现有进程}

已有 64 GiB direct-map 解决的是“物理页可以被访问”，还没有解决“不同尺寸
对象如何释放”和“内核虚拟区间如何安排”。v1.1 增加 buddy、可释放 kernel
heap/type cache、KVA allocator、动态 guard stack 与中间页表回收。

已经闭环的六个增量分别是动态 RAM/direct-map、64 KiB 可回收 kernel heap、
双位图 buddy、固定尺寸 type cache、KVA allocator 和动态内核栈。heap
以边界标记、best-fit、双向合并
和 100000 步模型证明
字节块生命周期；buddy 在同一页状态机上提供 order 0 兼容路径、连续块、
错阶拒绝、递归分裂/合并与另一组 100000 步模型。64 MiB/64 GiB QEMU 都
写回并回收八页连续块。type cache 用一个 heap 后备块、活动位图与槽内空闲链
完成另一组 100000 步模型，QEMU 耗尽、复用并销毁 32 槽后恢复 heap 基线。
这些分配层彼此不冒充；KVA 继续只表达虚拟区间所有权。

KVA allocator 只管理虚拟区间，不隐式拥有物理页。动态内核栈已经先取得
六页连续虚拟区，再把四个不连续物理帧映射到中间，并在两端留下
not-present guard。终止后先回到永久启动栈安全点，销毁顺序固定为撤销映射、
失效 TLB、清零并释放物理页、归还 KVA。单元、集成、100000 步随机模型和
正常/\#UD/\#PF 三条 QEMU 路径都要求累计创建等于销毁、活动栈归零。

本版本刻意保留四 PCB 和静态用户演示通路，但栈资源本身已先完成动态迁移。
若在 Process/Thread 尚不存在时删除 PCB，主分支会落入既没有旧对象也没有
新对象的真空。v1.2 对等验收通过后再迁移调度对象所有者；v1.1 尚余的资源
闭环是空 PT、PD 和 PDPT 回收。

\paragraph{v1.2：调度 Thread，并补全扩展现场}

v1.2 建立 Process/Thread、动态 run queue、WaitQueue/WakeReason 和三类锁。
调度随机模型必须在每一步验证 Ready、Running、Blocked、Exited 集合互斥，
并区分 Thread Exited 与 Process Zombie。

上下文不只有通用寄存器。x87 控制字、SSE 寄存器和 MXCSR 若不按 Thread
保存，一个线程的浮点计算会污染另一个线程。\code{FXSAVE} 区域需要 16 字节
对齐；创建时用确定初值初始化，切换时与通用现场一起归属于 Thread。

\paragraph{v1.3：CpuLocal 与原生入口单独验收}

本版本配置 STAR、LSTAR、FMASK 与 EFER，建立 SWAPGS、可信入口栈、统一
UserContext、canonical 检查及 IRET fallback。INT 0x80 继续存在，双入口对
同一调用必须产生相同副作用。这样架构入口错误不会与对象迁移错误混在一起。

\paragraph{v1.4：fd 只是局部引用}

FileTable 分块增长；fd 只是在某个 Process 中寻找引用的非负整数。
FileDescription 保存共享偏移和 file status flags，Vnode 表示底层命名对象。
duplicate 得到新 fd 但共享 FileDescription，独立 open 得到新
FileDescription。close-on-exec 是 fd flag，不能错误放入共享对象。

安装新 fd 采用两阶段提交：先获得对象引用与表容量，再在锁内发布槽位。任一
准备步骤失败都不能让半初始化 fd 对用户可见。

\subsection{波次 B：命名空间先于磁盘格式}

\paragraph{v1.5：用 memfs 和旧格式证明 VFS}

VFS 的价值是让 Path、Mount、Vnode 与 FileDescription 不依赖某一种 inode
字节布局。memfs 提供完整、快速、可随机测试的语义后端；legacy-fs 适配器只
实现读取、基础创建和 v1.0 回归所需子集。

完整 rename、unlink 与 truncate 不强塞给旧格式。v2.0 也不要求正/负 dentry
cache，因为缓存会新增失效、引用和并发状态，却不改变核心命名语义。先证明
\code{.}、\code{..}、根夹取、相对路径与挂载遍历，再谈加速。

\paragraph{v1.6：rootfs v2 只改变持久布局}

新格式加入版本化 superblock、inode/数据位图、目录项和直接/间接块。由于
VFS 已稳定，Shell 和用户 ABI 不知道磁盘格式已经更换。独立 mkfs 负责构造，
只读 fsck 负责从根遍历、核对位图与引用；Kernel 不得用自动格式化掩盖未知
非零磁盘。

本阶段建立完整 rename/unlink/truncate 和 ENOSPC 原子失败，但尚不引入
journal。先证明正常写集合与 flush 后的一致性，才能知道后续 journal 应该
保护哪些元数据。

\paragraph{v1.7：PID1 终结内嵌程序脚手架}

正常 Kernel 从 VFS 读取 \code{/sbin/init}，由 PID1 启动 Shell 并回收孤儿。
ELF 仍执行两遍验证：先验证所有结构和范围，再创建候选 AddressSpace。exec
失败不能破坏调用进程；成功提交才替换映像。

第一周期内嵌的 Shell、producer、consumer 和 worker 可以保留为根文件系统
不可信时的故障载荷，却不能再成为生产启动依赖。

\subsection{波次 C：地址意图、文件驻留与复制依次建立}

\paragraph{v1.8：匿名 VMA 是页故障的策略来源}

VMA 记录半开区间、权限、来源和映射策略。匿名 \code{mmap}、\code{brk} 与
guarded stack 先只登记意图；首次访问才分配 zero-fill 页面。PTE 只记录当前
是否驻留和硬件权限，不能取代 VMA。

split、merge 与 unmap 的随机模型必须保证区间永不重叠，失败时原树不变。
用户 heap 在该层之上用 freestanding C++20 构建，耗尽时返回明确错误而不是
依赖宿主运行时。

\paragraph{v1.9：文件页先保持 clean}

文件 VMA 通过 \code{(Vnode, page index)} 定位唯一权威 CachePage。多个
进程同时 fault 同一页时，只允许一个页面完成安装；其他请求引用它。LRU 可
直接丢弃 clean 页，因为内容能够从 rootfs 重读。

v2.0 支持 \code{MAP_PRIVATE} 与只读 \code{MAP_SHARED}。文件 write 或
truncate 必须失效相关 cache page 并撤销映射，不能让已有 PTE 永久指向旧
内容。本阶段没有 dirty/writeback，从而把“文件页身份”与“异步回写”分开。

\paragraph{v1.10：COW 是三个层次的协作}

fork 把父的私有可写页改为只读 COW，并增加物理页引用。写页故障必须同时检查
VMA 允许写、PTE 表示 COW、物理页引用关系有效；三者缺一都不能复制。

Kernel 的 \code{CopyToUser} 也会写用户页。若它绕开只读 PTE 直接通过
direct-map 修改物理页，父子隔离会被悄悄破坏。因此 user-copy 必须调用同一
COW break 逻辑。fork 在中途耗尽时还要恢复父 PTE 权限和全部引用。

\paragraph{v1.11：Unix I/O 证明对象可以组合}

pipe、duplicate、继承、close-on-exec 和重定向让独立程序形成资源图。外部
Shell 只保留改变自身 cwd、环境和作业状态所必需的内建命令；约 12 个核心
工具覆盖文件、目录、文本、进程和流水线。32 个工具是 v2.0 广度目标，不必
在第一次 I/O 组合闭环里一次写完。

16 级流水线的关键不是字符数量，而是任一中间 pipe/fork/duplicate/exec
失败后，Shell 能关闭所有临时端点。否则一个隐藏写端会让最末读者永远看不到
EOF。

\subsection{波次 D：共享地址空间中的并发和交互}

\paragraph{v1.12：TLS 与 private futex}

ThreadCreate 为每个用户 Thread 建立独立 user stack、Ring 0 stack 与
FS-base TLS。private futex 以 AddressSpaceId 和对齐用户 VA 为键，而不是
物理页地址；COW、页迁移和相同 VA 的不同进程因此不会错误合并等待队列。

compare-and-block 要在同一受保护事务中重新读取用户值并登记等待。munmap、
exec 和 ProcessExit 必须以 cancellation WakeReason 移除相关 waiter，不能
让内核长期持有已经失效的用户虚拟地址。

\paragraph{v1.13：时间先成为统一 deadline}

PIT tick 在第一周期只支持调度与毫秒日志。timed wait 需要统一的 64 位
monotonic time、溢出安全换算和 deadline queue。条件满足与 deadline 到期
仍竞争同一 WakeReason。sleep 必须阻塞；系统无 Ready Thread 时继续通过
相邻 \code{sti; hlt; cli} 等待硬件。

\paragraph{v1.14：signal 是异步用户控制流}

signal disposition 属于 Process，mask 属于 Thread。交付 handler 时，
Kernel 在验证后的用户栈上构造 signal frame；sigreturn 必须像系统调用返回
一样验证 canonical RIP/RSP、RFLAGS 和段状态。畸形 frame 只能终止目标
Process，不能 panic Kernel。

阻塞 syscall 必须逐项规定：已经传输部分字节时返回部分进度，尚无进度时是
中断错误还是自动重启。模糊的“一律重试”会让非幂等操作重复执行。

\paragraph{v1.15：TTY 把键盘事件变成作业语义}

TTY 位于 PS/2 字符与用户 read 之间，拥有输入模式、控制字符、session 和
foreground process group。Ctrl-C 不再是 Shell 自己解析的字节，而是 TTY
向前台进程组发送 signal。后台组读取控制终端必须被阻止，Shell 在前台作业
停止或退出后重新取得终端。

\subsection{波次 E：异步完成、崩溃恢复和冻结}

\paragraph{v1.16：BlockRequest 先于 journal}

轮询 ATA 时，发出命令的 Thread 占据 CPU 等待设备。IRQ14 模型把一次 I/O
表示为 BlockRequest：Thread 提交后进入 WaitQueue，IRQ 推进有限状态并完成
请求，其他 Ready Thread 可以运行。

页缓存此时才增加 clean、dirty、writeback 和 error 状态。dirty 上限产生
backpressure；写回失败不能把页面伪装为 clean。请求完成、超时和设备错误仍
必须由单赢家状态决定。

\paragraph{v1.17：ordered metadata journal}

journal 只保护元数据。每个事务在修改前预留 credits，依次写 descriptor、
元数据与 commit；与元数据相关的文件数据必须先稳定，commit 才允许落盘。
设备 FLUSH CACHE 是顺序的一部分，不是可选性能提示。

\paragraph{v1.18：冻结是一种工程能力}

最后一个开发版本停止增加基础机制，冻结 syscall 号、错误、结构布局、时间、
signal 和 ELF 契约。最小 devfs/procfs 提供设备与只读观察面，用户工具补齐
到 32 个，但不能要求新 Kernel 机制。

网站是独立仓库，教材又生成 PDF，因此“来自同一提交”不够精确。发布清单必须
记录主仓 SHA、web SHA、Sites 保存版本、PDF 哈希、目标代码量、QEMU 版本和
CPU 特性摘要。公开页面只有在这些身份一致时才能标为发布。

\section{测试频率是路线的一部分}

若每次提交都运行完整 64 GiB soak，反馈太慢；若只在发布前运行，容量错误又
会积累数月。测试按风险和成本分层：

\begin{longtable}{L{0.22\textwidth}L{0.60\textwidth}}
\toprule
\textbf{时机} & \textbf{必需证据}\\
\midrule
每次提交 & 受影响单元/集成/固定种子随机测试，64 MiB boot，256 MiB smoke\\
每个小版本 & 全部宿主测试、目标产物审计、完整 256 MiB functional\\
nightly / 候选发布 & 完整 64 GiB capacity、soak、故障和崩溃点矩阵\\
v2.0 发布 & 三种配置、所有故障镜像、教材/网站构建与发布溯源\\
\bottomrule
\end{longtable}

单元测试回答局部状态机，集成测试回答模块交接，固定种子随机测试回答大量操作
序列中的不变量，QEMU 回答真实指令、页表、中断和设备是否按预期发生。四类
证据不能互相替代。

第二周期还增加跨模块 oracle：

\begin{itemize}
  \item ResourceSnapshot 比较 frame、KVA、heap、Process、Thread、Vnode、
        CachePage 与 BlockRequest 的守恒；
  \item WaitQueue oracle 验证每次等待只有一个 WakeReason 和一次 Ready；
  \item UserContext oracle 比较双 syscall 入口并拒绝非法返回现场；
  \item AddressSpace oracle 验证 VMA 不重叠、PTE 权限来源和 COW；
  \item PageCache oracle 验证每个文件页只有一个权威副本及正确失效；
  \item journal oracle 验证旧/新事务二选一、replay 幂等和 fsck 一致。
\end{itemize}

随机失败要输出种子、迭代位置和最后成功操作；崩溃失败还要输出断电点、镜像
哈希、journal 序号和首个 fsck 不一致。只有这样，“随机”才是可复现工程证据。

\section{v2.0 是发布，不是最后一次冒险}

v2.0 本身不增加核心机制。它只整合 v1.1 至 v1.18 已经冻结的实现，并证明：

\begin{itemize}
  \item 64 MiB bootstrap、256 MiB functional 和 64 GiB capacity 全部通过；
  \item \code{/sbin/init -> /bin/sh -> /bin/*} 不依赖内嵌生产用户载荷；
  \item 256 Process、512 Thread 能完成 VM、I/O、signal、TTY 与资源回收；
  \item 所有单元、集成、随机、产物、QEMU、soak 与崩溃恢复测试通过；
  \item Kernel 和用户 ELF 不链接宿主运行时，不含隐藏构造器和未解析符号；
  \item 文档、教材、手机导出、网站和发布清单能够追溯到精确版本。
\end{itemize}

任何在冻结期才想到的新机制都进入 v2.x。真正成熟的版本不是功能最多的版本，
而是边界、失败语义和证据已经稳定到足以让下一位读者复现、解释并继续演进的
版本。
