\section{Shell 怎样用 fd 和 Pipe 连接程序}

Shell 解析出流水线以后，要建立由 Process、fd、FileDescription、Pipe、
物理页和等待队列组成的关系。相同的输出文本只覆盖成功路径；v1.11 还要求
失败路径把这些对象逆序回收到基线。

\topic{历史动机：为什么是 fd、fork、exec 和 pipe}
早期计算机常为终端、磁带和磁盘提供互不相同的调用。程序若想把一种设备的
结果交给另一程序，就必须知道双方的具体记录格式。Unix 选择把普通文件、
终端和管道统一放在小整数 file descriptor 后面，约定 fd 0、1、2 分别是
标准输入、标准输出和标准错误。统一的是连接方式，不是底层对象的全部语义。

\begin{center}
\begin{osgridtabular}{lll}
描述符 & 程序动作 & 实际对象可变化为 \\ \hline
0 & read & 终端、普通文件、管道读端 \\ \hline
1 & write & 终端、普通文件、管道写端 \\ \hline
2 & write diagnostic & 终端或独立日志目标 \\ \hline
\end{osgridtabular}
\end{center}

\code{fork} 保留父进程资源视图，\code{exec} 替换程序映像。两者分开，
恰好在中间留下“修改 child 的 fd 图”的窗口。Shell 无需链接 \code{cat}
或理解 \code{wc}，只需要让前者的 fd 1 与后者的 fd 0 指向同一条 Pipe，
然后分别 exec 两个磁盘 ELF。

管道是无消息边界的字节流。一次 write 可能对应多次短 read，一次 read 也
不表示取得某次 write 的完整数据。生产者必须处理短写和背压，消费者必须
处理短读和 EOF。这一选择牺牲记录边界，却让文本、二进制数据和设备流都能
使用同一组合规则。

\topic{四层对象分别拥有哪一种事实}
一条管道的“端点”至少横跨四层：

\begin{center}
\begin{osgridtabular}{L{0.22\linewidth}L{0.25\linewidth}L{0.40\linewidth}}
层次 & 所有者 & 保存的事实 \\ \hline
fd number & 单个 Process & FileTable 中的局部名字与 fd flags \\ \hline
FileTable entry & 单个 FileTable & 对 FileDescription 的强引用 \\ \hline
FileDescription & KernelObject manager & 读/写能力、共享状态与 finalizer \\ \hline
Pipe & PipeManager slot & 字节、索引、端点状态、等待条件与后备页 \\ \hline
\end{osgridtabular}
\end{center}

\code{dup2(3,0)} 复制的是强引用，不是 Pipe 数据。fork 后 parent 与 child
拥有独立 FileTable，但表项仍可引用同一个 FileDescription。对普通文件，
这意味着 offset 共享；对 Pipe reader，则意味着关闭一个 duplicate fd
不一定关闭逻辑读端。只有最后一个 FileDescription 强引用消失，finalizer
才通知 PipeManager 关闭真正端点。

若把 fd 直接当成 Pipe 数组下标，fork 后无法表达独立表和共享对象；若每次
duplicate 都复制 FileDescription，又会错误产生多个逻辑 reader/writer。
因此分层不是面向对象形式，而是 Unix 语义所要求的所有权边界。

\topic{64 KiB 逻辑容量为什么按 4 KiB 页承诺}
历史启动探针继续使用 64 字节固定环形缓冲。普通用户管道则具有
\(65536\) 字节逻辑容量，分成

\[
  \frac{65536}{4096}=16
\]

个后备页槽。刚创建时 buffered 和 allocated page count 都为零。写入某个
页覆盖的区间时才经 allocator callback 取得物理 frame，并通过 direct-map
访问它。于是 1024 条空 capacity Pipe 不会仅因声明容量就预占 64 MiB。

环形状态保存 read index、write index 和 buffered byte count。索引相等时，
buffered 区分空与满；可写空间始终为

\[
  \mathrm{writable}=65536-\mathrm{buffered}.
\]

任一逻辑字节位置 \(i\) 映射为

\[
  \mathrm{page}=\left\lfloor\frac{i}{4096}\right\rfloor,\qquad
  \mathrm{offset}=i\bmod4096.
\]

Pipe 不理解 E820、buddy 或页表层级。它只调用固定签名的页 acquire/release
回调；ProcessRuntime 把回调接到生产物理页生命周期。这样宿主测试能注入
确定性内存，目标 Kernel 又能使用真实 frame。

\topic{跨页写入是一项小型事务}
一次写可能同时触及多个尚未分配的页。若第一页和第二页申请成功、第三页失败，
不能推进 write index，也不能把前两页永久留给一条并未提交数据的操作。
实现先收集所需页，再逐页准备：

\begin{enumerate}[label=\arabic*.]
  \item 计算本次可提交的字节区间和缺失页；
  \item 为每个缺失页申请、清零并暂记所有权；
  \item 任一申请失败，只逆序归还本次新页；
  \item 全部页面准备完成后复制字节；
  \item 最后一次性推进 write index、buffered 和统计。
\end{enumerate}

释放同样不能先把地址槽清零、再尝试归还页面。若 release callback 报错而
槽已经遗忘地址，系统会把“仍拥有 frame”伪装成“已经释放”。当前实现只在
释放成功后清除已保存地址，使故障仍可审计。

\topic{EOF、WouldBlock 与 BrokenPipe 的状态推导}\par
\begin{center}
\begin{osgridtabular}{L{0.32\linewidth}L{0.27\linewidth}L{0.28\linewidth}}
状态 & read & write \\ \hline
空且 writer 存活 & WouldBlock & 可推进 \\ \hline
存在数据 & 返回当前可用短读 & 取决于剩余空间 \\ \hline
空且 writer 全关闭 & EOF & 不适用 \\ \hline
reader 全关闭 & 不适用 & BrokenPipe \\ \hline
满且 reader 存活 & 可读 & WouldBlock \\ \hline
\end{osgridtabular}
\end{center}

EOF 不是写入缓冲的特殊 byte，而是“未来不可能再出现数据”的生命周期结论。
writer 关闭时已有数据仍必须被 reader 排空；缓冲变空后的下一次 read 才返回
EOF。相反，只要任何 reader 强引用仍在，writer 就不能得到 BrokenPipe。

WouldBlock 也不是失败。用户包装先执行 try；只有条件暂不满足时才进入
WaitQueue，唤醒后重新检查条件。唤醒只表示状态可能改变，不预留字节，也
不能替代循环复验。Pipe 锁内禁止调度、串口输出和用户地址复制。

\topic{PipeManager 把容量、身份和回收集中起来}
单个全局 Pipe 无法实现 \code{pipe()}。PipeManager 持有最多 1024 个槽，
按 RAM 档开放 8、128、1024 项。槽位限制控制同时存活的流对象，lazy page
控制实际数据内存，两者解决不同维度。

创建先取得空槽并初始化两端。接着 ProcessRuntime 依次建立 reader
FileDescription、writer FileDescription、reader fd 和 writer fd。任何一步
失败都逆序关闭已经取得的对象，用户只会观察到完整的 16 字节 fd pair 或一个
明确错误。两端最后关闭后，manager 释放所有页并归还槽。

启动自检先占满本档所有槽，下一次创建必须被拒绝，再关闭全部对象。整机结束
只打印一次 capacity、active、peak、creation、release 和 rejection 摘要；
逐 Pipe、逐页和逐字节日志会改变调度时序，因此被禁止。

\topic{dup2 为什么必须精确且原子}
普通 duplicate 寻找不低于 minimum 的最小空 fd。流水线却必须把端点放在
精确的 0 或 1：

\begin{verbatim}
dup2(previous_pipe.reader, 0)
dup2(next_pipe.writer, 1)
\end{verbatim}

FileTable 的 \code{DuplicateTo} 先验证 source 和目标范围，需要时在锁外
准备新的 chunk；重新加锁后复验 source、取得新强引用并替换目标 entry。
旧目标引用在解锁后释放，因为 finalizer 可能进入 VFS、关闭 Pipe 或唤醒
Thread，不能在 FileTable 锁内执行。

source 等于 destination 必须直接成功。若错误地先关闭 destination，唯一
source 就会同时消失。fd 的 close-on-exec 属于 entry，FileDescription 的
offset 和访问状态属于共享对象；duplicate 时不能把两种 flags 混成一份。
functional hard limit 在本阶段提高到 512，capacity 保持 4096。

\topic{先完成纯解析，再允许任何系统调用}
若 Shell 边读字符边 fork，输入末尾的未闭合引号可能发生在三个 child 已经
创建之后。v1.11 先把整行转换为自包含的
\code{ShellExecutionPlan}：

\begin{verbatim}
storage[513]
arguments[128]
stages[16]
argument_count
stage_count
\end{verbatim}

argument 只保存 storage 内的 offset 和 length，stage 保存参数区间以及可选
输入/输出路径。解析器识别空格、单引号、双引号、反斜杠、\code{|}、
\code{<}、\code{>}，并拒绝空 stage、重复重定向、缺失路径、悬空转义、
未闭合引号和容量超限。任一拒绝都把输出计划保持为零，不产生 Process、fd
或 Pipe 副作用。

每 stage 暂限 8 个参数，完整计划用 \code{static\_assert} 保持在 4096
字节以内。用户栈 VMA 虽预留 8 MiB，却只允许相邻页面逐步增长；过大的单个
局部对象会让函数序言跨过未提交页，被 Kernel 正确判为非法 stack jump。
未来可把更大计划放入 UserHeap，本阶段不放宽栈安全策略来掩盖局部对象设计。

\topic{十六级流水线必须并发启动}
对 \(N\) 个 stage，parent 先创建 \(N-1\) 根 Pipe，然后依次 fork 全部
child，不在单个 stage 后立即 wait。child \(i\) 执行：

\begin{enumerate}[label=\arabic*.]
  \item 若 \(i>0\)，把前一 Pipe reader duplicate 到 fd 0；
  \item 若 \(i+1<N\)，把后一 Pipe writer duplicate 到 fd 1；
  \item 应用 \code{<} 与 \code{>} 打开的文件描述符；
  \item 关闭全部临时 Pipe fd；
  \item 从 rootfs exec 对应 \code{/bin/*} ELF。
\end{enumerate}

parent 在 fork 全部 stage 后关闭自己持有的全部端点，再 wait 每个 child。
若先运行并等待 stage 0，它输出超过 64 KiB 时会等待空间，而 stage 1 尚未
启动，系统形成确定性死锁。若 parent 或无关 child 遗留 writer，末端 reader
则永远看不到 EOF。

输出重定向使用 write、create、truncate 打开目标，再 duplicate 到 fd 1；
输入重定向以 read 打开并 duplicate 到 fd 0。改变的是 child 的表，parent
标准输出不变，所以下一条 prompt 不会落入文件。本阶段明确不支持 append、
stderr 重定向、here-document、环境展开和作业控制。

\topic{没有 libc 的十九个核心工具}
\code{core\_tool.cpp} 是 freestanding multi-call ELF。它从自研
\code{argc/argv} 栈取得 \code{argv[0]} 的 basename，并分派为不同工具：

\begin{center}
\begin{osgridtabular}{L{0.28\linewidth}L{0.56\linewidth}}
组合面 & 工具 \\ \hline
输出与退出状态 & help、echo、true、false \\ \hline
流式 stdin/stdout & cat、wc、head、tee \\ \hline
cwd 与目录 & pwd、ls \\ \hline
元数据 & stat \\ \hline
命名空间修改 & mkdir、touch、rm、rmdir、mv \\ \hline
文件内容与长度 & write、truncate \\ \hline
持久化 & sync \\ \hline
\end{osgridtabular}
\end{center}

所有 I/O 都经过自研 wrapper；十进制转换使用固定缓冲，字符串扫描有上界，
不调用 libc、iostream、malloc 或宿主 API。一个 ELF 共享实现代码，但
rootfs 中的 19 个路径、每次 fork/exec、每个 Process 的 fd 图都是真实的。
只有 \code{cd} 和 \code{exit} 留在 Shell，因为 child 无法修改 parent cwd，
也不能替 parent 退出交互循环。

\topic{失败路径为什么必须等待已经发布的 child}
第 \(k\) 个 fork 失败时，前 \(k\) 个 child 已经可以运行。parent 必须先关闭
全部 Pipe fd，使被阻塞 child 得到 EOF 或 BrokenPipe，再 wait 已发布孩子。
直接返回 prompt 会遗留 Zombie 和 FileDescription 强引用。child 接线失败
以 126 退出，exec/查找失败以 127 退出，不能返回 Shell 主循环，否则会产生
第二个交互 Shell 争用同一键盘 FIFO。

这是一条跨层逆序：

\begin{verbatim}
parse plan
  -> create Pipe slots and endpoint descriptions
  -> install parent fds
  -> fork children
  -> child dup2/close/exec
  -> parent close temporary fds
  -> wait all children
  -> release FileDescriptions, Pipe pages and slots
\end{verbatim}

每一层只释放自己已经取得的所有权。Pipe finalizer 不销毁 Process，
ProcessTree 不直接清空 Pipe 槽，Shell 也看不到 Kernel 对象地址。

\topic{五层证据怎样共同闭合}
单元测试验证 lazy page、跨页、回绕、EOF、BrokenPipe、分配失败回滚、
128 槽 manager、dup2 精确替换和 16 stage 解析。集成测试占满 1024 条 Pipe，
验证额外创建拒绝、全部端点关闭和槽复用。固定种子动态 Pipe 模型执行
100000 次操作；Shell 随机测试输入 4096 条任意 byte 序列并检查成功计划
或失败清零。

64 MiB bootstrap QEMU 真实执行基础外部工具；256 MiB functional 再通过
QMP 键盘逐字输入两次重定向和一条 16 级流水线。该流水线包含 echo、多个
cat、tee、head 和 wc，因而同时覆盖 15 根 Pipe、短读写、EOF、文件输出和
全部 child wait。

最终 functional 证据要求：

\begin{itemize}
  \item 88 个 Process 创建和回收，87 次 wait 成功；
  \item Pipe capacity 为 128，active 为 0，peak 精确为 128；
  \item creation 与 release 均为 143，rejection 至少一次；
  \item \code{REDIRECTION\_VERIFIED} 两次，
        \code{PIPELINE\_16\_VERIFIED} 一次；
  \item Zombie、FileDescription、用户页、页表和动态 Pipe 后备页回到基线。
\end{itemize}

测试总数会随着实现变化。稳定要求是：每层检查的性质明确、随机种子可复现、
QEMU 生命周期有截止时间，并且成功路径不能出现 Kernel fatal、panic 或
资源差异。
