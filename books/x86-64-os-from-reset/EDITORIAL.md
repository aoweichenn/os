# 书稿编辑手册

这份文件写给维护书稿的人，不进入教材正文。它把技术审校与文字编辑分开：
检查表留在这里，读者在书中看到的应当是问题、实验、代码和推理。

## 成文目标

书中的代码来自同一个可运行项目。每一章只增加当前阶段需要的能力，并通过
QEMU 输出、宿主测试或磁盘检查观察结果。读者遇到新的硬件概念时，先知道它
解决什么具体问题，再回到代码中看它怎样工作。

技术准确和自然叙事需要同时成立。不能用抽象名词掩盖控制流，也不能以“去
AI 化”为理由删掉地址、位宽、寄存器状态、失败路径和实验条件。

前三章面对完全零基础读者。需要理解 CPU、ROM、时钟、寄存器和总线的内容
必须放在正文，不能用几页摘要代替后再把真正解释放进附录。增加内容时先按
依赖顺序拆小，再补状态表、波形、手算、实验和项目连接；不能把旧稿整块
重新 `\input` 后宣称已经恢复。

附录只接收不会阻断主线的参考材料，例如完整误差推导、器件选型、高速信号
完整性、PCB 工程、静态时序例外、复杂 CDC、DRAM 训练、实体载板资料和超出
当前项目的平台。正文可以长，但每个新名词都要由前面已经解释的对象和动作
推出来。

## 三轮编辑

### 第一轮：删去骨架味

逐章处理以下内容：

- 重复出现的固定模板；
- 介绍“本章怎样组织”的元叙事；
- “完整、严格、深入、真正”等自我评价；
- 与教学无关的版本宣言和发布流程；
- 一句话容纳十几个并列机制的能力清单；
- 每节末尾重复出现的总结和范围声明。

这一轮可以缩短文字，但不能删除技术事实。被移出的版本、哈希、部署和维护
门禁放入 release note、维护文档或检查脚本。

### 第二轮：重新写教学叙事

动笔前先回答五个问题：

1. 读者此刻已经知道什么？
2. 现在遇到的具体问题是什么？
3. 为什么需要引入这个机制？
4. 项目中哪段代码第一次使用它？
5. 运行以后能观察到什么？

章节节奏由内容决定：

- 实模式和 A20 沿兼容历史与地址手算展开；
- UART 从第一次串口输出实验展开；
- 页表从一个虚拟地址的四级翻译展开；
- fork 从父子共享和写入隔离的冲突展开；
- journal 从写到一半断电的磁盘状态展开。

主要阶段至少加入一个真实问题案例。案例必须能在 Git 历史、测试输出、QEMU
日志、构建产物或调试记录中找到依据，按“现象、最初猜测、检查方法、真正
原因、修复”叙述。没有材料时宁可不写，也不能补造故事。

### 第三轮：技术审校

叙事稳定后逐项核对：

- 当前 `source/` 实现与注释；
- Intel SDM 或对应设备资料；
- ELF、ROM、磁盘镜像和反汇编等构建产物；
- QEMU 串口输出、退出状态与超时行为；
- 项目版本、ABI 版本和盘面版本。

每条数字必须能指出单位和来源；每个日志标记必须由当前代码实际输出；每个
失败案例必须能由测试或确定的输入重现。

## 插图审校

LaTeX 能检查页面是否越界，却不能判断箭头是否穿过文字、两条状态转换是否
挤在一起。每次修改插图都要把 PDF 页面渲染成图片检查，不能只看源码或
`Overfull` 警告。

- 数据流、控制流和返回路径使用不同泳道；交叉线不能靠颜色差异勉强区分。
- 状态机的前进边、回退边和异常边分开放置，标签避开多条边的汇聚点。
- `os arrow` 与 `os bus` 的行内标签保留白底和内边距，导线不能从字形下穿过。
- 一个结点连接三层以上对象时，优先拆成逐层路径，不把所有箭头汇聚到同一框。
- 组合图的每个子图先确定边界；长公式和说明文字不能伸入相邻子图。
- 同时检查整页比例和局部细节。A4 页面可读不代表手机缩放后仍能分辨。
- 全书构建完成后，先查看所有插图页的联系表，再以原始分辨率复核高密度页面。

视觉验收至少覆盖：节点不相交、标签不压线、箭头不穿字、图注不贴图、图形
不侵入正文或页边距。发现问题时应先重排信息层级，缩小字号只能作为最后手段。

## 章节边界和源码颗粒度

章节入口必须与内部正文一致。调度章不得提前展开 pipe，fd 章不得同时承担
路径与挂载，盘面章不得把 IRQ、writeback 和 journal 一次讲完。遇到超过
六个主节或跨越两个独立实验终点的正文，先移动材料，再修改标题。

正文代码清单一次只解释一个动作。复位向量、入口状态、设备初始化、轮询超时
和字符串遍历应分别展示；完整文件只给出仓库路径。超过约 40 行的清单必须
说明为何不能继续切分，不能用“代码来自真实项目”代替逐段讲解。

每章开头给出阅读路线。编号主节进入目录，不编号的 `\topic` 进入 PDF 书签
和页眉。读者在手机上应能直接跳到具体机制，而不必在几十页中反复翻找。

## 字体职责

按本书当前排版选择，中文正文、西文正文、标题、代码、寄存器、地址、路径和
日志统一使用 Maple Mono NF CN。正文与代码不依靠字体家族区分，而由字号、
字重、颜色、行距、底色和边框建立层级。构建后用 PDF 字体清单确认 Maple
Mono 已嵌入，并分别抽查标题、正文、公式、表格和代码页面。

## 段落与句子

- 一段只讲一个核心事实，通常为三至六句。
- 句子变长时先拆句，不继续添加顿号。
- 直接写动作：“Stage 1 把 BootInfo 地址放入 RDI，然后跳到 ELF 入口。”
- 抽象术语从具体动作中引出：“第四个页帧申请失败时释放前三个页帧”，随后
  才说明这是失败原子性。
- `deepening/` 不用 `v0.8`、`v1.16` 一类项目发布号组织机制。早期方案写成
  “早期实现”，前后依赖直接写“前一章”或机制名；ABI major、rootfs 盘面
  版本等会被机器实际解析的版本字段可以保留。
- “不变量、所有权、失败原子性”不能先出现在标题里，再用正文补定义。先给出
  一次入队、一次最后关闭或一次中途分配失败的具体动作，读者看到冲突以后再
  命名术语。
- 适量使用第一人称复数引导操作，例如“我们先读一个扇区”“在这里手算一次”。
- 不反复假设读者持有错误观点。可以直接说明事实时，少用“不是……而是……”。
- 段首标题描述问题、动作或机制，不以 `v0.8`、`v1.12` 之类项目版本号充当
  主语。版本号只在确实比较历史实现时进入正文。

## 高风险表达

检索下列词组并逐处判断，禁止批量换成同义词：

```text
完整展开  进一步展开  继续解释  逐项解释  逐层连接
共同证明  形成证据链  形成闭环  事实底座  严格边界
当前承诺范围  发布身份  可反驳证据  资源账本
生命周期闭环  能力闭环  冻结基线
```

遇到这些表达时，优先换成地址、位、对象、控制流或失败现象。`完整`、`唯一`
和`严格`在协议字段、数学约束或硬件语义中仍可能准确，必须结合上下文判断。

## 内容放置

| 内容 | 放置位置 |
|---|---|
| 学习问题、实验、推导、代码走读 | 教材正文 |
| 当前能力、最短构建与阅读入口 | README |
| 编辑方法与文字检查 | 本文件 |
| 章节依赖和素材归属 | STRUCTURE.md |
| 版本变化与已知限制 | `docs/releases/` |
| PDF 哈希、手机导出、网站同步 | 发布记录与工具输出 |
| 源文件数和代码行数 | 构建日志或在线维护页，不进入正文 |

正文不承担项目自我评价。读者应当从可运行代码、可复现实验和解释质量中判断
这本书是否可靠。
