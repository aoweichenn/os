# 阶段发布闭环

## 1. 文档目的

本项目把实现、测试、学习材料和公开网站视为同一个版本产品。阶段完成不是
“主仓代码已经合并”的别名，而是以下状态机全部结束：

```text
实现完成
  → 主工程验证完成
  → 文档与教材完成
  → 主仓提交并推送
  → 网站从精确主仓 SHA 同步
  → 网站测试、构建、提交并推送
  → Sites 保存版本并部署生产
  → 公网与 Worker 日志验证完成
  → 阶段完成
```

任一箭头失败都保留在当前状态。不得用“网站稍后更新”跳过发布步骤，也不得在
生产内容仍落后时开始下一阶段。

## 2. 四类身份与所有权

一次发布同时涉及四类独立对象：

| 对象 | 权威身份 | 所有者 | 不变量 |
| --- | --- | --- | --- |
| 操作系统主工程 | 主仓 commit SHA | 根目录 Git 仓库 | 代码、测试、文档与书稿源一致 |
| 教材 | PDF SHA-256 | `books/` 与手机书库 | 网站下载件和本地最终 PDF 字节一致 |
| 网站源码 | web commit SHA | `web/` 独立 Git 仓库 | 只公开主工程，不公开网站实现 |
| 生产网站 | Sites 版本与部署 ID | Sites 项目 | 保存版本来自精确、已推送 web commit |

`web/` 被主仓 `.gitignore` 排除，并拥有自己的 `.git/`。不得在主仓中强制加入
该目录；网站构建产物、部署压缩包和 Sites 临时清单也不得进入任一源码提交。

## 3. 主工程冻结

阶段实现完成后按顺序执行：

1. 运行完整构建、单元、集成、固定种子随机、产物、QEMU 和失败路径测试。
2. 更新需求、架构、路线、模块、调试、日志、发布记录和学习章节。
3. 重建 LaTeX 教材，检查页数、未定义引用、重复标签和横向溢出。
4. 执行手机教材导出，并核对源 PDF 与手机 PDF 的 SHA-256。
5. 执行 `git diff --check`，确认没有网站文件进入主仓。
6. 运行 `audit-release-identity`，在已物化两盘上完成三轮 `qemu-soak`，并生成
   绑定候选 SHA 的 `project_release.json`。
7. 提交并推送主仓，确认 `HEAD` 与远程分支相同且工作树干净；若最终提交改变
   SHA，必须用新 SHA 重新生成清单。

网站只能从这个已推送主仓 commit 生成。若主仓在网站生成后又发生任何内容
提交，旧网站快照立即失效，必须重新同步。

## 4. 网站同步

进入 `web/` 独立仓库后必须同步完整内容面，而不是只修改版本号：

- 首页当前能力、终端证据、测试总数和阶段标记；
- 路线页的完成数量、当前阶段总结与下一阶段；
- 架构页新增模块、数据流、失败边界和硬件连接；
- 文档目录中的发布记录、ADR、模块文档与学习章节；
- 代码目录快照、核心文件数量和有效代码行；
- 代码走读中的新增模块阅读路线；
- 教材页的版本、页数、内容摘要和最终 PDF；
- sitemap、公开元数据和发布清单。

网站同步脚本必须记录主仓 SHA、项目版本、核心代码统计、测试总数、教材页数、
教材大小和 PDF SHA-256。网站测试必须把该清单与代码目录、页面数据和 PDF
交叉核对；只要仍引用上一阶段，构建就应失败。

## 5. 网站验证与提交

本地依次执行：

```bash
cd web
npm run sync
npm test
npm run build
```

`npm run sync` 必须从相邻主工程生成代码目录和发布清单，并复制最终教材。
v2.6 起网站还必须读取主工程生成的结构化清单，核对 project/ABI/rootfs/机器
规格、ROM/Kernel 哈希和两块磁盘身份；不得只从页面常量猜测版本。
随后检查网站仓库 diff，提交全部源码和应提交的生成快照，推送精确 web
commit。提交后工作树必须干净。

不得先打包再修改或提交；Sites 保存版本使用的 archive 必须由已经推送的同一
web commit 构建。

## 6. Sites 保存与生产部署

在干净网站提交上运行：

```bash
npm run release:sites
```

该命令重新构建、生成标准 archive，并记录 archive SHA-256 与当前 web commit。
随后使用 `.openai/hosting.json` 中已有的项目 ID：

1. 保存 Sites 版本，传入精确 web commit 和刚生成的 archive；
2. 按当前访问控制与授权规则部署该保存版本；
3. 部署返回非终态时持续查询，直到成功或明确失败；
4. 记录用户可见 Sites 版本号、部署 ID 和生产 URL。

不得创建替代站点、猜测 ID、部署未保存版本或上传来自另一 commit 的 archive。

## 7. 公网验收

部署成功后必须从生产域名检查：

- `/`、`/architecture/`、`/roadmap/`、`/docs/`、`/code/` 和 `/book/`
  返回成功；
- 当前 `docs/releases/vX.Y.md` 对应网页可读；
- 本阶段新增的至少一个核心代码路径可读；
- 教材下载字节与本地最终 PDF 的 SHA-256 相同；
- `sitemap.xml` 包含当前发布文档和新增代码路由；
- `robots.txt` 返回有效策略；
- Worker 日志没有异常、1101 或新增服务器错误。

仅检查 Sites 控制面显示 `active` 不足以证明页面可用；仅访问首页也不足以证明
动态文档和代码路由已经同步。

## 8. 发布证据与失败状态

最终交付报告至少包含：

```text
项目版本
主仓 commit SHA
主工程测试数量与结果
核心代码文件数与有效代码行
教材页数、大小与 SHA-256
web commit SHA
网站测试与构建结果
Sites 版本号与部署 ID
生产 URL 与关键路由结果
Worker 错误日志结果
```

失败时使用精确状态：

- 主工程验证失败：阶段实现未完成；
- 教材失败：阶段文档未完成；
- 网站同步或构建失败：阶段发布未完成；
- Sites 保存或部署失败：阶段公开发布未完成；
- 公网内容或日志失败：阶段生产验收未完成。

只有所有状态都完成，才允许写“阶段已完整实现并发布”并进入下一阶段。
