## 1. 本阶段在解决什么

写操作系统最容易出现的误区，是先写一段汇编，看到 QEMU 黑屏或输出字符，再回头
补构建和测试。v0.0 反过来做：在第一条固件指令之前，先建立一个能持续回答下列
问题的工程系统：

- 宿主机是否安装了正确版本的 Clang、LLD、NASM、CMake、Ninja、QEMU 和
  GDB？
- 同一份纯逻辑 C++ 能否既在宿主机测试，又交叉编译成无宿主依赖的目标代码？
- 目标产物是否意外引用 libc、C++ ABI 或错误架构的符号？
- ROM、磁盘和 ELF 产物的尺寸、布局和权限是否满足契约？
- 测试失败时，能否区分代码错误、产物错误、QEMU 超时和工具缺失？
- 新机器能否仅根据仓库文档复现结果？

这一阶段没有可用操作系统界面，但它定义了后面所有阶段的可信度。

历史验收见 [v0.0 发布记录](../releases/v0.0.md)。

## 2. 前置知识

开始前应理解：

- 编译、汇编、链接和运行是四个不同步骤。
- 宿主程序与目标程序运行在不同环境。
- CMake 描述依赖图，Ninja 执行图中的命令。
- 单元测试验证纯逻辑，整机测试验证真实硬件边界。
- “文件生成成功”不代表二进制内容正确。

## 3. 仓库分层

当前仓库的职责划分是：

```text
source/
  foundation/       宿主与目标可复用的基础值类型和纯逻辑
  firmware/         复位 ROM
  boot/stage1/      自研 Stage 1
  abi/              Kernel/User 共享 ABI
  kernel/           x86-64 Kernel
  user/             Ring 3 运行时和程序

tools/
  os.py             唯一的人类入口
  os_tools/         构建、镜像、审计、QEMU 等宿主实现

tests/
  unit/             小范围确定性逻辑
  integration/      多模块契约
  randomized/       固定种子的边界组合
  tooling/          Python 工具
  system/           故障注入目标入口

docs/
  requirements/architecture/roadmap
  adr/modules/releases/learning

books/
  x86-64-os-from-reset/
```

依赖方向应尽量单向：宿主工具可以读取目标产物，目标代码不能依赖宿主 Python；
Kernel 可以依赖 foundation/abi，foundation 不能依赖 Kernel。

## 4. CMake 和 Preset

根 [CMakeLists.txt](../../CMakeLists.txt) 负责：

- 要求 CMake 3.28。
- 固定 C++20。
- 定义公共严格警告：`-Wall -Wextra -Wpedantic -Wconversion`
  `-Wsign-conversion -Wshadow -Werror`。
- 加入 foundation、abi、user、kernel、firmware、Stage 1 和 tests。
- 定义 ROM、磁盘、正常镜像和故障镜像的输出路径。
- 把镜像生成脚本纳入构建依赖，而不是依赖手工步骤。

[CMakePresets.json](../../CMakePresets.json) 定义 `developer`：

- Ninja generator。
- `build/developer` 独立构建目录。
- Debug 构建。
- `clang++`。
- 导出 `compile_commands.json`。
- 默认两个并行 job。
- 测试失败时输出详情，零测试也算错误。

Preset 的意义是把“大家口头约定的命令参数”变成版本控制内的可复现配置。

## 5. 宿主和目标是两套编译语境

### 5.1 宿主模型

可测试的纯逻辑会编译成普通 Linux 测试程序。例如地址范围、ELF 解析、页帧状态、
调度器、管道和文件系统格式都能先在宿主机快速运行。

宿主模型的作用不是模拟整个 CPU，而是把不依赖特权指令的算法从硬件入口中分离
出来：

```text
硬件入口/端口读写
   ↓ 提供原始状态
纯 C++ 状态机和校验逻辑
   ↓ 返回明确结果
硬件出口/日志/panic
```

### 5.2 目标编译

目标 C++ 使用 `x86_64-unknown-none-elf` 和 freestanding 选项。它没有标准
C++ 头、启动代码或系统库。构建必须防止生成：

- `__cxa_*` C++ ABI 符号。
- 异常展开和 RTTI。
- stack protector 支持函数。
- 宿主动态链接节。
- 不受控的全局构造器。
- SSE/red-zone 等内核尚未保存或允许的状态。

同一纯逻辑能通过宿主测试，不代表目标产物一定干净，因此还要做 ELF 和符号审计。

## 6. `tools/os.py` 是统一入口

[tools/os.py](../../tools/os.py) 只负责参数解析和命令路由，具体实现放在
`tools/os_tools/`。主要命令：

| 命令 | 职责 |
| --- | --- |
| `doctor` | 检查全部宿主工具和版本 |
| `configure` | 运行 developer preset 配置 |
| `build` | 构建全部目标 |
| `test` | 运行 CTest |
| `verify` | doctor → configure → build → test |
| `create-images` | 创建指定大小的空 ROM/磁盘 |
| `audit-firmware` | 检查 ROM 大小、入口和复位向量 |
| `audit-stage1` | 检查 Stage 1 描述符和负载 |
| `audit-kernel-image` | 检查 Kernel 磁盘容器 |
| `audit-kernel-elf` | 检查 Kernel ELF 入口、段和符号 |
| `audit-user-elf` | 检查用户 ELF |
| `qemu-smoke` | 执行整机成功与故障场景 |
| `qemu-file-system-persistence` | 用同一可写磁盘跨启动验收 |
| `source-metrics` | 统计真正进入目标系统的代码 |

工具调用外部进程时使用参数数组而不是拼接 shell 字符串，避免路径、空格和转义
变成隐藏输入。

## 7. Foundation 示例：地址范围

v0.0 的生产代码核心是
[address_range.hpp](../../source/foundation/include/os/foundation/address_range.hpp)
和
[address_range.cpp](../../source/foundation/src/address_range.cpp)。

它没有用裸 `uint64_t` 表达所有值，而是区分：

- `PhysicalAddress`：一个物理地址。
- `ByteCount`：字节数量。
- `AddressRange`：半开区间。
- `AddressRangeCreationStatus`：创建成功或地址溢出。

### 7.1 为什么不是简单 pair

如果接口接受两个裸整数，调用者可能把“结束地址”错当“长度”，或把页号错当
字节地址。强类型不能消除所有错误，但会把单位和语义写入函数签名。

### 7.2 `TryCreate` 的溢出证明

目标是形成 `[begin, begin + size)`。代码先计算：

```text
maximumSize = UINT64_MAX - begin
```

只有 `size <= maximumSize` 才执行加法。失败通过枚举返回，输出参数保持调用者可
控；没有异常、assert 或未定义回绕。

### 7.3 半开区间性质

`Contains(address)` 等价于：

```text
begin <= address && address < end
```

两个区间重叠等价于：

```text
a.begin < b.end && b.begin < a.end
```

空区间 `[x, x)` 不包含任何地址。相邻 `[a,b)` 和 `[b,c)` 不重叠。这些性质会
直接用于 Stage 1 载荷范围、ELF 段、页映射和物理内存保留区。

## 8. 测试分层

### 8.1 单元测试

[address_range_test.cpp](../../tests/unit/foundation/address_range_test.cpp) 验证：

- 普通创建。
- 零长度。
- 边界包含。
- 相邻和重叠。
- 最大地址附近的溢出。

### 8.2 随机测试

[address_range_randomized_test.cpp](../../tests/randomized/foundation/address_range_randomized_test.cpp)
用固定种子生成大量输入，并用独立的参考条件判断结果。固定种子同时满足覆盖和
可复现性。

### 8.3 集成测试

后续 boot layout 测试会复用地址范围，证明各保留区、装载区和栈没有重叠。纯
类型的价值在跨模块组合时体现。

### 8.4 产物与系统测试

产物审计验证“不运行也能证明”的事实，例如架构、大小、符号、入口和段权限。
QEMU 测试只验证必须由真实 CPU/设备路径证明的行为。

## 9. 失败语义

工程工具也需要明确失败语义：

- 工具缺失：`doctor` 报出具体名称，不继续伪运行。
- 子进程非零退出：保留命令上下文和输出。
- QEMU 未出现标记：区分超时、提前退出和禁止标记。
- 镜像尺寸错误：构建前或 QEMU 启动前拒绝。
- 审计失败：指出字段、实际值和预期值。
- 随机测试失败：输出固定种子和可复现输入。

超时不是“让测试别挂住”的附属选项，而是所有硬件等待的失败协议。

## 11. 实验

### 实验 A：证明宿主/目标分离

找到 foundation 的宿主测试目标和目标静态库目标，对比两者编译参数。说明为什么
同一 `.cpp` 可以进入两套产物。

### 实验 B：地址边界表

为 `TryCreate` 手工列出：

- `begin=0,size=0`
- `begin=UINT64_MAX,size=0`
- `begin=UINT64_MAX,size=1`
- `begin=UINT64_MAX-1,size=1`
- `begin=UINT64_MAX-1,size=2`

预测状态和最终区间，再与测试对照。

### 实验 C：审计比运行更早发现什么

列出至少五类无需启动 QEMU 就能发现的问题，并找到相应 Python 审计实现。

### 实验 D：安全制造失败

在临时分支增加一个只用于学习的错误尺寸输入，确认工具给出明确失败后恢复。不要
把失败输入覆盖正式镜像。

## 12. 阶段验收

- 为什么操作系统需要宿主模型、目标产物审计和 QEMU 三层证据。

- `verify` 的执行顺序。
