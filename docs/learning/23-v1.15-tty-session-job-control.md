# v1.15：从键盘字节到前后台作业

## 本章解决什么问题

到 v1.14，系统已经可以向一个进程组发送信号，但“谁是当前交互对象”仍没有
Kernel 级答案。控制台 FIFO 中的每个字节对所有进程都一样，后台程序只要先被
调度就可能偷走 Shell 的输入；Ctrl-C 也只是值为 3 的字节，不会自动终止正在
前台运行的管线。

v1.15 建立一个最小但完整的 Unix 终端模型：

```text
PS/2 扫描码
  → Ctrl 修饰状态与字符翻译
  → TTY canonical 行规程
  → 普通输入 / 控制动作
  → foreground process group
  → signal 默认动作
  → Stopped/Ready/Zombie
  → Shell wait event 与终端收回
```

本章重点不是记住 `jobs` 命令，而是理解硬件事件怎样经过多个所有权边界，最后
变成一个可以停止、继续和回收的用户作业。

整体关系见 [TTY 与作业控制结构图](assets/tty_job_control.svg)。

## 历史背景：为什么电传打字机影响了进程模型

早期计算机的交互终端来自电传打字机。设备按顺序接收字符、打印字符，并把按键
编码成字符流。Unix 延续了这套流式接口，但很快遇到一个问题：一个登录会话里
既有 Shell，也有 Shell 启动的程序；终端输入在任意时刻只能属于一个前台作业。

于是形成三个彼此不同的概念：

| 身份 | 作用 | 典型拥有者 |
| --- | --- | --- |
| process tree | 表达父子关系和 wait/reparent | PID1、Shell、子进程 |
| process group | 把一条管线视为一个信号目标 | `echo x \| cat \| wc` |
| session | 包围多个作业并关联控制终端 | 一次 Shell 登录 |

进程组不是“所有后代”。Shell 启动的一条管线可能包含多个兄弟进程，它们应收到
同一次 Ctrl-C；Shell 自己是父进程，却不应收到这次默认终止。平坦 PGID 正好
表达这种关系。

session 也不是更大的进程组。它回答“哪些进程组有资格操作这个控制终端”。
一个 session 可以轮流把不同 PGID 设为前台，但其他 session 不能抢走终端。

## 从 PS/2 线缆事件到 C0 控制码

QEMU 的 `send-key ctrl-z` 模拟的是键盘事件，不会直接把 ASCII `0x1A` 写进
Kernel。i8042 通过 IRQ1 提供 Set 1 扫描码。Ctrl 按下和松开分别产生 make/
break code；右 Ctrl 还带 `E0` 扩展前缀。

解码器必须保存修饰键状态：

```text
Left Ctrl make  0x1D      → left_control_pressed = true
Left Ctrl break 0x9D      → left_control_pressed = false
Right Ctrl make E0 1D     → right_control_pressed = true
Right Ctrl break E0 9D    → right_control_pressed = false
```

Ctrl 与英文字母的传统 C0 关系是保留低五位：

```text
Ctrl-C: 'C' & 0x1F = 0x03
Ctrl-D: 'D' & 0x1F = 0x04
Ctrl-Z: 'Z' & 0x1F = 0x1A
```

这段历史解释了为什么控制字符和可打印字符共享同一输入流。键盘驱动只负责
稳定地产生字符；`0x03` 究竟是数据还是“中断前台作业”，由 TTY 行规程决定。

## canonical mode 为什么需要两级输入缓冲

若每次按键都立即交给 `read`，用户程序会看到退格本身，还得自己维护行编辑。
canonical mode 先把未完成行保存在编辑缓冲，直到换行才提交到可读输入环：

```text
edit buffer:  h e l x ←Backspace→ h e l
                                    + l o \n
input ring:   h e l l o \n
```

本项目将容量显式冻结为 512 字节编辑区和 1024 字节已提交输入环。提交前，
阻塞读取不能看到半行；提交失败不能覆盖环中尚未读取的数据。

各控制字符的行为：

- Backspace/Delete：若编辑区非空，删除最后一个字节；
- CR/LF：提交编辑区并附加统一 LF；
- Ctrl-D：编辑区非空时不附加换行直接提交；为空时产生一次 EOF；
- Ctrl-C：撤销当前未提交行并请求中断前台组；
- Ctrl-Z：撤销当前未提交行并请求停止前台组。

`SubmitCharacter` 返回 `TerminalInputAction`，所以 IRQ 上层不用再次检查数字
常量。普通 `Buffered` 不唤醒 reader；`InputReady`/`EndOfFileReady` 唤醒
控制台 WaitQueue；`InterruptForeground`/`StopForeground` 转入组信号路径。

## 输入统计为什么不能再要求 submitted 等于 read

旧 FIFO 中所有提交字符最终都由用户读取，所以可以比较 `submitted==read`。
行规程会有意消费控制字节。一次退格既消费退格键本身，又撤销先前提交到编辑区
的一个字节；Ctrl-C 还会撤销整条未提交行。

因此精确不变量是：

\[
S=R+B+E+D+C
\]

其中 \(S\) 为 submitted，\(R\) 为 read，\(B\) 为已提交但未读，\(E\) 为
编辑区，\(D\) 为容量拒绝，\(C\) 为行规程消费。每次修改输入状态都必须保持
这个等式。QEMU 功能测试结束时 \(B=E=D=0\)，而三个控制键使 \(C=3\)。

## 为什么 TTY 需要 irq-save 锁

输入由 IRQ1 提交，读取和输出由系统调用执行。即使系统只有一个 CPU，用户写
串口期间也可能被键盘 IRQ 打断。若两条路径同时修改环索引，单核不等于安全：
中断形成了同核重入。

`Terminal` 因而持有 `IrqSaveSpinLock`。锁先保存 IF 并关闭本地中断，再取得
原子锁；释放时恢复调用前 IF。目标 Kernel 注入真实中断操作，主机单元测试
注入无操作版本。这样纯逻辑测试不依赖特权指令，而生产对象仍执行真实保护。

锁内不允许睡眠。输出环尝试立即向串口设备排空；设备失败返回错误。未来异步
终端输出需要独立请求队列，不能在当前锁内等待硬件。

## SID、PGID、PID 的不变量

PID1 初始状态为：

```text
PID=1, PGID=1, SID=1, session_leader=true
```

fork 子进程继承 SID 和 PGID，但获得新 PID，且不是 session leader。一个进程
可以创建 `PGID=自己的 PID` 的新组；加入其他组时，该组必须已经存在于同一个
SID。session leader 不能被移出自己的组。

`JobControlManager::Validate` 逐项证明：

1. 每个 active 记录有非零且唯一 PID；
2. 每个 PGID 在相同 SID 内至少有一个成员；
3. session leader 满足 PID=PGID=SID；
4. 统计 active 数等于实际扫描数；
5. inactive 槽没有残留身份。

选择固定表不是把 PID 限制为槽位。公开 PID 单调增长，查找后才得到可复用槽。
64 MiB/256 MiB/64 GiB 分档仍决定表容量。

## controlling terminal 与 foreground PGID

TTY 保存：

```text
terminal_id
controlling_session_id
session_leader_process_id
foreground_process_group_id
```

读取前检查调用者 SID 和 PGID：

```text
caller.SID == tty.controlling.SID
&& caller.PGID == tty.foreground.PGID
```

失败返回 `BACKGROUND_TERMINAL_READ`，不从输入环取走一个字节。这里没有把
后台 reader 永久阻塞，因为它不会仅因输入到达就获得读取资格；前台身份改变
才可能使条件成立。当前 ABI 让程序看到明确错误，未来可扩展为 SIGTTIN。

前台写终端仍允许。传统 Shell 需要在后台任务输出和提示符之间做更复杂的显示
协调；v1.15 的目标是先冻结输入所有权和控制信号。

## `/dev/console` 为什么是字符 vnode

控制台以前由标准 fd 的特殊 kind 直接表示，无法通过路径打开，也无法在目录中
观察。v1.15 加入最小设备文件系统：

```text
VFS mount /dev
  └─ console : CharacterDevice
```

它是只读命名空间：不能创建、删除或重命名节点，但可以打开字符设备。VFS
负责路径、vnode 引用、stat 和 readdir；`FileDescription` 负责把 read/write
转发到 `Terminal`。设备 vnode 没有普通文件 offset，也不能 truncate。

这样用户 ABI 只看到 fd 和目录项，不看到 Terminal 指针。以后替换为通用 devfs
时，路径层契约可以保持稳定。

## 停止不是退出

收到 SIGTSTP/SIGSTOP 默认动作时，Kernel：

1. 保存当前 `UserContext` 和 FXSAVE 区；
2. 把 ProcessTree 标为 Stopped 并产生 stopped event；
3. 把 Process 与所属 Thread 置为 Stopped；
4. 从当前 CPU 切换到下一个可调度 Ready Thread；
5. 唤醒正在等待子进程事件的 Shell。

地址空间、VMA、fd、文件偏移、内核栈和用户栈全部保留。SIGCONT 把原 Thread
重新接入 Ready queue，并产生 continued event。只有退出才销毁资源并进入
Zombie。

调度器必须跳过属于 Stopped Process 的旧 Ready 节点。判断“是否还有可运行
Thread”也不能只看队列非空，否则队列里全是停止成员时 idle 会反复空转。

## wait event 为什么与 wait exit 分开

旧 wait 只有一种终态：Exited，观察后立即回收 Zombie。作业控制需要观察
Stopped 和 Continued，但不能回收子进程。

`WaitProcessEvent` 接受位标志：

```text
Exited | Stopped | Continued | NoHang
```

返回结构同时包含 PID、父 PID、事件类型、终止原因、退出码、异常向量和信号号。
Stopped/Continued 只清除对应 pending event；Exited 才执行最终收集。

如果孩子在父进程运行前完成“停止→继续→退出”，ProcessTree 保留三个事实，
父进程仍按顺序观察。这避免 Shell 把已经继续的程序永久显示为 Stopped，或因
只看到退出而漏掉控制流证据。

## Shell 怎样创建一条前台管线

以 `echo hello | cat | wc` 为例：

1. Shell 申请作业槽并建立两条 Pipe；
2. fork 第一个 child，以其 PID 作为整条管线 PGID；
3. 后续 child 加入同一 PGID；
4. child 完成 fd 接线、关闭多余端点、恢复默认 SIGINT/SIGTSTP，再 exec；
5. parent 关闭自己的 Pipe 端点；
6. Shell 将 TTY foreground PGID 切到作业；
7. Shell 用 WaitProcessEvent 等待每个成员；
8. 作业停止或全部退出后，Shell 无条件收回 TTY。

父子双方都调用设置进程组。只让 child 调用会使 parent 在交接终端时不知道组
是否已建立；只让 parent 调用又会在 child 先 exec/exit 时产生竞态。

还有一个更隐蔽的窗口：parent 已把 TTY 交给新 PGID，但 child 尚未完成
`exec`。此时 Ctrl-Z 已经是一个真实的 pending 异步事实。`exec` 只能重置
Handler、清除活动 handler frame 和兄弟 Thread 状态，不能清掉 Process
pending 或 survivor pending；否则新映像会“忘记”用户已经按下控制键。QEMU
分步注入专门把控制字符放在这个窗口中，验证新映像在第一次返回用户态前兑现
默认停止。

极短命令还揭示了第二个生命周期问题：child 可能已经 Zombie。Kernel 保留
Zombie 的进程级组身份到 wait，允许父进程完成组记账；最终收集再同时删除
signal、job-control、scheduler 和 process-tree 状态。这与“Zombie 只保留
退出码”相比多保留少量固定元数据，却换来稳定的 PGID 语义。

## `&`、`jobs`、`fg` 和 `bg` 的状态机

Shell 的作业成员状态为 Running、Stopped、Exited；作业状态由成员归约：

```text
全部 Exited                → Done
所有未退出成员都 Stopped   → Stopped
其他                        → Running
```

`command &` 只允许 `&` 位于整行最后，防止解析器把中间 `&` 当普通参数产生
含糊语义。后台建立后立即打印 job id/PGID 并返回提示符。

`jobs` 先以 NoHang 收割所有可见事件，再显示状态。`bg` 对停止作业发送 SIGCONT，
不改变 TTY 前台组。`fg` 先交接 TTY，再发送 SIGCONT 并阻塞等待；任何失败路径
都尝试把 TTY 恢复给 Shell。

当前作业表为 16 项固定容量。容量满时新命令在 fork 前失败，旧作业不变。

## Ctrl-Z、fg、Ctrl-C 的完整时序

```text
QMP send-key ctrl-z
  → i8042 IRQ1
  → Set1 decoder: 0x1A
  → Terminal: StopForeground
  → SendProcessGroupSignal(foreground PGID, SIGTSTP)
  → default stop
  → scheduler saves frame and selects Shell
  → WaitProcessEvent: Stopped
  → Shell restores own foreground PGID
  → prompt

fg
  → TTY foreground = job PGID
  → SIGCONT
  → Continued event
  → child resumes old read

QMP send-key ctrl-c
  → Terminal: InterruptForeground
  → SIGINT to job PGID
  → default terminate
  → Exited event and Zombie collection
  → Shell restores foreground and remains alive
```

QEMU runner 不用固定 sleep 猜测时序。它等待 Shell 输出
`FOREGROUND_JOB_WAITING`，再注入控制键；每个命令等待新的
`COMMAND_COMPLETE`。单步 20 秒没有进展立即失败，并由 finally 回收 QEMU。

## 日志怎样既丰富又不刷屏

输入字符、扫描码和每次 scheduler 扫描都是热路径，不逐项写串口。稳定 marker
只放在低频事务边界：

```text
JOB_CONTROL_READY
FOREGROUND_JOB_WAITING
FOREGROUND_JOB_STOPPED
BACKGROUND_JOB_STARTED
COMMAND_COMPLETE
```

终态再统一打印：

- TTY committed/editing/consumed/control/output/foreground/rejection；
- scheduler stopped/stop/continue；
- signal default stop/continue；
- process tree event produced/observed；
- job-control active/session/group/change。

宿主 `[QEMU][T+...ms]` 只表示串口到达时间；来宾的单调时钟仍来自 PIT。

## 四层验证怎样证明不是“恰好跑通”

单元测试独立验证 Terminal、JobControlManager、字符设备 FS 和扫描码 Ctrl
状态；集成测试把 Terminal、JobControl、ProcessTree 和 ThreadScheduler
组合成 stop/continue/exit 事务；固定种子随机模型对 64 槽执行 100000 次
PGID 迁移；QEMU 则覆盖真实 IRQ 和 Ring 3。

整机终态同时要求：

\[
stops=continues,\qquad
stopped\_events=observed\_stopped\_events
\]

\[
continued\_events=observed\_continued\_events,\qquad
output\_queued=output\_written
\]

并且 stopped process、active job process、session、process group、Zombie、
TTY editing/buffer/pending output 全部为零。任一层不守恒都会输出
`USER_RESULT_INVALID`，不能只靠用户 marker 宣布成功。

## 当前边界与下一步

v1.15 是一个控制终端、canonical 模式和单 BSP 的教学基线，不是完整 termios。
没有 raw mode、波特率/回显属性、窗口尺寸、多个 pty、SIGWINCH、SIGHUP、
SIGTTIN/SIGTTOU 或孤儿进程组规则。

下一阶段 v1.16 转向存储 I/O：ATA PIO 从同步轮询变为 IRQ14 完成的有界
BlockRequest，Thread 可在磁盘等待期间真正阻塞，page cache 获得
clean/dirty/writeback/error 状态。TTY 阶段建立的 WaitQueue、deadline、
signal 和日志单赢家规则将直接复用到块请求完成。
