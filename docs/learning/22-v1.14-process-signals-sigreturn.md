# v1.14：从异步事件到受控用户 handler

## 本章解决什么问题

进程可以主动读取文件、等待子进程或睡眠，但硬件终端、父子关系和其他进程产生
的事件并不会等它下一次查询。信号提供一种异步控制消息：发送者只指定目标和
信号号，Kernel 决定何时、由哪个 Thread、以何种用户现场交付。

“调用一个函数”不是信号实现。完整机制必须回答：

1. disposition、mask 与 pending 分别归谁；
2. 一个多 Thread Process 中哪个 Thread 获得普通信号；
3. Thread 正阻塞在 I/O 或 deadline 时怎样只唤醒一次；
4. Kernel 怎样在不执行用户代码的前提下进入 handler；
5. 用户可修改返回帧时，怎样阻止伪造 Ring 3 返回现场；
6. fork、exec、exit 怎样改变信号状态而不泄漏。

## 历史背景：信号为什么像中断，却不是硬件中断

早期 Unix 需要把“终端中断”“非法指令”“子进程结束”等事件通知给进程。
统一的小整数编号比为每类事件设计独立 IPC 接口更容易组合，于是形成 signal。
它与硬件中断相似：都能改变顺序执行流；但所有权边界完全不同。

硬件中断由 CPU 根据 IDT 切换到 CPL0，入口和现场格式受 x86-64 约束。用户信号
由 Kernel 软件选择一个 Thread，再把下一次 CPL3 返回现场改写成用户 handler。
它不会建立新的硬件特权级，也不允许用户 handler 在中断上下文运行。

```text
硬件 IRQ
  设备 → PIC → IDT → Ring 0 interrupt frame → Kernel handler

用户信号
  sender syscall → Process pending/Thread selection
                 → user-return boundary
                 → user SignalFrame → Ring 3 handler
```

历史 Unix 的普通信号不是消息队列。同一普通信号在 pending 期间重复到来通常
只保留一位。这解释了“发送两次不保证 handler 运行两次”。POSIX 后来增加实时
信号队列来保留顺序和值；本项目 v1.14 有意实现普通合并语义，不伪装成实时信号。

## 三种状态为什么不能塞进一个对象

Process 是资源共享边界，Thread 是执行边界。信号正好跨过两者：

| 状态 | 所有者 | 原因 |
| --- | --- | --- |
| disposition | Process | 同一程序映像中的 Thread 共享 handler/ignore/default 决策 |
| process group | Process | 发送目标和后续 TTY 前台所有权以 Process 为成员 |
| Process pending | Process | 尚未找到可接收 Thread |
| mask | Thread | 每个执行流可独立推迟信号 |
| Thread pending | Thread | 已完成唯一 Thread 选择 |
| active handler frame | Thread | 必须返回到该 Thread 自己的寄存器与栈 |

若 disposition 放进 Thread，安装 handler 后新建 Thread 会看到不同动作；若 mask
放进 Process，一个 Thread 临时屏蔽就会意外阻挡全部兄弟；若活动帧只放 Process，
另一个 Thread 可以提交不属于自己的 sigreturn。

`SignalManager` 因而使用两张固定容量状态表，并以 scheduler 的 Process/Thread
槽索引关联。PID/TID 仍是公开单调身份，不等于槽位；查找 PID 后才得到内部索引。

## 普通信号的合并与唯一选择

信号号 \(s\) 映射到位：

\[
bit(s)=1 \ll (s-1),\qquad 1\le s\le63
\]

发送前同时检查 Process pending 和该 Process 全部 Thread pending。任一处已有
同一位时，本次发送记为 coalesced，不新建第二个所有者。否则从 Process 保存的
轮转游标开始扫描 Thread：

```text
active
  && thread.process == target
  && !(thread.mask & bit(signal))
  → 选择一次，写入 thread.pending
```

找不到合格 Thread 时写入 Process pending。Thread 修改 mask、注册或 handler
完成后重新扫描。轮转游标不是优先级保证，只防止每次都偏向最低槽位。

Kill 对应的位在设置 mask 时被清除，所以用户永远不能真正屏蔽它。安装 Ignore
或 Handler 也被 action 校验拒绝。这个约束必须在 Kernel 再执行一次，不能只
依赖用户运行库。

## Default、Ignore 与 Handler 是三种控制流

`SignalAction` 固定保存 disposition、handler 地址、restorer 地址、额外 mask
与 flags：

- Default：Child 默认忽略；当前其他具名信号终止 Process；
- Ignore：消费 pending，不构造用户帧；
- Handler：构造用户帧，临时把当前信号和 additional mask 加入 Thread mask。

Handler 运行期间再次发送同一普通信号会保持 pending，因为当前信号已自动屏蔽。
sigreturn 恢复原 mask 后，下一次用户返回边界才可再次投递。这避免在一个栈上
无限递归同一 handler；未来若支持显式 nodefer，需要新增并冻结 action flag。

## 进程组：信号目标不是“所有后代”

进程组是平坦成员集合，不是进程树的子树。fork 继承父组；进程可把自己移动到
以自身 PID 为组号的新组。按组发送会遍历所有活动 Process，为每个成员执行一次
普通 Process 发送，再唤醒被选中的 Thread。

QEMU 信号探针先调用 `SetProcessGroup(0)` 建立自己的组，然后把 User2 设为
Ignore 并按组发送。如果继续留在 PID1 的组中，init 也会收到 User2 的默认动作；
这不是内核随机选错目标，而是测试没有先隔离组所有权。这个调试过程正说明：
进程树负责 parent/wait/reparent，进程组负责终端作业和广播，两者不能混用。

## Signal 怎样加入 WaitQueue 单赢家

v1.13 的一个 Blocked Thread 可能同时属于业务 WaitQueue 和 deadline queue。
v1.14 没有建立第三条“信号 Ready 链”，而是把 Signal 作为第三个完成原因：

```text
                         scheduler irq-save lock
              ┌──────────────┼──────────────┐
         condition          timeout        signal
              └──────────────┼──────────────┘
                       WakeThread
                   Blocked → Ready 一次
```

发送路径取得目标 Thread 当前 WaitQueue，调用
`WakeThread(..., WakeReason::Signal)`。胜者：

1. 确认 Thread 仍为 Blocked；
2. 从 WaitQueue 摘除；
3. 取消活动 deadline；
4. 写入唯一 wake reason；
5. 接入一次 Ready queue。

condition 或 timeout 已经获胜时，Signal 只保留 pending，不能再次发布 Ready。
反过来 Signal 先赢时，deadline 被计为 cancellation，不会稍后再次唤醒 Thread。

## 中断系统调用与重启不是一个布尔开关

阻塞调用可能有三种状态：

- 尚无部分进度，可以报告 Interrupted；
- 尚无部分进度，且调用在策略表中可重启；
- 已经提交部分字节，必须返回部分结果，不能回退副作用。

当前阻塞入口保存系统调用号和 restartable 属性。Signal 获胜先把保存 RAX 写成
`INTERRUPTED=-52`。若 action 含 restart flag 且调用允许重启，Kernel 在信号帧
中保存一个经过修改的现场：

```text
saved RIP = RIP after SYSCALL - 2
saved RAX = original syscall number
```

x86-64 `SYSCALL` 指令编码固定为两个字节。sigreturn 恢复后，CPU 再执行同一条
指令；RDI/RSI/RDX/R10 仍保存原参数。这里使用的是 Intel 指令事实，不是 C++
包装器循环的偶然行为。

描述符/管道读写、wait process 与 join 当前允许重启；sleep 与 futex 不允许。
后两者含绝对时间或 compare-and-block 条件，盲目重启容易延长等待或掩盖值变化。
未来每增加一个可阻塞系统调用，都必须显式进入策略表，不能默认“全部重启”。

## 为什么 handler 入口需要 restorer

C++ handler 仍按 System V AMD64 ABI 调用。函数执行 `ret` 时需要栈顶有返回地址，
但被中断代码没有调用过 handler。Kernel 因而合成：

```text
高地址
  old RSP
  +---------------------------+
  | SignalFrame (240 bytes)   | ← RSI
  +---------------------------+  16 字节对齐
  | restorer return address   | ← handler RSP
  +---------------------------+
低地址
```

handler 入口 `RSP % 16 == 8`，与普通 `call` 后的函数入口一致；RDI 是信号号，
RSI 是帧地址。handler 返回到 `OsUserSignalReturnRestorer`。Intel NASM 代码：

```asm
OsUserSignalReturnRestorer:
    mov rdi, rsp
    mov rax, 61
    syscall
    ud2
```

handler 的 `ret` 已弹出 restorer 地址，所以此时 RSP 正好等于 SignalFrame
地址。成功 sigreturn 直接恢复旧现场；若它错误地普通返回，`ud2` 让错误显式
变成用户异常，不会沿未知栈继续。

## 主栈为什么需要专门的信号帧扩展

主用户栈是 8 MiB 保留 VMA，启动时只提交参数真正占用的高端页。handler frame
比当前 RSP 更低，可能刚好跨入紧邻的未提交页。初始 `PrepareUserStack` 只接受
“尚未提交任何页”的地址空间，不能在运行期再次调用。

v1.14 新增 `PrepareUserStackRange`：

1. 验证 frame 下界和当前 RSP 都在冻结主栈窗口；
2. 若尚未提交，复用初始批量准备；
3. 若 frame 低于 committed bottom，只允许逐个映射紧邻下页；
4. 每页复用用户态 write/not-present 页故障权限、VMA 和 64 KiB 增长间距；
5. 随后 `ResolveUserReturnMemory` 再验证 handler R-X 与 frame 页 RW-NX，并在
   fork 后需要时拆分 COW。

用户创建 Thread 的栈是带 guard 的匿名 VMA，不走主栈几何扩展；Kernel 只允许
frame 位于该 Thread 登记的 stack base/size 内，并要求页已经满足用户可写。

## SignalFrame 为什么需要 Kernel cookie

仅检查 magic 和版本不能证明帧身份；用户可以复制一份旧帧，再把地址传给
sigreturn。每次开始 Handler 投递时，Kernel 为 Thread 登记：

```text
frame_address
cookie
signal_number
restorer_address
previous_mask
```

帧复制完成后才提交精确地址。sigreturn 必须让五项与用户帧逐项相等。完成后立刻
清空活动登记，所以同一帧不能返回两次。cookie 使用 64 位单调值，零保留为
“无活动帧”；回绕到零时跳回一。它不是密码学令牌，但与精确地址和 Thread
所有权结合，关闭了旧帧重放和跨 Thread 提交。

## sigreturn 是特权返回验证，不是内存复制

用户可修改 SignalFrame 中的 RIP、RSP、RFLAGS 和段选择子。如果 Kernel 直接
复制到 `IRETQ` 帧，攻击者可尝试返回高半 Kernel 地址、不可执行页、错误段或
危险 flags。v1.14 按下列顺序拒绝：

1. 当前 Thread 确实有活动帧；
2. 用户地址等于登记地址，16 字节对齐且完整位于本 Thread 栈；
3. magic/version/size/reserved 正确；
4. cookie、信号、restorer、previous mask 与 Kernel 登记一致；
5. mask 不含 Kill；
6. RIP/RSP 通过 48 位 canonical 和低半用户范围检查；
7. CS/SS 是冻结的用户 selector，RFLAGS 通过统一用户现场校验；
8. RIP 页为用户 R-X，RSP 页为用户 RW-NX。

畸形帧调用现有非法用户返回隔离路径，只终止目标 Process，父进程 wait 看到
Exception/vector 13。Kernel 继续运行并回收子进程。`signal_probe` 的子进程
故意把 magic 清零，证明这条失败路径不是只存在于宿主模型。

## fork、exec、exit 的状态迁移

### fork

孩子复制父 Process 的 disposition 和进程组；创建出的唯一 Thread 复制调用
Thread 的 mask。pending 与 active frame 不复制。否则父进程尚未处理的事件会
在父子各执行一次，或孩子拿到指向父栈的活动帧地址。

### exec

新程序不知道旧 handler 地址，因此 Handler 必须恢复 Default；Ignore 可以
保留。pending、活动帧和被删除兄弟 Thread 的状态全部清空，survivor mask 保留。
这与“PID、父子关系、进程组仍是同一 Process”相容。

### exit

ThreadExit 删除 Thread 信号状态；未交付 pending 回到 Process 后可重新选择。
最后一个 Thread 或信号默认动作退出 Process 时，先终止全部 scheduler Thread，
再删除全部 ThreadSignalState，最后删除 ProcessSignalState。整机最终门禁要求
两种 active count 都为零。

## 日志为什么只记录状态边界

信号可能来自热路径，不能每次扫描 Thread 都打印。当前日志选择：

```text
ACTION_NUMBER / ACTION_DISPOSITION
QUEUED_COUNT                 # 只在实际入队计数达到二次幂时
DELIVERY_DISPOSITION
HANDLER_DELIVERY_COUNT       # 二次幂采样
DELIVERY_FAILURE_STAGE       # 仅失败
REJECTED_FRAME_COUNT         # 仅失败与二次幂
```

系统结束再打印 queued、coalesced、ignored、handler、default termination、
group send、interrupted/restarted wait 与 rejected frame 汇总。用户探针只在
一项事务完整提交后打印一次 marker。这样能定位动作表、选择、帧构造或返回验证
中的哪一层失败，又不会让日志改变调度竞争。

## 四层测试怎样分工

### 单元测试

直接驱动 `SignalManager`，验证两个 Thread mask 下的唯一选择、重复普通信号
合并、handler 活动帧五元组、fork 继承与 exec 重置。它能精确观察内部状态，
但不证明真实用户栈或 `SYSCALL`。

### 集成测试

把 SignalManager、ThreadScheduler、WaitQueue 和 DeadlineQueue 组合起来。
测试先让 Thread 同时拥有业务等待和 deadline，再让 Signal 获胜；随后 condition
再次 wake、deadline 再次 expire 都不能产生第二次 Ready，deadline cancellation
统计必须守恒。

### 固定种子随机测试

100000 步随机执行发送、改 mask、开始/完成投递和生命周期操作。参考模型在每步
计算 pending union，并要求同一 Process 的同一普通信号最多属于一个 Thread。
失败报告固定种子与步骤，可完全复现。

### QEMU 整机测试

`/bin/signal_probe` 经真实 ELF、页表、用户栈、Intel NASM restorer、原生系统
调用、fork/COW 和 PID1 wait 验证：

- 阻塞 descriptor wait 被 User1 打断并按 restart flag 重启；
- 屏蔽期间两次 User1 合并，解除 mask 后只运行一次 handler；
- 独立进程组按组发送 User2 并 Ignore；
- fork 孩子继承 User1 Handler，父计数不被孩子 COW 写入污染；
- 子进程篡改 frame 只隔离自己；
- Terminate 默认动作以 Signal 原因和信号号被父进程观察。

## 常见错误与定位

若安装 Handler 后仍默认终止，先看 `ACTION_DISPOSITION` 与
`DELIVERY_DISPOSITION`。前者为 Handler、后者为 Default 时检查 Process 索引
和 exec reset；两者都为 Handler但仍终止时检查 `DELIVERY_FAILURE_STAGE`，
通常是栈页、权限或 frame 提交失败。

若按组发送杀死 init，检查目标进程是否仍继承 PID1 进程组；不要把进程树后代
误当成独立组。若阻塞调用永不恢复，检查 Signal 是否通过 `WakeThread` 取消
deadline，以及保存的 syscall number、restartable 与 RIP 两字节回退。

若 handler 运行但返回后 vector 13，核对 restorer 进入时 RSP 是否正好指向
SignalFrame、frame 是否被 handler 越界写坏、saved RSP 是否仍在本 Thread 栈、
RIP 页是否 R-X。不要放宽 `ValidateUserContext` 来掩盖错误。

## 本阶段完成边界

v1.14 已建立普通信号、进程组、用户 handler、严格 sigreturn 和阻塞调用中断/
重启，但没有 TTY、session、前台组、Ctrl-C、stop/continue、alternate stack、
实时信号队列或 `siginfo_t`。v1.15 将把 i8042 输入先交给 TTY，再由 TTY 把控制
字符翻译成对前台进程组的信号；不会让键盘 IRQ 直接选择某个 PID。
