# v1.8：从地址空间意图到匿名按需分页

## 1. 这一阶段解决的根本问题

看到一条地址 `0x60001000` 时，处理器只关心当前页表能否把它翻译成物理地址。
操作系统却必须回答更多问题：

- 这个地址是否属于进程？
- 它是程序代码、匿名内存、heap 还是 stack？
- 允许读、写还是执行？
- 当前没有 PTE 是正常“尚未触及”，还是越界？
- 首次出现时应该读磁盘、复制共享页，还是构造全零页？
- 撤销后哪些物理页和页表页归谁释放？

v1.7 只有 eager ELF 与固定栈，所有合法页都预先存在，not-present 几乎等同
错误。v1.8 第一次把两类事实分开：

```text
VMA：软件承诺和策略
PTE：硬件当前可以观察到的驻留状态
```

完成这一阶段后，预留 32 MiB 地址可以只消耗一个 VMA 描述符；真正触及两个
相隔很远的页时才消耗两个数据 frame 和必要页表分支。

## 2. 历史背景：为什么既有 `brk`，又出现 `mmap`

### 2.1 连续数据段时代

早期 Unix 进程映像常被描述成：

```text
低地址
  text
  initialized data
  bss
  heap -> 向高地址增长
  ...
  stack -> 向低地址增长
高地址
```

`break` 是数据段的逻辑末端。`brk(new_end)` 改变末端，用户分配器再在这段
连续空间里切分小块。这个接口简单，适合程序只有一个主要动态区的时代。

它也有结构性限制：只能描述一段连续增长范围，难以表达文件映射、共享内存、
不同权限、稀疏大对象和独立释放的区间。

### 2.2 `mmap` 把对象统一成虚拟区间

随着虚拟内存成熟，系统需要把文件、匿名页、共享对象和设备页放在不同地址。
`mmap` 由此成为更一般的区间接口。一个用户分配器可以用 `brk` 管理小对象，
也可以用匿名 `mmap` 取得大块独立区间。

本项目在 v1.8 同时实现二者，不是为了复制所有 POSIX 选项，而是为了学习两种
地址所有权：

- program break：从 ELF 尾部开始的连续单调边界；
- anonymous mapping：匿名窗口中的独立半开区间。

### 2.3 为什么“申请虚拟内存”不等于“立即拿走物理内存”

64 位虚拟地址远多于机器实际 RAM。许多程序会预留大范围，但只访问少量页。
若预留时立即为每页分配 frame：

- 地址稀疏性的价值消失；
- 失败发生得过早；
- 大栈必须一次消耗完整上限；
- file fault、zero page、COW 等后续机制没有统一入口。

按需分页把动作推迟到处理器提供精确证据——某条用户指令真的访问了这一页。

## 3. x86-64 页故障到底提供了什么证据

### 3.1 页表遍历失败后发生的事情

用户指令发出线性地址后，处理器依次查 TLB 或四级页表。若翻译不存在、权限
不允许或页表保留位非法，处理器：

1. 不提交触发 fault 的内存访问；
2. 把线性地址写入 `CR2`；
3. 在 KernelStack 上建立异常现场；
4. 通过 IDT vector 14 进入本项目 NASM 异常桩；
5. 提供 page-fault error code；
6. 由 C++ 分发器决定恢复还是终止。

若 Kernel 建好页并从异常返回，处理器会重新执行原指令。按需分页不需要用户
代码显式“再试一次”。

### 3.2 error code 位

v1.8 使用以下架构位：

| 位 | 名称 | 为 0 | 为 1 |
| ---: | --- | --- | --- |
| 0 | P | not-present | protection violation |
| 1 | W/R | read | write |
| 2 | U/S | supervisor | user |
| 3 | RSVD | 无保留位错误 | 页表保留位非法 |
| 4 | I/D | data access | instruction fetch |

处理顺序很重要。RSVD 往往意味着 Kernel 构造页表错误，绝不能因为 P 位的
组合而被伪装成普通缺页。P=1 则表示页已经存在但权限失败，例如向只读匿名页
写入；也不能再分配一个可写页绕过策略。

### 3.3 CR2、RIP 和 RSP 各自证明什么

- `CR2`：哪一个线性地址导致 fault；
- error code：这次访问是读、写、取指以及来自哪个特权级；
- 保存的 `RIP`：返回时重试哪条指令；
- 保存的用户 `RSP`：栈 fault 是否与真实栈推进相邻。

仅凭 CR2 落在“栈最大范围”内就自动建页是不够的。程序可能错误地向栈保留区
深处写入；RSP 与连续 committed bottom 共同缩小合法集合。

## 4. VMA 与 PTE：策略层和机制层

考虑一段 16 KiB、RW、匿名 VMA，用户只触及第二页：

```text
VMA:
  [0x60000000, 0x60004000) Anonymous RW

PTE:
  0x60000000 -> not present
  0x60001000 -> frame 0x12345000, P|U|W|NX
  0x60002000 -> not present
  0x60003000 -> not present
```

四页都属于进程，但只有一页驻留。此时：

- `virtual_page_count = 4`；
- `anonymous_page_count = 4`；
- `resident_page_count` 只增加 1。

若访问 `0x60002000`，VMA 允许 Kernel 构造另一个零页。若访问
`0x60005000`，没有包含它的 VMA，即使页表上也恰好 not-present，语义仍是
越界。

## 5. 代码走读一：共享 ABI 和地址布局

先读
[`source/abi/include/os/abi/virtual_memory.hpp`](../../source/abi/include/os/abi/virtual_memory.hpp)。
这里没有 Kernel 私有指针或宿主 `size_t`，只有固定宽度数值：

- 4 KiB 页大小；
- R/W/X 与 FIXED flag；
- 512 MiB 匿名窗口；
- 8 MiB stack、guard 和 heap 限制；
- 112 字节 `VirtualMemoryStatistics`。

再读
[`source/abi/include/os/abi/system_call.hpp`](../../source/abi/include/os/abi/system_call.hpp)
中 39..42 与 `-39..-42`。编号只在尾部追加，已有用户 ELF 的 ABI 不被重排。

地址布局可以画成：

```text
0x0000000000000000
  ELF PT_LOAD pages
  program break VMA
0x0000000060000000  break limit / anonymous begin
  anonymous first-fit window, 512 MiB
0x0000000080000000  anonymous end
  unmapped gap
0x00007FFFFF7EF000  permanent guard, no VMA
0x00007FFFFF7F0000  stack VMA bottom
  8 MiB stack reservation, grows downward
0x00007FFFFFFF0000  stack top
```

这里的 512 MiB 是 v1.8 明确窗口，不是整个 x86-64 用户地址上限。处理器仍
报告至少 48 位虚拟地址宽度；项目故意用窄窗口让冲突、first-fit 和耗尽可以
在测试中被完整覆盖。

## 6. 代码走读二：VMA 描述符池与有序图

公开类型位于
[`source/kernel/include/os/kernel/memory/virtual_memory_area.hpp`](../../source/kernel/include/os/kernel/memory/virtual_memory_area.hpp)，
实现位于对应
[`virtual_memory_area.cpp`](../../source/kernel/src/memory/virtual_memory_area.cpp)。

### 6.1 为什么池与 map 分开

`VirtualMemoryAreaPool` 拥有实际描述符存储和自由链；`VirtualMemoryMap`
只拥有其中带自己 owner identifier 的节点。这样可以：

- 为全系统冻结 8192 元数据硬上限；
- 不在页故障路径递归调用 KernelHeap；
- 让不同 Process 共享容量但不能互相释放节点；
- 用全局 acquire/release 统计检查泄漏。

### 6.2 插入、排序和合并

`Insert` 先定位前后节点，再完成所有重叠检查。只有在确认不能和任一邻居合并
时才申请新描述符。

三个典型情况：

```text
[A same] + [new] + [B same] -> 扩大 A，删除并释放 B
[A same] + [new]            -> 只扩大 A.end
           [new] + [B same] -> 只降低 B.begin
```

这不仅减少描述符，也使多次相邻 `brk` 增长保持为一个 VMA。

### 6.3 中段移除为什么要先取得描述符

从 `[0, 16)` 移除 `[6, 10)` 会得到 `[0, 6)` 与 `[10, 16)`，区域数增加一。
若先改左半段、随后才发现池已耗尽，原映射会不可逆地损坏。因此实现分两遍：

```text
第一遍：验证所有重叠 kind，判断是否需要 split
预提交：若需要 split，先 Acquire
第二遍：执行 remove/trim/split
```

宿主单元测试使用只有一个描述符的池，要求中段移除返回
`AreaLimitExceeded` 且原区域逐字段不变。

### 6.4 `Validate` 在检查什么

池验证 free chain、活动数、owner 非零和累计守恒；map 验证：

- 链没有越界或环；
- previous/next 相互一致；
- owner 是本 map；
- 所有区间页对齐、非空、严格有序且不重叠；
- 相邻同属性区间已经被合并；
- 观察到的 area count 等于保存值。

这些检查不是性能路径上的每条指令都执行，但在系统调用边界、测试和销毁前
提供结构证据。

```text
RAX = system call number
```

## 8. 代码走读四：地址空间与统一页故障策略

核心实现位于
[`source/kernel/src/user/user_memory.cpp`](../../source/kernel/src/user/user_memory.cpp)。

### 8.1 ELF 装载阶段

`LoadUserAddressSpace` 的顺序是：

```text
ValidateUserElf
  -> reject stack collision
  -> calculate page-aligned break base
  -> initialize VirtualMemoryMap
  -> insert each ExecutableImage VMA
  -> insert full UserStack VMA
  -> create process page-table root
  -> eagerly map and fill ELF pages
```

ELF 仍 eager 是有意的阶段边界。v1.8 先让匿名 fault 稳定；v1.9 再引入需要
Vnode、page index、缓存身份和尾页清零的 file fault。

### 8.2 `MapDemandPage`

这个函数是匿名、break 与 stack 成功 fault 的共同提交点：

1. `AllocateAndMapUserPage` 从 buddy 取得 frame 并建立 PTE；
2. writable/executable 来自 VMA，不来自用户 fault 的猜测；
3. `ZeroPhysicalPage` 通过 direct-map 清完整页；
4. 清零失败时调用 `ReleaseUserPage` 回滚；
5. 更新 resident 与 peak。

“先映射再清零”在当前单核、当前地址空间上下文中由异常路径控制，用户指令
尚未返回，不会并发观察未清零页。后续 SMP 需要额外发布顺序与 shootdown。

### 8.3 `HandleUserPageFault`

建议按源码条件顺序阅读：

```text
user bit?
reserved bit?
present bit?
decode write / instruction?
FindContaining(CR2 page)?
PermissionsAllow?
stack policy?
ExecutableImage unexpectedly missing?
MapDemandPage?
update fault and stack counters
```

`ExecutableImage` 出现 not-present 在 v1.8 是内部不一致，因为 ELF 应 eager
驻留；它不会被悄悄当匿名零页。这个分支为 v1.9 改成 file-backed policy
留下明确替换点。

## 9. 栈：预留、提交与永久 guard

### 9.1 参数栈为什么仍要预提交

exec 构造 `argc/argv/envp` 时，Kernel 正在向候选地址空间写数据，尚没有
用户指令和可信 RSP fault。`PrepareUserStack` 因此根据已验证的最低参数地址
一次提交顶部所需页，再由 `CopyToUserAddressSpace` 写入。

### 9.2 正常增长

用户进入后，函数序言或局部数组让 RSP 向低地址移动。当第一次写到下一页：

```text
fault page + 4096 == committed bottom
```

且 fault/RSP 邻近检查通过，Kernel 提交这一页并降低 committed bottom。
一次只增长一页，使中间不能留下不可解释的 hole。

### 9.3 guard 为什么没有 VMA

若 guard 只是一个 not-present 但仍属于 stack VMA，通用缺页策略可能把它
变成正常页。v1.8 让 guard 完全不属于任何 VMA，因此第一道
`FindContaining` 就返回 `AreaNotMapped`。这比在 PTE 中设置一个私有软件位
更直接，也避免未来换页或 COW 误认。

## 10. `brk` 与 UserHeap 是两层不同机制

`SetProgramBreak` 只管理页级地址承诺：

```text
brk(old) -> brk(new high)
  insert/merge ProgramBreak VMA
  no frame allocated

brk(old) -> brk(new low)
  trim/remove ProgramBreak VMA
  release only resident pages above new rounded end
```

它不知道 24 字节对象、空闲块或 double free。`UserHeap` 才在用户空间管理
对象级分配。

### 10.1 BlockHeader

阅读
[`source/user/include/os/user/user_heap.hpp`](../../source/user/include/os/user/user_heap.hpp)
和
[`source/user/src/user_heap.cpp`](../../source/user/src/user_heap.cpp)。
每个 header 64 字节并按 16 字节对齐，字段全为显式 `uint64_t`：

```text
payload capacity
requested size
previous physical block offset
next / previous free offset
allocated-or-free state
signature
reserved
```

offset 相对 heap base，而不是宿主相关链表类型。空闲块同时参与：

- 物理相邻顺序，用于 coalesce；
- 空闲双链，用于 first-fit。

### 10.2 split 条件

找到容量大于请求的块时，只有余量至少能容纳一个 header 和最小 16 字节
payload 才拆分。否则把整个块交给调用者，但统计仍保存用户原始 requested
size，不把内部碎片冒充用户数据。

### 10.3 coalesce 顺序

释放后先尝试前一物理块，再尝试后一物理块。合并前从 free list 删除将消失的
节点，更新容量和下一块的 previous offset，最终只把合并结果保留一次。
`Validate` 通过两种遍历证明没有漏节点或重复节点。

## 11. 撤销与所有权回收

`UnmapAnonymousMemory` 先要求整个重叠集合都是 `Anonymous`。这意味着不能
用跨区间请求“顺便”删掉 stack 或 ELF。

对每页执行查询：

```text
NotMapped -> 只是 VMA reservation，继续
Mapped    -> ReleaseUserPage
Other     -> 地址空间结构损坏
```

`ReleaseUserPage` 返回额外回收的页表 frame 数。四级页表不是一页数据对应
四页固定开销；多个相邻页共享中间表。只有最后一个 PTE 消失时，相应 PT/PD
分支才可以回收，统计因此是实际结果而不是公式估算。

退出路径先切回 Kernel CR3，再销毁 Process 页表和 VMA。exec 则先完整建立
候选地址空间，提交后销毁旧地址空间。VMA 池 owner 防止候选与旧映像互相
释放元数据。

## 12. 失败语义表

| 场景 | 结果 | 地址空间变化 |
| --- | --- | --- |
| `mmap` 长度为零 | invalid range | 无 |
| fixed 地址不对齐 | invalid range | 无 |
| fixed 与已有 VMA 重叠 | address in use | 无 |
| VMA split 需要描述符但池耗尽 | metadata exhausted | 原 VMA 不变 |
| 首次匿名读 | 建零页并重试 | resident +1 |
| 写只读匿名页 | 用户 vector 14 退出 | 不升级权限 |
| 访问 stack guard | 用户 vector 14 退出 | 不建立 VMA/PTE |
| stack 跳过 committed 邻页 | 用户 vector 14 退出 | 无 |
| 缩小 break | 成功 | 区间缩小，驻留页与空表回收 |
| heap 请求超过上限 | capacity exhausted | 已有 allocation 不变 |
| heap 重复释放 | already released | free list 不重复插入 |

## 13. 测试如何分别证明算法和整机

### 13.1 单元测试

[`virtual_memory_area_test.cpp`](../../tests/unit/kernel/virtual_memory_area_test.cpp)
不需要 QEMU，直接验证区间算法和描述符池。

[`user_heap_test.cpp`](../../tests/unit/user/user_heap_test.cpp) 用宿主页对齐存储
模拟 break，使 split/coalesce/invalid pointer 可以快速定位。

### 13.2 固定种子随机测试

VMA 随机测试维护一个简单参考区间数组，每一步将生产实现与 oracle 对照，
共 100000 步。heap 随机测试保存每个活动 allocation 的尺寸和字节模式，
同样执行 100000 步。

固定种子意味着失败可重放。随机测试不是“多跑几次看运气”，而是确定性的
大状态空间遍历。

### 13.3 生命周期集成

[`user_virtual_memory_lifecycle_test.cpp`](../../tests/integration/boot/user_virtual_memory_lifecycle_test.cpp)
把 VMA、进程页表根和真实 frame allocator 组合 128 轮：

```text
create process root
reserve four-page VMA -> frame count unchanged
map one touched page
remove middle page -> VMA split
unmap -> empty page-table branches reclaimed
destroy VMA and process root
compare exact frame and descriptor baseline
```

### 13.4 QEMU

[`memory_probe.cpp`](../../source/user/programs/memory_probe.cpp) 在真实 Ring 3、
真实 CR3 与 `#PF` 下执行；两个故障 probe 证明非法情况没有被 happy path
吞掉。64 MiB、256 MiB、64 GiB 分别覆盖最小启动、完整功能和高内存规格。

```text
error_code

```

继续执行后，原用户 RIP 应重试并成功；不是跳到一条人工恢复指令。

## 15. 可以亲手完成的实验

### 实验 A：只预留不触页

把 memory probe 的匿名长度从 32 MiB 改为更大合法值，只查询统计，不解引用。
预期 virtual pages 增加，resident 不变。

### 实验 B：观察页表共享

依次触及同一 2 MiB 范围内多个页，再逐页 unmap。记录每次
`page_table_reclaimed_frame_count`；只有最后一个相关 PTE 消失时才回收共享
页表层。

### 实验 C：制造非法栈跳跃

不要访问永久 guard，而是直接写 stack VMA 底部附近。它虽然命中 stack VMA，
仍应因不连续和 RSP 距离被拒绝。

### 实验 D：观察 heap 外部碎片

交替申请大小不同的块，释放间隔块，再申请一个大块。比较
`largest_free_block_bytes` 与总空闲空间，理解 coalesce 能解决相邻碎片，
不能自动移动活动对象。

### 实验 E：验证 W^X

分别请求 `R|X` 与 `R|W|X`。前者可以建立 VMA但当前没有可写入的装载接口；
后者必须在系统调用边界拒绝。

## 16. 本阶段之后

匿名页只需要“分配并清零”，没有外部身份。文件页不同：它需要用
`(Vnode, page index)` 找到来源，处理文件尾页、缓存共享、truncate/write
失效和 `MAP_PRIVATE`。因此 v1.9 会复用本阶段的 VMA 与 fault 分发，但新增
file backing 与有界 clean page cache。

fork/COW 又依赖私有页引用和写 fault：父子先共享物理页并清除可写位，首次写
再复制。没有 v1.8 的 VMA 权限来源与统一 fault 路径，COW 只能变成散落在
页表代码里的特殊情况。
