# v1.18：ABI v2、devfs/procfs、工具宽度与冻结工程

## 1. 这一阶段为什么不是“再加一点功能”

操作系统发展到 v1.17 时，启动、进程、内存、I/O、信号、终端和持久化已经
形成闭环。此时最危险的做法，是为了让 2.0 看起来更丰富而继续增加机制。
每个新机制都会扩大用户 ABI、失败路径、锁关系、资源账本、教材和发布面。

v1.18 学习的是另一种能力：怎样停止改变边界，并证明已有边界足够稳定。
冻结包含四件事：

1. 把 syscall、错误、结构和 ELF 假设写成共享、可编译的 ABI；
2. 用 devfs/procfs 把设备命名和系统观察接入 VFS；
3. 用已有系统调用把用户工具补到 32 个，并证明它们真的运行；
4. 把构建、测试、教材、网站和生产部署身份连成可追溯发布。

这不是“文档阶段”。如果 ABI offset 写错，用户程序会把一种结构解释成另一
种；如果 procfs 持锁回调 VFS，读一个文本文件就可能死锁；如果 QEMU 在测试
并行中争抢 CPU，正确代码也会撞上超时。冻结同样需要设计和代码。

## 2. 背景：ABI 为什么会变成历史包袱

ABI 是已经编译的两段程序之间的约定。源代码接口可以重新编译后一起改变，
ABI 却可能被磁盘上的旧程序长期保存。它至少包含：

- 调用号和寄存器传参顺序；
- 成功值与负错误值；
- 结构大小、字段偏移、对齐和枚举底层值；
- 指针宽度、字节序和地址合法性；
- 可执行文件类型、机器类型、段权限与入口规则；
- signal frame 等由 Kernel 写、用户态再交回 Kernel 的双向结构。

Unix 历史上，系统调用和设备接口经常先服务当时的硬件，后来为了兼容旧程序
而长期保留。Linux 的 syscall number、`ioctl` 和 procfs 文本也体现了这种
成本。本项目不复制 Linux ABI，但要学习同一个工程事实：一旦宣布冻结，
“重排一下字段”就不再是无害重构。

因此 `version.hpp` 不是显示字符串。major=2 表示破坏兼容的边界代际；
minor/patch 为同一代内的兼容演进。当前 v2.0.0 冻结 69 个调用和 -1---57
错误区间。

## 3. ABI 代码走读

阅读顺序：

```text
source/abi/include/os/abi/version.hpp
  → source/abi/include/os/abi/elf.hpp
  → source/abi/include/os/abi/layout.hpp
  → source/abi/include/os/abi/system_call.hpp
  → source/kernel/src/user/user_elf.cpp
  → tests/unit/abi_v2_contract_test.cpp
```

`version.hpp` 给出唯一版本和 syscall/error 边界。`elf.hpp` 统一 ELF magic、
class、data encoding、文件类型、machine 和 program flags；Stage 1、Kernel
或用户工具不应各自维护一份“碰巧相同”的数字。

`layout.hpp` 使用 `offsetof` 和 `static_assert`。这些断言在编译目标代码时就
执行，不需要等到 QEMU 才发现结构漂移。例如 `ProcessLaunchRequest` 的六个
64 位字段固定在 0、8、16、24、32、40；`SignalFrame.context` 固定从 64
字节开始。若有人插入字段或更改类型，编译会停止。

仅检查 `sizeof` 不够。两个结构可能总大小相同而字段顺序不同；仅检查字段
offset 也不够，枚举号或错误边界仍可能漂移。因此独立 ABI 单元测试同时检查：

- 版本；
- enum 首尾；
- 错误首尾；
- 结构大小和对齐；
- 每个跨边界字段的 offset；
- ELF 目标身份。

## 4. 固定宽度类型与盘面/线协议

`long` 在 LP64 和 LLP64 平台宽度不同，`size_t` 表示宿主对象大小，
`bool` 的内存表示也不适合作为外部线协议。ABI、磁盘、硬件寄存器和汇编交接
必须使用 `uint8_t/uint16_t/uint32_t/uint64_t` 与对应有符号类型。

固定宽度解决“多少 bit”，不自动解决：

- 大小端；
- padding；
- 未对齐访问；
- 地址溢出；
- enum 是否在合法集合；
- 用户指针是否映射且有正确权限。

因此 rootfs 仍逐字段小端编码，syscall 仍先 copy-in，ELF 仍先验证范围再读取。
ABI 冻结不能替代输入验证。

## 5. 从专用 console 后端到 devfs

v1.15 只需要 `/dev/console`，专用文件系统可以完成教学闭环。但它把两个概念
粘在一起：

- “`console` 这个名字在 `/dev` 下存在”；
- “字符读写由 TTY/TerminalDevice 完成”。

v1.18 的 `Devfs` 只负责第一件事。调用者提供固定 `DevfsDevice[16]`，注册
成功后项中只有 node id、generation、名称长度、名称和 active。驱动对象不
进入 vnode，也不会经 stat 或目录项泄露。

控制流如下：

```text
Kernel 初始化
  → Devfs::Initialize(固定存储)
  → RegisterCharacterDevice("console")
  → Vfs::MountAt("/dev", devfs superblock)

用户 open("/dev/console")
  → VFS 逐组件解析
  → devfs lookup 返回 CharacterDevice vnode
  → FileDescription 选择 TerminalDevice
  → TTY 执行 canonical read/write
```

devfs 命名空间只读。create/remove/rename 返回 `ReadOnly`，普通文件 read/write
返回 `Unsupported`；真正字符读写不经过这些普通文件回调。这样避免同一设备
拥有两套 I/O 路径。

## 6. devfs 的失败与生命周期

注册先在锁内扫描全部槽位：

1. 若发现同名 active 项，增加拒绝计数并返回 `AlreadyExists`；
2. 同时记住第一个空槽；
3. 没有空槽时返回 `CapacityExhausted`；
4. 只有检查完成后才一次性发布完整新项。

没有“先 active，再复制名字”的半状态。v1.18 没有注销，因此一个已返回的
vnode 不会因设备槽复用而指向另一设备；未来若加入注销，必须增加 generation
演进和打开引用规则。

`Validate` 检查 superblock 身份、只读属性、节点号与槽位关系、名称范围、
重名和 open 统计。单元测试覆盖初始化、注册、lookup、readdir、open/close、
只读拒绝、容量、重名和破坏检测。

## 7. procfs 的历史动机与本项目边界

传统 Unix 倾向把很多对象暴露为文件：用户程序复用 open/read/close，不需要
为每个观察项增加 syscall。Linux procfs 后来承载大量进程和系统信息，但
也形成庞大、并非严格稳定的文本接口。

本项目学习“观察面复用 VFS”，不复制 Linux 目录树。固定六个文件已经足够：

```text
/proc/version
/proc/uptime
/proc/meminfo
/proc/processes
/proc/resources
/proc/mounts
```

所有文件只读、不可创建、删除、改名或截断。没有每 PID 目录、`/proc/self`
符号链接、权限、进程命令行或可写调优项。

## 8. 快照为何在 read 时生成

这些数值随调度、分配和 I/O 改变。若挂载时生成一次，内容立刻过时；若
procfs 为每个 open 长期保存完整快照，就需要动态分配和新的关闭生命周期。

当前选择是：每次 `read` 采集一次 `ProcfsSnapshot`，在 256 字节局部缓冲中
格式化，再按调用者 offset/capacity 短读。一次 read 内部一致；下一次 read
可以看到新状态。

```text
read(vnode, offset, capacity)
  → 校验 vnode 和目标缓冲
  → provider 采集 15 个 uint64_t
  → SnapshotWriter 有界格式化
  → offset >= size ? EOF
  → copy min(capacity, size-offset)
  → 更新 procfs 自己的低频统计
```

`stat` 也重新渲染以返回当前文本长度。于是 stat 后数值变化可能让随后的 read
长度不同，这是动态伪文件的正常语义；用户程序必须像读取普通流一样处理短读
和 EOF，不能把 stat size 当永远不变的事务承诺。

## 9. 最重要的锁规则：回调时不持 procfs 锁

snapshot provider 会读取：

- 物理页帧分配器；
- Kernel heap；
- ThreadScheduler/Process 观察摘要；
- FileDescription 和 Pipe 管理器；
- VFS mount/vnode 资源；
- rootfs journal 统计；
- PIT 单调时间。

若 procfs 先持有自己的锁，再依次取得这些锁，另一路径只要以相反方向执行，
就可能形成环。当前实现只用 procfs 锁保护 `ProcfsStatistics`；调用 provider
和格式化时完全不持该锁。

VFS 资源汇总也不在 VFS 全局锁下递归调用后端，而是遍历冻结 mount 数组，
每个后端返回数值后用 checked add 合并。procfs 自己的 resource usage 只
验证固定节点数，不再次采集快照，因此不会无限递归。

## 10. 有界十进制格式化

freestanding Kernel 不能依赖 `snprintf`、iostream 或动态 string。
`SnapshotWriter` 使用最多 20 字节的反向十进制缓冲：

1. 对 10 取余得到最低位；
2. 除以 10，直到值为零；
3. 原地反转；
4. 写入目标前检查剩余容量。

`uint64_t` 最大值恰好 20 位。每次追加都先检查
`length <= capacity - size`，避免 `size + length` 自身溢出。任一字段无法
完整写入时，整个 render 返回 `CapacityExhausted`，不把部分文本冒充成功。

## 11. 用户工具怎样复用观察面

新增工具不需要增加 syscall：

- `uptime/ps/free/uname/mounts/resources` 只是读取固定 procfs 文件；
- `basename/dirname` 只处理用户态字符串；
- `cp` 组合 open/read/write/close；
- `seq` 使用有上限的十进制解析与输出；
- `sleep` 把毫秒安全换算为纳秒，再调用已有 deadline sleep；
- `kill` 调用已有 signal syscall；
- `id` 调用已有 PID 查询。

`seq` 最多输出 100000 个值；`sleep` 在乘法前检查
`milliseconds <= UINT64_MAX / 1,000,000`；十进制解析在每个新 digit 前检查
`value <= (UINT64_MAX-digit)/10`。这些限制防止小工具成为无界日志或整数
溢出入口。

## 12. 为什么还需要 tool_probe

multi-call ELF 根据 `argv[0]` 分派，因此 32 个路径可以共享代码字节。但如果
构建脚本漏装一个路径，或者所有名字意外变成同一个硬链接，普通编译仍会成功。

`/bin/tool_probe` 在 PID1 启动序列中检查固定 32 项：

1. stat 必须成功且类型是 regular file；
2. 32 个 inode 必须全部不同；
3. 文件至少能容纳 ELF magic；
4. open/read 必须得到 `7F 45 4C 46`；
5. 每个 fd 必须成功关闭。

全部通过才输出 `ELF32_VERIFIED`。这证明磁盘镜像中的路径与文件，不只是
CMake 列表。256 MiB functional Shell 再实际运行新增工具，证明 dispatch、
参数、syscall、procfs 和资源回收。

## 13. 测试层次

| 层次 | 证明内容 |
| --- | --- |
| ABI 单元 | 版本、号值、结构大小/offset、ELF 身份 |
| devfs 单元 | 注册、重复、容量、lookup、readdir、只读和统计 |
| procfs 单元 | 六文件文本、短读、EOF、stat、失败 provider |
| VFS 集成 | rootfs/memfs/devfs/procfs 同时挂载和路径穿越 |
| 随机 | 100000 个 procfs offset/capacity/value 与独立 oracle |
| 产物 | Kernel/用户 ELF 段、权限、符号与 freestanding 依赖 |
| QEMU bootstrap | 32 唯一 inode/ELF、ABI/devfs/procfs 启动标记 |
| QEMU functional | 32 工具覆盖、16 级流水线、TTY、信号和资源守恒 |
| QEMU capacity | 64 GiB 来宾视图、4 GiB 以上实际页生命周期 |

所有 QEMU CTest 使用同一 `RESOURCE_LOCK`。宿主测试可开满 CPU，虚拟机必须
串行；否则多个 TCG 实例会把正确的 10 秒故障用例拖成超时。

## 14. 日志与时间

Kernel 新增三个低频标记：

```text
[OS][KERNEL] DEVFS_READY=/dev
[OS][KERNEL] PROCFS_READY=/proc
[OS][KERNEL] ABI_V2_FROZEN
```

QEMU runner 仍给串口行添加 `[QEMU][T+......ms]`，它表示宿主收到该行的相对
时间；来宾的 `/proc/uptime` 和 Kernel 单调统计来自 PIT。两种时间用途不同：
前者用于定位测试停滞，后者属于 OS 自己的时间语义。

devfs/procfs 不逐 open、逐 read 打日志。热路径只更新计数，结束摘要再输出
资源状态；错误只报告最接近根因的一次。日志本身不能改变调度和 ATA 时序。

## 16. 已知边界

- ABI v2 不是 Linux/POSIX ABI；
- procfs 没有每进程目录，文本格式只服务当前教学工具；
- devfs 没有注销、权限、major/minor 或热插拔；
- 32 个工具是小型实现，不追求 GNU 选项兼容；
- Kernel 仍为单 BSP，不声称这些锁已经 SMP-safe；
- wall clock、RTC、网络、USB、AHCI/NVMe、动态链接仍不进入 v2.0；
- v2.0 只做集成发布，任何新核心机制进入 v2.x。
