## 2. 历史背景：fork 为什么会长成今天这样

早期 Unix 把进程创建定义为“复制当前进程”。这让 Shell 可以先 fork，再在
子进程里调整描述符、工作目录或信号状态，最后 exec 目标程序；父进程保留
原环境并 wait。接口组合性很好，但早期机器复制整个地址空间很昂贵。

后来分页硬件提供页级保护，内核发现可以先让父子共享物理页，只把本来可写的
PTE 临时降为只读。只要没有人写，复制永远不会发生；首次写入者触发异常，
内核才为这一页建立私有副本。这就是 copy-on-write。

注意 COW 不是 CPU 的一条指令，也不是 ELF 属性。CPU 只报告“当前 CPL3
指令试图写一个 present 但 read-only 的用户页”。这究竟是合法 COW、真正
只读数据、越界写还是损坏页表，只能由内核结合 VMA 和软件元数据判断。

## 3. fork 的返回模型

用户调用：

```cpp
const int64_t fork_result = os::user::ForkProcess();
if (fork_result == 0) {
    // 子进程
} else if (fork_result > 0) {
    // 父进程，返回值是子 PID
} else {
    // 创建失败，当前进程保持原状
}
```

系统调用只实际进入内核一次。内核复制调用 Thread 的 `UserContext`，把子现场
的 `RAX` 改为 0，再让父现场的 `RAX` 接收子 PID。以后调度器分别恢复两个
现场，看起来就像同一调用在两个 Process 中各返回一次。

v1.10 明确“子 Process 只包含调用 Thread”。Process 持有地址空间、文件表、
文件系统上下文和父子关系；Thread 持有可调度现场、内核栈与 FXSAVE 状态。
即使以后一个 Process 有多个 Thread，也不能把其他 Thread 正运行到一半的
内核栈直接复制给子 Process。

## 4. x86-64 页故障给了哪些事实

页故障异常向量为 14。CPU 把故障线性地址写入 `CR2`，并压入 error code：

| 位 | 名称 | 为 1 时 |
| ---: | --- | --- |
| 0 | P | protection violation；为 0 表示 not-present |
| 1 | W/R | 访问是写；为 0 表示读 |
| 2 | U/S | 访问发生在 CPL3 |
| 3 | RSVD | 页表保留位被置位 |
| 4 | I/D | NX 启用时的取指 fault |

COW 的典型硬件事实是 `P=1, W/R=1, U/S=1`。但这还不充分：

- 写只读 `.text` 也是同样三位；
- 写只读文件映射也是同样三位；
- 页表损坏可能额外置 RSVD；
- Kernel 经 direct-map 复制用户物理页时甚至不会产生这个用户 PTE fault。

内核还要检查：

```text
VMA: 该地址属于可写 private 区间
PTE: Present=1, User=1, Writable=0, COW=1
metadata: 该物理页存在合法共享引用
```

任何一项不满足都不能当作 COW 成功处理。

## 5. PTE 软件位与 TLB

x86-64 四级 4 KiB leaf PTE 中有软件可用位。项目使用位 9 表示 COW。
编码后的核心关系是：

```text
原可写页：P=1 RW=1 US=1 COW=0
fork 共享：P=1 RW=0 US=1 COW=1
真正只读：P=1 RW=0 US=1 COW=0
```

页表 API 会拒绝 `RW=1,COW=1`，因为它既不会触发 fault，又声称需要写时
私有化，是自相矛盾状态。

CPU 可能已把旧 PTE 缓存在 TLB。修改当前地址空间中的父 leaf 后必须执行
`INVLPG [virtual_address]`；否则父进程可能暂时继续使用旧 writable 翻译，
在没有 fault 的情况下修改共享 frame。当前系统只有一个 BSP，所以不需要给
其他 CPU 发 shootdown IPI；这不是多核实现已经完成。

## 6. 为什么不为所有页永久保存引用数

如果为 64 GiB 规格中的每个 4 KiB frame 保存一个 64 位引用数，仅这一字段
就需要 128 MiB，而且内核页、页表页、cache 页和用户页的所有权语义并不相同。

v1.10 采用“独占隐含 1，共享才登记”的稀疏模型：

```text
没有表项              => 一个 AddressSpace 独占
第一次 fork           => 建表项，reference_count = 2
再次 fork             => reference_count += 1
一个映射销毁/私有化   => reference_count -= 1
剩余一个映射          => 可 RestoreExclusive，删除表项
最后一个映射销毁      => reference_count 归零并释放 frame
```

`UserPageReferenceManager` 使用外部固定存储，容量 32768 项。固定容量让失败
可预测，也能在 fork 准备/提交阶段明确返回资源耗尽；不会在持有页表状态时又
递归依赖尚未验证的动态容器。

## 7. fork 地址空间的两阶段事务

### 7.1 准备候选子对象

先创建还不可运行的 child：

1. 预留 ProcessTree 身份；
2. 建立独立页表根；
3. clone VMA 图和每个 FileBacking；
4. 对已经驻留的 leaf，在 child 中映射同一 frame；
5. 对 clean cache 页增加 cache mapping reference；
6. clone FileTable、FsContext 和调用 Thread 现场；
7. 创建带双 guard 的子内核栈与 FXSAVE 区。

此时父 PTE 仍保持原状。任何失败只需销毁候选 child，不会让父进程突然遭遇
COW fault。

### 7.2 提交父 COW

候选完整以后，再遍历父的可写 private leaf：

1. `RetainForFork` 建立或增加 frame 引用；
2. child leaf 已经是只读 COW；
3. 把 parent leaf 改成只读 COW；
4. 失效 parent 当前 VA 的 TLB；
5. 记录本页已提交。

只有全部页提交成功，才把 child 发布到 ProcessTree 与 ready queue。

### 7.3 失败回滚

如果第 N 页提交失败：

1. 销毁 child 地址空间，逐页释放 child 引用；
2. 对已经提交的 parent leaf 检查引用是否只剩 1；
3. 删除对应稀疏元数据；
4. 把 parent leaf 恢复 writable、清除 COW，并失效 TLB；
5. 逆序释放子文件表、文件系统上下文、Thread、内核栈与 Process 槽。

验收不只看“fork 返回失败”，还要比较 fork 前后的 frame、页表、VMA、KVA、
stack、对象引用与 ProcessTree 快照。

## 8. 一次真实 COW fault

假设父子共享 frame `F0`，引用数为 2，子进程执行：

```text
mov byte [user_address], 0xA7
```

CPU 页表遍历发现 child PTE `RW=0`，产生 `#PF`。内核：

1. 从 `CR2` 得到 fault VA，页对齐；
2. 解析 error code，排除 not-present、supervisor、reserved 和 instruction；
3. 找到可写 VMA；
4. 读取 leaf 并确认 COW；
5. 分配新 frame `F1`；
6. 经高半 direct-map 把 `F0` 的 4096 字节复制到 `F1`；
7. child PTE 替换为 `F1,RW=1,COW=0`；
8. `INVLPG`；
9. 释放 `F0` 的一个引用；
10. 返回原用户指令，CPU 重试，这次写入 `F1`。

父进程仍读到 `F0` 的旧字节。若父进程以后写，此时 `F0` 只剩一个引用，内核
不再复制，只删除元数据并把父 PTE 恢复 writable。

## 9. CopyToUser 为什么也要 break COW

系统调用返回结构常由 Kernel 写入用户缓冲区。例如
`GetVirtualMemoryStatistics` 把 200 字节结果复制到调用者提供的地址。

如果这个地址位于 COW 页，Kernel 通过 direct-map 访问的是物理 frame，不会
用用户页表执行那次写，也就不会自然触发 CPL3 `#PF`。若直接复制，父子会一起
看到被修改的数据。

因此用户指针处理分两层：

```text
ValidateUserWritableMemory
  → 对每页检查 VMA/PTE
  → 若是合法 COW，主动 BreakCopyOnWritePage
  → 确认最终 writable
CopyToUserAddressSpace
  → 只向已经私有化的 frame 复制
```

用户指令写和 Kernel 代写共享同一底层状态转换，避免两套近似实现逐渐分叉。

## 10. 文件与目录上下文怎样继承

### 10.1 FileTable 与 FileDescription

fd 是 Process 局部整数；FileDescription 是可共享的打开实例。fork 后：

```text
parent fd 3 ─┐
             ├─> same FileDescription(offset = 1)
child  fd 3 ─┘
```

两张 FileTable 相互独立地保存 fd 3 和该 fd 的 CLOEXEC 等 flags，但表项都
持有同一个 KernelObject 强引用。因此 child 再读一个字节后，parent 从新的
共享 offset 继续；parent 关闭 fd 3 不删除 child 表项。

`FileTable::CloneFrom` 必须保留精确槽号，不能用普通“安装到最低空闲 fd”
循环重建，否则有空洞的表会改变用户可见编号。

### 10.2 FsContext

cwd/root/mount namespace 值复制到 child。fork 时两者都在 `/bin`；child
之后 `chdir` 不改变 parent 当前目录。`Vfs::CloneContext` 负责增加所需后端
引用并生成独立上下文。

### 10.3 FileBacking 与 clean cache

VMA 不能只保存原 fd，因为用户可以在 mmap 后关闭 fd。fork 克隆
FileBacking，增加其 VFS 打开实例或内存来源引用。完整只读 file page 继续由
clean cache 管理；private 可写驻留 frame 进入 COW 引用表。两者不能混用
同一引用数。

| 层次 | 证明内容 |

| 单元 | 引用状态机、FileTable 精确 clone、FsContext 与 FileBacking 生命周期 |
| 集成 | 两张页表共享同一 frame、COW bit 编解码、替换后互不影响 |
| 随机 | 100000 步 fork/release/restore 与参考计数逐步一致 |
| Ring 3 | 真实 CPL3 写 fault、CopyToUser、cwd、fd offset、fork/exec/wait |

`/bin/fork_probe` 先建立匿名页、writable private 文件页和 readonly 文件页，
fork 后由 child 修改前两者并让 Kernel 把 VM 统计写进另一张 COW 页；parent

随后 parent 顺序执行 32 次 fork，child 都 exec `/bin/exec_target`，parent

## 13. 常见误解

**“fork 后虚拟地址应该不同。”**

父子通常保留相同虚拟地址，独立的是 CR3 和页表。共享期这些 VA 甚至指向同一
物理 frame；写后才指向不同 frame。

**“PTE 不可写就代表 VMA 不允许写。”**

COW 期间 VMA 仍允许写，PTE 暂时不可写是捕获首次写入的硬件手段。

**“只要复制数据，不必刷新 TLB。”**

CPU 可能继续使用旧 writable 翻译，必须在当前地址空间修改 leaf 后失效。

**“CopyToUser 总会触发用户页故障。”**

Kernel 经 direct-map 写物理页不会走用户 PTE，必须主动私有化。

**“引用数降到 1 以后仍应复制。”**

最后持有者已经独占；恢复权限即可，复制只会浪费内存。

**“fork 失败只要不返回 child PID 就安全。”**

父 PTE、frame 引用、FileBacking、fd 强引用、ProcessTree 预留也必须恢复。

## 14. 本阶段边界

v1.10 没有实现：

- 用户多 Thread 与 fork 停世协调；
- `vfork`、`clone`、共享匿名映射或 `madvise`；
- huge-page COW、swap、overcommit 与 OOM killer；
- writable `MAP_SHARED`、dirty/writeback 或 `msync`；
- SMP TLB shootdown；
- pipe/dup/重定向的完整 Unix I/O 组合。

下一阶段 v1.11 会在已经正确继承 FileTable 的基础上实现 pipe、dup、
close-on-exec、重定向、外部 Shell 和核心工具，不重新改写 COW 所有权模型。
