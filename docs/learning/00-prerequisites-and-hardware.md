# 前置篇：硬件、二进制与工具链

> 深度背景：本篇用于快速建立全貌。若某个概念是第一次接触，请配合
> [七册背景知识专题](background/README.md) 阅读；专题会补充 x86 历史、
> 数学推导、ABI、工具链、设备状态机和操作系统抽象的来龙去脉。

## 1. 学习目标

这一篇先建立后续所有代码共同依赖的机器模型。完成后应能回答：

- CPU 复位后为什么从 `0xFFFFFFF0` 取指？
- 物理地址、虚拟地址、端口地址和磁盘 LBA 有什么区别？
- x86 的实模式、保护模式、长模式和 Ring 0/Ring 3 分别解决什么问题？
- GDT、IDT、TSS、页表和控制寄存器之间怎样配合？
- 中断控制器、定时器、键盘、串口和 ATA 控制器怎样被软件访问？
- 为什么普通桌面 C++ 程序的构建方式不能直接用于内核？
- QEMU 在本项目中模拟了什么，又明确没有替项目做什么？

第一次阅读时不必背诵所有位值。先理解“谁向谁提供契约”，进入对应阶段后再结合
代码记忆具体常量。

## 2. 一台机器如何开始执行

### 2.1 电源、时钟和复位

真实计算机上电后，电源、时钟源和复位电路先让 CPU 与外设处于确定状态。复位
信号解除后，CPU 才开始取指。软件看到的第一个事实不是 `main()`，而是一组由
处理器手册规定的寄存器初值和复位取指地址。

QEMU TCG 用软件模拟了这套可观察行为。它不是逐根电线模拟主板，但会提供项目
使用的 x86 CPU 状态、RAM、ROM 映射、I/O 端口、PIC、LAPIC、PIT、i8042、
IDE 控制器和串口。

本项目通过 `-bios` 加载自己的 ROM。QEMU 不执行 BIOS 服务，也不会解析项目的
磁盘或 ELF。

若要观察现实中的电源、模组连接器、HDMI/USB/PCIe 差分对、按键和风扇怎样
落到原理图与 PCB，请对照
[N100 实体载板电路详解](physical-carrier-circuit-guide.md)。该实体平台通过
UEFI 启动，不是当前 QEMU 机器的即插即用替代品。

### 2.2 x86 复位取指

x86 复位后处于一种与 16 位实模式接近但具有特殊隐藏段基址的状态。关键值是：

- 可见 `CS = 0xF000`。
- `IP = 0xFFF0`。
- CS 隐藏基址为 `0xFFFF0000`，不是普通实模式计算出的 `0x000F0000`。
- 因此线性/物理取指地址是 `0xFFFF0000 + 0xFFF0 = 0xFFFFFFF0`。

这解释了为什么 ROM 必须覆盖 4 GiB 地址空间顶端，为什么复位向量只有最后
16 字节可直接放置短小跳转，也解释了为什么不能仅用可见 `CS << 4` 推导复位
地址。

项目把 128 KiB ROM 映射到：

```text
0xFFFE0000  +---------------------------+
            | ROM 主体                  |
            |                           |
0xFFFFF000  +---------------------------+
            | 16 位复位后主入口         |
            |                           |
0xFFFFFFF0  +---------------------------+
            | reset vector: near jump   |
0xFFFFFFFF  +---------------------------+
```

复位向量的 near jump 只改变 IP，保留特殊的 CS 隐藏基址，所以能到达
`0xFFFFF000`。入口随后显式建立普通段状态。

## 3. 四类地址不要混淆

### 3.1 物理地址

物理地址是 CPU 最终送往内存系统或设备映射的地址。RAM、ROM 和 MMIO 都占据
物理地址空间。

本项目常见的物理地址包括：

- `0x00007000`：早期实模式栈附近。
- `0x00008000`：Stage 1。
- `0x00010000` 起：Stage 1 临时页表和交接结构。
- `0x00100000`：Kernel ELF 入口和首个装载段。
- `0x03E00000`：Kernel 文件暂存区。
- `0x03FFF000`：早期 Kernel 栈顶。
- `0xFEE00000`：Local APIC MMIO。

### 3.2 线性地址和虚拟地址

分段先把逻辑地址转换成线性地址，分页再把线性地址转换成物理地址。64 位模式下
普通代码段/数据段基址通常为零，所以“线性地址”和“虚拟地址”在项目日常讨论中
基本指同一层。

Stage 1 最初建立恒等映射，即虚拟地址等于物理地址。内核随后继续保留低地址
恒等映射，同时增加高半区 Kernel heap 映射。用户进程则把相同用户虚拟地址映射
到各自不同的物理页。

### 3.3 I/O 端口地址

x86 还有独立的 16 位 I/O 端口空间。`IN`/`OUT` 指令访问它，不经过普通
指针和页表。

例如 `0x3F8` 表示 COM1 数据寄存器端口，不是 RAM 地址 `0x3F8`。端口读写
常带硬件副作用，因此编译器必须把它视为不可随意删除或重排的操作。

### 3.4 磁盘 LBA

LBA 是扇区编号，不是内存地址。当前 ATA 每扇区 512 字节：

```text
磁盘字节偏移 = LBA × 512
```

CPU 不能直接解引用 LBA。软件必须向 ATA 端口写入 LBA 和命令，再从数据端口
传输扇区内容到 RAM。

## 4. 数值表示与二进制布局

### 4.1 位、字节和十六进制

一个字节有 8 位。十六进制一位表示 4 位二进制，因此特别适合阅读寄存器位图和
地址：

```text
0xFF = 1111 1111b
0x1000 = 4096 = 一个 4 KiB 页的大小
0x200000 = 2 MiB
```

地址区间在项目中通常使用半开形式 `[begin, end)`。长度为 `end - begin`，
相邻区间可以无歧义拼接，也容易检查溢出。

### 4.2 小端序

x86 使用 little-endian。数值 `0x12345678` 写入连续内存后是：

```text
低地址 → 78 56 34 12 → 高地址
```

CPU 加载整数时会自动还原数值，但磁盘格式和外部协议必须明确规定字节序。项目的
Stage 1/Kernel 描述符和文件系统使用显式小端编码；`fw_cfg` 目录中的某些字段
则是大端，Stage 1 必须逐字节转换。

### 4.3 对齐

对齐要求地址为某个 2 的幂的整数倍。项目中的典型对齐：

- 栈在调用边界保持 16 字节对齐。
- ELF `PT_LOAD` 使用 4 KiB 对齐。
- 普通页是 4 KiB。
- Stage 1 临时恒等映射使用 2 MiB 大页。
- 页表自身占据并对齐到 4 KiB。

对齐既可能是硬件要求，也可能是 ABI、缓存或格式约定。文档中应明确是哪一种。

### 4.4 溢出安全

地址加长度不能直接写成“起点 + 长度后比较”，因为无符号整数可能回绕。正确
思路是先证明加法不会溢出，再形成半开区间。`source/foundation` 的地址范围
类型就是为了集中表达这些不变量。

## 5. x86 执行模式

### 5.1 实模式

传统实模式使用 `segment:offset`。常规线性地址近似为：

```text
segment × 16 + offset
```

它适合最早期 16 位代码，但没有页级内存保护，地址能力和指令操作数宽度有限。
复位后必须先在这种环境中运行，项目不能一上来执行 64 位 C++。

### 5.2 保护模式

保护模式让段寄存器保存“选择子”，通过 GDT 查找描述符。描述符规定段的基址、
界限、类型、存在位和特权级。

项目进入 32 位保护模式的直接目的，是建立进入 IA-32e 模式所需的中间状态，
而不是长期使用 32 位分段内存模型。

### 5.3 IA-32e 与 64 位子模式

进入 64 位模式至少需要：

1. 有效的 PML4 根页表。
2. 设置 `CR4.PAE`。
3. 把页表根物理地址写入 `CR3`。
4. 设置 `IA32_EFER.LME`。
5. 设置 `CR0.PG`，同时保持保护模式开启。
6. 通过指向 L 位代码段的远控制转移更新 CS。

`LME` 表示请求启用，`LMA` 表示硬件确认 IA-32e 已激活。项目会回读这些状态，
而不是假定写寄存器必然成功。

### 5.4 长模式仍然有段

64 位模式弱化了普通分段，但 CS 的 L、DPL 等属性仍决定代码宽度和特权级，
SS/DS 等选择子仍参与特权检查，FS/GS 也可以使用独立基址。GDT 没有消失。

## 6. 寄存器分类

### 6.1 通用寄存器

`RAX`、`RBX`、`RCX`、`RDX`、`RSI`、`RDI`、`RBP`、`RSP`、`R8`–`R15`
保存整数、地址、参数和临时状态。`RIP` 是当前指令指针，`RFLAGS` 保存条件码、
中断允许位等状态。

项目遵循 x86-64 System V 函数调用约定的主要部分：

- 前六个整数参数通常是 `RDI, RSI, RDX, RCX, R8, R9`。
- 返回值通常在 `RAX`。
- `RBX, RBP, R12`–`R15` 是被调用者保存寄存器。
- 调用点要求栈满足 16 字节对齐规则。

Kernel/User 的 `INT 0x80` ABI 是项目自己定义的协议，不完全等同于 C++ 调用
约定：第四个系统调用参数使用 `R10`。

### 6.2 段寄存器

`CS`、`SS`、`DS`、`ES`、`FS`、`GS` 保存选择子及硬件维护的隐藏描述符缓存。
修改 GDT 后必须通过规定的控制转移或寄存器重载刷新相关隐藏状态。

### 6.3 控制寄存器

- `CR0`：保护模式、分页和写保护等全局控制。
- `CR2`：页错误发生时的线性地址。
- `CR3`：当前四级页表根的物理地址及相关标志。
- `CR4`：PAE 等扩展功能。

切换 `CR3` 不只是换一个数字，而是在切换当前地址空间，并通常导致 TLB 状态
变化。

### 6.4 MSR

Model Specific Register 通过 `RDMSR/WRMSR` 访问。项目使用：

- `IA32_EFER`：LME、LMA、NXE。
- Local APIC 相关能力由 CPU/APIC 状态共同决定。

MSR 不是普通内存，也不是 I/O 端口。

## 7. 特权级、GDT 与 TSS

### 7.1 Ring 0 与 Ring 3

x86 定义 Ring 0–3，本项目只使用：

- Ring 0：内核，可执行特权指令、访问监督页和设备。
- Ring 3：用户程序，只能访问 U/S=1 的页面，不能直接操作 CR3、CLI 或端口。

当前特权级 CPL 来自 CS 选择子的低两位。描述符 DPL、门 DPL、选择子 RPL 和
页表 U/S 位共同形成边界；只改其中一个不足以建立用户隔离。

### 7.2 GDT

GDT 是描述符数组，`GDTR` 保存其基址和界限。项目最终建立：

- null 描述符。
- Ring 0 code/data。
- Ring 3 code/data。
- 占两个槽的 64 位 TSS 描述符。

`LGDT` 只替换 GDTR，不会自动刷新所有段寄存器的隐藏缓存。

### 7.3 TSS

64 位 TSS 不负责传统硬件任务切换。本项目使用它提供：

- 从 Ring 3 进入 Ring 0 时的 `RSP0`。
- IST1/IST2/IST3 紧急栈。
- I/O bitmap offset，用于禁止普通用户端口访问。

调度到不同进程时，内核更新 TSS.RSP0，使下一次用户中断进入该进程自己的内核
栈。

## 8. 中断、异常和 IDT

### 8.1 三种事件

- 异常：当前指令执行产生，例如 #UD、#GP、#PF。
- 硬件中断：外设通过中断控制器异步请求，例如 PIT IRQ0、键盘 IRQ1。
- 软件中断：代码执行 `INT n`，本项目用 `INT 0x80` 进入系统调用。

### 8.2 IDT 门

IDT 有 256 个门描述符。门包含目标代码选择子、64 位入口地址、门类型、DPL、
Present 和 IST 号。

interrupt gate 进入时会清 IF，避免普通可屏蔽中断立即嵌套。门 DPL 限制软件
执行 `INT n`，但不阻止硬件投递相同向量。

### 8.3 CPU 自动压栈

同级异常通常压入：

```text
RIP, CS, RFLAGS
```

某些异常还压入硬件错误码。跨特权级进入 Ring 0 时还会压入旧 `RSP, SS`，
并使用 TSS.RSP0 或 IST 切换栈。

项目汇编桩主动补齐缺失的错误码和向量号，再保存 15 个通用寄存器，使 C++ 总能
看到统一结构。恢复时必须严格按相反顺序弹出，并用 `IRETQ` 恢复硬件现场。

### 8.4 页错误

#PF 的错误码描述 present、read/write、user/supervisor 等原因，故障线性地址在
`CR2`。这两项必须同时记录。Ring 0 #PF 通常代表内核错误；Ring 3 #PF 在当前
版本终止进程。

## 9. 四级分页

### 9.1 地址分解

当前项目使用典型 48 位 canonical 地址和 4 KiB 页：

```text
63                    48 47      39 38      30 29      21 20      12 11       0
+-----------------------+----------+----------+----------+----------+----------+
| 符号扩展              | PML4 idx | PDPT idx | PD idx   | PT idx   | 页内偏移 |
+-----------------------+----------+----------+----------+----------+----------+
```

每级索引 9 位，可选择 512 项；页内偏移 12 位。每个页表正好 512×8=4096
字节。

### 9.2 关键页表位

- P：映射存在。
- RW：允许写。
- US：允许 Ring 3。
- PWT/PCD：缓存策略，MMIO 常需特殊设置。
- PS：在 PD 等层级形成大页。
- NX：禁止执行，需要先开启 EFER.NXE。

上层条目权限和叶条目权限共同生效。用户叶设 US 而上层未设 US，用户仍然不能
访问。

### 9.3 CR0.WP

如果不开 CR0.WP，Ring 0 可能仍能写只读页，导致内核只读映射失去自我保护。
项目开启 WP，并通过故障注入证明只读保护真实生效。

### 9.4 TLB

CPU 会缓存虚拟到物理的翻译。修改当前活动页表后需要适当失效 TLB；切换 CR3
通常也承担地址空间切换和刷新作用。不能只修改内存中的 PTE 就假定处理器立刻
看到新权限。

## 10. PC 设备与端口

### 10.1 COM1 串口

COM1 基址为 `0x3F8`。常见偏移：

| 端口 | DLAB=0 | DLAB=1 |
| --- | --- | --- |
| `+0` | 数据/接收缓冲 | 除数低字节 |
| `+1` | 中断使能 | 除数高字节 |
| `+2` | 中断识别/FIFO 控制 | 同左 |
| `+3` | Line Control | 同左 |
| `+4` | Modem Control | 同左 |
| `+5` | Line Status | 同左 |

项目配置 115200、8N1。发送前轮询 Line Status 的 THRE 位，并设置有限预算，
避免硬件永不就绪时永久死循环。

### 10.2 8259A PIC

两片级联 PIC 接受传统 IRQ0–15：

- 主片 command/data：`0x20/0x21`。
- 从片 command/data：`0xA0/0xA1`。
- 从片连接主片 IRQ2。

复位默认向量与 CPU 异常冲突，内核把它们重映射到 `0x20–0x2F`。mask 位为 1
表示屏蔽。处理真实 IRQ 后必须按来源发送 EOI；虚假 IRQ7/IRQ15 的 EOI 规则
不同。

### 10.3 Local APIC virtual-wire

现代 QEMU PC 的 CPU 侧通过 Local APIC 接收中断。项目映射
`0xFEE00000` MMIO，启用软件使能位，把 LINT0 配成 ExtINT，使传统 PIC 的
输出通过 LAPIC 到达 CPU：

```text
设备 → 8259A PIC → LAPIC LINT0 ExtINT → CPU IDT
```

这是单核兼容路径，不是 IOAPIC 路由和 SMP 方案。

### 10.4 PIT

PIT 基准频率约 1,193,182 Hz：

- channel 0 数据端口 `0x40`。
- mode/command 端口 `0x43`。

项目用 mode 2 周期地产生 IRQ0。实际周期由整数除数决定，所以时间换算使用真实
除数，而不是假定恰好 1 ms。

### 10.5 PS/2 i8042

- 数据端口 `0x60`。
- 状态/命令端口 `0x64`。

初始化过程必须检查输入缓冲是否可写、输出缓冲是否有数据，处理控制器配置、端口
启用、设备命令和 `0xFA` ACK。键盘 make/break 扫描码再由软件状态机转换为
字符。

### 10.6 ATA PIO

主 IDE 通道常用端口：

- `0x1F0`：16 位数据。
- `0x1F1`：错误/特性。
- `0x1F2`：扇区数。
- `0x1F3–0x1F5`：LBA 低、中、高字节。
- `0x1F6`：驱动器选择与 LBA 高 4 位。
- `0x1F7`：状态/命令。
- `0x3F6`：备用状态/设备控制。

关键状态位：

- BSY：设备忙，不能开始传输。
- DRQ：设备准备好交换数据。
- ERR：命令错误。
- DF：设备故障。

单扇区读取命令为 `0x20`，写入为 `0x30`，缓存刷新为 `0xE7`。每扇区交换
256 个 16 位 word。所有轮询都必须有超时预算。

### 10.7 QEMU fw_cfg

项目不用 BIOS 获取内存图，而是由 Stage 1 直接访问 QEMU 公开的硬件配置接口：

- selector 端口 `0x510`。
- data 端口 `0x511`。

目录和数据流有规定字节序。Stage 1 验证 `QEMU` 签名、查找 `etc/e820`，
把 QEMU 20 字节条目转换为项目 24 字节条目。

fw_cfg 是当前选定平台的硬件接口，不应误称为宿主文件 API。

## 11. 磁盘、内存和文件系统是不同层

一个用户文件字节最终经历：

```text
用户虚拟地址
  → 用户页表翻译到物理页
  → 系统调用复制到内核缓冲
  → 文件偏移映射到 inode 直接块
  → 文件系统相对块映射到磁盘 LBA
  → 块缓存决定命中、写回或驱逐
  → ATA PIO 向端口传输 512 字节
  → QEMU raw 磁盘镜像
```

这里的“页”和“块”当前都可能是 4096/512 等不同单位；不能因为都保存字节就
混用其编号、所有权和失败语义。

## 12. ELF、链接与装载

### 12.1 编译、汇编和链接

- C++ 编译器把翻译单元生成目标文件。
- NASM 把汇编源生成目标文件或平坦二进制。
- LLD 根据链接脚本合并 section、分配虚拟地址并生成 ELF segment。
- `objcopy` 可从 ELF 抽取 ROM 平坦字节。

section 服务于链接组织，segment 服务于运行时装载。Kernel loader 读取
program header 中的 `PT_LOAD`，不按 section 名称复制。

### 12.2 ELF 中的三个大小

一个可装载段至少涉及：

- 文件偏移 `p_offset`。
- 文件大小 `p_filesz`。
- 内存大小 `p_memsz`。

必须有 `p_filesz <= p_memsz`。装载器复制文件部分，再把
`p_memsz - p_filesz` 清零，这就是 BSS 的来源之一。

### 12.3 W^X

W^X 表示一个页面或段不同时可写和可执行。项目的 Kernel ELF、用户 ELF 和
最终页表都维持这一约束，防止数据页直接成为代码页。

## 13. freestanding C++ 与普通 C++ 的区别

普通 C++ 程序默认拥有宿主操作系统、启动代码、标准库、异常运行时、TLS 和系统
调用。内核启动时这些都不存在。

项目目标编译明确使用：

- `--target=x86_64-unknown-none-elf`
- `-ffreestanding`
- `-fno-exceptions`
- `-fno-rtti`
- `-fno-stack-protector`
- `-fno-threadsafe-statics`
- `-fno-use-cxa-atexit`
- `-mno-red-zone`
- `-mno-sse -mno-sse2`
- `-nostdinc++`

因此代码不能随意使用 STL、iostream、全局动态初始化、异常、宿主头或会偷偷
生成运行时调用的语言特性。`memcpy/memset` 等基础符号也由项目自行实现。

另一方面，能证明不会引入隐藏运行时的 C++20 类型、`constexpr`、枚举、
concept、RAII 和原子操作仍然有价值。freestanding 不等于退回无类型的 C。

## 14. NASM Intel 语法最低知识

项目使用：

```asm
mov destination, source
```

常见概念：

- `bits 16/32/64` 控制汇编器的默认编码模式。
- `section` 组织 ELF section；`org` 为平坦二进制指定地址假设。
- `db/dw/dd/dq` 放置 1/2/4/8 字节数据。
- `equ` 定义汇编期常量。
- `global/extern` 建立跨目标文件符号。
- `in/out` 访问端口。
- `lgdt/lidt/ltr` 加载架构表。
- `cli/sti/hlt` 控制中断与等待。
- `iretq` 从 64 位中断/特权转换现场返回。

汇编中的内存操作数宽度可能需要 `byte/word/dword/qword` 明确指定。16 位代码
放进 ELF32 只是构建容器选择，不代表 CPU 在执行 32 位指令。

## 15. QEMU 与 GDB 的观察边界

QEMU 串口日志适合证明阶段里程碑和失败码；GDB 适合观察寄存器、反汇编、内存和
控制流；构建产物审计适合证明布局和符号约束。这三种证据不能互相完全替代。

典型排查顺序：

1. 产物是否存在、尺寸和 ELF 布局是否正确？
2. 最后一个可靠串口标记是什么？
3. CPU 当前模式、`RIP/CS/CR0/CR3/CR4/EFER` 是什么？
4. 当前栈和描述符表是否仍在有效映射中？
5. 设备状态位是忙、未请求数据、错误还是超时？

不要依赖高频热路径日志验证调度和中断；日志自身会改变时序。项目使用计数器和
最终摘要证明这类行为。
