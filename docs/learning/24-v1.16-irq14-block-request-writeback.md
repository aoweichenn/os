# v1.16：IRQ14 块请求与共享文件页写回

## 本章解决什么问题

到 v1.15，文件系统已经能持久化，文件映射也能按需装入，但两条路径仍有明显
缺口：

- 运行期 ATA 操作由 CPU 轮询，设备等待期间不能把 CPU 交给其他 Thread；
- 文件页缓存只有 clean 页，可写 `MAP_SHARED` 无法表达“内存已经修改但尚未
  写回文件”。

v1.16 把两条控制流连接起来：

```text
用户写 shared 映射
  → x86 #PF 捕获第一次写
  → FilePageCache Clean→Dirty
  → PTE 开放 writable
  → sync 重新写保护
  → VFS WriteAt
  → rootfs BlockCache
  → BlockRequest(Flush)
  → ATA command
  → IRQ14
  → Completed + 定向唤醒
```

这里最重要的不是“用了中断”，而是每一刻都能回答：设备、请求、缓冲区、物理
页和落盘责任分别由谁拥有，失败后状态停在哪里。

整体关系见 [IRQ14 与写回结构图](assets/irq14_writeback.svg)。

代码走读入口：

```text

source/kernel/src/device/block_request.cpp
source/kernel/include/os/kernel/device/ata_pio.hpp

source/kernel/src/fs/vfs.cpp
source/kernel/src/fs/root_file_system.cpp
```

## 历史背景：轮询为什么先出现，中断为什么后来才安全

复位后的 ROM 没有进程、调度器、WaitQueue 或可靠 IDT。它想从磁盘加载下一
阶段，只能反复读取状态寄存器，并在预算耗尽后失败。Stage 1 同样处于启动
依赖链中：若它等待一个只有 Kernel 才能处理的 IRQ，Kernel 永远不会被加载。

因此 polling 不是“落后写法”，而是 early boot 的正确依赖边界：

```text
ROM / Stage 1
  CPU 是唯一执行者
  → 有界 polling

Kernel runtime
  IDT + PIC + PIT + scheduler + WaitQueue 已就绪
  → IRQ completion + Thread blocking
```

危险来自在第二种环境仍无限轮询，或者在第一种环境过早依赖中断。项目保留
同一 ATA 设备的两种适配方式，但规定它们不能同时拥有设备：early/synchronous
适配器临时设置 nIEN，运行期请求队列才开放 IRQ14。

传统 IDE primary channel 没有现代 NVMe 那样的 command identifier。设备发来
IRQ14 时，软件只能根据“当前命令”解释它。因此 v1.16 采用单飞队列：软件可以
排多个 Queued 请求，但硬件中同时只有一个 Issued 请求。

## 芯片与线路：IRQ14 怎样到达 CPU

QEMU `pc` 模型中的路径是：

```text
ATA primary controller
  └─ asserts IRQ14
      → 8259A slave IR6
      → slave INT 接到 master IR2
      → master INT
      → Local APIC LINT0 ExtINT
      → CPU vector 0x2E
      → IDT entry
      → NASM IRQ stub
      → InterruptRuntime
```

IRQ14 是 slave PIC 的第 6 条输入，所以同时解除两位屏蔽：

- master data port `0x21` 的 bit 2：允许 slave 级联；
- slave data port `0xA1` 的 bit 6：允许 IRQ14。

v1.16 当时还开放 IRQ0 与 IRQ1，mask 为 `0xBFF8`；当前 V2.10.3a 为 secondary ATA
BlockIo probe 继续开放 IRQ15，mask 已变为 `0x3FF8`：

```text
master 0xF8 = 1111 1000b  → IRQ0、IRQ1、IRQ2 开放
slave  0xBF = 1011 1111b  → slave IRQ6，即系统 IRQ14 开放
```

中断结束必须先向 slave command port `0xA0` 发送 EOI，再向 master command
port `0x20` 发送 EOI。顺序错误可能让级联线保持 in-service，后续磁盘中断
看似“偶发消失”。

## ATA primary channel 寄存器和标志位

| 端口 | 读语义 | 写语义 | 宽度 |
| --- | --- | --- | ---: |
| `0x1F0` | Data | Data | 16 bit |
| `0x1F1` | Error | Features | 8 bit |
| `0x1F2` | Sector Count | Sector Count | 8 bit |
| `0x1F3` | LBA 0..7 | LBA 0..7 | 8 bit |
| `0x1F4` | LBA 8..15 | LBA 8..15 | 8 bit |
| `0x1F5` | LBA 16..23 | LBA 16..23 | 8 bit |
| `0x1F6` | Device/Head | Device/Head | 8 bit |
| `0x1F7` | Status | Command | 8 bit |
| `0x3F6` | Alternate Status | Device Control | 8 bit |

Status 的关键位：

| 位 | 名称 | 含义 | 软件动作 |
| ---: | --- | --- | --- |
| 7 | BSY | 控制器忙 | 不能搬数据或发下一命令 |
| 6 | DRDY | 设备就绪 | 辅助诊断，不单独代表传输完成 |
| 5 | DF | device fault | 当前请求以 DeviceError 完成 |
| 3 | DRQ | 请求 CPU 传输数据 | 以 256 次 16-bit PIO 搬一个扇区 |
| 0 | ERR | 命令错误 | 读取 Error 并以 DeviceError 完成 |

Device Control 的关键位：

| 位 | 名称 | 含义 |
| ---: | --- | --- |
| 2 | SRST | software reset；置位后再清零以重置通道 |
| 1 | nIEN | 置一禁止设备中断，置零允许 IRQ14 |

读取 `0x1F7` status 可能确认设备中断；读取 `0x3F6` alternate status 不做
这件事，所以轮询等待和 IRQ handler 的读取意图不同。数据端口必须使用
16-bit `IN/OUT`，一个 512 字节扇区恰好是 256 个 word。

v1.16 使用 READ SECTORS、WRITE SECTORS 和 FLUSH CACHE。Read IRQ 到达且
DRQ 置位后读数据；Write 的第一个 DRQ IRQ 表示设备可接收扇区，写完后仍需
等待完成 IRQ；Flush 没有数据阶段，只等待完成或错误。

## CPU 标志与异常错误码

`RFLAGS.IF` 控制可屏蔽外部中断。初始化期间保持 IF=0；IDT、PIC、设备状态和
请求队列全部就绪后才执行 STI。IRQ 公共入口由硬件保存旧 RFLAGS，并在
IRETQ 时恢复，C++ handler 不应随意 STI 形成嵌套设备中断。

writable shared 的第一次写由 page fault error code 分类：

| 位 | 名称 | v1.16 写通知所需值 |
| ---: | --- | --- |
| 0 | P | 1：页存在，是权限 fault |
| 1 | W/R | 1：访问是写 |
| 2 | U/S | 1：来自用户态 |
| 3 | RSVD | 0：不是保留位损坏 |
| 4 | I/D | 0：不是取指 fault |

只有 present+write+user 且 VMA 是 writable FileShared 时，才可能进入
MarkDirty。not-present fault 仍负责首次装页；真正只读映射仍应失败；private
映射写 fault 进入 COW，三者不能混为一条“把 PTE 改成可写”的捷径。

## BlockRequest 为什么需要独立状态机

请求状态如下：

```text
              ┌──────── Cancelled ────────┐
Unused → Queued → Issued → Succeeded      │
                         → DeviceError     ├→ Reap → Unused
                         → TimedOut        │
              └───────────────────────────┘
```

Queued 表示队列拥有请求，但硬件尚未拥有命令；Issued 表示请求、buffer 和 ATA
通道绑定；Completed 表示最终结果已经冻结；通用消费方 Reap 后槽位才恢复
Unused。生产 ATA 适配器在 IRQ/超时路径复制完成记录后立即 Reap，再把复制出的
owner、identifier 与 result 交给调度器，因此等待 Thread 不依赖队列槽继续
存活。

如果完成后立即清槽，等待 Thread 醒来时可能读到后续请求。若只用数组下标作为
身份，槽位复用又会产生 ABA：旧等待者把新请求误认成旧请求。因此 identifier
使用 64 位单调数，与槽位下标分离。

队列不动态分配。64 槽存储由 InterruptRuntime 长期拥有，IRQ handler 不会因
堆锁或内存不足进入不可预测路径。容量满时 Submit 返回 CapacityExhausted，
调用者决定回压或失败，不能覆盖最旧请求。

## IRQ、超时和取消如何只让一个结果获胜

假设请求 deadline 到达的同一时刻，设备也拉高 IRQ14：

1. 若 IRQ14 先进入，Complete 把 Issued 改为 Completed；随后 PIT 看见请求
   已非 Issued，不再写 TimedOut。
2. 若 PIT 先进入，ResolveTimeout 完成 TimedOut 并 software reset；迟到
   IRQ 找不到仍在 Issued 的同一请求，不能覆盖结果。

唯一提交点不是靠“通常不会同时发生”，而是状态转移本身拒绝重复解析。统计中
保留 duplicate resolution，便于发现异常设备或路由行为。

取消只接受 Queued。Issued 命令已经进入设备，不能仅从软件链表删除；否则
下一请求可能把前一命令的 IRQ 当成自己的完成。

## 为什么超时后必须 reset 设备

只把 Thread 唤醒并返回 timeout 不够。ATA 可能仍处于 BSY、等待 data word
或将在稍后产生 IRQ。若马上发下一命令，两个协议阶段会交叉。

software reset 的边界是：

```text
请求解析 TimedOut
  → SRST=1
  → 设备规定的延时读取
  → SRST=0
  → 等待 BSY 清除（仍有界）
  → 才允许 IssueNext
```

reset 本身失败必须记录为设备不可继续使用，不能以“超时已经返回”为理由继续
污染队列。实现会冻结 controller available 状态，把已排队请求逐个以
DeviceError 完成，并拒绝后续提交；这样所有等待者都能有界退出，又不会再
接触状态未知的通道。

## Thread 阻塞和其他工作前进

`sync` 完成内存页与 VFS 写回后提交异步 Flush。当前 Thread 保存请求身份并
进入 `WaitCondition::BlockIo`：

```text
Thread A: Submit Flush → Blocked(BlockIo)
Scheduler: 选择 Thread B
Thread B: 继续用户或内核工作
IRQ14: Complete → copy result → Reap → Match(owner, identifier) → Ready(A)
Scheduler: 稍后恢复 A → 从保存现场取得系统调用结果
```

IRQ handler 只把 A 从 Blocked 变为 Ready，不直接在任意内核栈上切换到 A。
owner Thread 槽与 64 位 identifier 必须同时匹配；若 A 已退出或槽已复用，
迟到完成只增加 abandoned 诊断，不会唤醒无关 Thread。
QEMU marker `OTHER_THREAD_PROGRESS=1` 证明 A 等 I/O 期间至少有另一 Ready
Thread 前进。这比只证明“最终 sync 返回”多验证了调度语义。

当前 rootfs 普通扇区 Read/Write 仍通过有界同步 PIO 适配器执行；v1.16
接入 BlockIo 的真实生产消费者是显式 sync 最后的 ATA FLUSH。异步
Read/Write 状态机已经实现，为后续迁移 journal 和块消费者提供边界，但本章
不把“API 已存在”写成“全部文件 I/O 已异步化”。

## 页缓存为何需要五种状态

| 状态 | 页中数据 | 落盘责任 | 可否 clean LRU 淘汰 |
| --- | --- | --- | --- |
| Empty | 无 | 无 | 不适用 |
| Clean | 与文件一致 | 无 | 零引用时可以 |
| Dirty | 比文件新 | 有 | 不可以 |
| Writeback | 正在提交快照 | 有 | 不可以 |
| Error | 上次提交失败 | 仍有 | 不可以 |

只用 dirty 布尔值无法表达 Error。若失败时清 dirty，会把未落盘数据伪装为
安全；若保持 dirty，又无法区分是否已有写回者。显式 Error 允许下一次 sync
从同一页重试。

dirty page limit 是正确性边界。MarkDirty 先检查上限，再改变状态；达到上限
时写 fault 失败，PTE 仍只读。这样不会出现用户已经继续写，但 cache 无法为
这次修改记账的窗口。

## writable MAP_SHARED 如何捕获写入

x86 页表没有“每次写都通知软件”的模式。Kernel 使用 write-protect trap：

1. FileShared 页按需装入，多个 alias 指向同一 cache frame，PTE 初始只读；
2. 第一次写触发 protection fault；
3. Kernel 验证 VMA、页对齐、文件范围和 writable open 权限；
4. cache `Clean→Dirty` 成功；
5. 仅将对应共享 PTE 改为 writable，并执行 `INVLPG`；
6. CPU 重试原写指令，这次成功。

同一页的另一个只读 alias 立刻看到共享 frame 的新字节，但仍不能自行写。
fork 继承 FileShared PTE 时不设置 COW；父子写的仍是同一文件页。

`sync` 前先把所有 writable FileShared PTE 重新改为只读。否则写回进行时，
用户可在 Kernel 已复制该页之后再次写，而 PTE 不再 fault，缓存会错误保持
Clean。重新写保护把“写回快照之后的新写”变成下一轮 Dirty。

## 从 cache page 到稳定介质

本阶段的同步次序是：

```text
ProtectUserSharedFileMappings
  → FilePageCache Writeback(Dirty/Error)
      → UserFileBackingManager::WritePage
      → Vfs::WriteAt
      → RootFileSystem block transaction
  → Vfs::Sync
      → rootfs block cache write
  → ATA FLUSH request
  → IRQ14 completion
```

`WriteAt` 不使用共享 OpenFile offset；页缓存按 file offset 回写，不能推进某个
用户 fd 的当前位置。文件 identity 也不能使用 fd，因为 fd 可以关闭和复用，
映射却仍有效。

rootfs 事务 generation 描述盘面提交次数，VFS superblock generation 描述
一次 mount 的对象身份。若每次写事务都修改后者，同一 inode 会在写前后得到
两个 cache key，shared alias 就会失去共享。v1.16 的集成测试专门冻结 mount
generation 稳定而 transaction generation 增长。

## 日志怎样丰富但不冲屏

不能在每次 status poll、每个 PIO word 或每次 cache lookup 中打印。这些路径
频率高，串口本身又会显著改变时序。v1.16 只记录低频语义边界：

```text
ATA_IRQ14_READY
ATA_REQUEST_CAPACITY
FLUSH_SUBMIT_REQUEST
FLUSH_SUBMIT_TIME_NS
COMPLETION_RESULT
COMPLETION_TIME_NS
OTHER_THREAD_PROGRESS
FILE_SHARED_WRITEBACK_VERIFIED
```

QEMU runner 另为每条串口行添加宿主单调到达时间 `[QEMU][T+...ms]`；来宾
请求时间使用 PIT 单调纳秒。前者用于测试定位，后者用于 Kernel deadline，
两种时间不能混用。

## 测试分层

| 层 | 证明内容 |
| --- | --- |
| 单元 | 请求参数、FIFO、单飞、完成/超时/取消/Reap、dirty limit、Error 重试 |
| 集成 | IRQ/timeout 完成后下一请求推进、rootfs identity 稳定、PIC 级联 mask |
| 随机 | 100000 步请求参考模型与 100000 步页状态参考模型 |
| 产物 | IRQ14 桩、C++ dispatcher、目标源码和 ELF 边界 |
| QEMU | 真实 ATA IRQ、三档 RAM、shared alias/写回/private 隔离、Thread 前进 |
| 故障 | ATA busy/error/timeout、迟到完成、写回 writer 失败 |

并发跑多个 64 GiB TCG QEMU 可能让逐键 Shell 协议超过进度门限。因此完整
回归可以并行跑宿主测试，但交互式/容量 QEMU 应串行复验；不能简单扩大到无限
超时，否则真实死锁会重新变成永久卡住。

本阶段的串行复验还抓到一个与存储无关、但必须修复的历史竞态：父 Shell 已把
新 PGID 设为前台，child 却可能尚未运行到恢复默认信号处置；此时 Ctrl-Z 会
调用从 Shell 继承的 handler。修复不是延迟按键，而是 fork 前屏蔽 Ctrl-C/Z，
让 child 先恢复默认 action、加入 PGID，再恢复旧 mask。窗口内到达的普通
信号保持 pending，解除 mask 时才按 child action 交付。它说明完整回归还承担
发现跨阶段竞态的职责。

## 当前边界和下一步

- ATA 仍是 primary master、LBA28、PIO、单飞，没有 DMA/AHCI/NVMe；
- ROM 和 Stage 1 仍使用有界轮询；
- shared writable 暂只支持完整页；
- 只有显式全局 `sync`，没有 `msync` 和后台 flusher；
- Error 页会产生明确回压，不会静默丢弃；
- v1.17 将在同一请求与 FLUSH 边界上加入 ordered metadata journal、credits、
  commit/checkpoint 和断电重放。

这些限制让 v1.16 保持可解释：先证明异步完成与数据写回责任，再在下一阶段
讨论多个元数据块怎样作为一个事务原子恢复。
