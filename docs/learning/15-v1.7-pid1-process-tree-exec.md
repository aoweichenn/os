# v1.7：从 PID1 到进程树、磁盘 ELF 与原子 exec

## 1. 为什么“能进入 Ring 3”还不等于有用户空间

早期系统把几个用户 ELF 作为只读字节数组链接进 Kernel。这条路径能回答：

- x86-64 特权级是否切换正确；
- 用户页、用户栈和 CR3 是否可用；
- PIT 是否能抢占；
- `SYSCALL/SYSRET` 与 `INT 0x80` 是否等价；
- 用户异常是否只终止故障进程。

但它没有回答“程序是什么”。如果程序只能在编译 Kernel 时决定，它更像
Kernel 自测载荷，而不是文件系统中的用户程序。真正的程序链必须跨越：

```text
path name
  -> VFS lookup
  -> rootfs inode and block tree
  -> ATA sectors
  -> ELF metadata
  -> page table mappings
  -> initial user stack
  -> scheduled Process/Thread
```

v1.7 的目标是把已有的文件、内存、调度和系统调用机制接成这条链，并让用户
空间自己决定下一步启动谁。

## 2. PID1 的历史职责

早期 Unix 内核在完成初始化后创建第一个用户进程。它后来通常执行名为
`init` 的程序，并获得 PID 1。不同 Unix 和 Linux 系统中的 init 实现差异
很大，但两个职责长期稳定：

1. 启动系统所需的用户服务；
2. 回收失去原父进程的孤儿进程。

父进程先于子进程退出时，子进程不能保留一个已经无效的父指针。传统模型把
它重新托管给 PID1；子进程最终退出后，PID1 调用 wait 取得状态并释放最后
的进程记录。

本项目不复制 systemd、SysV 脚本或服务管理器。`/sbin/init` 是一个小型
freestanding C++20 验收程序，但它承担真实 PID1 语义：创建进程树、等待
直接子进程、收养孤儿、检查退出结果，并在没有 Zombie 后退出。

## 3. Process、Thread、PID 和槽位是四个概念

### 3.1 Process 是资源容器

当前 Process 拥有：

- 用户地址空间根 CR3；
- FileTable；
- FsContext；
- 进程身份和父子关系；
- 退出结果。

### 3.2 Thread 是调度实体

Thread 拥有：

- 通用寄存器现场；
- Ring 0 KernelStack；
- 用户 RSP；
- x87/SSE2 扩展现场；
- run queue 或 WaitQueue 关系；
- TLS base 和 signal mask 的预留位置。

v1.7 每个正常 Process 仍只有一个 Thread，但数据模型不再把两者混为一体。
后续用户线程会扩大 Thread 数，而 fork、exec、wait 继续围绕 Process 定义。

### 3.3 PID 不是数组下标

调度器为了有界存储使用 `process_index`。槽位 3 被回收后可以再次使用槽位
3；若用户也把 3 当 PID，旧父进程保存的 PID 就可能误命中新进程。

因此 PID 是独立单调 64 位身份：

```text
slot 3: PID 7  -> reaped
slot 3: PID 12 -> new process
```

用户 ABI、进程树日志和 wait 都使用 PID；只有 Kernel 内部在验证范围后使用
槽位。

## 4. 为什么退出后还要有 Zombie

考虑父进程 `P` 与子进程 `C`：

```text
C exits with code 42
P has not called wait yet
```

若 Kernel 立即删除 C 的全部记录，P 就无法知道：

- C 是否存在过；
- C 是正常退出还是异常；
- 退出码是什么；
- wait 的 PID 是否写错。

若 Kernel 保留 C 的全部页表、栈和 fd，又会让一个没有执行能力的进程长期
占用大量资源。

Zombie 是两者之间的最小状态：

```text
execution resources released
identity + parent + exit status retained
```

wait 取得状态后才回收最后的 Process 槽位。Zombie 不是“坏进程”；不可达或
永久不被 wait 的 Zombie 才是生命周期缺陷。

## 5. 进程树状态机

`ProcessTree` 使用三个状态：

```text
Unused --Register--> Alive --MarkExited--> Zombie --Collect--> Unused
```

每个条目保存：

```cpp
struct ProcessTreeEntry final {
    uint64_t process_id;
    uint64_t parent_process_index;
    ProcessTreeState state;
    ProcessTreeExitStatus exit_status;
};
```

父关系保存槽位而不是 PID，是因为 Kernel 访问条目时需要有界索引；对外结果
再取父条目的当前 PID。所有操作都检查：

- 存储是否初始化；
- 索引是否落在当前配置容量内；
- PID 是否非零、非 `WAIT_ANY` 且不重复；
- 父进程是否存在且 Alive；
- 状态迁移是否合法。

`Validate` 不只检查每个条目，还重算 active/alive/zombie 并与累计统计比较。
这类“从事实重建计数”的验证能发现某条失败路径忘记加一或减一。

## 6. reparent 的顺序为何重要

父进程退出时：

1. 把父条目改成 Zombie；
2. 扫描全部活动项；
3. 找到 `parent_process_index` 指向该父的子项；
4. 把它们改指 PID1 槽位；
5. 记录 reparent 数；
6. 唤醒 child-exit wait queue。

Alive 子进程必须改父；已经 Zombie 但尚未 wait 的子进程也必须改父。只处理
Alive 会留下不可回收 Zombie。

PID1 退出是特殊边界：如果它仍有任何子项，`MarkExited` 返回
`ProcessHasChildren`。这比“PID1 退出后由 Kernel 随便扫尾”更能暴露用户空间
回收缺陷。

## 7. wait、waitpid 与阻塞

公开接口用一个值表达两种请求：

```text
requested_pid == UINT64_MAX -> wait any child
otherwise                   -> wait that child
```

零不是合法 PID，也不表示 any。`TryWait` 有三类正常结果：

- 匹配 Zombie：立即收集；
- 匹配 Alive：`ChildStillRunning`；
- 没有匹配子进程：`NoMatchingChild`。

第二种结果不能让用户态忙循环。系统调用把当前 Thread 放入
`WaitCondition::ChildProcess`，调度器运行其他 Thread；子进程退出后唤醒
等待者。用户包装器被恢复时再次发起 wait，因为“被唤醒”只表示条件可能改变，
不等于这个 Thread 已经独占某个退出结果。

结果用户页必须在收集前验证可写。否则可能发生：

```text
remove zombie
  -> copy result to bad pointer fails
  -> parent can never observe child again
```

v1.7 先验证固定 40 字节结果范围，再改变进程树。

## 8. ELF 为什么适合两遍读取

ELF 把“文件中有哪些字节”和“进程地址空间要有什么映射”分开描述。`PT_LOAD`
给出：

- 文件 offset；
- 目标 virtual address；
- file size；
- memory size；
- R/W/X flags；
- alignment。

`memory_size > file_size` 的尾部是 BSS，必须清零，不从磁盘读取。

若一边读程序头一边立刻分配并映射，后面的程序头可能暴露：

- 两段重叠；
- W+X；
- 文件范围越界；
- 入口不在可执行段；
- 总映射页数超限。

此时前面的页已经产生，需要复杂回滚。v1.7 先读取并验证全部元数据，形成
`UserElfLayout`；只有布局完整通过才开始分配。即使第二遍仍可能遇到 I/O 或
内存失败，回滚对象已经是一个封闭候选地址空间。

## 9. `UserElfReader` 如何隔离来源

接口只有：

```cpp
using UserElfReadOperation = bool (*)(
    void *context,
    uint64_t offset_bytes,
    uint8_t *destination,
    uint64_t length_bytes) noexcept;
```

加上稳定的 `image_size_bytes`。内存 reader 从字节数组复制；VFS reader
设置 `OpenFile.offset_bytes` 后循环 read，直到精确长度完成。

调用者不需要知道文件位于：

- Kernel 内嵌故障夹具；
- rootfs direct block；
- single/double/triple indirect block；
- 未来的 page cache。

reader 不是流式“下一块”接口，因为 ELF 程序头和加载段要求随机 offset
读取。它也不返回裸 VFS 状态，避免 ELF 校验层依赖某个后端；来源层负责把
失败映射成可执行文件读取错误。

## 10. 从 inode 到一个用户页

假设加载段的某页对应文件 offset `F`：

```text
LoadUserAddressSpace
  -> reader.Read(F, physical_page, bytes)
  -> Vfs::Read(OpenFile)
  -> RootFileSystem::Read
  -> inode logical block lookup
  -> direct/indirect pointer traversal
  -> BlockCache
  -> AtaPioDevice::ReadSectors
  -> INSW from IDE data port
  -> high-half direct map physical page
```

QEMU 在这条链中只模拟 IDE 寄存器和扇区。它不理解 ELF、inode 或页表。

物理页先完整清零，再覆盖 `file_size` 范围，因此：

- BSS 为零；
- 文件最后一页未覆盖尾部为零；
- 不会暴露刚分配 frame 的旧内容。

PTE 权限来自已验证段 flags：用户可访问，W/X 严格互斥。用户栈是 RW/NX。

## 11. 初始用户栈从哪里来

历史 Unix 进程入口通常从栈取得参数；System V ABI 还对调用边界对齐有规定。
本项目同时把三个值放入寄存器，便于 freestanding 入口直接声明：

```cpp
void OsUserEntry(
    uint64_t argument_count,
    const char *const *arguments,
    const char *const *environment) noexcept;
```

对应：

```text
RDI = argc
RSI = argv
RDX = envp
```

栈中仍保存规范化的 argc/argv/envp，未来建立更完整 crt0 时无需改变 Kernel
布局。

### 11.1 为什么字符串从高地址向下放

固定栈顶不变时，先计算所有字符串总量，便可得到字符串区起点：

```text
string_begin = stack_top - total_string_bytes
```

再计算指针元数据大小并向下对齐：

```text
metadata_pointer_count = argc + envc + 3
raw_rsp = string_begin - metadata_pointer_count * 8
rsp = align_down(raw_rsp, 16)
```

三个固定指针槽对应 argc 值、argv 终止 null 和 envp 终止 null。

### 11.2 为什么 128 KiB 还需要 256 KiB 栈

128 KiB 是字符串及其 NUL 的合计，不包含：

- 最多 512 个字符串指针；
- argc；
- 两个 null；
- 对齐；
- 程序开始运行后的调用栈。

256 KiB 给元数据与最初执行留下余量。它仍有明确 guard：栈底下方页不映射。
动态增长属于 v1.8 VMA 阶段。

## 12. 大参数为什么不能进内核栈

Ring 0 栈为四个数据页，即 16 KiB，并在上下保留 guard。若写：

```text
uint8_t arguments[128 KiB]
```

函数一进入就跨过 guard，产生 Ring 0 page fault 和 panic。把内核栈扩大到
128 KiB 以上也不是好答案：每个 Thread 都会永久支付最坏参数成本。

v1.7 使用 256 字节搬运缓冲：

```text
validate one ProcessString
  -> copy at most 256 bytes from old user mapping
  -> locate candidate physical page
  -> copy chunk
  -> repeat
```

总工作量与输入长度线性，瞬时内核栈占用为常量。

## 13. exec 的本质是替换，不是创建

spawn 创建新 Process，因此得到新 PID。exec 替换当前 Process 的程序映像，
因此必须保留：

- PID；
- 父子关系；
- cwd/root；
- 非 CLOEXEC fd；
- 已积累的 Process 身份。

成功 exec 后，父进程仍等待同一个 PID。若 exec 创建新 PID，父子关系和
wait 目标都会断裂。

## 14. 为什么 exec 必须先建立候选映像

失败可能发生在很多位置：

```text
path copy
VFS lookup/open/stat
ELF header read
program header validation
physical frame allocation
page table allocation
segment data read
argument copy
stack metadata write
CR3 activation
```

如果先销毁旧映像，任何失败都无法把错误码返回给调用者。正确顺序是：

```text
old image is authoritative
  |
  +-- build candidate
  +-- validate candidate
  +-- hardware activation probe
  |
commit point
  |
  +-- scheduler CR3/RSP
  +-- runtime ownership
  +-- CLOEXEC
  +-- destroy old image
  +-- new UserContext
```

提交点之前只有候选资源发生变化；提交点之后只有新映像是权威状态。

## 15. CR3 激活探针在证明什么

页表结构在软件验证中可能看似正确，但真正写 CR3 时还受处理器物理地址宽度、
对齐和保留位约束。v1.7 在提交前：

1. 切到永久 Kernel 页表；
2. 尝试加载候选 CR3；
3. 成功后切回旧用户 CR3；
4. 再回永久 Kernel 页表完成所有权提交。

这不是执行候选用户代码，只证明处理器接受页表根。由于候选页表共享 Kernel
高半映射，探针期间 Kernel 指令和栈仍可访问。

## 16. UserContext 如何被重建

成功提交后不能保留旧寄存器，因为旧程序可能把任意值留在通用寄存器、RFLAGS
或返回现场中。实现把 176 字节 `UserContext` 清零后只写入：

- RDI/RSI/RDX 参数；
- 新 RIP；
- 用户代码/数据段选择子；
- 允许的初始 RFLAGS；
- 新 RSP。

扩展状态的策略当前是沿用该 Thread 已有 FXSAVE 区；程序不应依赖 exec 前
浮点/SSE 值。未来若把 POSIX exec 语义进一步冻结，可在提交时显式恢复默认
浮点环境，并增加对应 ABI 测试。

## 17. close-on-exec 为什么属于 fd 而不是打开文件

两个 fd 可以 duplicate 到同一个 FileDescription，共享文件偏移，但各自拥有
独立 CLOEXEC flag。exec 关闭的是带 flag 的 fd 表项，而不是“某个打开文件
对象的所有引用”。

v1.4 已经把：

```text
fd entry -> KernelObject handle -> FileDescription
```

分层。本阶段成功 exec 调用 `FileTable::CloseOnExec`，最后引用才触发
FileDescription finalizer。失败 exec 完全不调用 close-on-exec。

## 18. rootfs 如何在启动前获得用户程序

Kernel 不应在挂载时自动把内嵌程序写入磁盘，否则：

- 程序来源仍是 Kernel；
- 每次启动会修改生产 rootfs；
- 丢失“严格挂载、不自动格式化”的 v1.6 边界；
- 构建镜像不可静态审计。

构建工具在宿主执行：

```text
format empty rootfs
  -> validate install paths
  -> create /sbin and /bin
  -> assign inode numbers/generations deterministically
  -> allocate file and directory blocks
  -> build indirect pointer trees
  -> write inode/data bitmaps
  -> write Clean superblock
  -> independently inspect full filesystem
```

安装器只操作构建产物，不参与运行时。QEMU 启动后所有修改仍走用户系统调用、
VFS、RootFileSystem 和 ATA。

## 19. 代码走读：正常启动

从 `RunKernel` 开始：

1. `PrepareRequiredProcesses` 初始化 ProcessRuntime，但 normal 模式不创建
   内嵌普通程序；
2. 初始化 PIC/PIT/PS2/ATA；
3. 严格挂载 rootfs v2；
4. 建立 VFS 根和 `/tmp` memfs mount；
5. `AttachProcessVfs` 把 VFS 交给 ProcessRuntime；
6. `CreateInitialDiskProcess` 传入 `/sbin/init` 和初始参数；
7. `LoadExecutableFromPath` 用 VFS reader 建立地址空间；
8. `RegisterRuntimeProcess` 注册 PID1、Thread、KernelStack、FileTable 和
   ProcessTree；
9. `ExecuteProcesses` 激活用户 CR3 和 UserContext；
10. PID1 通过系统调用 36 创建子进程；
11. 子进程通过系统调用 37 替换映像；
12. PID1 通过系统调用 38 阻塞并回收；
13. PID1 退出后 Kernel 收集 init；
14. 聚合验证全部资源与统计；
15. 同步文件系统并进入事件循环。

## 20. 代码走读：一次 spawn

`DispatchSpawnProcess`：

1. 验证请求结构尺寸；
2. 从当前用户页复制 48 字节请求；
3. `SpawnCurrentProcess` 复制有界路径；
4. 规划 argv/envp；
5. 读取当前 Thread 和父 Process；
6. 使用父 FsContext 解析路径；
7. 建立候选页表和初始栈；
8. 调度器分配 Process 和 Thread；
9. KernelStackManager 建立双 guard 栈；
10. 初始化 FileTable、标准 fd 和 FsContext；
11. ProcessTree 注册父子关系；
12. 所有步骤成功后返回新 PID。

任一步失败都按所有权逆序回滚；只有完全注册后候选地址空间才清空本地所有权，
转交 RuntimeProcess。

## 21. 代码走读：一次 wait

`DispatchWaitProcess`：

1. 验证结果结构尺寸和用户可写范围；
2. `TryWaitCurrentProcess` 回收已退出 Thread；
3. ProcessTree 查找调用者的匹配子进程；
4. Alive 返回 WouldBlock，系统调用进入 child WaitQueue；
5. Zombie 取得退出结果；
6. Scheduler 回收 Process 槽位；
7. RuntimeProcess 标记 inactive；
8. 固定结果复制到用户页；
9. RAX 返回被回收 PID。

父进程退出时 `CompleteCurrentThread` 先关闭 fd/FsContext，再标记进程树
Zombie、执行 reparent、唤醒 waiters，然后终止调度器 Thread 并销毁用户
地址空间。

## 22. 测试分层为什么不能省

### 单元测试

ProcessTree 和 ProgramArgumentPlan 是纯逻辑模块，单元测试直接检查每个状态
和精确边界。reader ELF 测试可以故意在第二次读失败，并证明调用者输出布局
未被半覆盖。

### 集成与随机测试

4096 轮集成生命周期反复复用相同槽位，能发现累计计数、父指针和清理顺序
错误。固定种子随机测试改变 PID、退出顺序、退出原因、参数数量和长度；失败
会报告种子与迭代位置。

### QEMU 系统测试

只有真实 QEMU 能证明：

- CR3/TLB/页权限；
- Ring 0/Ring 3 栈；
- ATA PIO 与 rootfs 块树；
- PS/2 中断唤醒 Shell；
- SYSCALL 被硬件 IRQ 打断；
- FXSAVE/FXRSTOR；
- 全部跨模块资源快照。

一次 QEMU 不足以代替随机状态搜索，纯宿主模型也不能代替硬件行为。

## 23. 如何调试

### PID1 没有启动

依次寻找：

```text
ROOTFS_V2_MOUNTED
VFS_READY
[PROC] SPAWN_PID=...1
USER_ELF_VALID
USER_RING3_ENTER
[USER][INIT] STARTED
```

缺在 `SPAWN_PID` 前通常是路径、文件或 ELF 读取；有 `USER_RING3_ENTER` 但无
INIT 日志通常检查初始 RSP、RDI/RSI/RDX 和用户页权限。

### exec 失败后旧程序崩溃

检查：

- 失败路径是否销毁了 `previous_address_space`；
- scheduler CR3 是否在候选完整前更新；
- `CloseOnExec` 是否提前执行；
- 候选 CR3 探针后是否切回旧 CR3；
- `program_argument_plan` 是否在提交前仍与候选栈一致。

### wait 永久阻塞

比较：

```text
EXIT_PID
PROCESS_TREE_WAIT_BLOCKS
SCHEDULER_WAKEUPS
WAIT_REAPED_PID
```

有 exit 无 wake：检查 `WaitCondition::ChildProcess` 映射；有 wake 无 reap：
检查父关系和请求 PID；有 reap 但用户无返回：检查结果页和恢复 UserContext。

### 最终资源不守恒

先看 ProcessTree registered/exited/collected，再看 scheduler created/reaped，
最后看 KernelStack、KVA、frame、object、FileDescription 和 FileTable。
第一个不相等的所有权层通常最接近根因，不要只提高期望常量。

## 24. 当前边界和下一步

v1.7 仍使用 eager ELF：exec 时立即分配并读取全部 `PT_LOAD`。用户栈固定
映射 256 KiB，没有 VMA、动态增长或 heap。spawn 创建新资源集合，不复制父
地址空间、cwd 或 fd；fork/COW 尚未实现。

下一阶段 v1.8 将先引入 VMA、匿名 page fault、`mmap/munmap/brk`、guarded
stack growth 和用户 heap。只有“地址空间意图”与“当前驻留页”分离后，v1.9
才把磁盘 ELF 和 clean page cache 改成按需加载。
