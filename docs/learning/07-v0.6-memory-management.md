# v0.6：物理内存、页表权限与早期堆

> 背景先修：
> [内存、分页、保护与异常](background/04-memory-paging-protection-and-exceptions.md)。
> 该专题先把物理发现、页帧所有权、地址翻译和访问权限拆开，再进入本阶段的
> 精确 E820、布局和源码。

## 1. 本阶段要拆开的三个概念

Stage 1 的低地址恒等页表只负责“让 CPU 成功进入 Long Mode 并继续执行”，它
不能长期充当内核内存管理器。v0.6 首次把三个概念分开：

1. **物理内存发现**：平台报告哪些物理区间是什么类型。
2. **物理页所有权**：哪些 4 KiB frame 可分配、已分配或永久保留。
3. **虚拟地址翻译**：某个 virtual page 映射到哪个 physical frame，权限是什么。

v1.0 基线在低 64 MiB 内完成这套闭环：

```text
fw_cfg etc/e820
  → BootInfo v2
  → validate/summarize memory map
  → 2-bit physical frame allocator
  → reserve platform/Kernel/stack
  → allocate Kernel-owned PML4
  → map text/rodata/data/guards/heap/MMIO
  → enable NX + WP
  → switch CR3
  → permission and heap self-tests
```

历史验收见 [v0.6 发布记录](../releases/v0.6.md)，架构决策见
[ADR 0009](../adr/0009-fw-cfg-memory-map-and-kernel-page-tables.md)。

> 当前 v1.6 `main` 已在 v1.0 之后加入 64 GiB 动态页帧管理、高半区
> direct-map 和完整可回收资源基础。
> 本篇主体先讲 v1.0 基线，末尾单独说明当前源码差异，避免把第二周期机制倒灌进
> 第一周期学习顺序。

## 2. Stage 1 获取 E820

### 2.1 为什么不调用 BIOS E820

项目使用自研 ROM，没有 BIOS `INT 15h,E820` 服务。Stage 1 直接访问 QEMU PC
的 `fw_cfg` 硬件接口：

- selector port `0x510`。
- data port `0x511`。
- signature selector `0`。
- file directory selector `0x19`。

### 2.2 签名与目录

[memory_map.asm](../../source/boot/stage1/src/memory_map.asm)：

1. 选择 signature，读取 4 字节，要求为 `QEMU`。
2. 选择 file directory。
3. 读取大端 32 位 entry count，要求 1..256。
4. 流式读取每个 64 字节目录项。
5. 比较完整文件名 `etc/e820`。
6. 保存该文件 size 和 selector。

目录整数是 big-endian，代码用“左移 8 位再读一字节”的循环转换。E820 文件
内容中的 base/length/type 则按接口格式读取，不能把目录字节序规则套到所有数据。

### 2.3 20 字节到 24 字节

QEMU 每项：

```text
u64 base
u64 length
u32 type
```

项目 ABI：

```text
u64 baseAddress
u64 lengthBytes
u32 type
u32 attributes
```

Stage 1 在尾部补零 attributes，形成 24 字节固定项。文件大小必须非零、能被
20 整除，entry count 必须为 1..128。

### 2.4 排序

fw_cfg 不承诺 E820 顺序。Stage 1 对最多 128 项做按 base 的 bubble sort。
启动数据规模很小，简单、固定上界、易审计比渐进复杂度更重要。

Kernel 仍会独立检查有序和不重叠；“Stage 1 已排序”不是跳过防御验证的理由。

### 2.5 staging 区验证

在读取 1 MiB Kernel 文件前，Stage 1 要求
`[0x03E00000,0x03F00000)` 完整落在同一个 type=1 usable 区间。不能仅因
QEMU 命令行写了 `-m 64M` 就假定该地址可写。

## 3. Kernel 验证内存图

[physical_memory_map.hpp](../../source/kernel/include/os/kernel/memory/physical_memory_map.hpp)
定义 24 字节 ABI 和汇总结果。

v1.0 验证：

- pointer 非空。
- count 1..128。
- managed limit 有效。
- 每项 length 非零。
- `base+length` 不溢出。
- 按 base 单调。
- 区间不重叠。
- total/usable 汇总不溢出。
- 管理窗口内至少存在一个完整可用页。

汇总值有意区分：

- 所有描述区间的长度和。
- 全部 E820 usable bytes。
- 当前 managed window 内 usable bytes。
- 最高描述地址。
- 最高 usable 地址。

高地址 MMIO hole 或 reserved 区不能被误计为 RAM。

## 4. v1.0 物理页帧分配器

### 4.1 页和 frame

虚拟地址空间按 4 KiB page 划分；物理 RAM 按 4 KiB frame 划分。二者大小
相同便于映射，但 page number 和 frame number 不是同一所有权对象。

v1.0 管理低 64 MiB：

```text
64 MiB / 4 KiB = 16384 frames
```

每帧使用 2 bit，因此状态存储：

```text
16384 × 2 / 8 = 4096 bytes
```

### 4.2 四种状态

[PhysicalFrameAllocator](../../source/kernel/include/os/kernel/memory/physical_frame_allocator.hpp)
内部状态：

- `Unavailable`：非 usable、部分页或管理范围外。
- `Free`：可分配。
- `Allocated`：动态所有者持有。
- `Reserved`：启动、平台或 Kernel 长期占用。

统计始终满足：

```text
managed = unavailable + free + allocated + reserved
```

公开统计不必暴露 unavailable，但内部计数转换必须守恒。

### 4.3 初始化

先把全部 frame 设为 Unavailable，再把每个 type=1 区间内“完整落入的 4 KiB
frame”设为 Free。区间开头/末尾的半页不能分配。

随后保留：

- 低 1 MiB：IVT、启动结构、Stage 1、页表及传统平台区域。
- 链接器符号界定的完整 Kernel image。
- 64 KiB early Kernel stack。

### 4.4 Reserve 是两遍事务

若一个 reservation 跨过 Allocated frame，应完整失败，不能把前半段先改成
Reserved。实现先检查全部 frame，再提交状态变更。

### 4.5 Allocate/Release

分配使用从 `nextSearchFrameIndex` 开始、可回绕的 next-fit：

- 避免每次从 frame 0 扫描。
- 找到 Free 后改为 Allocated。
- 更新 free/allocated 计数和下一起点。

释放要求：

- 4 KiB 对齐。
- 位于 managed range。
- 当前状态必须是 Allocated。

因此 reserved、unavailable、double free 和任意地址都会得到明确错误。

## 5. 内核四级页表

### 5.1 `PageTableManager`

[page_table.hpp](../../source/kernel/include/os/kernel/memory/page_table.hpp) 把硬件位图封装为：

- `PageTableIndices`。
- `PagePermissions`。
- `PageMapping`。
- `PageTableStatus`。

Map 时按 PML4→PDPT→PD→PT 行走，缺失中间表就从 frame allocator 分配、清零并
连接。Query 反向解码叶条目。Unmap 清叶条目并失效 TLB，但 v1.0 不回收空的
中间表。

### 5.2 v1.0 映射

| 虚拟区域 | 物理来源 | 权限 |
| --- | --- | --- |
| page 0 | 无 | not-present |
| Kernel `.text` | identity | supervisor R+X |
| `.rodata` | identity | supervisor R+NX |
| `.data/.bss` | identity | supervisor RW+NX |
| 其余低 64 MiB 启动区 | identity | supervisor RW+NX |
| early stack guard | 无 | not-present |
| DF/NMI/MC/RSP0 guard | 无 | not-present |
| 每进程 Ring 0 stack guard | 无 | not-present |
| `0xFFFF800000000000` 64 KiB heap | 16 个离散 frame | supervisor RW+NX |
| `0xFFFF800000100000` test page | 一个 frame | supervisor R+NX |
| LAPIC MMIO | identity | supervisor RW+NX, cache-disabled |

Kernel section 边界来自 linker symbols，而不是手写“代码大概到哪里”。

### 5.3 NX 与 WP

在使用 NX bit 前用 CPUID 检查能力，并设置 `IA32_EFER.NXE`。

设置 `CR0.WP` 后，Ring 0 也不能写 read-only present page。若只依赖 PTE.RW=0
而 WP=0，Kernel 可能绕过自己的只读保护。

### 5.4 切换 CR3

新表完成后：

1. 确认当前 RIP、栈、GDT、IDT、TSS、串口和所有静态数据在新表可达。
2. 开 NX/WP。
3. 写新 PML4 physical address 到 CR3。
4. 回读 CR3、EFER、CR0。
5. Query 关键地址权限。
6. 验证 page 0 和 guard pages 都 not-present。

切 CR3 是不可回滚的关键点：新表漏映当前栈会立即产生难以处理的递归 fault。

## 6. Guard page

栈存储按：

```text
[4 KiB guard][16 KiB usable stack]
```

分配。guard 仍占静态/物理存储，但在页表中 not-present。栈向低地址增长，越过
可用底部首先访问 guard，形成明确 #PF，而不是静默破坏相邻对象。

guard 不能阻止一次跨越多页的野指针，也不能自动恢复栈溢出；它提供的是稳定的
早期检测边界。

## 7. 早期高半区堆

[KernelHeap](../../source/kernel/include/os/kernel/memory/kernel_heap.hpp) 是 64 KiB
单调 allocator：

- 初始化一次。
- size 必须非零。
- alignment 必须是非零 2 的幂。
- 对齐 padding 和地址计算检查溢出。
- 容量不足明确返回。
- 失败不修改 output pointer 和统计。
- 不提供 free。

目标自检：

1. 申请一个 16-byte aligned 小对象。
2. 申请一个 4 KiB aligned 对象。
3. 写入两个不同 64 位 pattern。
4. 读回。

这同时执行高半区翻译、RW/NX 映射和对齐逻辑。

## 8. 写保护故障注入

独立镜像在 Ring 0 写只读 test page：

```text
virtual address = 0xFFFF800000100000
#PF error = 0x3
```

error bits：

- P=1：页存在，是权限错误。
- W/R=1：写访问。
- U/S=0：supervisor。

若看到 not-present error，说明映射根本没建好；若没有 fault，通常是 CR0.WP
未启用或 PTE 错误可写。

## 9. 当前 v1.6 中由 v1.1 奠定的可回收资源扩展

提交 `89de15e` 已把第一周期的低 64 MiB 正式管理上限扩展为第二周期基础：

- 从 `CPUID.80000008H` 读取 physical/virtual address width。
- managed limit 取 E820、CPU 物理宽度和 64 TiB direct-map 容量的最小值。
- 2-bit frame metadata 按实际 PFN 范围动态计算，并放入低 64 MiB 启动可达 RAM。
- 高半区 direct-map base 为 `0xFFFF888000000000`。
- usable RAM 内部优先用 2 MiB page，E820 边界使用 4 KiB。
- 新 CR3 激活后，页表和普通物理页通过 direct-map 解引用。
- 64 GiB 主配置会从 4 GiB 以上分配、写读并释放 frame。
- 64 MiB 仍是最小兼容配置，Stage 1 临时映射仍保持 64 MiB。

这只是 v1.1 的第一个增量；v1.1 随后还依次完成：

| 增量 | 当前能力 | 设计记录 |
| --- | --- | --- |
| 可回收 Kernel heap | best-fit、对齐、释放、合并、非法释放与一致性统计 | [ADR 0020](../adr/0020-reclaimable-kernel-heap.md) |
| 双位图 buddy | order-0 兼容接口、连续页、分裂/合并和十万步模型 | [ADR 0022](../adr/0022-bitmap-buddy-frame-allocator.md) |
| 固定尺寸 type cache | 活动位图、对齐槽、槽内 LIFO free index | [ADR 0023](../adr/0023-heap-backed-fixed-size-type-cache.md) |
| KVA allocator | 32 TiB 高半窗口、256 个有序所有权描述符 | [ADR 0024](../adr/0024-reclaimable-kernel-virtual-address-allocator.md) |
| 动态 Ring 0 stack | 六页 KVA、上下 guard、四个独立物理后备页 | [ADR 0025](../adr/0025-kva-backed-dynamic-kernel-stacks.md) |
| 页表空分支回收 | 根所有权、PT/PD/PDPT 逆序回收和映射失败回滚 | [ADR 0026](../adr/0026-owned-page-table-branch-reclamation.md) |

这些都不是 v1.0 完成条件，而是 v1.1 的已落地基础；v1.2–v1.4 的

能力之上。阅读当前
[memory_manager.cpp](../../source/kernel/src/memory/memory_manager.cpp) 时，应把
`MapDirectMemory`、动态 metadata 和 high-memory self-test 视为本节增量；
v1.0 精确快照是提交 `65b0e95`。

## 12. 实验

### 实验 A：页帧状态

给定一张含 usable、reserved 和非页对齐边界的 E820 图，手算每个 frame 初始
状态，再加入低 1 MiB、Kernel 和 stack reservation。

### 实验 B：四级索引

手算 Kernel heap base 和 write-protection page 的四级索引，说明两者在哪一级
开始分叉。

### 实验 C：页错误码

分别预测：读 page 0、Ring 0 写 read-only page、Ring 3 读 supervisor page
的 #PF error bits。

### 实验 D：v1.0 与当前 v1.6

用上述 `git diff` 把变更分成“容量发现、metadata、页表访问方式、direct-map、
验收证据”五组，说明 Stage 1 的 64 MiB 映射为什么不必跟着扩大。
