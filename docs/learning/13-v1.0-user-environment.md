# v1.0：交互式用户环境、统一描述符与完整系统闭环

> 背景先修：
> [键盘 IRQ 与 idle](background/05-interrupts-time-and-pc-devices.md)、
> [描述符、阻塞 I/O 与 Shell](background/06-processes-syscalls-files-and-shell.md)、
> [QMP 整机证据](background/07-testing-debugging-and-evidence.md)。

## 1. 阶段目标

v1.0 不是简单增加一个打印提示符的函数，而是把前面所有阶段第一次收束成普通
用户可以操作的系统：

```text
宿主 QMP sendkey
  → QEMU 虚拟 PS/2 键盘
  → i8042 数据端口
  → PIC IRQ1
  → IDT 中断入口
  → Set 1 扫描码解码
  → 256-byte ConsoleInput FIFO
  → 唤醒等待 fd 0 的 Shell
  → Ring 3 系统调用
  → 统一描述符
  → 串口 / 管道 / 文件 / 目录
  → ATA raw disk
```

完成这一阶段后，系统拥有：

- 独立 Ring 3 Shell ELF。
- `stdin/stdout/stderr`。
- 文件、目录、管道共用的描述符命名空间。
- 非阻塞 Try 与显式 Wait 组成的阻塞 I/O。
- 没有 Ready 进程时的无竞态空闲路径。
- 真实键盘中断驱动的命令行输入。
- help、echo、pwd、ls、mkdir、write、cat、sync、exit。
- 自动化、可重复、可审计的整机交互测试。

历史验收见 [v1.0 发布记录](../releases/v1.0.md)，核心设计决策见
[ADR 0015](../adr/0015-unified-descriptors-interactive-shell-and-idle.md)。

> 本页严格解释提交 `65b0e95` 的 v1.0 固定八槽描述符和 PCB 调度模型。
> v1.2 已用 Process/Thread/ThreadScheduler 替换 PCB/ProcessScheduler，
> v1.4 已用 KernelObject、FileDescription 和动态 FileTable 替换
> IoDescriptorTable。学习历史源码可用 `git show 65b0e95:<path>`；阅读当前
> 实现则从 [v1.2](../releases/v1.2.md)、[v1.4](../releases/v1.4.md) 和
> [FileTable](../../source/kernel/include/os/kernel/io/file_table.hpp) 继续。

## 2. 为什么交互式 Shell 必须最后出现

Shell 本身只是一个用户程序，但它依赖几乎全部已有基础设施：

| Shell 行为 | 依赖的早期阶段 |
| --- | --- |
| 作为独立 ELF 加载 | v0.4、v0.8 |
| 在 Ring 3 执行 | v0.5、v0.8 |
| `int 0x80` 进入内核 | v0.8 |
| 输入时阻塞、按键后恢复 | v0.7、v0.9 |
| 与其他进程共同运行 | v0.9 |
| 管道端点继续工作 | v0.10 |
| `mkdir/write/cat/ls/sync` | v0.11 |
| 键盘输入 | v0.7、v1.0 |
| 无 Ready 时安全等待 | v0.9、v1.0 |

如果直接在 Kernel 中写命令解析器，屏幕上同样能出现提示符，却不能证明 Ring 3、
用户地址空间、系统调用、调度、阻塞、文件系统和资源回收真正连通。因此当前
Shell 必须是一个由用户 ELF loader 创建的普通进程，业务逻辑全部位于
[shell.cpp](../../source/user/src/shell.cpp)。

## 3. v0.11 到 v1.0 的接口收束

v0.10、v0.11 已有专用管道和文件系统调用：

- `TryReadPipe`、`TryWritePipe`、`WaitPipeReadable`……
- `OpenFile`、`ReadFile`、`WriteFile`、`CloseFile`……

这些接口能验证单个子系统，但用户程序必须事先知道“这个整数是管道还是文件”，
无法形成标准输入输出。v1.0 保留旧编号做回归兼容，正常用户环境改用：

- `TryReadDescriptor`
- `TryWriteDescriptor`
- `WaitDescriptorReadable`
- `WaitDescriptorWritable`
- `CloseDescriptor`
- `OpenDirectory`
- `ReadDirectory`

收束后的核心思想是：

```text
用户只持有 fd
    |
    v
每进程 IoDescriptorTable 判定 kind
    |
    +-- ConsoleInput
    +-- ConsoleOutput / ConsoleError
    +-- RegularFile
    +-- Directory
    +-- PipeReader / PipeWriter
```

“统一”指统一命名、通用读写、等待和关闭入口，不代表所有对象支持所有操作。
目录使用同一 fd 空间和 Close，但仍通过结构化 `ReadDirectory` 迭代，不能当成
任意字节流读取。

## 4. 硬件输入：i8042 与 PS/2 键盘

### 4.1 端口与状态位

[ps2_keyboard.cpp](../../source/kernel/src/device/ps2_keyboard.cpp) 使用：

| 端口 | 读 | 写 |
| --- | --- | --- |
| `0x60` | 输出缓冲区中的扫描码/应答 | 键盘设备命令或配置字节 |
| `0x64` | 控制器状态 | 控制器命令 |

重要状态位：

- bit 0：output buffer full。为 1 才能从 `0x60` 读取。
- bit 1：input buffer full。为 0 才能向控制器写入。

这里的 input/output 以控制器为视角：

- CPU 写给控制器的数据进入 input buffer。
- 控制器交给 CPU 的扫描码进入 output buffer。

初始化和命令等待都有固定轮询上界，设备不响应时返回明确错误，不能无限自旋。

### 4.2 初始化序列

`Ps2Keyboard::Initialize()` 的顺序是：

1. 等 input buffer 可写。
2. 发送 `0xAD`，禁用第一端口。
3. 发送 `0xA7`，禁用第二端口。
4. 最多读取 32 个旧 output bytes，清理历史状态。
5. 发送 `0x20` 读取 controller configuration。
6. 设置第一端口中断位和 translation 位。
7. 清第二端口中断位与第一端口 clock-disabled 位。
8. 用 `0x60` 写回 configuration。
9. 用 `0xAE` 重新启用第一端口。
10. 向键盘发送 `0xF4` 开启扫描。
11. 要求设备返回 `0xFA` ACK。

开启 translation 后，当前解码器面对稳定的 Set 1 扫描码。系统没有借助 BIOS
键盘服务；进入 Kernel 后，端口访问、命令时序和失败处理都由自己的驱动负责。

### 4.3 IRQ1

键盘属于 legacy PIC 的 IRQ1。按键发生后：

1. 键盘把扫描码送入 i8042 output buffer。
2. i8042 拉起 IRQ1。
3. PIC 把请求映射到 Kernel 的硬件中断向量。
4. 汇编入口保存寄存器并构造 `ExceptionFrame`。
5. C++ 中断分派调用
   `InterruptRuntime::HandleKeyboardInterrupt()`。
6. 中断尾部向 PIC 发送 EOI。
7. `iretq` 恢复被中断上下文，或恢复调度器选出的另一个用户上下文。

硬件中断入口、PIC 和 EOI 的详细背景在
[v0.7 文档](08-v0.7-interrupts-and-devices.md)。v1.0 新增的是从扫描码到
用户可读字符和进程唤醒的后半段。

## 5. Set 1 扫描码不是 ASCII

键盘先产生物理键位置编码，而不是字符。当前解码逻辑位于
[device_model.cpp](../../source/kernel/src/device/device_model.cpp)：

- make code 表示按下。
- break code 的 bit 7 为 1，表示释放。
- `0xE0` 表示下一个字节是扩展扫描码。
- 左 Shift 是 `0x2A`。
- 右 Shift 是 `0x36`。
- Caps Lock 是 `0x3A`。

解码器保存跨中断状态：

```text
leftShiftPressed
rightShiftPressed
capsLockEnabled
extendedPrefixPending
```

字母大小写的规则是：

```text
uppercase = shiftPressed XOR capsLockEnabled
```

数字和标点只看 Shift，不受 Caps Lock 影响。例如：

```text
0x02             → '1'
Shift + 0x02     → '!'
0x1E             → 'a'
Caps + 0x1E      → 'A'
Caps+Shift+0x1E  → 'a'
```

基础 US 键区还覆盖空格、Enter、Backspace、Tab、反引号、反斜线以及三行
字母周围的标点。方向键等扩展事件可以被识别为键盘事件，但 v1.0 的最小 Shell
没有光标移动功能，因此不会提交字符。

`HandleKeyboardInterrupt()` 只把“pressed 且 character 非零”的事件送入
控制台；break code 和纯修饰键不会变成用户字节。

## 6. 中断处理的热路径

[interrupt_runtime.cpp](../../source/kernel/src/arch/interrupt_runtime.cpp) 中的键盘路径
只做有界工作：

```text
keyboardInterruptCount++
TryReadScanCode()
Decode()
supportedKeyboardEventCount++
若是可提交字符：
    SubmitConsoleCharacter(character)
保留一个兼容诊断事件
```

它不会：

- 在每个按键上打印串口日志。
- 在 IRQ handler 中解析命令。
- 直接修改 Shell 用户缓冲区。
- 在 IRQ handler 中访问文件系统。
- 等待用户进程立即运行。

中断只生产一个内核字节并使等待者变为 Ready。真正的读、回显、解析和执行都在
后续 Ring 3 调度时间中完成。这既缩短关中断时间，也让设备层、内核缓冲层和
用户策略层边界清晰。

## 7. 256 字节 ConsoleInput FIFO

[console_input.hpp](../../source/kernel/include/os/kernel/io/console_input.hpp) 定义固定
256-byte 环形缓冲区：

```text
bytes[256]
readIndex
writeIndex
submittedByteCount
readByteCount
droppedByteCount
bufferedByteCount
```

### 7.1 Submit

提交一个字符时：

1. 若 `bufferedByteCount == 256`，计一次 dropped，返回 Full。
2. 写入 `bytes[writeIndex]`。
3. `writeIndex = (writeIndex + 1) % 256`。
4. submitted 与 buffered 各加一。

满时拒绝新字符，不覆盖最旧字符。这样丢失可由统计观察，并且已被用户输入的
前缀不会被悄悄改写。

### 7.2 TryRead

读取时：

1. 先把 `readBytes` 设为 0。
2. 空 FIFO 返回 Empty。
3. 实际长度为 `min(capacityBytes, bufferedByteCount)`。
4. 逐字节处理环回。
5. 增加 read 统计，减少 buffered。

`ReadCanProgress()` 只回答当前是否非空。它不消费数据，因此可以用于
“检查条件后决定是否阻塞”。

### 7.3 v1.0 的并发边界

FIFO 没有内部自旋锁。当前系统是单核：

- IRQ handler 进入时 IF 已清。
- 系统调用和调度临界路径也在关中断区域运行。
- 因而 Submit 与 TryRead 不会在同一 CPU 上并发改动索引。

这不是天然的 SMP 安全设计。未来加入 AP 后，必须增加锁、每 CPU 队列或适合的
无锁生产者/消费者协议，不能把“单核中断串行化”误当成通用 C++ 线程安全。

## 8. 每进程统一描述符表

v1.0 的 `io_descriptor.hpp` 为每个 PCB 提供 8 个槽位：

| fd | 初始化 kind | 是否可被普通 Close |
| ---: | --- | --- |
| 0 | `ConsoleInput` | 否 |
| 1 | `ConsoleOutput` | 否 |
| 2 | `ConsoleError` | 否 |
| 3..7 | `Closed`，或指定管道端点 | 是 |

所有 kind：

```text
Closed
ConsoleInput
ConsoleOutput
ConsoleError
RegularFile
Directory
PipeReader
PipeWriter
```

`Initialize(attachPipeReader, attachPipeWriter)` 完整覆盖所有槽位，并根据程序
角色把 consumer 的 fd 3 设为 PipeReader、producer 的 fd 3 设为 PipeWriter。
普通文件和目录从 fd 3 开始分配第一个空槽。

### 8.1 描述符与底层 handle

表中只存 kind。文件系统的真实 `FileSystemHandle` 保存在 PCB 的平行数组：

```text
descriptors[fd]  → 这个 fd 是 RegularFile 还是 Directory
fileHandles[fd]  → 对应的 inode、offset、权限等文件系统状态
```

管道在 v1.0 仍是受控的系统级单管道，因此 kind 能确定它引用 reader 还是
writer；以后支持任意多个 pipe 时，槽位还要携带对象索引或对象指针。

### 8.2 为什么标准 fd 不允许关闭

`CloseDescriptor` 对 fd 0、1、2 返回 permission denied。这样保持课程阶段的
固定用户环境，避免 Shell 意外关闭自己的控制台后丢失全部诊断能力。

完整 Unix 当然允许关闭和重定向标准 fd；那要求补齐 dup、引用计数、继承和
对象生命周期，并非简单删掉权限检查。

### 8.3 一个真实的 freestanding C++ 陷阱

描述符数组最初带类内初始化。Clang 为全局 PCB 数组生成了动态初始化记录
`.init_array`。当前自研启动链没有 hosted C++ runtime，也不会偷偷遍历构造器表。

最终实现：

- 移除 `IoDescriptorTable` 数组的类内初始化。
- 保持类型平凡构造。
- 在任何读取前显式调用 `Initialize()`，完整覆盖所有槽位。
- 由 Kernel ELF audit 拒绝任何意外 `.init_array`。

这说明“代码看起来有默认值”不等于“freestanding 二进制启动后真的执行过
初始化”。必须同时审计源码语义和最终 ELF。

## 9. 通用读写的 kind 分派

核心逻辑在
[process_runtime.cpp](../../source/kernel/src/process/process_runtime.cpp)。

### 9.1 TryRead

| kind | 行为 |
| --- | --- |
| ConsoleInput | 从 ConsoleInput FIFO 读；空时 WouldBlock |
| RegularFile | 调 FileSystem::Read；0 bytes 表示 EOF |
| PipeReader | 调 Pipe::TryRead；成功后唤醒 DescriptorWritable |
| 其他 | PermissionDenied |

PipeReader 观察到 writer 全部关闭且缓冲耗尽时返回 EOF；读取腾出空间后必须
唤醒等待写的进程。

### 9.2 TryWrite

| kind | 行为 |
| --- | --- |
| ConsoleOutput | 逐字节写 COM1 |
| ConsoleError | 逐字节写 COM1 |
| RegularFile | 调 FileSystem::Write |
| PipeWriter | 调 Pipe::TryWrite；成功后唤醒 DescriptorReadable |
| 其他 | PermissionDenied |

v1.0 的 stdout 和 stderr 最终都落到同一串口，但保留两个不同 kind 是 ABI
语义：未来可以分别重定向。

### 9.3 Close

动态 fd 的关闭顺序取决于 kind：

- RegularFile/Directory：先关闭 FileSystemHandle，再关闭表项。
- PipeReader：关闭 reader，唤醒等待 writable 的 writer，使其观察 broken
  pipe。
- PipeWriter：关闭 writer，唤醒等待 readable 的 reader，使其观察 EOF。

进程正常退出和异常终止时也遍历 fd 3..7，执行同样的底层资源回收和对端唤醒。
仅把表项标成 Closed 会泄漏文件 handle，也会让管道对端永久睡眠。

## 10. 系统调用 ABI

[system_call.hpp](../../source/abi/include/os/abi/system_call.hpp) 是 Kernel 与所有
用户 ELF 共同编译的 ABI 事实来源。

### 10.1 编号

v1.0 新编号：

| 编号 | 调用 | 返回语义 |
| ---: | --- | --- |
| 16 | TryReadDescriptor | 正数为读取字节数，0 可为 EOF，负数为错误 |
| 17 | TryWriteDescriptor | 非负数为写入字节数，负数为错误 |
| 18 | WaitDescriptorReadable | 0 成功，负数错误 |
| 19 | WaitDescriptorWritable | 0 成功，负数错误 |
| 20 | CloseDescriptor | 0 成功，负数错误 |
| 21 | OpenDirectory | 非负数 fd，负数错误 |
| 22 | ReadDirectory | 1 为一项，0 为 EOF，负数错误 |

每次通用 descriptor transfer 最大 256 bytes。0 长度 read/write 是合法的空
操作；超过上限会返回 `DESCRIPTOR_TRANSFER_TOO_LARGE`。

### 10.2 寄存器

项目 ABI：

```text
RAX = syscall number / return value
RDI = argument 0
RSI = argument 1
RDX = argument 2
R10 = argument 3
```

用户 C++ 调用普通 System V 函数时，第五个函数参数在 R8。
[system_call.asm](../../source/user/src/system_call.asm) 因此执行：

```asm
mov rax, rdi
mov rdi, rsi
mov rsi, rdx
mov rdx, rcx
mov r10, r8
int 0x80
ret
```

R8 到 R10 的搬运虽然在当前三参数通用 I/O 上不显眼，却保证四参数 syscall
不会把 C++ 调用约定误当成内核 ABI。

### 10.3 用户内存永远不直接信任

Kernel dispatch 的基本模式：

```text
检查长度
验证用户地址范围和页权限
CopyFromUser 到固定 Kernel buffer
执行设备/文件操作
CopyToUser 返回结果
映射内部 status 为稳定 ABI 错误码
```

TryRead 使用 Kernel 侧 256-byte 临时缓冲，操作成功后才 CopyToUser。
TryWrite 先 CopyFromUser，再访问底层对象。这样设备和文件系统不会在 Ring 0
直接解引用任意用户指针。

## 11. 为什么拆成 Try 与 Wait

如果 Kernel 只提供一个“阻塞 read”，内部很容易混在一起：

- 条件检查。
- 数据传输。
- PCB 状态变化。
- context switch。
- 唤醒后重试。

v1.0 把协议拆开：

```cpp
while (true) {
    result = TryReadDescriptor(fd, buffer, capacity);
    if (result != WOULD_BLOCK) {
        return result;
    }
    result = WaitDescriptorReadable(fd);
    if (result < 0) {
        return result;
    }
}
```

[system_call.cpp](../../source/user/src/system_call.cpp) 中的 `ReadDescriptor()` 和
`WriteDescriptor()` 封装了这个循环。Shell 使用阻塞外观，内核仍保留清晰的
Try/Wait 状态机。

`WriteDescriptor()` 还把任意用户长度切成最多 256 bytes 的多次传输，并处理
partial write；不能假设一次 TryWrite 总能写完全部数据。

### 11.1 Wait 不是“无条件睡眠”

内核 Wait dispatch 先调用：

- `CurrentProcessDescriptorReadCanProgress()`，或
- `CurrentProcessDescriptorWriteCanProgress()`。

条件已成立就直接返回；条件不成立才把当前进程设为 Blocked。这防止用户在
Try 返回 WouldBlock 后、真正进入 Blocked 前漏掉已经到来的事件。

对象的进展条件：

| kind | readable | writable |
| --- | --- | --- |
| ConsoleInput | FIFO 非空 | 不支持 |
| ConsoleOutput/Error | 不支持 | true |
| RegularFile | true | true |
| Directory | 可执行专用迭代 | 不支持 |
| PipeReader | 有数据或可观察 EOF | 不支持 |
| PipeWriter | 有空间或可观察 broken pipe | true/false 由 pipe 决定 |

注意：Directory 被视为可执行目录迭代的对象，但通用字节 `TryReadDescriptor`
仍拒绝它。结构化目录 ABI 不应被误读为普通文件流。

## 12. 键盘到 Shell 的阻塞与唤醒

Shell 请求一个字符时的完整状态变化：

```text
Shell Running
  → TryRead(fd 0)
  → FIFO Empty
  → WOULD_BLOCK
  → WaitDescriptorReadable(fd 0)
  → 再检查 FIFO，仍空
  → Shell Blocked(reason=DescriptorReadable)
```

按键到来：

```text
IRQ1
  → Decode(character)
  → ConsoleInput.Submit(character)
  → WakeBlockedProcesses(DescriptorReadable)
  → Shell Ready
```

下一次调度：

```text
Shell Ready → Running
  → Wait 返回 0
  → 用户 wrapper 回到循环
  → 再次 TryRead(fd 0)
  → 消费字符
```

唤醒只表示“值得重试”，不承诺资源仍属于该进程。如果未来多个 reader 被同时
唤醒，第一个可能先消耗数据，其他进程必须再次 Try 并接受 WouldBlock。这也是
循环不能省略的原因。

## 13. 最后一个 Running 进程阻塞

### 13.1 新的合法状态

早期调度器隐含“总有一个 Ready”。交互式 Shell 打破这一假设：

```text
Shell 等键盘
Producer 等管道
Consumer 等管道
Worker 已终止或暂不可运行
```

此时可能没有 Ready，但仍有 Blocked，系统并未完成。

v1.0 的 `process_scheduler.cpp` 在最后一个 Running 阻塞时：

1. 将它设为 Blocked，记录 wait reason 和 block count。
2. 清当前进程索引。
3. 找不到 Ready 时仍返回 Succeeded。
4. scheduling decision 的 `switched=false`。

`NoReadyProcess` 是“当前没有可启动对象”的调度查询结果，不等于“全部进程
完成”。只有不存在 Blocked 且所有进程已 Terminated，运行时才退出整个用户
执行阶段。

### 13.2 返回永久 Kernel 上下文

用户通过 `int 0x80` 进入 Kernel 时，当前栈属于这个用户进程的特权栈。如果它
阻塞且没有 successor，不能留在即将睡眠进程的 Kernel 栈上无限等待。

`BlockCurrentProcess()` 因此：

1. 保存当前 `ExceptionFrame` 到 PCB。
2. 调度器把进程设为 Blocked。
3. 发现 `decision.switched == false`。
4. 激活永久 Kernel CR3。
5. 恢复默认 `TSS.RSP0`。
6. 调 `osKernelReturnFromUserMode()`，退回外层 `ExecuteProcesses()` 调用链。

下一次该进程被唤醒，保存的 frame、用户 CR3 和特权栈仍可重新激活。

## 14. 无竞态空闲：`sti; hlt; cli`

[processor.cpp](../../source/kernel/src/arch/processor.cpp) 把三条指令固定在同一内联
汇编块：

```asm
sti
hlt
cli
```

### 14.1 为什么不能先检查、再普通 HLT

危险序列：

```text
检查：没有 Ready
键盘中断到来并把 Shell 设为 Ready
CPU 执行 HLT
```

如果中断恰好落在检查和 HLT 之间，而且已经被处理，CPU 可能在有 Ready 进程时
仍睡到下一个无关中断。

### 14.2 STI interrupt shadow

x86 在 STI 后，对可屏蔽中断的识别延迟到下一条指令之后。这使：

```asm
sti
hlt
```

成为经典的原子式“允许中断并等待”组合：

- 中断已经 pending：HLT 先执行，随后立即被中断唤醒。
- 中断稍后到达：CPU 正常睡眠，事件到来后唤醒。

IRQ 返回后执行 CLI，把控制重新带回调度器的关中断临界区。

### 14.3 为什么必须在一个汇编块

最初分别调用 `EnableInterrupts()` 和 `WaitForInterrupt()`，编译后可能变成：

```text
sti
ret
call WaitForInterrupt
hlt
```

此时 STI 的“下一条指令”是 RET，不再覆盖 HLT。源代码两行相邻不能证明机器
指令相邻。因此：

- 实现使用单一 `asm volatile("sti; hlt; cli")`。
- ELF audit 解析最终反汇编，断言三条指令连续。

这是本项目“最终产物也是规格”的典型例子。

## 15. 独立 Ring 3 Shell ELF

[shell_entry.cpp](../../source/user/programs/shell_entry.cpp) 的入口极小：

```cpp
extern "C" [[noreturn]] void osUserEntry() noexcept {
    ExitProcess(RunShell());
}
```

Shell 与 producer、consumer、worker 一样：

- 被构建为独立 freestanding ELF。
- 有自己的用户页表和用户栈。
- 从 Ring 3 开始执行。
- 通过 `int 0x80` 请求 Kernel 服务。
- 正常返回值交给 `ExitProcess`。
- 不链接 libc 或 hosted C++ 标准库。

Shell 使用固定数组，不使用 heap、异常、RTTI、iostream、`std::string` 或
动态容器。

## 16. Shell 主循环

[shell.cpp](../../source/user/src/shell.cpp) 的高层流程：

```text
打印 banner 与 READY
loop:
  打印 "[os:/]$ "
  逐字符读取一行
  超长 → 报错并继续
  解析命令行
  空行 → 继续
  解析错误 → 报错并继续
  执行 built-in
  Exit → 返回 0
  Fatal I/O → 返回 1
```

启动时输出：

```text
x86-64 OS Lab v1.0
输入 help 查看可用命令。
[OS][USER][SHELL] READY
[os:/]$
```

`READY` 是宿主测试的同步边界：只有看到它，QMP 输入线程才开始发按键。

## 17. 行编辑

Shell 行缓冲最大 128 bytes，另有 1 byte NUL：

- 每次从 fd 0 阻塞读取一个字符。
- printable ASCII `0x20..0x7E` 和 Tab 被接受并回显。
- Enter 回显 CRLF、补 NUL 并结束本行。
- Backspace 在非空且未进入 overflow 状态时删除一个字节，并输出
  `"\b \b"` 擦除终端字符。
- 其他控制字节被忽略。

### 17.1 超长行

达到 128 bytes 后：

- 设置 `lineTooLong=true`。
- 继续读取并丢弃后续普通字符，直到 Enter。
- 不执行截断后的前 128 bytes。
- 输出明确错误，再进入新提示符。

继续排空到换行很重要。如果在第 129 字节立刻返回，剩余输入会被下一条命令
误用，造成命令边界错位。

超长状态下 Backspace 不恢复编辑，因为被丢弃的尾部长度已不再完整保存；这种
保守语义避免“看似修复到 128 以下，实际内容不可知”。

## 18. 无分配解析器

[shell_parser.hpp](../../source/user/include/os/user/shell_parser.hpp) 定义：

```text
storage[129]
arguments[8] = { offsetBytes, lengthBytes }
argumentCount
```

argument 保存 offset 而不是 `char *`，使结构复制后仍然自包含，也方便单元和
随机测试检查边界。

解析规则：

- 空格和 Tab 分隔参数。
- 单引号和双引号移除自身，但保留内部内容。
- 空引号也能开始一个零长度参数。
- 反斜线转义下一个字符。
- 单引号内部反斜线按普通字符处理。
- 最多 8 个参数。
- 拒绝未闭合引号。
- 拒绝行末悬空反斜线。
- 拒绝超过 128 bytes 的输入。

示例：

```text
echo hello world
  → ["echo", "hello", "world"]

echo "hello world" 'again'
  → ["echo", "hello world", "again"]

echo one\ two
  → ["echo", "one two"]

echo ""
  → ["echo", ""]
```

失败原子性是测试不变量：输出 `ShellCommandLine` 只有成功时才成为解析结果，
错误不能留下部分 arguments 让调用者误执行。

## 19. Built-in 命令

当前没有 fork/exec，所以命令是 Shell ELF 内的 built-in，而不是单独程序。
这仍然是用户态策略：Kernel 不认识 `help`、`cat` 或命令行语法。

### 19.1 help

- 必须恰好 1 个参数，即命令名本身。
- 打印所有命令和参数格式。
- 输出稳定 `COMMAND=HELP` 标记。

### 19.2 echo

- 接受 0 个或多个文本参数。
- 用一个空格重新连接解析后的参数。
- 最后输出 CRLF。

引号只影响解析，不会被重新输出。

### 19.3 pwd

- 必须无额外参数。
- 固定输出 `/`。

v1.0 没有 per-process current working directory，文件系统仍要求绝对路径；
提示符 `[os:/]$` 也明确显示这一限制。

### 19.4 mkdir

- 接受一个绝对路径。
- 调 `CreateDirectory`。
- AlreadyExists 是可识别的非致命结果。
- 其他操作失败打印错误并继续 Shell。

### 19.5 write

语法：

```text
write <path> <text...>
```

实现：

1. 把第二参数之后的解析结果用空格连接到固定 256-byte payload。
2. 用 write/create/truncate flags 打开文件。
3. 通过 `WriteDescriptor` 完整写入。
4. 无论写结果如何都尝试 Close。
5. 写入长度和关闭均成功才输出 `ok`。

payload 超过 256 bytes 会被明确拒绝，绝不溢出固定数组。

### 19.6 cat

1. 以 read flag 打开文件。
2. 每次从文件 fd 读取最多 128 bytes。
3. 正数长度写到 stdout。
4. 0 表示 EOF。
5. 关闭 fd。
6. 输出换行。

这里用同一个 `ReadDescriptor` 同时读取 RegularFile，说明 Shell 不依赖专用
`ReadFile` 入口。

### 19.7 ls

- 无参数时打开 `/`。
- 一个参数时打开指定绝对目录。
- `OpenDirectory` 返回普通动态 fd。
- `ReadDirectory` 每次返回一个固定结构。
- 返回 0 表示目录末尾。
- Directory 类型名称后附 `/`。
- 最后用通用 `CloseDescriptor` 关闭。

### 19.8 sync

- 必须无额外参数。
- 调 `SyncFileSystem`。
- 触发 write-back cache 写回与 ATA flush。

Shell 的 write 结束不等价于跨掉电持久；显式 sync 保持 v0.11 的持久顺序。

### 19.9 exit 与未知命令

- `exit` 必须无额外参数，输出 COMMAND 和 EXIT 标记，正常返回 0。
- 未知命令打印稳定拒绝标记和错误消息，但不退出。

稳定标记服务于自动验收；面向用户的文本可以改善，测试协议边界仍保持明确。

## 20. 目录项 ABI

Kernel 与用户共享的 `DirectoryEntry` 精确 64 bytes：

```text
offset 0   uint64 inodeNumber
offset 8   uint64 type
offset 16  uint64 nameLengthBytes
offset 24  uint8  name[40]
total      64 bytes
```

`static_assert(sizeof(DirectoryEntry) == 64)` 固定布局。`ReadDirectory` 要求用户
传入的 entry size 精确等于 64：

- 返回 1：复制了一项。
- 返回 0：EOF，没有新项。
- 返回负数：错误。

名称由显式长度界定，不要求 NUL terminator。Shell 必须按
`nameLengthBytes` 写出，不能把 `name` 当 C string。

## 21. 自动化输入仍走真实硬件路径

[qemu_runner.py](../../tools/os_tools/qemu_runner.py) 不向 Guest RAM 填命令，也不
调用 Kernel 测试后门。看到 Shell READY 后，它连接 QMP：

1. Unix socket 握手。
2. 执行 `qmp_capabilities`。
3. 把每个字符映射为 QEMU key name。
4. 发送 `human-monitor-command: sendkey <key> 1`。
5. 字符间等待一个很短的固定间隔。

QEMU 随后像虚拟键盘一样生成 make/break 扫描码。Guest 必须自己经历：

```text
PS/2 → IRQ1 → decoder → FIFO → wake → fd 0 → Shell
```

自动脚本输入十条命令：

```text
help
echo hello world
pwd
mkdir /demo
write /demo/message hello
cat /demo/message
ls /demo
sync
unknown
exit
```

加上十个换行共 109 bytes。最终 Kernel 要求：

```text
submitted = 109
read      = 109
dropped   = 0
buffered  = 0
```

这个不变量同时证明按键没有丢失、没有重复、没有留在 FIFO，也没有绕过
ConsoleInput 统计路径。

## 22. 整机并发场景

正常镜像不只运行 Shell，还运行历史工作负载：

| PID | 程序 | 主要职责 |
| ---: | --- | --- |
| 1 | Shell | 交互、目录和文件命令 |
| 2 | Producer | 文件写入与管道生产 |
| 3 | Consumer | 管道和文件双重验证 |
| 4 | SchedulerWorker | 调度与时间片验证 |

因此一次 v1.0 成功启动同时覆盖：

- Shell 因 fd 0 阻塞。
- 管道 reader/writer 因可读/可写条件阻塞。
- PIT 抢占与轮转。
- IRQ1 唤醒 Shell。
- 多个进程共享 Kernel，但保有独立用户地址空间和 fd 表。
- 文件系统跨不同进程读写。
- 进程退出后的描述符、页表和物理页回收。

全部进程结束后，Kernel 独立检查：

- 每个用户结果和退出码。
- 管道字节、EOF、broken-pipe 与阻塞统计。
- ConsoleInput 四项统计。
- 文件系统 Sync 与全盘 consistency。
- 已知 payload 可由 Kernel 再次打开并验证。
- 进程地址空间资源全部回收。

最后才输出 READY 并进入 Kernel 的长期事件循环。

## 24. 典型失败与定位

### 24.1 提示符出现，但键盘无响应

依次检查：

1. QMP 是否在 READY 后发送。
2. IRQ1 是否 unmask。
3. i8042 output-full 是否出现。
4. scan code 是否读出。
5. decoder 是否产生 pressed character。
6. ConsoleInput submitted 是否增长。
7. DescriptorReadable 是否唤醒。
8. Shell 是否重新 TryRead。

不要先在 IRQ handler 每键打印大量日志；这会改变时序并可能掩盖 FIFO 问题。

### 24.2 Shell 永久卡住

区分：

- FIFO 中已有字符但进程仍 Blocked：唤醒或 wait reason 错。
- FIFO 空且 CPU 没进入 HLT：调度 NoReady 路径错。
- CPU HLT 后永不醒：IF、PIC mask、EOI 或 PS/2 初始化错。
- Wait 返回但 wrapper 不重试：用户 Try/Wait 循环错。

### 24.3 命令完整执行但最终验收失败

v1.0 曾出现统一 DescriptorReadable/Writable 等待没有计入旧管道阻塞统计。
表面 Shell 全部通过，Kernel 最终历史不变量仍拒绝成功。

修复原则不是删掉旧断言，而是让统一等待路径在底层 pipe 条件确实会阻塞时更新
相同统计。新抽象必须保持历史证据，不能用新功能覆盖旧回归。

### 24.4 Kernel ELF 出现 `.init_array`

检查新全局对象、类内初始化、非平凡构造和静态局部初始化。不能简单让启动代码
无条件执行 hosted 构造器；先判断对象能否改成平凡存储加显式 Initialize。

### 24.5 `ls` 打印乱码

检查是否错误地把 40-byte name 当作 NUL 字符串。正确实现必须使用
`nameLengthBytes`，并验证长度不超过 40。

### 24.6 文件写入成功但重启丢失

`write` 只更新文件系统事务与 cache；跨启动验收还需要 `sync`、ATA FLUSH 和
QEMU `snapshot=off` 的同一可写 raw disk。

### 实验 C：证明 Try/Wait 循环

构造时间线：

1. Shell TryRead 得到 WouldBlock。
2. 按键在 Wait syscall 进入前到达。
3. Wait 内核先检查 condition。

解释为什么 Shell 不会睡过已经到来的字符。然后假设 Wait 不做二次检查，说明
丢失唤醒如何发生。

### 实验 D：证明 `sti; hlt`

分别分析中断：

- STI 之前 pending。
- STI 与 HLT 的概念边界之间 pending。
- CPU 已 HLT 后到达。
- IRQ handler 返回后立刻又有中断 pending。

说明 interrupt shadow 和尾部 CLI 对每种情况的作用。

### 实验 E：解析器边界

手工给出以下输入的结果或错误：

```text
echo "a b" c\ d
echo ''
write /x "a b" 'c d'
echo "unterminated
echo dangling\
a b c d e f g h i
```

检查参数个数、每个 offset/length、失败是否保留半成品。

### 实验 F：命令端到端

对 `write /demo/message hello` 画出：

```text
line editor
→ parser
→ OpenFile
→ fd allocation
→ CopyFromUser
→ FileSystem transaction/cache
→ WriteDescriptor
→ CloseDescriptor
→ later sync/ATA flush
```

指出“命令返回 ok”“cache 已写”“跨重启持久”三者分别由什么条件保证。

### 实验 G：扩展设计

在不立即编码的前提下，为“支持 `echo hello > /x`”写设计：

- parser 如何表达 redirection。
- 是否需要 dup/dup2。
- stdout kind/对象如何改变。
- fork/exec 前后 fd 如何继承。
- 引用计数由谁拥有。
- close-on-exec 如何表示。
- 需要哪些单元、随机和 QEMU 测试。

如果设计只是让 Shell 特判 `>` 并直接 OpenFile，它能实现一个命令效果，却没有
建立可组合的进程 I/O 模型。

## 27. v1.0 已知边界

- 无 fork、exec、wait、进程树或作业控制。
- 无信号、前后台进程组和终端控制。
- 无 pipeline、重定向、环境变量或通配符。
- cwd 固定为 `/`，文件系统只接受绝对路径。
- 每进程固定 8 个 fd。
- 无 dup、引用计数、继承或 close-on-exec。
- 控制台只有单字节 ASCII。
- 无 Unicode、历史、光标移动、raw/canonical 模式。
- 目录无 delete、rename 或并发迭代快照。
- stdout 与 stderr 暂时都写 COM1。
- ConsoleInput 依赖单核关中断串行化，不支持 SMP。
- 历史专用 pipe/file syscalls 尚未删除。

这些是明确的下一版本输入，不应被包装成已有 Unix 兼容能力。

## 28. 从零到 v1.0 的最终启动闭环

至此可以把全课程压缩成一条因果链：

```text
CPU reset vector
→ 自研 128 KiB ROM
→ Stage 1 descriptor/payload
→ A20、GDT、PAE、EFER.LME、paging
→ Long Mode
→ ATA 加载 Kernel ELF
→ BootInfo + e820 + kernel-owned page tables
→ GDT/TSS/IDT/异常
→ physical frames + heap + VM
→ PIC/PIT/PS2/ATA
→ Ring 3 ELF + int 0x80
→ scheduler + address-space switch
→ spinlock + pipe + block/wake
→ transactional filesystem + cache + persistence
→ unified fd + console FIFO
→ interactive Shell
→ QMP 真按键系统回归
→ 资源、一致性与故障路径最终验收
```

任何箭头断开，后面的可见现象都不足以宣布系统完成。例如：

- 打印 Shell banner 不证明输入经过 IRQ1。
- 文件读回不证明跨重启持久。
- 用户程序结束不证明地址空间已回收。
- C++ 编译成功不证明 ELF 没有动态初始化。
- 源码中的 STI/HLT 相邻不证明机器指令相邻。

## 29. 阶段验收

完成本章后，应能脱离文档解释并在源码中定位：

- i8042 `0x60/0x64`、状态位、初始化命令和 ACK。
- IRQ1 到 Set 1 decoder 的数据流。
- Shift、Caps Lock、make/break 和扩展扫描码。
- ConsoleInput 的 256-byte ring、满策略和四项统计。
- 每进程 8-slot fd 表与 0/1/2 语义。
- Console、File、Directory、Pipe 的统一边界与不统一之处。
- syscall 16..22、RAX/RDI/RSI/RDX/R10 和 256-byte copy boundary。
- Try→Wait→Try 为什么不会漏唤醒。
- 最后一个 Running 阻塞时如何返回永久 Kernel 上下文。
- `sti; hlt; cli` 为什么必须是相邻机器指令。
- Shell 行编辑、无分配 parser、九个 built-in 和失败语义。
- 64-byte DirectoryEntry ABI。
- QMP sendkey 为什么仍然属于真实 PS/2 整机测试。
- 109-byte 输入和最终统计如何形成端到端证据。
- 73 项 v1.0 回归如何共同覆盖正常、持久和故障路径。

能完成这些说明和实验，就完成了本项目从零到 v1.0 的第一轮学习。接下来不要
急着堆功能；先选择一个明确边界，例如动态物理内存、exec/文件描述符对象、
多管道或日志恢复，再重复“规格 → 最小实现 → 故障路径 → 自动证据”的方法。
