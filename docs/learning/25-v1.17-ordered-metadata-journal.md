# v1.17：ordered metadata journal、断电窗口与幂等恢复

## 1. 这一阶段真正解决什么

“write 返回成功”不是“一个多块文件系统操作已经原子落盘”。创建文件至少要
改变 inode 位图、inode 表和父目录；目录扩容还会改变 data 位图、目录 inode
与指针块。CPU 会按程序顺序调用写函数，但设备 cache、宿主 cache 和断电可以
把这条顺序切在任意位置。

v1.6 的 Dirty/Clean 位能让 mount 拒绝可疑镜像，却不能自动恢复。v1.17 增加
写前日志（write-ahead logging，WAL）：先把“准备写到哪些 home block 的完整
新字节”稳定到独立 journal，再发布 commit，最后把新字节复制到 home block。
断电后只需判断 commit 是否完整存在：

- 不存在：旧 home metadata 仍是权威状态；
- 存在且全部校验通过：journal payload 是权威新状态，必须 replay。

这不是数据库术语装饰，而是把多块更新变成一个有明确线性化点的持久状态机。

## 2. 为什么历史上的文件系统需要 journal

早期 Unix 文件系统直接覆盖 inode、free list 和目录。异常断电后只能运行
`fsck`，从目录树和 inode 重新推导一致性。磁盘越大，完整扫描越慢；更麻烦的
是 fsck 能修复结构，却未必知道某个半完成 rename 原本应该选择旧名字还是新
名字。

日志文件系统把最近事务写进一段可顺序扫描的区域。ext3 等系统后来区分三种
常见策略：

- data journal：数据和元数据都入日志，保证强但写放大大；
- ordered：只记录元数据，但相关数据先稳定；
- writeback：只保证元数据结构，不保证数据先于引用它的元数据。

本项目选择 ordered metadata journal。它正好连接 v1.16 已有的 dirty page
写回与 ATA FLUSH，又不把 v2.0 变成一个通用高性能文件系统项目。

## 3. 先区分四个容易混淆的词

### 3.1 write

把一个块交给设备接口。成功只表示当前接口接受/完成了命令，不必然表示掉电
后仍存在。

### 3.2 FLUSH

要求当前设备模型把此前写入推进到它承诺的稳定边界。它建立持久顺序，而不只是
“多等一会”。

### 3.3 commit

一条格式完整、校验通过且已 FLUSH 的 commit record。它是恢复选择新事务的
持久线性化点。

### 3.4 checkpoint

把 committed payload 复制到正常 home metadata block。checkpoint 后 journal
才可以清理并用于下一事务。

## 4. 格式 3 盘面

rootfs 仍是 256 MiB、512 B 文件系统块，但 magic 变为 `OSRFV003`，并固定
预留 256 块 journal。固定位置让 mount 在信任 superblock 之前就能恢复：

```text
relative block 0                    superblock home
relative block 1..                  bitmaps / inode table
relative block 4227..4482           journal（256 blocks）
relative block 4483..524287         file/directory data
```

journal 内部：

```text
0        header
1..4     descriptor blocks
5..128   124 payload blocks
129      commit record
130..255 reserved zero
```

四个 descriptor 块末尾各留 4 字节 CRC32，剩余 4092 字节容纳 31 个 16 字节
entry；总容量是 `4 × 31 = 124`。这是从盘面布局推导出的常量，不是随手选择
的魔法数字。

## 5. 一条记录怎样绑定到 home block

descriptor entry 保存 64 位 rootfs-relative target 和 32 位 payload CRC。
header 再保存 sequence、entry count、descriptor count 和自身 CRC；commit
重复 sequence、entry count 与 header CRC，并有独立 CRC。

恢复时必须同时验证：

1. header 和 commit 的 magic/version；
2. sequence、entry count 一致；
3. count 在 1..124；
4. 每个 descriptor 块 CRC；
5. 每个 target 不在 journal 内且未重复；
6. 每个 payload CRC；
7. commit CRC。

先验证全部记录，再写任何 home block。若边验证边 replay，后半条损坏会留下
一次由恢复代码自己制造的半事务。

CRC32 检测随机损坏，不提供密码学认证。恶意介质仍必须被边界检查拒绝，但
不能把 CRC 描述成防攻击签名。

## 6. transaction credit 为什么是正确性机制

如果修改做到一半才发现 journal 放不下，内核必须回滚所有内存状态，而且可能
已经改写相关数据。更稳妥的接口让调用方在 Begin 时预留 credit。`RootJournal`
拒绝零 credit 和超过 124 的请求；事务内首次 stage 一个新 target 消耗一个
credit，同 target 的后续覆盖只更新 overlay。

rootfs 当前串行一个 mutation，并预留 journal 上限。每个操作的元数据最终都
必须在 124 个不同块内；若超过，stage 返回 CreditsExhausted，rootfs abort，
恢复 superblock、统计与 allocation hint 快照。home metadata 在 commit 前
从未被覆盖。

未来若为了并发按操作精确计费，需要先做两遍规划或给 inode/目录算法提供
worst-case credit 公式，不能在持锁修改中猜测。

## 7. overlay 让未提交状态可读

事务内刚更新 inode block，紧接着更新目录时可能再次读取该 inode。如果读
函数只看 BlockCache，会看到旧值。v1.17 的 metadata read 顺序是：

```text
RootJournal staged overlay
        ↓ miss
BlockCache / block device
```

相同 target 再 stage 会替换 overlay 中的整块字节。整块 copy 的代价可控，
也避开“多个小 patch 的应用顺序”和越界组合问题。固定数组避免恢复路径依赖
动态内存。

## 8. 完整提交时序

### 8.1 相关数据先稳定

创建或扩展文件时，新数据块先写 home。rootfs cache 执行 sync + FLUSH 后，
metadata 才能声明 inode 指向这些块。

### 8.2 prepared transaction

写 header、四个 descriptor 块和实际使用的 payload，再 FLUSH。此时日志材料
稳定，但还没有 commit。断电恢复会丢弃它。

### 8.3 commit

写 commit record 并 FLUSH。从这个 FLUSH 成功开始，新 metadata 事务已经
持久提交，即使 home block 全是旧值也必须 replay。

### 8.4 checkpoint 与清理

把 payload 写到 target home block，FLUSH；随后清零 header/commit，再
FLUSH。最后一次 FLUSH 防止下一次 mount 又把已消费事务误判为 pending。

## 9. 断电窗口逐项推导

| 断电位置 | 稳定状态 | mount 动作 | 结果 |
| --- | --- | --- | --- |
| data 写入前/中 | 旧 metadata | 无 journal | 旧结构 |
| data FLUSH 后 | 旧 metadata + 可能新数据 | 无 journal | 旧结构 |
| prepared 写入中 | 旧 metadata + 截断日志 | discard/reject corruption | 不伪造新事务 |
| prepared FLUSH 后 | 完整 payload，无 commit | discard | 旧结构 |
| commit 写入中 | commit CRC/字段不完整 | discard 或拒绝 | 旧结构/显式错误 |
| commit FLUSH 后 | 完整 committed log | replay | 新结构 |
| checkpoint 中 | 部分 home 新 | replay 全部 | 新结构 |
| checkpoint FLUSH 后、clear 前 | home 全新 + commit | replay 同字节 | 新结构 |
| clear 中 | header/commit 之一可能残留 | 严格匹配或 clean | 新结构，不越界 |

“旧结构”不等于“旧数据内容”。覆盖同一个已分配数据块时，旧 inode 仍可见，
块内容却可能已经是新字节。metadata-only journal 只冻结结构原子性。

## 10. replay 为什么必须幂等

checkpoint 过程中可能再次掉电，因此 replay 不能依赖“目标仍是旧值”。本项目
记录完整 512 B 新块镜像，对同一 target 重复写同一 payload。操作满足：

```text
Apply(Apply(home, payload), payload) = Apply(home, payload)
```

恢复测试在第一个 mount replay 后保留镜像，再执行第二次 Recover；第二次
必须报告 Clean。checkpoint FLUSH 失败时不清 commit，让下一 mount 还有唯一
权威材料。

## 11. 源码走读

### 11.1 `root_journal.hpp`

冻结盘面可推导容量、status、recovery result、统计和固定 `StagedBlock`。
接口不接触 VFS，对宿主测试与 Kernel 使用同一实现。

### 11.2 `RootJournal::Begin/Stage/Abort`

Begin 检查 sequence 和 credit；Stage 验证 target、整块长度与 journal
自引用，计算 payload CRC；Abort 只丢 overlay。所有类成员访问显式使用
`this->`，计数和地址均为固定宽度整数。

### 11.3 `WritePreparedTransaction/WriteCommitRecord`

字段通过显式小端 StoreUint32/StoreUint64 写入，不把 C++ struct 强转成盘面
字节。这样编译器 padding、ABI alignment 和宿主端序不会偷偷成为格式。

### 11.4 `LoadCommittedTransaction`

恢复 parser 先验证 header，再判断 commit；完整 committed transaction 会
读取全部 descriptor/payload 到固定 staged array，检查 CRC、target 和重复项。
任何失败都在 checkpoint 前返回 Corrupt。

### 11.5 `root_file_system.cpp`

Initialize 先初始化并恢复 journal，再读 superblock。metadata read/write
通过 overlay；data write 仍走 BlockCache。顶层 Create/Remove/Rename/Write/
Truncate 在逻辑失败时统一 AbortTransaction，在 commit/checkpoint 设备失败时
冻结文件系统。

## 12. 独立 fsck 的角色

journal 回答“最后一个事务是否提交以及怎样补完”；fsck 回答“最终文件系统
结构是否满足全局不变量”。两者不能互相替代：

- replay 不从根目录重算 reachability；
- fsck 不知道一个无 commit 的新目录项是否原本应该完成。

Python fsck 独立解析格式 3，从根重新计算 inode/data 可达集合、链接、位图和
指针范围。它不调用 Kernel `RootJournal`，因此不是同一实现给自己作证。

## 13. 测试怎样证明性质

### 单元

覆盖非法 credit、同 target 覆盖、overlay read、abort、正常 commit、prepared
无 commit、header 损坏和 committed payload 损坏。

### 1000 个确定性 crash point

故障块设备把每个 Write/Flush 都编号，在指定编号后模拟断电。每个镜像重新
初始化一个 `RootJournal` 并恢复，然后逐块比较：

```text
all targets == old blocks
        XOR
all targets == new blocks
```

任何“部分旧、部分新”立即失败。恢复后再恢复一次必须 Clean。

### 100000 步随机模型

固定种子随机执行 Begin、Stage、Abort、Commit 和非法操作；oracle 维护独立
active/staged/durable 模型。每一步检查 durable blocks 只在 commit 后改变，
失败操作不改变已发布状态。

### QEMU

64 MiB bootstrap、256 MiB functional、64 GiB capacity 和跨启动 persistence
都要求 `ROOTFS_JOURNAL_READY`。persistence 第二次启动读取第一次启动创建的
内容，证明 production mount 路径真实执行格式 3 恢复边界。

## 14. 日志为什么不能逐块打印

一次 124-credit commit 可能包含数百次块写/校验。逐条串口输出会显著改变
ATA IRQ、PIT deadline 和 QEMU 时序，甚至制造本来不存在的超时。Kernel 只在
初始化和结束摘要打印：

```text
ROOTFS_JOURNAL_READY
ROOTFS_JOURNAL_CREDIT_CAPACITY
ROOTFS_JOURNAL_COMMITS
ROOTFS_JOURNAL_REPLAYS
ROOTFS_JOURNAL_DISCARDED
ROOTFS_JOURNAL_CHECKSUM_FAILURES
```

时间使用来宾单调纳秒；宿主 runner 时间只协助判断“卡在哪一层”。

## 15. 当前边界与下一阶段

v1.17 不实现 data journal、后台 checkpoint、多个并行 transaction、SMP、
`fsync/fdatasync/msync`、snapshot 或在线扩容。它也不把 LBA28 PIO 升级为
AHCI/NVMe。

v1.18 不再增加基础机制，而是冻结 ABI v2，补齐 procfs/devfs 观察面、至少
32 个用户工具、畸形输入和资源审计，以及从主仓、网站到教材 PDF 的发布
provenance。journal 的盘面字段、错误边界和恢复顺序在冻结期只允许修复明确
bug，不再随意扩展。
