## 1. 从工程基线到第一条指令

v0.0 只能证明工具链可靠，尚未证明 CPU 会执行项目产物。v0.1 建立第一条真实
硬件闭环：

```text
QEMU 映射自研 ROM
  → CPU 从 0xFFFFFFF0 取指
  → near jump 到 0xFFFFF000
  → 初始化 16 位执行环境
  → 配置 COM1
  → 有界轮询并输出串口标记
  → QEMU 测试进程读取串口并验收
```

阶段目标不是“能打印”，而是同时证明复位地址、ROM 布局、机器码、串口寄存器、
超时失败路径和宿主判定协议。

历史验收见 [v0.1 发布记录](../releases/v0.1.md)，模块契约见
[firmware.md](../modules/firmware.md)。

## 2. 硬件契约

### 2.1 复位状态

CPU 在 `0xFFFFFFF0` 取指，距离 4 GiB 顶端只有 16 字节。这里不适合放完整
初始化代码，只放一条编码可审计的 near jump。

项目设置：

```text
目标入口      0xFFFFF000
复位向量      0xFFFFFFF0
near jump 长度 3 bytes
位移 = 0xF000 - 0xFFF0 - 3 = -0x0FF3
```

机器码为 `E9 0D F0`。`E9` 是相对 near jump，后两个字节是小端有符号位移
`0xF00D`，按 16 位解释就是 `-0x0FF3`。

near jump 不重载 CS，所以复位时特殊的 CS hidden base 保持不变，目标物理
地址为 `0xFFFF0000 + 0xF000 = 0xFFFFF000`。

### 2.2 为什么入口要重新建立段和栈

复位状态只足以取到第一条指令，不应假定 DS、ES、SS 和栈适合项目使用。入口：

```asm
cli
cld
xor ax, ax
mov ds, ax
mov es, ax
mov ss, ax
mov sp, 0x7000
xor bp, bp
```

- `CLI`：初始化期间禁止可屏蔽中断。
- `CLD`：保证后续字符串指令按地址递增。
- DS/ES/SS=0：数据和栈使用可预测的低物理地址。
- SP=`0x7000`：避开中断向量表、BIOS 数据传统区域、描述符缓冲和 Stage 1。

这里没有 C++ 启动代码替你建立栈。

### 2.3 COM1

COM1 的输入时钟经除数产生波特率。项目使用除数 1，得到 115200 baud，并配置：

- 禁用 UART 中断。
- DLAB=1，写除数低/高字节。
- 8 data bits、no parity、1 stop bit，即 8N1。
- 启用和清空 FIFO。
- 配置 modem control。
- DLAB=0，恢复数据寄存器语义。

发送一个字符前读取 Line Status Register，等待 THRE=`0x20`。UART 状态可能
永不就绪，所以最多轮询 `0xFFFF` 次。

### 2.4 PIT 在固件中的作用

当前最终固件还会把 PIT channel 0 配为 mode 2、除数 `0x04A9`。v0.1 的
核心验收是复位和串口；PIT 标记为后续硬件时序建立早期可观察状态。此时中断仍
未开放，不能把“编程 PIT”误认为“内核已经处理时钟 IRQ”。

## 3. ROM 链接布局

[rom.ld](../../source/firmware/linker/rom.ld) 明确指定：

```text
0xFFFE0000  .rom_start，至少放一个字节确保起始地址
0xFFFFF000  .text.entry
0xFFFFFFF0  .reset_vector
0xFFFFFFFF  .rom_end，确保镜像覆盖到最后一字节
```

两个 `ASSERT` 在链接时检查：

- 入口代码不能侵入复位向量。
- `.reset_vector` 不超过 16 字节。

`llvm-objcopy --gap-fill=0xff -O binary` 把 ELF 中的地址空洞填成 ROM 常见的
`0xFF`，生成精确 131072 字节平坦镜像。

### 为什么 NASM 使用 `elf32`

源代码声明 `bits 16`，CPU 执行的是 16 位指令。NASM 选择 `elf32` 只是为了
让当前 LLD i386 链接流程能够承载 section、symbol 和 relocation；目标文件
容器位宽不等于运行时指令模式。

## 4. 源码逐段导读

主文件是
[reset_and_vga.asm](../../source/firmware/src/reset_and_vga.asm)。

本章描述提交 `22bb2c5` 的历史 COM1 实现；当前 `main` 已把同一启动位置迁移到
VGA 文本控制台。对照历史代码时应使用该提交，当前文件用于观察后来演进后的
VGA、PIT、ATA 与 Stage 1 组合路径。

### 4.1 常量区

常量按领域分组：

- ROM runtime offset 和栈。
- COM1 端口、偏移、位值和轮询上限。
- PIT 端口和除数。
- ATA、Stage 1 和失败码——这些在 v0.2 重点解释。
- reset vector 机器码参数。

汇编阶段计算 jump displacement，避免手写魔法字节与入口地址脱节。

### 4.2 `os_firmware_entry`

当前最终版本的入口做：

1. `CLI/CLD`。
2. 初始化段和栈。
3. 调用 `os_firmware_initialize_com1`。
4. 调用 `os_firmware_initialize_pit`。
5. 依次写复位、串口、时钟里程碑。
6. 进入 v0.2 的 Stage 1 加载流程。

学习 v0.1 时先在第 5 步结束，后续分支暂时当作下一阶段扩展。

### 4.3 字符发送约定

底层字符发送函数用 carry flag 表达成功/失败：

- CF=1：发送成功。
- CF=0：超时失败。

字符串函数逐字节读取以零结尾的文本，每个字符都复用相同失败语义。一旦底层失败，
上层立即停止，避免继续假装日志完整。

### 4.4 字符串地址计算

固件链接在高物理地址，但 DS 被设置为 0，16 位 SI 只能直接表示低 64 KiB
offset。代码使用入口 runtime offset 与“标签相对 section 起点”的差值，形成
当前 CS 窗口内可用的 16 位地址。理解 `$`、`$$` 和链接 VMA 的区别非常重要。

### 4.5 halt

不可恢复失败最终执行关闭中断后的 HLT 循环。单次 `HLT` 之后不能假定 CPU 永远
停止，因为 NMI、SMI 或平台事件仍可能唤醒；因此 fatal halt 通常是循环。

## 5. 构建链

[source/firmware/CMakeLists.txt](../../source/firmware/CMakeLists.txt) 的每个
ROM 变体经过：

```text
reset_and_vga.asm
  --nasm -f elf32-->
firmware object
  --ld.lld -m elf_i386 -T rom.ld-->
firmware ELF
  --llvm-objcopy --gap-fill=0xff -O binary-->
128 KiB ROM
```

同一源文件还会通过 NASM define 生成串口超时、IDE busy 和 IDE error 的故障
变体。变体只替换受控硬件观测，不另写一套近似逻辑。

## 6. 产物审计

`tools/os_tools/firmware_audit.py` 不启动 QEMU就检查：

- 文件精确等于 128 KiB。
- ROM offset 与物理地址换算正确。
- `0xFFFFFFF0` 处 opcode 为 `E9`。
- 位移目标精确落在 `0xFFFFF000`。
- 复位向量没有越过 ROM 末尾。

这些是静态事实，没必要等黑盒启动失败后才猜。

## 7. 串口日志是一份协议

项目日志不是随意的调试文本。阶段里程碑有固定顺序，QEMU runner：

1. 启动 QEMU TCG。
2. 指定项目 ROM 和 raw IDE 磁盘。
3. 把 serial 重定向到宿主进程管道。
4. 按顺序匹配必需标记。
5. 拒绝禁止出现的失败标记。
6. 在终止标记后留出短暂 settle window。
7. 超时或 QEMU 提前退出时报告上下文。

因此改变日志文本、顺序或失败码相当于改变测试协议，需要同步更新文档和测试。

## 8. 失败路径

### 8.1 串口永不就绪

故障 ROM 保留第一条真实串口输出，随后让第二次状态观察持续不满足 THRE。这样能
区分“ROM 根本没执行”与“发送等待超时”。

正确结果是：

- 早期复位证据存在。
- 正常后续标记不存在。
- 固件停止。
- QEMU 测试把这个停止识别为预期失败，而不是测试框架超时。

### 8.2 ROM 尺寸错误

QEMU 对 ROM 映射有固定要求。系统测试生成比正确大小多一字节的镜像，验证 runner
或 QEMU 明确拒绝，不允许错误产物进入正常启动判定。

### 8.3 入口覆盖 reset vector

这类错误由链接脚本 `ASSERT` 在构建期阻止，比运行时观察不可达代码更可靠。

## 9. 调试方法

如果没有串口输出，按顺序检查：

1. ROM 是否正好 131072 字节。
2. offset `0x1FFF0` 是否为 `E9 0D F0`。
3. QEMU 是否使用项目 ROM，而非默认固件。
4. GDB 中 `RIP/CS` 是否从 `0xFFFFFFF0` 到 `0xFFFFF000`。
5. `SP` 是否建立在 `0x7000`。
6. `DX` 是否为预期 COM1 端口。
7. LSR 的 THRE 位是否出现。

不要先在每条指令后加串口打印：串口本身正是待验证机制。

## 11. 实验

### 实验 A：手算跳转

不看源码重新计算 `E9` 的 16 位位移，并在 ROM 二进制中找到三个字节。

### 实验 B：串口配置表

列出初始化过程中每次 `OUT` 的端口、值、DLAB 状态和目的。说明如果忘记清 DLAB，
后续向 `0x3F8` 写入会发生什么。

### 实验 C：超时预算

只在学习分支中调小轮询预算，观察成功平台何时开始失败。实验后恢复，不能用无限
轮询“修复”不稳定。

### 实验 D：链接断言

临时扩大入口 section 使其碰到 `0xFFFFFFF0`，确认链接期失败信息，再恢复。
