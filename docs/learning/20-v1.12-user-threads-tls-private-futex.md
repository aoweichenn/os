# v1.12：用户 Thread、FS-base TLS 与 private futex

> 对应实现：ABI `thread.hpp` 与系统调用 47--53，Kernel
> `process/thread_scheduler.*`、`process/process_runtime.*`、

> `synchronization.*` 与 `programs/thread_probe.cpp`。

## 1. 为什么已有多进程还不等于支持线程

Process 是资源容器，Thread 是 CPU 可以调度的执行流。两个 Process 可以有
相同虚拟地址但不同页表；同一 Process 的多个 Thread 则共享页表、fd 和 cwd，
同时必须拥有不同的寄存器、栈与 TLS。

```text
Process
├─ AddressSpace / VMA / CR3
├─ FileTable / FileDescription references
├─ FsContext / cwd
├─ ProcessTree identity and exit status
└─ Thread list
   ├─ TID + general/FXSAVE context
   ├─ KernelStack + user stack
   ├─ FS-base TLS
   ├─ signal mask reservation
   └─ run queue or WaitQueue relation
```

若调度器仍把 Process 当执行实体，加入第二个用户栈只会制造两个无法独立保存
现场的入口。v1.2 已经完成结构分离；v1.12 才把该边界开放给 Ring 3。

历史上 Unix 早期主要以进程表达并发，线程库后来需要在共享地址空间与独立
执行现场之间建立契约。Linux 最终让可调度实体共享或不共享不同资源集合。
本项目不复制完整 Linux clone flags，而是先冻结教学上最小、可证明的集合。

## 2. Thread 创建到底创建了什么

用户 `Thread::Create` 先通过自研匿名 VMA 建立 68 KiB 保留区：

```text
low address
  4 KiB unmapped guard
  64 KiB readable/writable, non-executable stack
high address

separate 4 KiB readable/writable, non-executable TLS page
```

向下增长的栈越过底部会先命中 guard。初始 RSP 位于栈顶减 8 字节，使函数入口
满足 System V x86-64 的 `RSP mod 16 == 8` 约束；该 8 字节槽写入零返回地址，
但线程入口被标为 noreturn，正常路径最终调用 `ExitThread`。

Kernel 不相信请求中的任何地址。它验证：

- entry 在用户程序窗口内，VMA 可执行且不可写；
- stack base/page size 对齐，区间无溢出；
- stack VMA 是匿名、可读写、不可执行；
- RSP 精确等于 stack end - 8；
- TLS base 16 字节对齐且可写；
- 新栈/TLS 不与同 Process 的活动 Thread 重叠。

随后准备 KernelStack、ThreadEntry、UserContext 和干净 FXSAVE 区。只有所有
字段完成后才恢复中断，让 Ready Thread 可以被 PIT 选中。这叫“准备后发布”。

### 创建返回前子线程可以先运行

Create 系统调用把新 Thread 放进 ready queue。当前 Thread 仍在 Kernel 中，
但恢复中断后的任一 tick 都可能先运行新 Thread。因此父 Thread 不能假定：

```text
Create returns to parent
  → parent writes child TLS
  → child starts
```

真实顺序也可能是：

```text
Kernel publishes child
  → timer selects child
  → child starts
  → parent has not returned
```

所以子入口自行调用 `GetThreadId` 并写自己的 `ThreadRuntimeState`。父线程只
保存用于 Join 的 TID，不写子 TLS 的身份字段。

## 3. 为什么 TLS 需要一个专门的 CPU base

全局变量被同 Process 所有 Thread 共享。错误号、当前 Thread runtime、
allocator cache 等状态若也放全局，就会互相覆盖。TLS 需要让相同机器指令在
不同 Thread 中解析到不同地址。

x86-64 长模式弱化了传统分段，但保留 FS/GS base。有效地址可以写成：

```text
linear address = IA32_FS_BASE + instruction offset
```

本项目把 `ThreadRuntimeState* self` 放在 offset 0：

```cpp
ThreadRuntimeState *state;
asm("mov state, qword ptr fs:[0]");
```

每次调度切换都恢复目标 Thread 的 IA32_FS_BASE。Kernel 的 CpuLocal 与可信
系统调用入口继续使用 GS/SWAPGS；用户 TLS 使用 FS，职责清晰且互不覆盖。

### 为什么不能在系统调用入口写 FS selector

传统保护模式常在切到 Kernel 时执行：

```asm
mov fs, kernel_data_selector
```

在本项目开始使用 FS-base TLS 后，这条历史习惯会破坏隐藏 base：第一次系统
调用可能把 FS base 重置到描述符 base 0。Kernel 本身不需要 FS，所以入口只
切换 DS/ES；Thread 真正切换时由 C++ 架构包装写 IA32_FS_BASE。

这也是“历史包袱不能机械搬进 64 位模式”的实例：selector 与 base 在长模式
里的职责已不同。

## 4. 为什么 mutex 不能只用原子循环

最小自旋锁可以不断 compare-exchange：

```text
while (!CAS(0 → 1)) {
    retry
}
```

在单 vCPU 上，持锁 Thread 若被抢占，等待 Thread 会浪费整个时间片，直到持锁
者再次运行。竞争持续时，系统看似“CPU 很忙”，实际没有任何工作前进。

理想用户 mutex 分两条路径：

```text
uncontended:
  CAS 0 → 1
  success, no syscall

contended:
  observe 1
  futex_wait(word, expected=1)
  wake and retry CAS
```

unlock 用 release store 写 0，再 wake one。原子操作负责内存顺序，futex
只负责睡眠和唤醒；Kernel 不替用户理解 mutex ownership。

## 5. 丢失唤醒窗口从哪里来

若 wait 分成两个不原子的动作：

```text
waiter reads value == expected
                         waker changes value and wakes nobody
waiter enters queue
```

waiter 会永久睡眠。正确实现必须把“最后一次比较”和“进入等待队列”放在 wake
无法穿过的同一个临界区。

本项目在 irq-save 调度器锁内重新复制 32 位用户 word，然后 Acquire futex
entry 并调用 `BlockCurrentThread`。wake 也持同一锁。于是只可能：

1. wake 先完成，wait 的二次比较看到值已改变；
2. wait 先入队，wake 找到它；
3. 两者没有并发，因为单 BSP 临界区关闭中断。

第一次锁外读取仍有价值：它先验证用户页可访问并触发合法按需 fault，避免在
调度器锁内处理缺页。锁内第二次读取才决定是否睡眠。

## 6. futex key 为什么包含 AddressSpaceId

两个 Process 常把堆映射在相同 VA：

```text
Process A: 0x60001000 → frame X
Process B: 0x60001000 → frame Y
```

若 key 只有 VA，A 的 unlock 会唤醒 B。若 key 使用物理地址，又会遇到：

- 尚未 fault 的匿名 VMA 没有 frame；
- fork COW 后父子暂时共享 frame，但 private futex 不能跨 Process；
- 写 fault 会替换 frame；
- unmap/remap 后旧物理身份失效。

因此 key 是 `(AddressSpaceId, aligned VA)`。AddressSpaceId 在 load/fork 时
单调分配，不等于 CR3 frame，也不因槽位复用而复用。

地址按 4 字节对齐，因为 futex word 固定为 `uint32_t`。这不是依赖平台的
`unsigned long`；ABI 的位宽和对齐都是显式契约。

## 7. PrivateFutexManager 怎样管理等待队列

管理器拥有 512 个固定上界 entry：

```text
entry
├─ active
├─ AddressSpaceId
├─ aligned user VA
└─ WaitQueue
```

第一个 waiter Acquire 空 entry 并初始化唯一 queue id；同 key 后续 waiter
复用。wake 或 cancellation 清空队列后调用 `ReleaseIfEmpty`，Reset WaitQueue
并归还 entry。若 waiter 仍在，释放必须明确返回 `WaitersRemain`。

固定上界不是能力退化，而是当前无动态分配热路径下的可证明资源规格。容量
耗尽返回 `FUTEX_LIMIT_EXCEEDED`，用户同步原语把它当失败，不悄悄忙等。

## 8. ConditionVariable 为什么使用序列号

条件变量不保存“条件是否成立”；条件由调用者在 mutex 保护下维护。条件变量
只保存一个 32 位序列：

```text
wait:
  observed = sequence
  unlock mutex
  futex_wait(&sequence, observed)
  lock mutex
  recheck caller predicate

notify:
  sequence += 1 (release)
  futex_wake(...)
```

若 notify 发生在 unlock 与 wait 系统调用之间，Kernel 二次比较发现 sequence
已变化，返回 `FUTEX_VALUE_CHANGED`，waiter 重新加锁并检查条件，不会睡过
通知。

`NotifyAll` 使用 `UINT64_MAX` 表示唤醒当前 entry 的全部 waiter。序列号允许
自然回绕；正确性依赖调用者循环检查 predicate，而不是把一次序列变化当作
永久状态。

## 9. Once 为什么需要三态

Once 的状态为：

| 值 | 意义 |
| ---: | --- |
| 0 | 尚未开始 |
| 1 | 某个 Thread 正在执行 |
| 2 | 已完成并以 release 发布结果 |

唯一 CAS 0→1 成功者执行函数，完成后 store 2 并 wake all。看到 1 的 Thread
等待；看到 2 的 Thread 直接返回。若只用 bool，“正在初始化”与“已经完成”
无法区分，竞争者可能读取尚未发布的数据。

本阶段初始化函数没有异常和取消语义。若执行者永不返回，其他 Thread 继续
等待；robust once 属于后续扩展。

## 10. ThreadExit、Join 与 ProcessExit 的所有权

普通 ThreadExit 不能关闭 FileTable，因为其他 Thread 仍在使用它。它只：

```text
save exit value
mark current Thread Exited
wake ThreadJoin waiters
schedule another Thread
```

Join 成功后 Kernel 销毁目标 KernelStack 并 Reap Thread 槽；用户运行库再
撤销目标 64 KiB 栈和 TLS 页。这个次序保证 Kernel 不再引用用户现场后才释放
用户映射。

ProcessExit 更强：

```text
cancel all futex waiters
terminate Ready/Blocked siblings
close shared descriptors and FsContext
publish ProcessTree Zombie
destroy AddressSpace
parent wait reaps all Thread stacks and Process
```

Blocked sibling 必须先从原 WaitQueue 删除，并把这次取消记入 queue/thread/
scheduler wake 账本；否则队列表面为空，`enqueue - wake` 却仍为 1，资源
验证会发现矛盾。

最后一个 Thread 调用 ThreadExit 时，Process 已无其他执行者，路径自然提升为
Process 退出。

## 11. 多线程 exec 为什么要终止 sibling

exec 替换整个 AddressSpace，而 sibling 的 RIP/RSP/TLS 都指向旧映像。不能
只替换调用 Thread 的 CR3 后让 sibling 继续运行。

本阶段顺序：

1. 在独立候选 AddressSpace 中读取、验证、映射 ELF 和用户栈；
2. 激活候选页表做硬件可用性探针，再回旧页表；
3. 取消旧 AddressSpaceId 的 futex wait；
4. 终止并回收所有 sibling；
5. 提交调用 Thread 的新 CR3/RSP，FS base 清零；
6. 销毁旧地址空间。

步骤 1 或 2 失败时不触碰 sibling。步骤 3 以后若内部守恒失败，旧 Thread 集合
已不可安全恢复，Kernel 停机而不伪装普通 exec 错误。

fork 的语义不同：它只复制调用 Thread，child 从返回值 0 继续，不复制其他
Thread 的栈与等待关系。这与现代类 Unix 系统的基础行为一致，也保持当前
资源事务可证明。

## 12. unmap 为什么必须理解 Thread 与 futex

如果 Thread A 在地址 X 上 futex wait，Thread B 直接 unmap X：

- waiter 留在 Kernel queue；
- 以后 wake 无法安全访问或解释旧地址；
- 同 VA 重新映射后可能错误接收旧 wake。

所以成功 unmap 后按 AddressSpaceId 和范围取消对应 entry，把 waiter 返回值
写为 `WAIT_CANCELLED`。同时任何活动 Thread 的 stack/TLS 不能被 unmap；
否则下次中断返回、函数调用或 FS 访问会落入已释放地址。

用户运行库的 Join 在 Kernel Reap 之后撤销已退出 Thread 的映射，因此不会被
活动区间检查拒绝。

## 14. 测试怎样证明没有丢失唤醒

### 单元

- 同 VA、不同 AddressSpaceId 得到不同 entry；
- 重复 key 复用同一 WaitQueue；
- waiter 未清空时 entry 不能释放；
- 4-entry 小容量耗尽返回明确状态；
- Process 退出同时处理一个 Blocked、一个 Running 和一个 Ready Thread；
- 更新 TLS 后按 TID 查找仍得到同一 Thread。

### 固定种子随机

private futex 模型在 8 个 AddressSpaceId × 8 个 VA 上执行 100000 步
Acquire、复用、Release 和周期 Validate；最终 acquire/release 守恒。
调度器的既有 100000 步随机模型继续覆盖 WaitQueue 状态迁移。

### QEMU

thread probe 先尽可能创建 worker：

- bootstrap 创建 0 个，证明上限 1；
- functional 创建 31 个，main 合计 32；
- capacity 创建 63 个，main 合计 64，并额外尝试一次确认拒绝。

所有 worker 在 mutex 保护下报告 ready，通过 condition variable barrier 后
竞争 once 和共享计数。每个 worker 执行 32 次临界区递增并在结束前再次检查
FS:0/TID。main Join 每个 TID并核对独立 64 位退出值。

成功标记：

```text
FUNCTIONAL_32_READY 或 CAPACITY_64_READY
TLS_ISOLATED
FUTEX_SYNCHRONIZATION_VERIFIED
JOIN_RECLAIMED
COMPLETED
```

Kernel 只在计数到二次幂时记录 Thread/Futex 进度。QEMU 捕获器再给每行添加
宿主到达时间，既能定位停顿，又不让 Kernel 在热路径刷日志。

## 15. 本阶段明确没有实现什么

- 只有一个 BSP/vCPU 调度域，没有 SMP 与跨核 memory ordering 验收；
- futex 只有 private wait/wake，没有 timeout、requeue、PI 或 robust list；
- Thread 必须 Join，没有 detach；
- 没有异步 signal、取消点和清理 handler；
- 没有 pthread 或 libc 兼容层；
- ConditionVariable 需要调用者循环检查 predicate；
- FS-base TLS 是项目运行时布局，不是 ELF `PT_TLS` 动态装载 ABI。

这些不是隐藏缺陷，而是 v1.13 单调时间/deadline、v1.14 signal 和后续运行时
演进的输入。
