# v1.6：从扇区到稀疏文件、三级间接树与完整命名空间

## 1. 本阶段解决什么缺口

v1.5 已经回答“路径属于谁、挂载如何跨后端、cwd 如何表示”，但生产根仍是
v0.11 的教学小格式。它能证明持久化闭环，却不能承载后续从磁盘加载程序：
5120 字节单文件太小，没有删除和重命名，Kernel 还同时承担 mount 与 format。

v1.6 的任务不是把 Linux 文件系统整体复制进来，而是先建立一条完整、可画出
每个字节和失败点的持久对象链：

```text
用户路径
  -> VFS 父目录与末组件
  -> inode / directory entry
  -> logical block
  -> direct or indirect pointer
  -> rootfs relative block
  -> ATA LBA
  -> QEMU IDE disk sector
```

完成本章后，应能解释：

1. 为什么盘面不能直接保存 C++ struct；
2. inode、目录项、bitmap 和数据块分别回答什么问题；
3. direct/single/double/triple 如何把逻辑块号拆成索引；
4. 空洞为何不等于一串真实零块；
5. unlink、rename 和 open reference 为什么会产生生命周期冲突；
6. Dirty/Clean 能检测什么，又为什么还不是 journal；
7. 内核 Validate 与独立 fsck 为什么必须是两份实现；
8. 如何用真实近满 256 MiB 格式证明短写和 ENOSPC。

## 2. 从硬件扇区到文件系统块

当前 QEMU `pc` 机器提供传统 IDE/ATA 设备。Kernel 的 ATA PIO 驱动向命令块
端口写入 LBA 和命令，轮询 STATUS 的 BSY/DRQ/ERR/DF，再通过 16 位 DATA
端口搬运一个 512 字节扇区。QEMU 只实现设备电气/寄存器行为；它不知道
`inode`、文件名或目录。

rootfs 选择 512 字节块，恰好对应一个 ATA 扇区。因此相对块 `r` 的设备
LBA 是：

```text
LBA = 2048 + r
```

这不是说文件系统块永远必须等于硬件扇区。现代磁盘可能使用 4 KiB 物理扇区，
文件系统也常用 4 KiB 块；本阶段选择 512 是为了让每次读写与已有驱动一一
对应，减少教学阶段的 read-modify-write 维度。

启动盘的逻辑长度是 1 GiB，但宿主文件采用 sparse 表示。文件尾的 offset
存在，不等于中间每个字节都占用宿主物理块。QEMU 看到的是完整 LBA 空间；
宿主文件系统可以把尚未写入的范围表示为 hole 并在读取时返回零。

## 3. 为什么需要盘面格式

断电后 C++ 对象、指针和 vtable 都不存在。磁盘必须只保存跨启动仍有意义的
事实：

- 格式版本和区域边界；
- 哪些 inode/data block 已分配；
- 每个 inode 的类型、大小、代次、父与块树；
- 目录中的名字到 inode 身份映射；
- 哪些事务完整结束；
- 对象是否被意外改写。

C++ struct 不能直接写盘，原因包括 padding、enum 底层宽度、编译器布局和
字节序。v1.6 的 encoder/decoder 因而逐字段读写 little-endian `uint64_t`/
`uint32_t`，先把保留区清零，再计算 CRC32。这样 Python 可以在完全不加载
Kernel 代码的情况下读出同一介质。

## 4. 256 MiB 区域如何分割

当前 rootfs 从 LBA 32768 开始，包含 524288 块。v1.6 首次实现时曾使用
LBA 2048，v1.9 因启动载荷增长迁移并由布局契约统一：

| 相对块 | 字节范围 | 作用 |
| --- | --- | --- |
| 0 | 0..511 | superblock |
| 1..2 | 512..1535 | inode bitmap |
| 3..4098 | 1536..2098687 | inode table |
| 4099..4226 | 2098688..2164223 | data bitmap |
| 4227..524287 | 2164224..268435455 | 数据和 pointer block |

8192 个 inode 每个 256 字节，恰好占 4096 块。data bitmap 的每一位对应
data 区的一个相对索引；128 块 bitmap 能描述 524288 位，略多于实际 data
block 数，多余位必须保持未分配且不允许成为指针目标。

superblock 不只保存这些数值，还验证它们必须等于冻结布局。自描述字段的价值
是让检查器能解释镜像和未来迁移工具能识别版本；严格匹配的价值是防止损坏
字段把 inode table 指向启动代码或盘外。

## 5. inode 与名字为何分离

目录项保存“某个父目录下，这个名字指向哪个 inode”；inode 保存“对象本身
是什么、内容在哪里”。分离之后，rename 只需改变名字边，而文件数据身份可以
保持不变。

Unix 从早期就采用这种思路。名字不属于 inode 本身，所以一个 inode 理论上
可以有多个硬链接。v1.6 暂不实现硬链接，根以外活动 inode 恰有一条目录边，
link count 固定为一；该限制让 fsck 可以把重复引用直接判为损坏。

generation 解决 inode number 复用问题：删除 inode 7 后，未来新文件仍可能
使用编号 7，但 generation 必须不同。目录项、vnode 与 stat 都携带代次，
旧身份不能只凭相同编号误命中新对象。

## 6. 四级块树的寻址公式

每个 inode 有 `D=8` 个 direct 指针；每个 pointer block 有 `P=63` 个指针。
给定逻辑块号 `L`：

```text
if L < D:
    direct[L]
else:
    L -= D
    if L < P:
        single[L]
    else:
        L -= P
        if L < P*P:
            double[L / P][L % P]
        else:
            L -= P*P
            triple[L / (P*P)][(L / P) % P][L % P]
```

单个 pointer block 不能使用全部 64 个 64 位槽，因为块尾还要保存 checksum
和规范保留字节，所以 `P=63`。树的理论数据块覆盖为：

```text
8 + 63 + 63² + 63³ = 254087 blocks
```

理论字节数超过 64 MiB，但公开规格主动冻结为 67108864 字节。上限应由稳定
产品契约决定，不应把当前内部结构“刚好能走多远”误当成 ABI。

小文件只使用 direct，不支付 pointer block；大文件按需逐层增加元数据。
这也是 Unix 传统设计的折中：常见小文件便宜，少数大文件仍可寻址。

## 7. 稀疏文件不是压缩

稀疏文件的某些逻辑块没有物理块。它不是把零运行编码压缩，也不扫描数据内容；
即使用户本来想写全零，写过的范围仍通常拥有真实块。只有未分配指针才是 hole。

读 hole 时 Kernel 直接清零目标缓冲。这样既不访问设备，也不会泄露刚释放块
中的旧内容。truncate 扩展只增加 size，新增范围自然是 hole；越过文件尾写入
只为目标范围建树，中间距离不分配。

`stat.size_bytes` 表示逻辑长度，`stat.allocated_size_bytes` 表示数据块与
间接元数据块实际占用。两者不同不是错误，而是稀疏性证据。

## 8. truncate 为何比“改 size”复杂

扩展可以只改 size；缩小必须回收所有已经不可达的块。若新尾落在某个保留
数据块中，还必须把尾后字节清零：否则文件将来再次扩展时可能读到旧内容。

对三级树逐个扫描全部理论叶会浪费时间。实现给每棵子树计算其覆盖的逻辑块
区间：

- 与释放范围不相交：立即返回；
- 整棵树都应释放：递归释放已存在分支；
- 部分相交：只进入相关子节点；
- 子 pointer block 已全零：释放它并把父指针清零。

测试从 64 MiB 文件缩到不同边界，再缩到零，核对数据/元数据计数与 bitmap
全部回到预期。

## 9. 创建、删除和 rename 的状态变化

创建需要同时改变 inode bitmap、inode table、父目录数据和可能的 data
bitmap。若最后一步才发现没有目录槽，前面已经发布的 inode 就会成为 orphan。
因此操作先检查参数和容量，再进入事务。

删除反向执行：验证类型、空目录、打开引用和目录边，再清除目录项、释放树、
释放 inode。v1.6 不允许删除已打开文件，因为“名字消失、内容继续存活”需要
持久 orphan 状态；当前返回 Busy，把尚未实现的语义明确暴露。

rename 的难点不是复制字符，而是不变量组合：

- source 可能与 destination 同名；
- destination 可能不存在或需要替换；
- 替换对象可能是非空目录或正在打开；
- source 目录可能被移动到自己的子孙；
- 两个父目录可能不同；
- 两条路径可能跨 mount。

VFS 负责跨 mount 规则，后端在一个事务中修改两边目录。移动目录后更新其
parent inode；检测环时从 destination parent 一直向根追踪，遇到 source
立即拒绝。

## 10. Dirty/Clean 时间线

一个修改事务按以下时间线运行：

```text
T0  disk is Clean generation N
T1  write Dirty generation N; flush
T2  write data, pointer blocks, inode, directory, bitmap
T3  flush every dirty block and ATA cache
T4  write Clean generation N+1; flush
```

若调用在 T4 后成功返回，介质是完整新状态。若设备在 T1..T3 失败，下次挂载
会看到 Dirty 并拒绝。这个方案防止“半个事务被误当成正常”，但不能把磁盘
自动恢复到 T0 或 T4，因此不是 journal。

journal 需要先记录能重放的元数据、预留日志空间、写 commit record，再按
规则 checkpoint；启动时还要幂等 replay。v1.6 有意把它留作后续阶段，让
当前每个失败边界都能单独理解。

## 11. fsck 怎样建立第二个 oracle

Kernel 的 `Validate` 从根 inode 开始遍历目录和块树，在内存中重建两张
bitmap。独立 Python fsck 做同样的数学检查，但使用另一份解析和遍历代码：

1. 解码并验证 Clean superblock；
2. 读取 inode bitmap；
3. 从根开始遍历目录；
4. 验证 directory entry generation/type；
5. 遍历 direct/single/double/triple 并拒绝重复块；
6. 核对 inode 的 allocated counts；
7. 比较重建 bitmap 与盘面 bitmap；
8. 拒绝不可达 inode、非法父链、CRC 或保留字节。

如果工具直接调用 Kernel 的同一函数，一个共同 bug 可能同时得出“正确”。
两份独立实现加上共同盘面规范，才形成有意义的交叉验证。

## 12. 测试为什么必须包含真实近满格式

把 data block 常量在测试版本里缩成 16，只能证明小模型，不足以证明真实
bitmap 边界、三级树和 256 MiB 布局。容量测试因此直接构造完整格式：

- 四个 reservoir 文件拥有大量 direct/indirect 树；
- 只留下约八个可分配块；
- 目标文件请求跨多个块写入；
- 第一次只能完成前缀，形成真实 short write；
- 第二次一个字节也无法分配，返回 ENOSPC；
- 文件大小、free count 和 short-write count 精确核对；
- Kernel Validate 与独立格式规则继续一致。

宿主块设备只为实际写入块保存内存页，因此测试不会为了模拟 256 MiB 而真的
建立一个等大连续数组。

随机测试则让 memfs 与 rootfs 使用同一种子执行 100000 步。二者的存储机制
完全不同，若路径、rename、truncate 或错误语义不一致，会在精确步骤直接
报告。单元、容量、随机和 QEMU 分别回答不同问题，不能互相替代。

## 13. 从 Shell 走读到磁盘

以 `mv /a /dir/b` 为例：

1. Shell parser 识别 `mv` 并取得两个非终止依赖的字节切片；
2. 用户包装器把 source address/length 放入系统调用参数；
3. 原生 SYSCALL 入口保存统一 UserContext，第四参数规则仍使用 `r10`；
4. Kernel 验证两段用户地址并复制到有界内核缓冲；
5. ProcessRuntime 从当前 Process 取得 FsContext；
6. VFS 分别解析两个 parent 和 final component；
7. VFS 检查 mount、根、挂载点与跨设备边界；
8. RootFileSystem 取得锁，开始 Dirty 事务；
9. 后端验证 source/destination、类型、打开引用与祖先环；
10. 修改目录项和可选 parent inode，sync 后提交 Clean；
11. 结果经 UserContext 返回 Ring 3；
12. 后续 `stat`/`ls` 重新解析对象，观察新名字。

整个过程中 QEMU 没有替项目处理路径或文件系统；它只响应 CPU 指令、端口 I/O
和磁盘扇区访问。

## 15. 可重复实验

构建并检查镜像：

```bash
python3 tools/os.py build
python3 tools/os.py inspect-rootfs build/developer/images/boot_disk.img
python3 tools/os.py fsck-rootfs build/developer/images/boot_disk.img
```

只运行 rootfs 直接证据：

```bash
ctest --test-dir build/developer \
  -R 'root_file_system|vfs_namespace_randomized' \
  --output-on-failure
```

复制镜像后注入损坏，不要破坏原构建产物：

```bash
cp --sparse=always build/developer/images/boot_disk.img /tmp/rootfs-lab.img
python3 tools/os.py corrupt-rootfs /tmp/rootfs-lab.img root-inode-checksum
python3 tools/os.py fsck-rootfs /tmp/rootfs-lab.img
```

最后运行完整验证：

```bash
python3 tools/os.py verify
```

预期损坏实验中的 fsck 失败是成功证据；脚本和 QEMU 都必须有明确超时，不能
把“进程仍在运行”解释为系统正确。
