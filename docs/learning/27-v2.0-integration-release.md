# v2.0：把冻结实现变成可复现发布

## 1. 为什么“功能都写完了”仍然不是发布

开发版本回答“这个机制能否工作”，正式版本还要回答另外三个问题：

1. 哪一份源码被验证过？
2. 哪一组二进制、文档和教材由这份源码产生？
3. 另一位读者能否取得相同输入并重复得到相同结论？

如果只保存一段成功启动的串口日志，就无法判断日志来自当前源码还是前一版
镜像；如果只给出 Git 标签，就无法证明教材 PDF、网站代码目录和公开下载件
也来自这个标签；如果只运行正常启动，就无法证明损坏镜像、缺失 CPU 特性和
用户畸形输入仍按冻结语义失败。

v2.0 因此没有新增系统调用、驱动或文件系统格式。它把 v1.1 至 v1.18 已经
分别建立的局部证据，提升为一个具有精确身份、完整测试矩阵和公开交付物的
整体证据。

## 2. 版本号、ABI 版本和盘面版本不是一件事

项目同时存在三类版本：

| 版本 | 当前值 | 变化条件 |
| --- | --- | --- |
| 项目发布版本 | 2.0.0 | 整个产品进入新的公开基线 |
| 用户 ABI 版本 | 2.0.0 | syscall、错误值或跨 Ring 结构兼容边界变化 |
| rootfs 盘面格式 | 3 | superblock、inode、journal 等持久字节布局变化 |

这三个数字恰好都接近 2，并不表示它们必须同步增加。v2.0 只把 CMake 项目
版本从 1.18.0 提升到 2.0.0；ABI 和 rootfs 都保持 v1.18 已冻结的值。若为了
“让数字看起来一致”修改 ABI 常量或盘面 magic，就会把纯集成发布变成新的
兼容性开发阶段。

这种分离在成熟系统中很常见：软件包版本描述一组交付物，系统调用 ABI 描述
内核与用户程序之间的线协议，文件系统版本描述磁盘上的持久协议。三者有不同
消费者、不同生命周期，也必须有不同升级条件。

## 3. 冻结的含义

冻结不是“不再阅读代码”，也不是“发现问题后保持沉默”。它表示：

- 不再扩大承诺范围；
- 继续审计现有承诺是否真的成立；
- 发现会破坏当前承诺的缺陷时，在发布前修正并重跑证据；
- 新想法进入 v2.x 的 ADR 和路线，不混入 v2.0；
- 发布后若需要破坏 ABI 或持久格式，显式提升对应版本。

v1.18 的最后审计曾用真实 QEMU 命令发现 `dirname` 没有折叠重复 `/`。这是
已经承诺的路径语义缺陷，必须在冻结期修复。相反，加入 SMP、网络或动态链接
会扩大承诺和测试组合，必须留给后续独立阶段。

## 4. 一次发布包含哪些对象

本项目的发布不是一个压缩包，而是四个相互引用的对象：

```text
主工程 Git commit
  ├─ 目标 ELF、ROM、Stage 1、Kernel、rootfs 镜像
  ├─ 173 项测试与 QEMU 验收结果
  └─ LaTeX 书稿 ──> PDF ──> 手机副本
           │
           └─ 主仓 SHA + PDF SHA-256
                         ↓
独立 web Git commit ──> Sites 保存版本 ──> 生产部署
```

主工程和网站必须使用独立仓库。否则网站自身的 TypeScript、生成目录和部署包
会污染“目标系统真实代码量”，网站代码浏览器也可能意外公开自己的实现。
网站同步脚本只读取已经推送且工作树干净的主仓提交，再生成代码目录和发布
清单。

### 4.1 为什么既需要 Git SHA，又需要文件哈希

Git commit SHA 标识一棵源码树和历史父节点，适合证明“哪份源码”。PDF
SHA-256 标识最终字节，适合证明“哪份导出物”。同一书稿可能因字体、TeX
版本或构建环境产生不同 PDF，所以不能用主仓 SHA 代替 PDF 哈希。

手机导出后再次计算 SHA-256，要求它与书稿构建目录中的 PDF 完全相同。
复制成功但字节不同必须视为交付失败。

### 4.2 为什么网站需要自己的 commit

网站包含由主仓生成的代码索引、版本清单和 PDF。即使主仓不变，代码浏览器
实现、路由或样式仍可能变化，因此网站必须有独立身份。Sites 保存版本同时
记录这个 web commit 和由该提交构建的归档，部署只能引用已经保存的版本。

## 5. 三档机器不是同一个测试重复三次

三档 QEMU 配置分别回答不同问题：

| 配置 | RAM | 主要问题 |
| --- | ---: | --- |
| bootstrap | 64 MiB | 最低内存下复位、启动链、异常和历史失败路径能否成立 |
| functional | 256 MiB | PID1、Shell、32 工具、VM、I/O、信号、TTY 是否完整组合 |
| capacity | 64 GiB | 动态容量、256 Process、512 Thread 与 4 GiB 以上物理页是否真实工作 |

如果只跑 64 GiB，宽松内存会掩盖小内存分配和回滚错误；如果只跑 64 MiB，
又无法证明直接映射、页帧元数据和地址计算越过 32 位边界。capacity 用例必须
实际在 4 GiB 以上分配、写入、读回并释放物理页，不能只检查配置字符串。

functional 也不是 bootstrap 的“大内存版”。它通过真实 PS/2 输入让外部
Shell 执行工具、重定向、16 级流水线、作业控制和 procfs 读取，从而证明
不同模块通过冻结 ABI 组合。

## 6. 测试图为什么必须分层

v2.0 的 173 项 CTest 分为五类：

- 单元测试：检查布局、状态转换、范围和错误返回；
- 模块集成测试：检查两个或多个所有权边界的交接；
- 固定种子随机测试：以独立模型检查十万步不变量；
- 目标产物测试：读取实际 ELF、ROM、镜像和符号表；
- QEMU 系统测试：执行真实 x86-64 指令、页表、中断和设备协议。

单元测试通过不能证明 NASM 入口和链接脚本正确；QEMU 启动成功也不能穷举
十万步状态转换。不同层次使用不同 oracle，避免实现和测试共享同一个错误。

### 6.1 为什么宿主测试并行、QEMU 串行

纯宿主测试可以充分使用 caw 的 CPU。24 项 QEMU 测试则共享 TCG 算力和来宾
内存；若同时启动多个实例，故障用例的 10 秒墙钟超时可能因资源争抢而误报。
CTest 的资源锁把“同一时刻只运行一项 QEMU”写入测试图，调用者即使使用
`--parallel 20` 也不会破坏该约束。

这不是把所有测试改为串行。149 项宿主测试仍并行运行，只有共享稀缺资源的
系统测试串行。资源约束属于测试设计，不应依赖执行者记忆。

### 6.2 超时为什么必须有边界

操作系统测试可能因 lost wakeup、IRQ 未送达、QEMU 退出路径或 SSH 传输永久
等待。每条远端命令都必须有有限 timeout；QEMU runner 还要在超时后保存串口
尾部和缺失 marker。超时只终止本次验证创建的进程，不能扫描或停止验证机上
其他用户的任务。

## 7. 精确源码怎样进入 caw

验证流程使用唯一临时目录，不在共享工作目录上直接构建：

1. 从当前工作树生成源码归档；
2. 本地计算 SHA-256；
3. 传输到 caw 的唯一 `/tmp/aoweichen-os-*` 目录；
4. 远端重新计算 SHA-256，必须逐字节相同；
5. 在空构建目录中配置和编译；
6. 运行完整 CTest 和三档 QEMU；
7. 记录编译器、QEMU、CPU、内存、耗时和结果；
8. 只清理本次验证拥有的临时状态。

若 SCP 因链路停滞超过边界，流程会取消该传输并从已经确认的字节偏移继续，
最终仍以完整归档 SHA-256 为准。传输“看起来完成”不是证据。

## 8. 目标产物为什么仍要独立审计

C++ 编译与链接成功只证明宿主工具接受输入，不证明目标没有偷偷依赖宿主
运行时。产物测试必须检查：

- Kernel 与用户程序都是 AMD64 `ET_EXEC`；
- `PT_LOAD` 权限满足 W^X，地址和对齐位于冻结窗口；
- 没有 libc、libstdc++、异常、RTTI、构造器或未解析运行时符号；
- 用户 ELF 真实写入 rootfs，32 个工具拥有独立 inode；
- ROM 复位向量、Stage 1 描述符、Kernel 容器和 CRC 与构建图一致；
- ABI 结构大小、对齐和 offset 与共享头文件一致。

这层检查直接读取最终字节，能够发现“源码看起来正确、链接产物却改变”的
问题。

## 9. 教材和网站怎样成为测试对象

文档不是发布完成后的宣传材料。LaTeX 构建会检查：

- 所有 `\input` 文件存在；
- 章节数量和图资源满足结构约束；
- 没有未定义引用、重复标签或构建失败；
- 生产代码统计只扫描 `source/` 中的 `.cpp`、`.hpp` 和 `.asm`；
- 网站 PDF 与手机 PDF 和最终书稿 PDF 哈希一致。

网站同步测试再交叉检查：

- 项目版本来自根 `CMakeLists.txt`；
- 主仓 SHA 是已经推送的干净 `main`；
- CTest 数、核心文件数和有效代码行与主工程一致；
- 当前发布文档、学习章和关键源码存在于代码目录；
- 网站实现自身没有进入公开代码目录；
- 生产包包含 Worker、路由、预压缩资源和正确托管项目 ID。

部署完成后还要从公网访问首页、架构、路线、文档、代码、教材、sitemap 和
robots。控制面显示 `active` 不能代替真实 HTTP 200；首页能开也不能证明
数百个静态代码路由没有丢失。

## 10. v2.0 的最终不变量

v2.0 接受的不是“功能很多”，而是下面这些关系同时成立：

```text
项目版本 = 2.0.0
ABI 版本 = 2.0.0（保持冻结）
rootfs 格式 = 3（保持冻结）
系统调用数量 = 69
用户工具数量 = 32
CTest = 173/173
QEMU = 24/24
bootstrap + functional + capacity + persistence = 通过
手机 PDF SHA-256 = 网站 PDF SHA-256 = 书稿 PDF SHA-256
网站清单主仓 SHA = 已推送主仓 main
Sites 版本源码 SHA = 已推送 web main
```

任一等式失败，准确状态都只能是“v2.0 发布未完成”。不能把缺少的证据解释为
未来补充，也不能用手工修改网页数字让表面一致。

## 11. 读者实践

完成本节后，应能够独立执行并解释：

1. 说明项目版本、ABI 版本和 rootfs 版本为何独立；
2. 画出主仓、PDF、web 仓和 Sites 版本的身份链；
3. 解释三档 RAM 配置各自排除哪类错误；
4. 从 CTest 标签区分宿主测试与真实 QEMU 测试；
5. 解释为什么 QEMU 资源锁不会降低宿主测试并行度；
6. 对比 Git SHA 与文件 SHA-256 的证明对象；
7. 从生产网站随机选择一个文档路由和一个源码路由，追溯到主仓文件；
8. 提出一个 v2.x 新机制，并说明为何它不能回写 v2.0。

完成这些任务，才算理解“发布”也是操作系统工程的一部分：它把硬件状态、
软件状态、测试结论和学习材料绑定成他人可以复现的事实。
