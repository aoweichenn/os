## 1. 本阶段解决的不是“多几个命令”

v1.10 已能从磁盘执行独立 ELF，也能 fork 出资源视图近似相同的 child。
然而下面这行仍无法表达：

```text
echo hello | cat | wc > /tmp/count
```

它同时要求：

1. 创建一个由 Kernel 拥有的字节流；
2. fork 多个同时存活的 child；
3. 把每个 child 的 fd 0/1 精确接到不同端点；
4. 关闭每个进程不再使用的端点；
5. 从 rootfs exec 独立工具；
6. 在 EOF、短读、失败和退出时回收完整进程图。

所以 v1.11 的学习对象是“资源图如何组合”，不是 Shell 文法表面。真正的验收
也不是屏幕打印了 `hello`，而是动态 pipe、FileDescription、fd、Process、
Thread、VMA、页表和物理页在结束后全部回到基线。

## 2. 为什么 Unix 选择字节流和描述符

早期系统常让每种设备拥有不同调用：终端写字符、磁带读记录、磁盘按块访问。
Unix 的关键抽象是让普通文件、终端和管道都通过小整数 fd 进入 read/write。
这并不表示设备内部相同，而是让程序连接方式相同：

```text
program ──fd 0/read──> input object
program ──fd 1/write─> output object
program ──fd 2/write─> diagnostic object
```

Shell 不需要知道 `cat` 如何读文件，也不需要把 `wc` 链接进自己。它只改变
child 的 fd 图，再让 child exec。`fork` 与 `exec` 分成两个操作的历史价值
正在这里体现：两者之间留下了修改资源关系的窗口。

管道选择无消息边界的字节流也有代价。一次 write 不保证对应一次 read；
消费者必须处理短读，生产者必须处理短写和背压。好处是文本工具、二进制程序
和设备可以复用同一种连续流语义。

## 3. 四层对象不能混为一谈

v1.11 的一条管线同时出现四种“看起来像端点”的对象：

| 层 | 例子 | 所有者 | 何时销毁 |
| --- | --- | --- | --- |
| fd number | child 的 0、1、3 | 单个 Process 的 FileTable | close/exec/exit |
| FileTable entry | handle + fd flags | 单个 FileTable | 对应 fd 删除 |
| FileDescription | reader/writer、status、offset | KernelObject 强引用 | 最后强引用 |
| Pipe | 环形流与缓冲页 | PipeManager slot | 两逻辑端点都关闭 |

duplicate 复制的是 FileTable entry 对 FileDescription 的强引用。它不会复制
Pipe 数据，也不会创建新的独立文件 offset。fork 又克隆整张 FileTable，
所以 parent/child 的 fd 槽独立，但仍可指向同一个 FileDescription。

这解释一个容易写错的场景：

```text
reader fd 3 ─┐
reader fd 7 ─┴─> same reader FileDescription ─> same Pipe
```

关闭 fd 3 不能立刻让 writer 看到 broken pipe；fd 7 仍持有同一个逻辑读端。
只有 reader FileDescription 的最后强引用释放时，finalizer 才真正关闭读端。

## 4. 64 KiB 动态 pipe 怎样占用物理内存

### 4.1 容量不是立即承诺

每条 pipe 的逻辑容量为 65536 字节，分成 16 个 4096 字节页。刚创建时：

```text
capacity = 65536
buffered = 0
allocated pages = 0
```

第一次写入落在哪些页，就只申请哪些页。空的 1024 条 capacity pipe 因而不会
预占 64 MiB 数据区。slot 控制对象使用固定上界，数据页使用真实物理 frame。

### 4.2 环形索引

Pipe 保存：

```text
read_index
write_index
buffered_byte_count
capacity_bytes
```

写入位置按

```text
(write_index + 1) mod capacity
```

推进，读取同理。`buffered` 区分“索引相等且为空”和“索引相等且已满”。可写
字节数始终是 `capacity - buffered`。

跨页地址先计算：

```text
page_index  = byte_index / 4096
page_offset = byte_index % 4096
```

再通过已保存的 direct-map 指针访问目标 byte。Pipe 本身不知道 x86 页表或
buddy；目标 Kernel 的 allocator 回调负责把 frame 转成 direct-map 地址。

### 4.3 多页申请必须先准备后提交

一次 write 可能跨越多个尚未分配的页。若申请到第二页后第三页失败，不能留下
“前两页已经占用，但没有任何字节可见”的半提交。实现记录本次新申请的页；
失败时只归还这些页，原有页、索引和 buffered 均保持不变。

这是小型事务：

```text
discover needed pages
  → allocate and clear each missing page
  → any failure: rollback new pages
  → all ready: copy bytes and advance indexes
```

### 4.4 EOF 与 broken pipe 不是同一状态

| 当前状态 | read | write |
| --- | --- | --- |
| empty，writer open | WouldBlock | 可写 |
| data available | 返回短读或完整读取 | 取决于剩余容量 |
| empty，writer closed | EndOfFile | 不适用 |
| reader closed | 不适用 | BrokenPipe |
| full，reader open | 可读 | WouldBlock |

EOF 不是一个存入缓冲区的特殊字节。它是“未来不再可能产生新数据”的端点
生命周期结论。writer 关闭后，reader 仍必须先排空已有数据，下一次空读才是
EOF。

## 5. PipeManager 为什么是独立模块

旧 `process_pipe` 是启动固定探针，只有一个全局对象。用户 `pipe()` 要求：

- 多条并存；
- 按内存配置选择 slot 上限；
- 创建容量拒绝；
- slot 复用；
- 创建/释放守恒统计；
- 两端 finalizer 共同结束生命周期。

`PipeManager` 因而持有固定的 1024 个 Pipe 存储和 active bitmap。选中的
运行配置只开放前 8、128 或 1024 项。创建先占用 slot，再初始化 Pipe；关闭
任一端后检查是否 fully closed，只有两端都关闭才把 slot 归还。

启动自检把所选 slot 全部创建出来，下一次必须返回 CapacityExhausted，再关闭
全部对象。结束日志同时验证运行期新增管道：

```text
DYNAMIC_PIPE_CAPACITY
DYNAMIC_PIPE_ACTIVE
DYNAMIC_PIPE_PEAK_ACTIVE
DYNAMIC_PIPE_CREATIONS
DYNAMIC_PIPE_RELEASES
DYNAMIC_PIPE_CAPACITY_REJECTIONS
```

热路径不逐次打印，避免 16 级管线把串口刷成调度条件；阶段结束才输出摘要。

## 6. `dup` 与 `dup2` 为什么都需要

普通 duplicate 解决“找一个新 fd”：

```text
duplicate(source=3, minimum=8) → lowest free fd >= 8
```

流水线接线解决“必须成为 fd 0 或 1”：

```text
dup2(pipe_reader, 0)
dup2(pipe_writer, 1)
```

`DuplicateTo` 的事务顺序是：

1. 在锁内确认 source 存在、destination 合法；
2. 若 destination 所在 chunk 不存在，锁外准备 chunk；
3. 重新加锁并复验 source；
4. 为 source FileDescription 取得新强引用；
5. 原子替换 destination entry；
6. 解锁后释放旧 destination handle。

旧对象的 finalizer 可能关闭 pipe、VFS 文件或唤醒线程，不能在 FileTable 锁内
执行。新引用获取失败发生在提交前，此时 destination 保持不变；若替换提交后
旧对象 finalizer 报错，表项不能回滚，因为新 fd 已经公开，API 会返回显式
release failure 并由内核把它当作资源账本错误。source 等于 destination 时
必须成功返回自身；若先关闭 destination，就会把唯一 source 一起删除。

fd flags 和 file status flags 也不能混淆。CLOEXEC 属于某个 fd entry；
文件 offset 和 readable/writable status 属于共享 FileDescription。

## 7. Shell 解析为什么要与执行分开

若边读字符边创建 child，输入末尾的未闭合引号可能发生在已经 fork 三个
进程之后。v1.11 先把整行转换为无指针、固定容量的执行计划：

```text
ShellExecutionPlan
  storage[513]
  arguments[128]
  stages[16]
  argument_count
  stage_count
```

每个 argument 只保存 storage 内的 offset/length。stage 保存参数区间与
可选输入/输出路径。这样输入行缓冲复用后，计划仍然自包含。

解析器识别：

- 空格与 Tab；
- 单引号、双引号；
- 反斜杠转义；
- 有无空格的 `| < >`；
- 空 stage、重复重定向、缺失路径、悬空转义和未闭合引号。

任一错误都不返回部分计划，也不触发系统调用。

### 7.1 为什么每 stage 目前只有 8 个参数

用户栈 VMA 虽然预留 8 MiB，但按相邻 page fault 逐页提交。解析函数曾在一个
栈帧中构造超过 4 KiB 的计划，函数序言直接跨过未提交页，fault 地址不再紧邻
当前 committed bottom，Kernel 正确把它识别为非法 stack jump。

v1.11 让执行计划保持不超过 4096 字节，并用 `static_assert` 冻结。它不是
永远的 Unix 参数上限；后续可以把大计划放入 UserHeap，或让栈 fault 支持受控
多页探测。当前先选择易证明的单页对象。

## 8. 16 级流水线怎样同时启动

假设 stage 数为 `N`：

1. parent 创建 `N-1` 条 pipe；
2. 依次 fork `N` 个 child，但不在每次 fork 后等待；
3. child `i`：
   - `i > 0`：把 pipe `i-1` reader dup2 到 fd 0；
   - `i+1 < N`：把 pipe `i` writer dup2 到 fd 1；
   - 应用 `<`/`>`；
   - 关闭继承的所有临时 pipe fd；
   - exec；
4. parent 关闭自己持有的所有 pipe fd；
5. parent wait 全部 child，最后 stage 决定命令结果。

不能“fork stage 0，wait，fork stage 1”。若 stage 0 输出超过 64 KiB，它会
等待可写空间，而 stage 1 尚未存在，系统必然死锁。

每个 child 必须关闭不使用的 writer。否则最后一个真实 writer 已退出时，
某个无关 child 仍持有 writer fd，reader 永远观察不到 EOF。

## 9. 重定向发生在 child 的 exec 之前

输出重定向的 child 执行：

```text
open(path, WRITE | CREATE | TRUNCATE)
  → dup2(opened_fd, 1)
  → close(opened_fd)
  → close all pipe temporaries
  → exec
```

输入重定向同理接到 fd 0。parent 的标准描述符绝不能被改变，否则下一条 Shell
提示符也会写入文件。

当前只支持截断输出 `>`，没有追加 `>>`、错误重定向或 here-document。这是
明确版本边界，不用隐藏语法“解析成功但忽略语义”。

## 10. 外部工具怎样做到没有 libc

`core_tool.cpp` 是 freestanding 多调用程序。入口接收项目自建的
`argc/argv` 栈布局，从 `argv[0]` 取最后一个路径组件：

```text
/bin/cat → cat
/bin/wc  → wc
```

再分派到工具函数。所有读写都经过自研系统调用 wrapper；数字输出使用固定
20 字节十进制缓冲，字符串长度有 4096 字节上界，没有 `strlen`、iostream、
malloc 或宿主文件 API。

十九个路径覆盖不同组合面：

| 组合面 | 工具 |
| --- | --- |
| 纯输出/退出状态 | help、echo、true、false |
| 流式输入输出 | cat、wc、head、tee |
| 工作目录/目录流 | pwd、ls |
| 元数据 | stat |
| namespace mutation | mkdir、touch、rm、rmdir、mv |
| 文件内容/大小 | write、truncate |
| 持久化边界 | sync |

Shell 只保留 `cd` 和 `exit`，因为外部 child 无法修改 parent Shell 的 cwd，
也不能替 parent 决定退出主循环。

## 11. 失败清理逐层走读

### 11.1 CreatePipe

准备顺序：

```text
Pipe slot
  → reader FileDescription
  → writer FileDescription
  → reader fd
  → writer fd
```

reader object 创建失败时直接关闭 Pipe 两端。writer object 创建失败时，
reader RAII reference 的 Reset 触发 reader finalizer，再关闭 writer。
reader fd 安装失败时两个 reference 都 Reset；writer fd 安装失败时关闭已安装
reader fd 并 Reset writer reference。

用户永远只能看到完整 pair 或明确错误。

### 11.2 部分 fork

第 `k` 个 fork 失败时，parent 已有 `k` 个 child。它先关闭所有 pipe fd，
使阻塞的 child 能观察 EOF/broken pipe，然后等待这 `k` 个 child。不能直接
回 Shell 主循环，否则 Zombie 和 pipe strong reference 会保留。

### 11.3 exec 失败

child 的 fd 图已经与 parent 分离。exec 不成功时 child 使用 127 退出；
dup/open 失败使用 126。child 不允许返回 Shell 解释器，因为那会生成第二个
交互 Shell，并共同读取同一个键盘 FIFO。

## 13. 测试怎样证明不是“看起来能运行”

### 单元

- 空动态 Pipe 不分配页；
- 跨越两页再 17 字节的数据逐字节保持；
- 中途页申请失败回滚全部本次页；
- functional 128 slot 耗尽、拒绝、关闭和复用；
- dup2 替换打开 fd、source==destination、共享引用；
- 16 stage、引号、转义、重定向和每种语法错误。

### 集成

独立 capacity 测试创建 1024 条 Pipe，再创建一条必须失败。关闭全部端点后
`active=0` 且 creation/release 都为 1024。

### 固定种子随机

动态 Pipe 用 65536 字节参考 ring 对照 100000 次读、写、关闭和边界操作。
Shell 执行解析器用 4096 轮任意 byte 输入，任何成功计划都必须满足 stage/
argument/storage 区间不变量，任何失败都不能泄露部分计划。

### QEMU

64 MiB bootstrap 执行基础命令序列；256 MiB functional 额外执行：

- `>` 输出重定向和 `<` 输入重定向；
- touch/true/false；
- 包含 echo、12 个 cat、tee、head、wc 的 16 级流水线；
- 文件清理和未知命令拒绝。

真实功能日志最终显示 88 个 Process 全部 exited/collected，87 次成功 wait，
15 条运行期 Pipe 与 128 条自检 Pipe 的创建/释放完全守恒。
