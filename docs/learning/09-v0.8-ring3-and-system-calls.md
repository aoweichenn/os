## 1. “用户程序”必须由硬件隔离

在 Kernel 中调用一个普通 C++ 函数，即使把它命名为 user，也仍以 Ring 0 权限
运行。v0.8 首次建立真实边界：

```text
独立 freestanding user ELF
  → Kernel 严格解析
  → 分配用户物理页
  → 以 U/S=1、W^X 映射代码/数据/栈
  → 构造 SS:RSP:RFLAGS:CS:RIP
  → IRETQ 到 CPL3
  → INT 0x80 回到 Ring 0
  → 验证用户现场和指针
  → 返回 Ring 3 或终止用户执行
```

用户代码对 Kernel 的限制不再是约定，而由 GDT、TSS、IDT、页表和特权指令共同
执行。

历史验收见 [v0.8 发布记录](../releases/v0.8.md)，决策见
[ADR 0011](../adr/0011-user-mode-elf-and-int80-boundary.md)。

## 2. 独立 `abi` 与 `user` 模块

### 2.1 共享 ABI，不共享 Kernel 实现

[system_call.hpp](../../source/abi/include/os/abi/system_call.hpp) 只放 Kernel 和
User 都必须一致的：

- system call number。
- vector `0x80`。
- 最大传输长度。
- flag 和固定结构布局。
- `int64_t` 结果码。

它不能包含 Kernel 内部类、物理指针或设备对象。ABI 是两侧共同遵守的二进制
协议，而不是“让用户 include Kernel 头”。

### 2.2 User 也是 freestanding

`source/user` 使用与 Kernel 类似的限制：

- `x86_64-unknown-none-elf`。
- 无 libc/C++ 标准库。
- 无异常、RTTI、动态初始化。
- 自己提供必要 `memcpy/memset`。
- 独立 linker script 和入口。

Ring 3 并不自动获得一个 C 标准库；系统调用只是最底层能力。

## 3. 用户 ELF

### 3.1 链接布局

[user.ld.in](../../source/user/linker/user.ld.in)：

- `ET_EXEC` AMD64。
- entry=`osUserEntry`。
- virtual base=`0x40000000`。
- text RX、rodata R、data/bss RW。
- 4 KiB 对齐。
- 丢弃 unwind/note/comment。

不同用户程序可以使用同一组虚拟地址，因为 v0.9 以后它们位于不同 CR3。

### 3.2 当前装载约束

[user_elf.cpp](../../source/kernel/src/user/user_elf.cpp) 只接受：

- 完整 ELF64 little-endian x86-64 `ET_EXEC`。
- 正确 header/program-header 大小。
- 有界 program header table。
- 最多 8 个 load segment。
- 最多 32 个映射页。
- program window `[0x40000000,0x80000000)`。
- 4 KiB alignment 和 offset/address congruence。
- 文件区间和内存区间均不溢出。
- 每段可读、权限位已知、W^X。
- 段间不重叠。
- entry 落在 executable、not-writable segment。
- 不与用户栈和 guard 相交。

用户 parser 比通用 ELF loader 更窄：它只接受当前能完整执行和回收的布局。拒绝
暂不支持的格式比“尽量加载”更安全。

### 3.3 ELF 如何进入 Kernel

当前构建把 shell、smoke、worker、IPC 和故障用户 ELF 通过
[user_images.asm.in](../../source/kernel/src/user/user_images.asm.in) 的 `incbin`
嵌入 Kernel read-only segment。

[user_program_images.cpp](../../source/kernel/src/user/user_program_images.cpp) 只根据
枚举返回镜像 begin/end。Kernel 仍解析真实 ELF 字节，不直接调用编译期已知的
C++ 函数。

“嵌入”是 v1.0 的程序来源限制，不是地址空间共享。v1.3/后续路线才从磁盘 exec。

## 4. 用户虚拟地址布局

```text
0x0000000000000000    unmapped low/null area
0x0000000000010000    通用用户合法地址下界

0x0000000040000000    user program window begin
...                   ELF text/rodata/data/bss
0x0000000080000000    user program window end

0x00007FFFFFFEA000    stack guard, not-present
0x00007FFFFFFEB000    4-page user stack begin
0x00007FFFFFFF0000    stack top, exclusive
0x0000800000000000    canonical low-half end
```

用户栈是 RW、NX、U/S=1；guard not-present。代码页 RX，数据页 RW/NX。

### 4.1 映射事务

创建地址空间时：

1. 验证完整 ELF，不分配。
2. 为每个覆盖页分配 frame。
3. 创建必要页表，并让所有上层条目带 U/S。
4. 按合并后的页权限映射。
5. 通过内核可访问映射清零整页。
6. 复制各段 `p_filesz`。
7. 保持 BSS 为零。
8. 分配/清零四个 stack pages。
9. 最终 query 每页权限。

任一步失败都逆序释放已映射用户页和页表。失败不能留下“半个用户进程”。

当前 v1.8 在高物理内存上通过 direct-map 清零/复制；v1.0 基线物理页仍位于低
64 MiB identity window。用户可见虚拟布局不因物理访问机制变化。

## 5. Ring 3 所需的四道门

### 5.1 GDT DPL

- user code selector=`0x23`。
- user data/stack selector=`0x1B`。

低两位 RPL=3，描述符 DPL=3。CPL 由 CS 低两位体现。

### 5.2 页表 U/S

用户叶和从 PML4 到 PT 的所有上层路径都必须 U/S=1。Kernel 页保持 U/S=0。
只建立 Ring 3 segment 但把所有页设 supervisor，会在第一次用户取指 #PF。

### 5.3 TSS.RSP0

用户执行 `INT 0x80` 或发生异常时，CPU 从 TSS 取 Ring 0 栈顶，把用户
SS:RSP 等现场压在内核栈上。Kernel 不能继续使用用户提供的栈执行特权代码。

### 5.4 IDT gate

IDT[0x80]：

- present。
- interrupt gate。
- target Kernel code selector。
- DPL=3。

DPL3 允许用户执行 `INT 0x80`。普通 Kernel gate 仍 DPL0，用户不能任意
`INT` 到设备 handler。

## 6. 用 `IRETQ` 进入用户态

首次用户 frame 包含：

```text
RIP       user entry
CS        0x23
RFLAGS    0x202 (reserved bit + IF)
RSP       user stack top
SS        0x1B
```

加上 15 个通用寄存器和 normalized vector/error，就是当前 176 字节
`UserPrivilegeFrame`。

v0.8 初版有专用 `osKernelEnterUserMode`，保存外层 Kernel 调用链后 `IRETQ`；
v0.9 当前代码把它演进为
`osKernelEnterScheduledProcess`，直接恢复 PCB 中同形 frame。

`IRETQ` 会同时：

- 恢复 RIP/CS/RFLAGS。
- 发现 CPL 从 0 变 3。
- 恢复用户 RSP/SS。
- 按新 CPL 和页表权限开始取指。

## 7. `INT 0x80` ABI

### 7.1 寄存器

当前 ABI：

| 寄存器 | 含义 |
| --- | --- |
| RAX | system call number，返回时也是 `int64_t` result |
| RDI | argument 0 |
| RSI | argument 1 |
| RDX | argument 2 |
| R10 | argument 3 |

[system_call.asm](../../source/user/src/system_call.asm) 的 C++ wrapper 输入使用
System V：

```text
RDI=number, RSI=arg0, RDX=arg1, RCX=arg2, R8=arg3
```

汇编重排为项目 ABI后执行 `INT 0x80`。选择 R10 避开 RCX 是为未来
`SYSCALL` 会覆盖 RCX 的演进留下空间。

### 7.2 版本演进

- v0.8：WriteLog、ExitProcess。
- v0.9：GetProcessId。
- v0.10：管道 Try/Wait/Close。
- v0.11：文件 open/read/write/close、mkdir、sync。
- v1.0：统一 descriptor Try/Wait/Close、directory open/read。

当前编号 1..22 稳定保存在 ABI 头中；旧专用接口仍兼容，但 v1.0 正常路径优先
统一 descriptor。

## 8. 系统调用入口验证

CPU 能进入 handler 不代表 frame 可信。Kernel 验证：

- process runtime 正在运行且存在 current process。
- frame 来自 CPL3。
- normalized vector 是 `0x80`。
- CS/SS 是预期 user selectors。
- RIP 位于当前地址空间的 user RX、not-writable page。
- 用户 RSP 位于四页 stack range。
- stack page 是 user RW、NX。

只有满足这些前提才读取 system call number。

## 9. 用户指针不是 Kernel 指针

`WriteLog(pointer,length)` 的 pointer 只是当前进程的虚拟地址。必须验证：

1. length 上限。
2. `[pointer,pointer+length)` 无溢出且位于 canonical 用户范围。
3. 覆盖的每一页 present、U/S=1。
4. 读取时无需 writable；输出 buffer 则必须 writable。
5. 逐块复制到有界 Kernel buffer。
6. 再让设备或文件系统消费 Kernel buffer。

不能只检查首尾地址，中间页可能 not-present；不能先解引用再验证；不能在持有
pipe/filesystem lock 时执行复杂用户页复制。

当前 [user_memory.cpp](../../source/kernel/src/user/user_memory.cpp) 使用页表 query
和受控物理映射完成复制。

## 10. 返回和终止

### 10.1 普通返回

dispatcher 只把 `frame.registerRax` 改为返回值，返回同一 frame。汇编恢复全部
寄存器并 `IRETQ` 回 Ring 3。

### 10.2 Exit

Exit 不返回用户下一条指令。v0.8 恢复进入用户前保存的 Kernel 调用链；v0.9
以后终止 PCB，可能直接切换到下一个进程，最后一个进程才恢复外层 Kernel 栈。

### 10.3 用户异常隔离

异常 dispatcher 通过 CS.RPL 判断来源：

- Ring 0 #UD/#PF → panic。
- Ring 3 #UD/#PF → 记录 vector/error/RIP/CR2，终止当前用户主体。

相同 vector 的策略因来源不同，不是因为异常名称变化。

## 11. v0.8 验收程序

正常 smoke：

1. 传未映射 pointer，要求返回 invalid user memory。
2. 调未知 number，要求返回 unknown number。
3. WriteLog 输出 `HELLO_FROM_RING3`。
4. Exit(0)。

故障程序：

- `invalid_opcode.cpp` 执行 `UD2`，vector 6，不 panic。
- `page_fault.cpp` 读 `0x30000000`，#PF error `0x4`
  （not-present/read/user），CR2 同地址，不 panic。
- truncated ELF 在进入 Ring 3 前由 parser 拒绝。

## 14. 实验

### 实验 A：四道门

分别假设 GDT DPL、IDT DPL、leaf U/S、TSS.RSP0 配错，预测第一次失败发生在
IRETQ、用户取指还是 INT 0x80。

### 实验 B：跨页缓冲

设计一个从页末最后 8 字节开始、长度 16 的 buffer。列出 Kernel 必须 query
的两页，以及第二页 absent/read-only 时读/写系统调用差异。

### 实验 C：用户 #PF

解码 error `0x4`，与 v0.6 Ring 0 写保护的 `0x3` 比较。

### 实验 D：ELF 嵌入不等于执行

沿 `incbin → UserProgramImage → ValidateUserElf → map/copy → IRETQ` 写出每个
边界，说明 Kernel 为何没有直接调用用户 `osUserEntry` 符号。
