# v1.9：从磁盘字节到按需驻留的文件页

## 1. 这一阶段解决的不是“读文件”，而是页面身份

v1.6 已经能从 rootfs 按偏移读取文件，v1.7 已经能装入磁盘 ELF，v1.8 已经
能处理匿名缺页。为什么还需要 v1.9？

普通 `read` 的结果是复制到调用方缓冲区的一段字节。文件映射则要求同一组文件
字节长期参与虚拟内存：

- 它尚未驻留时，CPU 访问产生 `#PF`；
- 它驻留后，PTE 直接让 CPU 读物理 frame；
- 多个进程可以观察同一个只读页面；
- fd 关闭不能让仍存在的映射失效；
- 文件被写或截断后，旧 PTE 不能永久指向陈旧内容；
- 缓存达到上限时必须可回收或明确失败。

因此核心问题从“怎样读字节”变成“谁拥有这一页、怎样唯一标识、何时可丢弃、
谁还在引用”。

## 2. 历史背景：为什么 Unix 把文件和内存接在一起

早期系统装入程序时通常由 loader 主动把文本与数据复制到内存。虚拟内存成熟
后，执行文件和普通文件都可以成为页面的后备来源：尚未访问的部分不必读入，
只读文本还可以跨进程共享。

这产生了现代系统常见的统一视角：

```text
虚拟地址
  -> VMA 判断合法性、权限和来源
  -> PTE 判断当前是否驻留
  -> page fault 根据来源取得物理页
  -> 匿名来源：zero fill
  -> 文件来源：按 offset 读取或命中 page cache
```

Linux 的 page cache 还管理 dirty、writeback、readahead 和复杂并发。本项目
不能把成熟内核的全部机制一次照搬；v1.9 先实现只有 clean 页的最小闭环。

## 3. 四层事实必须分开

| 层 | 回答的问题 | 不负责什么 |
| --- | --- | --- |
| VMA | 该地址是否允许读/写/执行，来源是什么 | 当前是否有 frame |
| PTE | CPU 当前怎样翻译与保护 | 文件身份和生命周期 |
| FileBacking | 缺页时从哪里按偏移重新读 | 某页当前是否缓存 |
| CachePage | 某个文件页的 clean frame 与引用 | 地址区间政策 |

如果把后备指针直接塞进 PTE，PTE 不存在时反而找不到来源。如果用 fd 作为后备，
`close` 或 fd 复用会让 VMA 指向别的文件。如果 cache entry 直接拥有所有
映射语义，中段 `munmap` 又无法表达区间 split。

分层不是抽象装饰，而是让每种失败都落到唯一负责者。

## 4. 从 fd 得到稳定文件身份

fd 只是 FileTable 中的局部索引。下面两段代码中的 `3` 没有跨时间身份：

```text
fd=3 -> /bin/app
close(3)
fd=3 -> /tmp/data
```

缓存使用：

```text
(superblock_identifier,
 superblock_generation,
 node_identifier,
 node_generation,
 page_index)
```

superblock 区分挂载文件系统，node 区分 inode，generation 阻止对象删除后
同号复用。page index 等于文件 offset 除以 4096。

`FileBackingManager` 另外为后备槽保存 generation。VMA 同时携带 descriptor
与 generation，旧句柄即使指向被复用的槽也会被拒绝。

## 5. 为什么映射在 close 后仍然有效

`mmap` 的语义不是“每次 fault 回头查 fd”。建立映射时，Kernel 从 fd 取得
FileDescription/VFS 打开实例的独立引用：

```text
Process FileTable fd
       |
       +-- mmap 时 retain --> FileBacking
                               |
close fd ----------------------+  映射仍持有
                               |
munmap/exit ------------------> 最后释放
```

页故障只查 FileBacking。这样 fd 关闭、表槽复用或共享 offset 改变都不会改变
映射来源。`ReadAt` 接受显式 offset，不修改 FileDescription 的顺序读位置。

## 6. 文件 VMA 的几何

文件 VMA 保存虚拟半开区间和对应文件半开区间：

```text
VA [0x60000000, 0x60003000)
       | page 0       -> file [offset+0,    offset+4096)
       | page 1       -> file [offset+4096, offset+8192)
       | page 2       -> file [offset+8192, offset+data_length)
```

中间解除一页时，左段保持原 offset；右段的 offset 增加被移除前缀大小。
如果只切虚拟地址而忘记平移文件 offset，右段下一次 fault 会静默读错内容。

合并也不能只比较权限。两个邻接 VMA 只有在同一后备、同一 generation、文件
offset 连续、data length 视图连续时才是一个逻辑区域。

## 7. x86-64 页故障位怎样参与决策

CPU 在 vector 14 的 error code 中给出：

| 位 | 为 1 时 |
| --- | --- |
| P | present protection fault，而非 not-present |
| W/R | 引发访问是写 |
| U/S | 来自用户态 |
| RSVD | 页表保留位错误 |
| I/D | 指令取值 |

v1.9 只处理用户 not-present fault。RSVD 表示页表损坏，present+write 可能是
只读保护错误；都不能伪装为文件 cache miss。

合法 fault 的步骤是：

1. CR2 向下对齐到页；
2. 查找包含地址的 VMA；
3. 用 W/R、I/D 检查软件权限；
4. 计算页内相对偏移和文件 offset；
5. 选择 cache frame 或私有 frame；
6. 构造 U/S、R/W、NX PTE；
7. 更新驻留、fault、cache 引用统计；
8. 返回用户态重试原指令。

## 8. ELF 的文件字节与内存字节并不总相等

ELF `PT_LOAD` 同时有 `p_filesz` 和 `p_memsz`。常见 data 段：

```text
file:   [ initialized data ]
memory: [ initialized data ][ zero-filled BSS ]
```

loader 不能把文件后面的下一个 segment 字节当作 BSS。fault 页先整页清零，
再只读取本段有效 file bytes。最后一页因此可能同时包含文件数据和零。

普通 3000 字节文件映射一页也要求：

```text
byte 0..2999    = file content
byte 3000..4095 = zero
```

v1.9 让这种部分页使用私有 frame，不进入共享 cache。完整只读页才拥有唯一且
无歧义的文件页内容。

## 9. clean page cache 状态机

当前 entry 只有三种可解释状态：

```text
inactive
   |
   | miss + free/LRU slot + frame + successful read
   v
active clean, refs=0
   |
   | map
   v
active clean, refs>0
   |
   | unmap/exit
   v
active clean, refs=0
   |
   | LRU eviction / file invalidation
   v
inactive + frame returned
```

不存在 dirty 和 writeback。正因如此，refs=0 的页可以无条件丢弃：需要时从
rootfs 重读即可。

## 10. LRU 为什么需要单调 generation

每次命中、装入或释放引用都推进 `access_generation`。缓存满时扫描 refs=0
的 entry，选择 generation 最小者。

这是 O(capacity) 的教学实现，容量最大 4096，边界清晰。哈希表与链表可以把
平均查找和淘汰降为常数，但会新增桶、链表和 resize 生命周期；当前证据首先
验证正确身份和回收。

generation 溢出前可执行重编号或明确失败。64 位计数在当前工作负载中不可达，
但代码仍不能依赖有符号溢出。

## 11. shared 与 private 的真正区别

`MAP_SHARED` 表示映射观察共享文件视图；`MAP_PRIVATE` 表示修改只属于进程。

v1.9 的支持矩阵：

| 请求 | 结果 |
| --- | --- |
| shared + read | 支持，完整页可共享 cache |
| shared + write | 明确不支持 |
| private + read | 支持 |
| private + read/write | 支持，使用私有 frame |
| W+X | 拒绝 |

可写 private 页第一次 fault 就复制文件内容到私有 frame。完整 COW 要等
v1.10；当前选择多用一页内存，但语义正确且所有权简单。

## 12. 文件写入为什么必须撤销 PTE

假设 cache 被失效但旧 PTE 仍存在：

```text
VMA -> old PTE -> old frame
cache key removed
file contains new bytes
```

CPU 再次读取不会 fault，仍看到 old frame。正确顺序是撤销匹配 PTE、释放
cache mapping reference，再删除零引用 cache entry。下一次访问重新进入 fault
路径并读到新内容。

当前 write wrapper 把 4096 字节拆成 16 次 256 字节系统调用。第一次写已撤销
唯一缓存页；后续块没有新 entry 可失效。因此日志必须比较调用前后累计计数，
不能因为累计值仍为 1 就重复打印十六次。

## 13. truncate 的边界

缩短文件时，原来完全有效的最后一页可能变成部分页，甚至全部越过 EOF。所有
旧文件映射 PTE 都先撤销。下一次 fault 依据新的 size：

- offset >= size：映射语义拒绝或提供该 VMA 冻结允许的零尾；
- offset < size < offset+4096：读有效前缀，其余清零；
- 完整页仍在 size 内：可重新进入 clean cache。

VFS 后备可以在 size 为零时继续存在；“空文件”不是“无效后备”。

## 14. Zombie 为什么会影响文件写

进程退出后，地址空间已销毁，但父进程 wait 前还需要退出结果，因此运行时槽
保持 active Zombie。文件失效代码若只看 `active`，就会向一个
`root_physical_address == 0` 的地址空间执行撤销并得到 NotInitialized。

这不是文件系统错误，而是跨模块生命周期边界。正确扫描集合是“active 且地址
空间仍存在”的进程。该故障只在 Shell 和文件探针并发交错下出现，说明端到端
测试能发现局部单元测试看不到的所有权组合。

## 15. 启动暂存区为何也在本阶段变化

按需 ELF 增加 Kernel 和用户探针代码后，payload 超过历史 1 MiB 暂存区。
Stage 1 先把容器读到低物理内存，再解析 ELF；这个缓冲区不能覆盖 Kernel
可加载段、页表、栈或 rootfs 区域。

v1.9 冻结：

```text
Kernel load end exclusive  0x03600000
staging begin              0x03600000
staging end                0x03E00000
staging capacity           8 MiB
rootfs start               LBA 32768 = 16 MiB
```

汇编、C++ 和 Python 若各写一份不同常量，打包问题会反复出现。因此 Python
布局模块是镜像工具权威，契约测试再扫描目标常量是否一致。

## 17. 测试怎样对应状态空间

单元测试适合：

- cache miss/hit/release/invalidate；
- LRU 候选和全 busy 容量失败；
- FileBacking owner/generation；
- VMA offset rebase 和 merge；
- ELF 大窗口、尾零和权限。

集成测试适合：

- 两个 AddressSpace 的 PTE 指向同一 frame；
- 先撤销一个映射时 frame 仍存在；
- 最后引用释放后 frame/cache entry 可回收；
- fd 关闭后后备仍能 ReadAt。

固定种子随机测试执行 100000 步，逐步对照参考模型的 active key、refs、
resident、eviction 和 invalidation。失败必须输出 seed 与 operation index。

QEMU 才能证明 CR2/error code、真实 PTE 权限、指令重试、系统调用分块、进程
交错与 ATA/VFS 路径共同成立。

## 18. 三档内存为何运行同一 workload

- 64 MiB：证明最低档没有被固定大 cache 或描述符池挤爆；
- 256 MiB：日常完整功能，QEMU 约十余秒完成；
- 64 GiB：证明 E820/direct-map/高 frame 和容量对象仍兼容同一 VM 语义。

64 GiB 运行完成 512 个内核栈对象、2048 个映射页的容量生命周期并全部回收。
这不代表当前支持 512 个同时活跃用户线程工作负载，而是证明底层资源结构容量
与回滚路径。

## 19. 常见错误与诊断

### `FILE_CREATE_OR_WRITE`

检查是否直接调用单次最大 256 字节的旧 `WriteFile`。大缓冲应使用会自动分块的
`WriteDescriptor`。

### 写文件后 shared 映射仍是旧值

检查是否只删除 cache entry 而未撤销 PTE；检查文件 identity generation。

### 随机出现 filesystem corrupt

检查失效扫描是否把已销毁地址空间的 Zombie 当作活映射。

### `USER_RETURN_REJECTED`

按需 ELF 入口页可能尚未驻留。返回前应解析 executable VMA 页面，再验证 PTE，
不能沿用 eager loader 假设。

### 每次打包超过边界

运行 boot layout contract，比较 payload size、staging capacity、Kernel load
end 和 rootfs LBA；不要只扩大某一份常量。

## 20. 本阶段边界与下一步

v1.9 的 cache page 永远 clean，没有异步回写。可写 private 页从 fault 起就是
独占，不是 COW。下一阶段 v1.10 将：

- fork 复制 VMA 与页表视图；
- 私有可写页转为只读 COW；
- 增加物理页共享引用；
- 在用户写 fault 和 Kernel `CopyToUser` 上使用同一 break-COW 逻辑；
- 证明中途失败恢复父页权限和全部引用。

先把文件身份与 clean 共享做对，COW 才不会同时承担两种尚未稳定的共享语义。
