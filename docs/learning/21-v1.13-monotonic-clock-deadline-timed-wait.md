# v1.13：从周期中断到可组合的时间等待

## 本章解决什么问题

PIT 每秒大约产生一千次 IRQ0，并不等于系统已经拥有“时间”。tick 是离散硬件
事件；`sleep(20 ms)`、互斥等待超时和条件变量 deadline 则需要同一个不会
倒退、不会因整数除法持续漂移、能与普通唤醒竞争的内核契约。v1.13 建立的
不是日历，而是一条从晶振分频到用户等待结果的完整因果链。

本章沿实际实现回答四件事：

1. 为什么 x86 PC 兼容平台留下 8253/8254 PIT；
2. 为什么整数 tick 不能直接冒充毫秒；
3. deadline 与条件通知同时发生时，谁有权完成等待；
4. 怎样用宿主模型和真实 QEMU 共同证明“不早醒、不重复、不残留”。

代码走读入口：

```text
source/kernel/time/monotonic_clock.*
source/kernel/time/deadline_queue.*
source/kernel/process/thread_scheduler.*
source/kernel/process/process_runtime.*
source/kernel/arch/interrupt_runtime.*
source/user/system_call.*

source/user/programs/time_probe.cpp
```

## 历史背景：为什么现代 64 位系统还看见 PIT

IBM PC 使用 8253 可编程间隔定时器提供周期事件，后来的 AT 采用兼容的
8254。设备有三个计数通道；传统通道 0 接入 8259A 的 IRQ0，通道 2 还与扬声器
门控等历史用途相连。PC 兼容性让这个接口在远超最初处理器能力的机器上长期
存在。QEMU `pc` 机器也模拟它，所以本项目可以只依赖自写端口 I/O 与 PIC
路由取得稳定的早期时钟事件。

PIT 输入频率约为 1.193182 MHz。软件把一个 16 位除数写入通道 0，计数器按
模式 2 周期重装。若期望约 1000 Hz，整数除数只能取接近值；设备不会为软件
保存“1 ms”这个抽象。历史上很多内核以 jiffy 表示 tick，再在更高层转换为
时间。现代系统通常还会选择 TSC、HPET 或 LAPIC timer，但它们没有消除
clock source、clock event 与软件 deadline 的分层问题。

本项目保留 PIT 是为了把这条链看清楚：

```text
14.31818 MHz 平台参考时钟
  ÷ 12
1.193182 MHz PIT 输入
  ÷ 1193（实际整数 divisor）
约 1000 Hz IRQ0
  → PIC / LAPIC virtual-wire
  → IDT vector 32
  → C++ interrupt runtime
```

## 时间源、时钟事件与墙钟不是同一件事

三个概念必须分开：

- clock source 回答“单调经过了多少”；
- clock event 回答“什么时候让 CPU 进入处理程序”；
- wall clock 回答“现在是哪个日期和时区”。

PIT 同时为当前实现提供周期 clock event 和换算单调时间的输入事实。它没有
电池、日期或时区。若把 RTC 校时、闰秒或管理员改时间用于超时判断，一个向后
校时就可能让等待额外延长，向前校时又可能让全部 deadline 一起过期。因此
v1.13 明确只公开 monotonic nanoseconds，wall clock 不进入 v2.0。

宿主日志前缀 `[QEMU][T+...ms]` 也不是来宾时钟：它是 Python 在宿主收到
串口行时记录的墙钟间隔，会受 TCG、宿主负载和串口打印量影响。来宾
`MONOTONIC_START_NS` 才由自写 PIT/IRQ 路径生成。

## 精确换算：余数也是状态

设 PIT 输入频率为 \(f\)，实际除数为 \(d\)，一 tick 的纳秒数是：

\[
\Delta t = \frac{d \times 10^9}{f}
\]

这个值通常不是整数。若每次都只取整数商：

\[
t_n = n \left\lfloor\frac{d \times 10^9}{f}\right\rfloor
\]

每 tick 丢弃的分数会累积为线性漂移。正确实现保存余数 \(r\)：

\[
q, r' = \operatorname{divmod}(r + k d 10^9, f)
\]
\[
t' = t + q
\]

其中 \(k\) 是一次推进的 tick 数。新余数永远小于 \(f\)，下一次继续参与
计算。这样不是用浮点数近似，而是在整数范围内保存同一个有理数累计器。

公式正确不代表可以直接按书写顺序连乘。实现先把 \(k\) 切成满足
`chunk * d <= UINT64_MAX` 的有限分块；每块又先对
`remaining_cycles * 1e9` 做除法，再把旧余数加入已经小于 \(f\) 的新余数。
因此中间乘积越界而最终纳秒仍可表示时，结果依然精确，不会过早进入饱和。

为什么不用 `double`？freestanding Kernel 不应隐式依赖浮点运行时；浮点
舍入模式又属于每 Thread FXSAVE 现场，IRQ 热路径改变它会污染用户状态。
固定宽度整数使每一步都能检查上溢，也能在宿主与目标得到相同结果。

## 64 位边界：饱和优于回绕

64 位纳秒大约可表达 584 年。项目未打算连续运行这么久，但边界仍必须定义。
如果计数回绕，新的小值会让未来 deadline 看似极远，排序关系也会失效。
`MonotonicClock` 因而分块消除可避免的中间乘积越界，并在最终纳秒加法前
检查范围；只有结果本身不能表示时才进入饱和状态并固定为 `UINT64_MAX`。

用户 `SleepFor(duration)` 也使用饱和加法把相对时长转换为绝对 deadline：

```text
now > UINT64_MAX - duration
  ? deadline = UINT64_MAX
  : deadline = now + duration
```

这不是隐藏错误，而是明确的“最远可表达未来”。调度器的比较仍保持全序，
不会把超大时长误判成已经到期。

## 为什么统一使用绝对 deadline

若每一层都保存剩余时长，线程每次被信号、虚假唤醒或重新取得 Mutex 都要扣除
已经经过的时间。多次整数换算会积累误差，忘记扣减则会让总等待超过请求。
绝对 deadline 只计算一次：

```text
user duration
  → saturating now + duration
  → absolute deadline
  → scheduler queue
```

ConditionVariable 醒来后重新检查谓词；若谓词仍不成立，它继续用原 deadline
等待，而不是重新获得完整时长。

## DeadlineQueue：顺序、身份与容量

当前系统最多 512 个 Thread，每个 Thread 同时只能处于一个 Blocked 等待，
因此每个 Thread 最多有一个活动 deadline。队列用 Thread 索引直接定位槽，
活动槽按 `(deadline, insertion_sequence)` 排序。sequence 解决相同 deadline
的稳定顺序，也让随机模型能给出唯一预期。

为什么队列不保存 `WaitQueue*` 或用户 futex 地址？ThreadScheduler 已经拥有
Thread 与 WaitQueue membership 的权威关系。deadline 只需要定位 Thread；
到期时调度器再从 Thread 当前状态解析原队列。这样 `munmap`、exec 或进程退出
不会把 timer 层变成第二份悬空地址索引。

当前有序链表的插入是 \(O(n)\)，查看/弹出最早项是 \(O(1)\)。512 的硬容量
让这个取舍可测且有界。未来若 deadline 数量增长，可在不改变接口与语义的
前提下替换为二叉堆或分层时间轮。

## 单赢家：通知和超时不能各赢一次

考虑一个 Thread 同时在 condition WaitQueue 和 deadline queue 中：

```text
               scheduler irq-save lock
              /                       \
NotifyOne → Wake(reason=Condition)   IRQ0 → Expire(reason=Timeout)
              \                       /
                Blocked → Ready 一次
```

两条路径都先取得同一 scheduler lock。胜者确认 Thread 仍是 Blocked，把它从
WaitQueue 摘除、解析 deadline，并只接入一次 Ready queue。败者看到状态已经
变化，不能再写 wake reason。这里的关键不是“两个操作大概不会同时发生”，
而是唯一状态转换点把竞争线性化。

普通 Wake 会取消 deadline；Timeout 会消费到期项。统计因而满足：

```text
schedules = expirations + cancellations + active
```

Thread 被终止时也走 cancellation。整机结束 active 必须为零，不能把已退出
Thread 留在时间结构里。

## 从 IRQ0 到用户返回寄存器

IRQ0 处理按以下顺序推进：

1. `MonotonicClock::AdvanceTicks(1)`；
2. 更新调度 tick 与 PIC EOI；
3. 在 scheduler lock 下反复解析所有已经到期的队首；
4. 对 sleep 设置成功返回，对 timed futex 设置 `TIMED_OUT`；
5. 若有 Thread 变为 Ready，则提交 need-resched；
6. 在安全调度边界恢复选中的用户 frame。

超时结果直接写入该 Thread 保存现场的 RAX，因为它恢复时会从阻塞系统调用
继续。timed futex 到期后还要尝试释放空 futex entry，否则反复超时会耗尽
512 个 key 槽。

即使当前没有 Running Thread，idle 路径仍以 `sti; hlt; cli` 开中断等待。
PIT 唤醒 CPU，IRQ0 解析 sleeper，再由返回边界选择 Ready Thread。这证明
sleep 是阻塞而非忙等；若只在“当前中断来自 Ring 3”时解析 deadline，系统
一旦进入 idle 就再也不会醒来。

## 用户 ConditionVariable 的锁语义

`WaitUntil(mutex, deadline)` 的语义不是“内核替我检查条件”。调用者必须：

```text
lock(mutex)
while (!predicate) {
    result = condition.WaitUntil(mutex, deadline)
    if (result == TimedOut) break
}
```

运行库观察 sequence、释放 Mutex、进入 timed futex，返回后无论通知、超时
还是失败都重新取得 Mutex，再把强类型结果交给调用者。通知只说明“条件可能
变化”，因此谓词仍要循环检查。sequence 变化与内核 compare-and-block 共同
关闭 unlock 到 sleep 之间的丢失通知窗口。

## 四层验证怎样互补

单元测试能精确推进虚拟 tick，验证余数、长跨度和 `UINT64_MAX`；它不依赖
宿主真实时间。DeadlineQueue 单元测试验证相同 deadline 稳定顺序、重复
登记拒绝、取消和结构一致性。

集成测试把 MonotonicClock、ThreadScheduler 和 WaitQueue 放在一起，证明：

- deadline 之前不能早醒；
- 到期只产生一次 Timeout；
- condition 先赢时 deadline 被取消；
- 败者再次解析没有副作用；
- 所有 Thread 回收后队列为空且统计守恒。

固定种子随机测试执行 100000 次 schedule、cancel、advance 与 expire，并在
每一步与宿主参考模型比较队首、活动集合、顺序和统计。失败输出种子与步骤，
而不是用下一次随机运行“碰运气”。

QEMU 最后验证无法由宿主纯模型替代的链：真实端口编程、IRQ0、IDT、idle、
用户/内核切换、系统调用返回现场和 PID1 回收。`/bin/time_probe` 要求
20 ms sleep 不早醒，10 ms futex 超时，条件通知先于 200 ms deadline，
以及无通知的 10 ms condition 超时。

## 日志为何只在边界打印

一千赫兹 IRQ 中每 tick 打串口会把 PIO 延迟引入被测时序，既改变调度行为又
产生海量日志。v1.13 只在用户语义提交和系统结束时记录：

```text
[OS][USER][TIME] MONOTONIC_START_NS=...
[OS][USER][TIME] MONOTONIC_WAKE_NS=...
[OS][USER][TIME] SLEEP_VERIFIED
[OS][USER][TIME] FUTEX_TIMEOUT_VERIFIED
[OS][USER][TIME] CONDITION_WON_BEFORE_DEADLINE
[OS][USER][TIME] CONDITION_TIMEOUT_VERIFIED
[OS][KERNEL][TIME] ACTIVE_DEADLINES=0
```

数字日志证明时间确实前进，语义 marker 证明对应事务已经完成，最终汇总证明
没有残留。三类信息不能互相替代。

## 常见错误与定位

如果 sleep 永远不醒，先确认 idle IRQ 也解析 deadline，而不是先扩大宿主
timeout。如果偶尔早醒，检查比较单位是否混用 tick、毫秒和纳秒。如果条件
通知与超时产生两次 Ready，检查两条路径是否共用 scheduler lock，以及普通
wake 是否取消 deadline。

如果长时间模型出现漂移，检查是否每 tick 丢弃余数；如果时间突然变小，检查
乘加回绕与饱和状态。如果 timed futex 多次运行后容量耗尽，检查 Timeout、
unmap、exec、ProcessExit 是否都会释放空 key。

## 本阶段完成边界

v1.13 已建立单 BSP 周期时钟上的统一绝对 deadline，但没有 RTC、日期、时区、
高精度 timer、tickless 或信号中断等待。下一阶段 v1.14 会让 Signal 成为
第三个等待竞争者；它必须复用本章的单赢家 WakeReason，不能另建一套绕过
WaitQueue 与 deadline 的唤醒状态机。
