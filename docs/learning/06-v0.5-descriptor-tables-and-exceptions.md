> [栈、call、异常帧与 ABI](background/02-data-address-assembly-and-abi.md)、

## 1. 内核为什么必须接管架构状态

v0.4 Kernel 虽然运行在 C++ 中，仍借用 Stage 1 的 GDT、页表和异常缺省状态。
加载器一旦完成交接，内核就不应永久依赖加载器的隐藏可变状态。

v0.5 建立：

```text
Kernel-owned GDT
  → 64-bit TSS + RSP0 + IST
  → 256-entry IDT
  → 32 exception stubs
  → normalized ExceptionFrame
  → C++ dispatch policy
  ├─ INT3: resume with IRETQ
  └─ other Ring 0 faults: panic + halt
```

历史验收见 [v0.5 发布记录](../releases/v0.5.md)，决策依据见
[ADR 0008](../adr/0008-kernel-descriptor-tables-and-exception-abi.md)。

## 2. 当前 GDT

v0.5 初版有五槽：null、Kernel code、Kernel data 和占两槽的 TSS。v0.8 加入
两个 Ring 3 段后，当前 GDT 为七槽：

| index | selector | 内容 |
| ---: | ---: | --- |
| 0 | `0x00` | null |
| 1 | `0x08` | Ring 0 64-bit code |
| 2 | `0x10` | Ring 0 data |
| 3 | `0x1B` | Ring 3 data，含 RPL=3 |
| 4 | `0x23` | Ring 3 64-bit code，含 RPL=3 |
| 5–6 | `0x28` | 64-bit TSS descriptor |

普通 code/data descriptor 是 8 字节；64 位 TSS descriptor 需要 16 字节，
因为它要保存 64 位 base。

### 2.1 TSS descriptor 编码

[descriptor_layout.cpp](../../source/kernel/src/arch/descriptor_layout.cpp) 将：

- 20 位 inclusive limit。
- base bits 0..63。
- type=available 64-bit TSS (`0x9`)。
- Present。

拆入 descriptor 的非连续位域。函数返回 `{low, high}`，测试再独立解码回原
base/limit。

### 2.2 加载 GDT

[architecture.asm](../../source/kernel/src/arch/architecture.asm) 中
`osKernelLoadGdtAndTss`：

1. `LGDT [RDI]`。
2. 压入新 code selector 和返回 RIP。
3. `RETFQ` 刷新 CS。
4. 把 Kernel data selector 装入 DS/ES/FS/GS/SS。
5. `LTR` 装入 TSS selector。
6. 返回 C++。

`LGDT` 本身只改 GDTR，不刷新已缓存的 CS/SS。

## 3. TSS、RSP0 和 IST

### 3.1 104 字节 TSS

[TaskStateSegment](../../source/kernel/include/os/kernel/arch/descriptor_layout.hpp) 精确
104 字节，`static_assert` 防止编译器布局漂移。

关键字段：

- `privilegeStackPointer0`：未来 Ring 3→Ring 0 使用的栈顶。
- `interruptStackPointer1`：double fault。
- `interruptStackPointer2`：NMI。
- `interruptStackPointer3`：machine check。
- `ioPermissionBitmapOffset=sizeof(TSS)`：表示没有用户可用的 I/O bitmap。

### 3.2 为什么关键异常用 IST

普通异常继续使用当前栈；如果异常就是由栈溢出或栈页损坏引起，处理器可能无法
压入异常现场，继而形成 double fault 或 triple fault。

IST 门要求 CPU 无条件切到 TSS 中的专用栈。项目分配：

- #DF → IST1。
- NMI → IST2。
- #MC → IST3。

每个可用栈 16 KiB。当前存储前还留有一页 guard 区，v0.6 建立内核页表后才会
真正把 guard page 设为 not-present。

### 3.3 RSP0 的演进

v0.5 时 RSP0 指向默认 privilege transition stack，尚无 Ring 3。v0.9 调度
不同进程时会把它更新为当前进程的 Kernel stack top。

## 4. IDT

### 4.1 门布局

每个 16 字节 interrupt gate 包含：

- handler offset low/middle/high。
- Kernel code selector。
- IST index 低 3 位。
- type attributes。
- reserved=0。

当前 IDT 有 256 项。阶段演进：

- v0.5：0..31 架构异常 present，其余 not-present。
- v0.7：32..47 加入 PIC IRQ。
- v0.8：`0x80` 加入 DPL3 system call gate。

当前 #BP 和 #OF 门也允许 DPL3 软件触发；普通异常门为 DPL0。硬件异常不受门
DPL 的同种限制。

### 4.2 `LIDT` 与验证

内核构造 `DescriptorTablePointer{limit, base}` 后调用 `LIDT`。随后使用：

- `SGDT`
- `SIDT`
- 读取 CS
- 读取 SS
- `STR`
- 检查 TSS RSP0/IST/io bitmap

证明 CPU 实际装入预期表，而不是只证明内存里写了某些字节。

## 5. 异常硬件栈

### 5.1 CPU 压入的字段

同特权级无硬件错误码异常，低地址方向的最终内容可概括为：

```text
RSP → RIP
      CS
      RFLAGS
```

有错误码异常在 RIP 前再压入 error code。跨 Ring 3→Ring 0 还增加旧 RSP 和
SS。

当前项目认为下列向量由 CPU 压入错误码：

```text
8, 10, 11, 12, 13, 14, 17, 21, 29, 30
```

### 5.2 入口宏规范化

无硬件错误码：

```asm
push 0        ; normalized error code
push vector
jmp common
```

有硬件错误码：

```asm
push vector   ; CPU 已经压入 error code
jmp common
```

进入 common 后，两者都有统一的：

```text
vector
errorCode
RIP
CS
RFLAGS
```

### 5.3 保存 15 个通用寄存器

公共入口依次 push RAX、RBX、RCX、RDX、RBP、RSI、RDI、R8..R15。由于栈向
低地址增长，最终 RSP 指向 R15，恰好匹配 C++ `ExceptionFrame` 字段顺序：

```text
R15..R8, RDI, RSI, RBP, RDX, RCX, RBX, RAX,
vector, errorCode, RIP, CS, RFLAGS
```

20 个 `uint64_t`，总计 160 字节。跨用户特权级的 `UserPrivilegeFrame` 再加
user RSP 和 SS，总计 176 字节。

### 5.4 DF 和调用栈对齐

入口先 `CLD`，避免被中断代码遗留的 direction flag 破坏 C++ 字符串操作。
随后：

```asm
mov rdi, rsp
and rsp, -16
call osKernelDispatchException
```

原始 frame 指针保存在 RDI；临时对齐 RSP 只为了满足 C++ ABI。C++ 返回一个
要恢复的 frame 指针，汇编把 RSP 切过去。这一设计在 v0.9 自然扩展为“IRQ
返回另一个进程的 frame”。

## 6. C++ 异常策略

[exceptions.cpp](../../source/kernel/src/arch/exceptions.cpp) 的当前策略：

1. frame 为空直接 halt。
2. 若 CS.RPL=3，读取必要的 CR2，终止当前用户进程——这是 v0.8/v0.9 扩展。
3. Ring 0 `INT3` 且 normalized error=0：输出 handled，原 frame 返回。
4. 其他 Ring 0 异常：`PanicFromException`。

在 v0.5 阶段还没有用户进程，所以核心策略是“只有受控 breakpoint 可恢复，
其他异常不可恢复”。

不能用“给 RIP 加固定字节数”跳过所有 fault：

- 指令长度可变。
- trap、fault、abort 的重启语义不同。
- 页错误可能应该修页再重试。
- 随意跳过会把 Kernel 缺陷伪装成继续运行。

## 7. Panic 设计

[panic.cpp](../../source/kernel/src/arch/panic.cpp) 遵守最小依赖原则：

1. `CLI`。
2. 检查全局 panic state；递归 panic 直接 halt。
3. 标记 active。
4. 重新初始化最小串口。
5. 尽力写 vector、error code、RIP、CS、RFLAGS。
6. #PF 额外写 CR2。
7. 写 `PANIC`。
8. 永久 halt。

panic 不分配内存、不获取普通锁、不使用格式化库、不做复杂栈回溯。故障可能正由
堆、锁或栈损坏引起，panic 不能依赖这些组件仍然健康。

串口写失败也不会尝试递归报告“报告失败”。

## 8. 自检与故障注入

### 8.1 正常 `INT3`

Kernel 初始化表后执行真实 breakpoint：

```text
CPU 查 IDT[3]
  → 异常 stub 3
  → 补 error=0/vector=3
  → 保存寄存器
  → C++ 输出 BREAKPOINT_HANDLED
  → 返回同一 frame
  → 恢复寄存器
  → 跳过 vector/error
  → IRETQ 回到 INT3 下一条
```

最终输出 `EXCEPTION_SELF_TEST_READY`，证明入口和返回都有效。

### 8.2 `UD2`

故障镜像执行 `UD2`，预期 #UD vector 6、error 0、panic，且不得出现 READY。

### 8.3 页错误

v0.5 访问 Stage 1 低 64 MiB 映射之外的 `0x04000000`，预期 #PF vector 14，
并从 CR2 看到该地址。

v0.6 会增加更精细的只读保护故障。

## 9. 测试

### 单元/随机

- TSS descriptor 的 64 位 base 与 limit 编解码。
- IDT gate handler address 的低/中/高位。
- IST mask、reserved bits、type attributes。
- 哪些异常有硬件错误码。
- ExceptionFrame/UserPrivilegeFrame 大小和 offset。

### 产物审计

最终 Kernel ELF 必须包含：

- 32 个 vector stub。
- stub table。
- common dispatch。
- C++ dispatcher。
- GDT/IDT load helpers。
- 无未解析运行时符号。

### QEMU

分别运行 normal、#UD 和 #PF 镜像。故障镜像只替换受控入口或选择，必须复用
同一生产异常路径。

## 10. 常见故障

### 加载 GDT 后立即 #GP

检查 selector index、descriptor Present/L/D/DPL、TSS type 和 limit，以及
`RETFQ` 栈顺序。

### `LTR` #GP

检查 TSS descriptor 是 available 而非错误 type，base canonical，limit 至少
覆盖 104 字节，selector 不含错误 RPL。

### 异常向量错位

检查该向量是否硬件压入错误码。重复补一个零或漏补零会使后面所有 RIP/CS/RFLAGS
字段错 8 字节。

### C++ 返回后崩溃

检查 push/pop 顺序、`add rsp,16` 是否只移除 vector/error，以及进入 C++ 前
对齐是否保留原 frame 地址。

### 三重故障重置

常见原因是 IDT gate 不存在、handler 不 canonical、code selector 无效、当前栈
不可写，或异常处理自身再次 fault 且 #DF 也不能建立栈。

## 13. 阶段验收

应能完整解释：

- Kernel 为什么不能永久使用 Stage 1 GDT。
- 当前七槽 GDT 与 v0.5 五槽初版的关系。
- 64 位 TSS descriptor、RSP0 和三个 IST。
- IDT gate 的 handler、selector、IST、DPL 和 Present。
- 两类硬件异常栈如何规范为 160 字节 frame。
- C++ dispatcher 如何决定 resume、terminate 或 panic。
- panic 为什么要最小依赖、不可重入并禁止中断。
