# v0.3：从实模式进入 Long Mode

> 背景先修：
> [8086、A20、保护模式与 AMD64](background/01-computer-pc-and-x86-history.md)、
> [寄存器与控制转移](background/02-data-address-assembly-and-abi.md)、
> [分段与四级分页](background/04-memory-paging-protection-and-exceptions.md)。

## 1. 阶段目标

Stage 1 已能在 16 位实模式运行，但 ELF64 Kernel 需要 64 位指令、寄存器和
分页环境。v0.3 必须按硬件规定顺序完成：

```text
A20 enable + alias test
  → GDT
  → CR0.PE
  → far jump 到 32-bit code segment
  → 建立 PML4/PDPT/PD
  → CR4.PAE + CR3
  → IA32_EFER.LME
  → CR0.PG
  → 检查 IA32_EFER.LMA
  → far jump 到 64-bit code segment
```

每一个箭头都有硬件前置条件，不能把它写成一组可任意换序的寄存器赋值。

历史验收见 [v0.3 发布记录](../releases/v0.3.md)，Stage 1 当前契约见
[stage1.md](../modules/stage1.md)。

## 2. A20 地址线

### 2.1 历史原因

8086 的物理地址由 `segment<<4 + offset` 形成，某些组合会超过 1 MiB。早期
兼容硬件把第 20 地址位屏蔽，使地址在 1 MiB 处回绕。进入现代内存布局前必须
确认 A20 已开放。

### 2.2 Fast A20 gate

项目读取 system control port A `0x92`：

- 设置 bit 1 开启 A20。
- 清 bit 0，避免触发 fast reset。
- 写回端口。

“写了开启位”不等于“硬件状态一定正确”，所以紧接着做别名测试。

### 2.3 别名测试

选择两个理论上相差 1 MiB 的地址：

```text
0000:0000 → 0x000000
FFFF:0010 → 0x100000
```

流程：

1. 保存两个地址的原字节。
2. 向低地址写 `0x5A`。
3. 向高地址写 `0xA5`。
4. 回读两者。
5. 若相等，说明高地址写入回绕并覆盖低地址，A20 无效。
6. 无论成功失败都恢复原字节和寄存器。

测试必须恢复现场，否则“验证 A20”会破坏中断向量表起点或 1 MiB 位置的数据。

## 3. Stage 1 GDT

当前 GDT 有四项：

| 选择子 | 描述符 | 用途 |
| ---: | --- | --- |
| `0x00` | null | 捕获空选择子 |
| `0x08` | `0x00CF9A000000FFFF` | 32 位 Ring 0 code |
| `0x10` | `0x00CF92000000FFFF` | Ring 0 data |
| `0x18` | `0x00AF9A000000FFFF` | 64 位 Ring 0 code |

32 位 code/data 是基址 0、4 KiB granularity、覆盖 4 GiB 的平坦段。64 位
code 设置 L=1、D=0。

`os_stage1_gdt_descriptor` 包含：

- 16 位 inclusive limit=`size-1`。
- 32 位线性基址=`0x8000 + os_stage1_gdt`。

因为 Stage 1 是 `org 0` 平坦二进制，标签是相对负载起点的 offset，传给硬件
的 GDT base 必须补上实际物理加载地址。

## 4. 进入 32 位保护模式

实模式代码：

1. `LGDT [descriptor]`。
2. 读取 CR0。
3. 设置 PE bit 0。
4. 写回 CR0。
5. 立即 far jump 到选择子 `0x08` 和 32 位入口。

far jump 同时刷新 CS 和预取/译码状态。只设置 PE 后继续执行一长段 16 位代码，
会让“当前编码被怎样解释”变得脆弱。

32 位入口立即：

- 把 DS/ES/SS 设为 `0x10`。
- 把 ESP 设为 `0x7000`。
- 使用 32 位串口函数输出 `PROTECTED_MODE`。

## 5. 临时页表

### 5.1 v1.0 基线与当前代码共同保留的布局

```text
0x10000..0x10FFF  PML4
0x11000..0x11FFF  PDPT
0x12000..0x12FFF  PD
```

代码先用 `rep stosd` 清零三个 4 KiB 页，再设置：

```text
PML4[0] → 0x11000 | P | RW
PDPT[0] → 0x12000 | P | RW
PD[0..31] → 0,2MiB,...,62MiB | P | RW | PS
```

因此当前 Stage 1 恒等映射低 64 MiB。

v0.3 最初验收只需要最低 2 MiB；随后 v0.4 为 Kernel 暂存区、装载窗口和栈扩展
为 64 MiB。学习阶段概念与当前源码的容量演进要区分。

### 5.2 为什么使用 2 MiB 大页

若使用 4 KiB 页，映射 64 MiB 还需要 32 个 PT 页和 16384 个叶条目。Stage 1
只需要一个简单的临时恒等窗口，大页能减少代码与保留内存。

内核在 v0.6 会换成自己的 4 KiB 页表，以获得精确 W^X 和 guard page。

### 5.3 条目值

- 上层 PML4E/PDPTE flags=`0x003`：Present + Writable。
- PDE flags=`0x083`：Present + Writable + Page Size。
- 每个条目 8 字节；当前物理地址低于 4 GiB，高 dword 清零。

### 5.4 自检

构建后代码逐项回读 PML4、PDPT 和 32 个 PDE。这里只证明内存中的字节符合预期，
真正启用分页后还要回读 CR3 和 LMA。

## 6. PAE、LME 和分页

### 6.1 PAE 与 CR3

```asm
mov eax, cr4
or eax, 0x20
mov cr4, eax
mov eax, 0x10000
mov cr3, eax
```

随后回读 CR4.PAE 和 CR3。CR3 保存 PML4 的物理地址，不是 C++ 指针，也不是
PML4 第一项内容。

### 6.2 EFER.LME

`IA32_EFER` 的 MSR 编号是 `0xC0000080`：

```asm
mov ecx, 0xC0000080
rdmsr
or eax, 0x100
wrmsr
rdmsr
test eax, 0x100
```

`RDMSR/WRMSR` 使用 EDX:EAX 表示 64 位值，ECX 表示 MSR 编号。代码保留
EFER 其他位，只设置 LME。

### 6.3 CR0.PG 和 LMA

设置 CR0.PG 后，硬件在 PE、PAE、LME 和有效页表均满足时激活 IA-32e。
代码回读：

- CR0.PG。
- EFER.LMA=`0x400`。

LME 是软件请求，LMA 是当前激活状态。只有 LMA 成立才继续。

## 7. 进入 64 位代码

分页激活后，代码仍需要 far jump 到 GDT 的 L 位代码段 `0x18`。64 位入口：

- 重新加载数据段选择子。
- 设置 64 位 RSP。
- 使用 RSI、RCX、RDX 等 64 位寄存器版本输出 `LONG_MODE`。

为什么有三套串口例程：

- 16 位代码使用 SI/CX/DX 和 16 位地址假设。
- 32 位代码的字符串地址是 `0x8000 + label`，使用 ESI/ECX/EDX。
- 64 位代码使用 RSI/RCX/RDX。

端口协议相同，但指令编码、寄存器宽度和标签地址形成方式不同。为了省几行代码
强行跨模式复用，反而会隐藏最重要的学习边界。

## 8. 当前 `entry.asm` 的完整分区

[entry.asm](../../source/boot/stage1/src/entry.asm) 按执行模式组织：

1. `[bits 16]` 入口、A20、GDT。
2. `[bits 32]` 保护模式、页表和控制寄存器。
3. `[bits 64]` Long Mode、E820、Kernel loader 和 Kernel transfer。
4. 再回到 `[bits 16]` 放置只会由早期路径调用的辅助代码和数据。
5. include `memory_map.asm` 与 `kernel_loader.asm`。

NASM 的 `bits` 只控制随后指令编码；它不会在运行时替 CPU 切换模式。CPU 模式
必须由实际控制寄存器和远跳决定。

## 9. 成功和失败标记

成功顺序：

```text
A20_READY
GDT_READY
PROTECTED_MODE
PAGE_TABLES_READY
PAE_READY
LME_READY
PAGING_ENABLED
LONG_MODE
```

独立失败：

- `A20_INVALID`
- `PAGE_TABLES_INVALID`
- `PAE_INVALID`
- `LME_INVALID`
- `PAGING_INVALID`

每个失败都在当前仍可靠的模式和串口例程中报告，然后进入相应位宽的 halt loop。

## 10. 常见故障

### 10.1 设置 PE 后三重故障

通常检查：

- GDTR base 是否忘记加 `0x8000`。
- limit 是否写成 size 而非 size-1。
- code descriptor present/type/D 位。
- far jump selector。

### 10.2 开分页后立即重置

通常检查：

- CR3 是否 4 KiB 对齐。
- PML4/PDPT/PD 是否都在当前可访问 RAM。
- 上层 Present 位。
- 当前 RIP、栈、GDT 和串口代码是否落在恒等窗口内。
- PAE/LME/PE 的先后。

### 10.3 出现 LME 但没有 LMA

说明只请求了 Long Mode，分页激活条件没有完全满足。检查 CR0.PG、CR4.PAE、
CR3 和页表保留位。

### 10.4 64 位入口能到，字符串错误

检查标签是否加 Stage 1 物理 base，RSI 是否 canonical，DS/ES/SS 是否刷新，
以及先前 `CLD` 是否仍保持。

## 11. 测试与审计

宿主集成测试验证：

- GDT 和页表物理区不重叠。
- 32 个 PDE 精确覆盖低 64 MiB。
- Stage 1、描述符缓冲、页表和后续 Kernel 区域的布局。

产物反汇编可验证：

- 16/32/64 位关键指令编码。
- `LGDT`、CR0/CR4/CR3、RDMSR/WRMSR 和 far jump 存在。

QEMU 顺序标记证明 CPU 真正经过每个模式。单看 ELF/bin 字节不能证明硬件接受
页表，单看 `LONG_MODE` 也不能证明失败分支分类正确。

## 13. 实验

### 实验 A：解码 GDT

把三个非空 64 位描述符拆成 base、limit、type、S、DPL、P、L、D/B、G，解释
为什么 32 位 code 和 64 位 code 不能共用同一属性。

### 实验 B：页表手算

手算虚拟地址 `0x0000000003E01234` 使用哪个 PML4、PDPT、PD 项和大页内偏移，
证明它在当前 64 MiB 窗口中。

### 实验 C：A20 别名

分别模拟 A20 开/关时两次写入后的低、高地址内容，解释代码为何通过“是否相等”
判断，而不是检查某个固定值。

### 实验 D：模式切换寄存器快照

在 GDB 中分别停在 16、32、64 位入口，记录 CS、CR0、CR3、CR4 和 EFER。
不要依赖 GDB 对当前模式的自动猜测，结合反汇编编码判断。
