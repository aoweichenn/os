## 1. 从模式切换器到内核

进入 Long Mode 只改变了 CPU 能力，Stage 1 仍是一个固定地址平坦二进制。
v0.4 第一次装载由 C++20 编写、按链接地址组织的 ELF64 Kernel：

```text
读取 Kernel descriptor
  → 验证 descriptor CRC32 和保留区
  → 读取完整 ELF 到 staging buffer
  → 验证精确文件 CRC32 与扇区零填充
  → 第一遍验证 ELF 和全部 PT_LOAD
  → 第二遍复制 p_filesz 并清零 BSS
  → 构造版本化 BootInfo
  → 切换独立 Kernel stack
  → RDI=BootInfo，CALL ELF entry
  → Kernel 重新验证交接环境
```

历史验收见 [v0.4 发布记录](../releases/v0.4.md)，架构选择见
[ADR 0007](../adr/0007-two-pass-elf-loader-and-boot-info.md)。

## 2. Kernel 磁盘容器

### 2.1 为什么不直接把 ELF 放在固定扇区

Stage 1 需要知道：

- 文件精确长度。
- 占用扇区数。
- 起始 LBA。
- 文件完整性。
- 描述符自身是否损坏。

如果只“从 LBA 66 读到某个固定上限”，CRC 会混入填充，ELF parser 也无法区分
合法末尾和隐藏数据。

### 2.2 当前描述符

Kernel descriptor 位于 LBA 65 (`0x41`)，有效头 48 字节：

| 偏移 | 大小 | 字段 | 约束 |
| ---: | ---: | --- | --- |
| 0 | 8 | magic | `OSKERN64` |
| 8 | 2 | version | 1 |
| 10 | 2 | header size | 48 |
| 12 | 4 | flags | 0 |
| 16 | 8 | payload LBA | 固定 66 |
| 24 | 8 | file size | 非零，当前最多 1 MiB |
| 32 | 8 | sector count | `ceil(file size / 512)` |
| 40 | 4 | payload CRC32 | 只覆盖精确 ELF 文件 |
| 44 | 4 | header CRC32 | 覆盖整 512 字节描述符 |

48..511 的保留区必须全零。计算 header CRC 时，header CRC 字段临时按零处理。

Stage 1 当前 staging 区是：

```text
0x03E00000..0x03F00000  1 MiB
```

v0.4 初版是 512 KiB；v0.10 随内核增长迁移并扩大到当前 1 MiB。当前实现还会在
v0.6 的 E820 信息到达后确认整个 staging 区属于 usable RAM。

### 2.3 CRC32

项目实现 IEEE CRC32 的 reflected 算法：

- 初值 `0xFFFFFFFF`。
- 每字节与 EAX 低字节异或。
- 每位右移，carry 为 1 时异或 `0xEDB88320`。
- 最终按位取反。

payload CRC 只覆盖精确文件长度。最后一个扇区中文件末尾之后的字节必须全零，
避免攻击者或工具把未校验数据藏在 padding。

## 3. ELF64 基础

### 3.1 ELF header

Stage 1 只接受：

- magic `0x7F 'E' 'L' 'F'`。
- ELFCLASS64。
- little-endian。
- current version。
- `ET_EXEC`。
- machine=`EM_X86_64` (`0x3E`)。
- entry=`0x00100000`。
- ELF header 64 字节。
- program header 56 字节。
- program header count 1..64。
- 整个 program header table 位于文件范围内。

### 3.2 Program header 而非 section

链接器用 section 组织 `.text/.rodata/.data/.bss`；运行时装载器只需 program
header。每个 `PT_LOAD` 描述：

- 文件区间 `[p_offset, p_offset+p_filesz)`。
- 目标虚拟地址 `p_vaddr`。
- 目标物理地址 `p_paddr`。
- 内存区间长度 `p_memsz`。
- R/W/X flags。
- alignment。

不需要装载的 section 可以完全不出现在运行时决策中。

## 4. 严格 `PT_LOAD` 验证

当前每个 load segment 必须满足：

1. flags 不含 R/W/X 之外的未知位。
2. 必须可读。
3. 不能同时 W 和 X。
4. `p_filesz <= p_memsz`。
5. `p_memsz != 0`。
6. 文件 offset 与 size 不溢出且完全位于精确文件内。
7. alignment 精确为 4 KiB。
8. `p_offset mod 4096 == p_vaddr mod 4096`。
9. `p_vaddr == p_paddr`，当前只接受恒等装载。
10. 目标区间位于 `[0x00100000, 0x03E00000)`。
11. 目标结束计算不溢出。
12. 不与任何之前的 `PT_LOAD` 重叠。
13. 固定 entry 位于至少一个 executable segment 内。

这同时保护 Stage 1 本体、页表、descriptor/BootInfo/scratch、staging buffer 和
Kernel stack。

## 5. 为什么必须两遍装载

错误做法是：

```text
验证第 1 段 → 复制第 1 段
验证第 2 段 → 发现非法 → 停止
```

此时失败虽然被发现，目标 RAM 已被部分改写，甚至可能覆盖诊断所需状态。

项目采用：

```text
Pass 1:
  验证 ELF header
  验证 program header table
  验证每个段
  验证段间关系和 entry
  不写目标区

Pass 2:
  对每个 PT_LOAD:
    copy p_filesz bytes
    zero p_memsz - p_filesz bytes
```

程序头最多 64 个，两两重叠检查最坏 O(n²)，但启动期上界明确，换来了简单可靠的
事务边界。

### BSS

链接脚本中的 `.bss (NOLOAD)` 不占 ELF 文件字节，但落在 data `PT_LOAD` 的
`p_memsz` 尾部。Stage 1 的 `rep stosb` 把这部分清零。

Kernel 启动后：

1. 读取一个放在 BSS 的 probe。
2. 要求它初始为零。
3. 写成非零。
4. 再次确认写入可见。

这同时证明 loader 清零和 writable data 映射。

## 6. Kernel 链接脚本

[kernel.ld.in](../../source/kernel/linker/kernel.ld.in)：

- `ENTRY(osKernelEntry)`。
- link address=`0x00100000`。
- 三个 `PT_LOAD`：
  - text：R|X。
  - rodata：R。
  - data+bss：R|W。
- 每个区域按 4 KiB 对齐。
- entry section 用 `KEEP` 防止被链接垃圾回收。
- 丢弃 comment、note、eh_frame。
- 导出 image/text/rodata/writable 的 begin/end 符号，供 v0.6 页权限使用。

链接脚本负责生成预期布局，Python ELF audit 和 Stage 1 parser 独立验证实际产物。

## 7. BootInfo 交接 ABI

### 7.1 为什么不用散乱寄存器

交接内容会随版本增长，寄存器数量有限，也难以表达版本和结构大小。BootInfo 使用
固定 `uint64_t` 字段，并带 magic/version/size。

### 7.2 当前 BootInfo v2

固定地址 `0x14000`，共 104 字节、13 个字段：

| 偏移 | 字段 |
| ---: | --- |
| 0 | magic=`OSBOOT64` |
| 8 | version=2 |
| 16 | structure size=104 |
| 24 | Kernel ELF staging physical address |
| 32 | 精确 Kernel file size |
| 40 | entry address |
| 48 | load segment count |
| 56 | Stage 1 CR3 physical address |
| 64 | identity map size=64 MiB |
| 72 | Kernel stack top |
| 80 | physical memory map address |
| 88 | memory map entry count |
| 96 | memory map entry size=24 |

v0.4 初版是 80 字节 v1；v0.6 加入 E820 三个字段后提升到 v2。当前文档和源码均
以最终 v2 为准。

### 7.3 调用边界

Stage 1：

```asm
mov rsp, 0x03FFF000
mov rdi, 0x00014000
mov rax, [rdi + kernel_entry_offset]
call rax
```

调用前 RSP 16 字节对齐；`CALL` 压入 8 字节返回地址，进入 C++ 函数时符合
System V AMD64 栈约定。首个整数参数 BootInfo 指针位于 RDI。

Kernel 被设计为不返回。如果返回，Stage 1 输出 `KERNEL_RETURNED` 并停止，这
是明确的契约违例。

## 8. 首次 C++ Kernel

入口在 [entry.cpp](../../source/kernel/src/boot/entry.cpp)，使用：

- `extern "C"`：导出稳定无修饰符号。
- `.text.os_kernel_entry`：确保链接脚本首先放置入口。
- `noexcept`：禁止异常路径。
- `[[noreturn]]`：声明生命周期。

`RunKernel` 的 v0.4 子集：

1. 内核自行初始化 COM1，不继续依赖 Stage 1 函数。
2. 输出 `ENTERED`。
3. `ValidateBootInfo` 逐字段验证。
4. 验证 BSS。
5. 读取 CR3，与 BootInfo 的 `0x10000` 比较。
6. 输出 file size、load segment count 和 `READY`。
7. HLT loop。

当前 v1.4 `RunKernel` 已继续扩展，阅读 v0.4 时先关注最前面的
`ValidateBootEnvironment`。

## 9. 编译与 freestanding 运行时

Kernel C++ 不拥有 libc。项目实现目标端 `memcpy/memset` 等必要符号，并使用
Clang/LLD 的 freestanding 配置。

ELF 审计拒绝：

- 动态链接依赖。
- 未解析宿主运行时。
- `.init_array` 等不受控动态初始化。
- 错误 entry 或 machine。
- 非预期 PT_LOAD 数量、地址或权限。
- W+X segment。

这解释了为什么普通 `std::vector`、iostream、异常或静态对象构造不能直接进入
Kernel。

## 10. 失败分类

Stage 1 分别报告：

- `KERNEL_HEADER_INVALID`
- `KERNEL_CHECKSUM_INVALID`
- `KERNEL_ELF_INVALID`
- `KERNEL_ATA_TIMEOUT`
- `KERNEL_ATA_ERROR`

Kernel 分别报告 BootInfo 校验状态、BSS 或 CR3 错误。错误层级保持清晰：
容器完整性错误不伪装成 ELF 语义错误，ELF 错误不允许进入 Kernel，交接错误由
Kernel 自己重新检查。

## 13. 实验

### 实验 A：三段 ELF

使用 `llvm-readelf -h -l` 检查 Kernel，逐个说明 `Offset/VirtAddr/PhysAddr/
FileSiz/MemSiz/Flg/Align` 如何通过 loader 条件。

### 实验 B：BSS

找出 data segment 的 `p_memsz-p_filesz`，说明它与链接脚本 `.bss` 大小的
关系，以及 Stage 1 实际清零的目标地址。

### 实验 C：两遍事务性

设计两个 PT_LOAD：第一段合法，第二段重叠。分别说明边验证边复制与两遍算法的
最终 RAM 差异。

从 `0x14000` 开始画出 104 字节，手工推导 Kernel C++ 每个字段的地址。
