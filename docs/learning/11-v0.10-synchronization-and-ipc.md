# v0.10：同步、阻塞/唤醒与有界管道

> 背景先修：
> [并发、acquire/release、阻塞、丢失唤醒与管道](background/06-processes-syscalls-files-and-shell.md)。

## 1. “等待”不等于反复重试

v0.9 中所有存活进程都必须 Ready 或 Running。若管道暂时无数据，用户只能不停
系统调用：

```text
TryRead → WouldBlock → TryRead → WouldBlock → ...
```

这会消耗时间片，而且无法表达“条件变化前不应参与调度”。v0.10 加入：

```text
Try operation
  ├─ can progress → transfer
  └─ WouldBlock
       → Wait system call
       → Running → Blocked(reason)
       → schedule another process
       → producer/consumer changes condition
       → wake matching Blocked → Ready
       → eventually resume after Wait
       → user loops back to Try
```

历史验收见 [v0.10 发布记录](../releases/v0.10.md)，核心不变量见
[ADR 0013](../adr/0013-blocking-wakeup-and-bounded-pipe.md)。

## 2. 单核也需要同步

只有一个 CPU 不等于只有一个执行上下文：

- 普通 Kernel 代码可被 IRQ 抢占。
- PIT 可在系统调用过程中触发。
- 共享对象被多个进程先后操作。
- 编译器和 CPU 可能重排普通内存访问。

当前系统调用通过 interrupt gate 进入，硬件清 IF，所以“检查条件→把当前进程
标记 Blocked→选择后继”在单核本地不会被普通 IRQ 插入。但对象自身仍使用明确
锁和内存序，为模块边界和后续多核演进建立正确语义。

## 3. SpinLock

[spin_lock.cpp](../../source/kernel/src/sync/spin_lock.cpp) 使用编译器原子内建：

- `TryLock`：atomic exchange 1，acquire。
- `Unlock`：atomic store 0，release。
- `IsLocked`：relaxed load。
- 竞争等待：先尝试 exchange，失败后 relaxed 观察并执行 `PAUSE`。

### 3.1 acquire/release

成功 acquire 后的访问不能跑到获取之前；release 前的写不能跑到解锁之后。于是
上一个 holder 在临界区的写，对下一个成功 acquire 的 holder 可见。

`volatile` 不能替代：

- 它不提供原子 read-modify-write。
- 不保证互斥。
- 不建立跨线程 happens-before。

### 3.2 `PAUSE`

自旋循环中的 `PAUSE` 给 x86 前端和超线程资源调度提示，减少紧循环代价。它不
释放锁、不睡眠，也不保证公平。

### 3.3 RAII guard

`SpinLockGuard` 构造时 Lock，析构时 Unlock，并禁止复制赋值。虽然 Kernel
禁用异常，RAII 仍能覆盖普通多返回分支，减少忘记解锁。

锁只允许保护短小、不阻塞的临界区。持锁时不能 Wait、做 ATA 长轮询或访问可能
fault 的用户页。

## 4. Blocked 状态

调度器加入：

```text
Unused → Ready → Running
                    ├─ quantum/other ready → Ready
                    ├─ wait condition      → Blocked(reason)
                    └─ exit/fault          → Terminated

Blocked(reason) --Wake(reason)--> Ready
```

v0.10 wait reasons：

- `PipeReadable`
- `PipeWritable`

v1.0 再加入 descriptor-readable/writable。

### 4.1 定向唤醒

Wake 接受 reason 和 maximum count：

- 只匹配相同 reason。
- Blocked→Ready。
- 清 wait reason。
- 更新每进程和全局 wake statistics。
- 不直接把它变 Running；正常 scheduler 决定运行顺序。

### 4.2 v0.10 的 no-ready 限制

v0.10 要求阻塞时存在另一个 Ready 后继，否则返回 `NoReadyProcess` 诊断，尚无
安全 idle。

v1.0 修复这一限制：最后一个 Running 可以 Blocked；若无 Ready 但仍有
Blocked，返回永久 Kernel context 执行 `sti;hlt;cli`，由键盘 IRQ 唤醒。这在
v1.0 文档中详解。

## 5. 64 字节环形管道

[Pipe](../../source/kernel/include/os/kernel/ipc/pipe.hpp) 持有：

- `buffer[64]`。
- `readIndex`。
- `writeIndex`。
- `bufferedByteCount`。
- 总读写字节/操作统计。
- reader/writer closed。
- initialized。
- spin lock。

不依赖“readIndex==writeIndex”区分空/满，而用独立 byte count：

```text
empty: count=0
full:  count=64
0 < count < 64: partial
```

索引每传一个字节：

```text
index = (index + 1) % 64
```

## 6. 管道状态真值表

### 6.1 Read

| 缓冲 | writer | 结果 |
| --- | --- | --- |
| `count>0` | open/closed | 读取 `min(capacity,count)` |
| `count=0` | open | `WouldBlock` |
| `count=0` | closed | `EndOfFile` |

writer 关闭后，已缓冲数据必须先读完，只有空时才 EOF。

### 6.2 Write

| 缓冲 | reader | 结果 |
| --- | --- | --- |
| 有空间 | open | 写 `min(length,space)` |
| full | open | `WouldBlock` |
| 任意 | closed | `BrokenPipe` |

reader 关闭后不再接受新字节，即使缓冲还有空间。

### 6.3 Close

- 重复关闭 → `AlreadyClosed`。
- close writer 后唤醒 reader，使其读余量或观察 EOF。
- close reader 后唤醒 writer，使其观察 BrokenPipe。
- 进程正常 Exit 或用户 fault 都自动关闭其拥有端点。

关闭也是条件变化，必须参与唤醒。

## 7. Try/Wait 为什么拆成两个 syscall

若一个 syscall 内部执行：

```text
check → block → wake → 假装原 I/O 已完成
```

唤醒只表示“条件可能变化”，不能保证资源仍可用。多个等待者、close 或未来信号
都会让条件再次改变。

当前 ABI：

- `TryReadPipe`
- `TryWritePipe`
- `WaitPipeReadable`
- `WaitPipeWritable`
- `ClosePipeReader`
- `ClosePipeWriter`

用户 wrapper：

```text
while remaining:
    result = Try(...)
    if success:
        advance by partial bytes
    elif WouldBlock:
        Wait(...)
        continue
    else:
        return error/EOF
```

Wait 返回不代表 transfer 发生；用户必须重新 Try。这就是 condition variable
风格的“在循环中检查谓词”。

## 8. 避免丢失唤醒

危险序列：

```text
consumer: 检查 empty
producer: 写入并 wake（此时 consumer 还不是 Blocked）
consumer: 标记 Blocked
结果：数据存在，但 consumer 永久睡眠
```

v0.10 依赖同一同步规则封闭“条件检查与阻塞转换”：

- Try 在 pipe lock 下观察对象。
- Wait 进入 Kernel 时 IF 已清。
- Wait 重新判断 `ReadCanProgress/WriteCanProgress`。
- 只有条件仍不满足才在不可被本地普通 IRQ 插入的区间标记 Blocked并调度。
- 生产/消费/close 先提交对象状态，再 wake。

未来 SMP 不能只依赖 IF，必须让等待队列和条件改变共享适用于多 CPU 的锁规则。

## 9. 用户复制与锁的顺序

### 写管道

1. 验证完整用户 readable range。
2. 复制最多 64 字节到 Kernel stack buffer。
3. 获取 pipe lock。
4. 提交部分字节。
5. 释放 lock。
6. 唤醒 reader。

### 读管道

1. 在消费前验证完整用户 writable range。
2. 获取 pipe lock。
3. 取到 Kernel buffer。
4. 释放 lock。
5. 复制到用户页。
6. 唤醒 writer。

绝不能持 pipe lock 直接访问用户 pointer：页表检查、复制或 fault 会扩大临界区，
甚至在锁持有期间终止进程。

读操作一旦从 pipe 消费就难以回滚，所以必须在消费前证明目标用户范围可写。

## 10. Producer/Consumer 工作负载

Producer 生成 256 字节：

```text
byte[i] = (i × 37 + 11) & 0xFF
```

Consumer 使用 31 字节 buffer 循环读并逐字节重算期望值。

容量组合刻意选择：

- pipe 64。
- payload 256。
- read chunk 31。

它保证出现：

- 多次 full/empty。
- partial write/read。
- 环形 wrap-around。
- writer/reader block 和 wake。
- writer close 后 drain + EOF。

若 buffer 也是 64 或 payload 只 32 字节，很多关键状态不会发生。

v1.0 最终进程身份是 PID2 Producer、PID3 Consumer；v0.10 初版是其前两项
工作负载，其他槽继续 scheduler isolation。

## 11. 结果守恒

冷路径最终检查：

```text
bytesWritten = 256
bytesRead = 256
buffered = 0
readerClosed = true
writerClosed = true
EOF observed = 1
```

并检查：

- producer 只写不读。
- consumer 只读不写。
- block/wakeup 达到语义下界。
- 每次 block 最终有匹配 wake 或终止原因。
- 全部进程页帧回收。

具体抢占次数受 QEMU 时序影响，不作为精确常量。

## 12. freestanding 初始化审计

v0.10 发现全局 `InterruptRuntime` 曾生成 `.init_array`。自研 Kernel 入口没有
C++ CRT 去运行构造器，即使当前显式 Initialize 恰好覆盖状态，二进制契约仍是
错误的。

修复：

- 用 `constexpr/constinit` 或平凡静态存储。
- 所有运行态对象显式 Initialize。
- ELF audit 拒绝 `.init_array/.fini_array/.ctors/.dtors`。

这说明“目标测试暂时通过”不能替代产物级运行时依赖审计。
