# v0.9：独立地址空间、进程与抢占调度

> 背景先修：
> [CR3、地址空间和回收](background/04-memory-paging-protection-and-exceptions.md)、
> [PIT 与中断时间](background/05-interrupts-time-and-pc-devices.md)、

## 1. 从一次用户调用到多个进程

v0.8 只有一个同步用户执行单元。v0.9 要证明：

- 多个进程可以在相同用户虚拟地址保存不同数据。
- PIT 能在用户代码没有主动让出的情况下抢占。
- 每个进程使用自己的 CR3、Ring 0 stack 和 TSS.RSP0。
- 退出或用户异常后，全部用户 frame、page 和 page table 可回收。

控制流：

```text
create PCB + address space + initial frame
  → scheduler chooses Ready
  → activate CR3 + TSS.RSP0
  → IRETQ to Ring 3
  → PIT IRQ0 saves current frame
  → scheduler tick/quantum decision
  → possibly select another PCB frame
  → switch CR3 + TSS.RSP0
  → common IRQ epilogue IRETQ
```

历史验收见 [v0.9 发布记录](../releases/v0.9.md)，决策见
[ADR 0012](../adr/0012-preemptive-process-scheduling.md)。

> 本页主体描述 v0.9–v1.0 的历史 PCB/ProcessScheduler 模型。v1.2 已将它
> 替换为 Process、Thread、ThreadScheduler 和 WaitQueue；当前实现见
> [thread_scheduler.hpp](../../source/kernel/include/os/kernel/process/thread_scheduler.hpp)、
> [process_runtime.cpp](../../source/kernel/src/process/process_runtime.cpp) 和
> [v1.2 发布记录](../releases/v1.2.md)。

## 2. 先分离纯调度状态机

v0.9 的 `ProcessScheduler` 不操作 CR3、栈或页表。它只维护：

- capacity 4。
- quantum 4 PIT ticks。
- monotonic 64-bit PID，起始 1。
- 每槽 process id/state/run ticks/dispatch count。
- 当前 index、elapsed quantum 和全局统计。

v0.9 初始状态是 `Unused/Ready/Running/Terminated`；v0.10 加 `Blocked` 和
wait reason；当前头文件显示的是最终 v1.0 状态机。

### 2.1 不变量

- 最多一个 Running。
- 未初始化不能创建/启动。
- quantum 必须非零。
- PID 一经对外分配不因创建回滚而复用。
- Running tick 只记给真正运行的主体。
- 时间片到期但没有其他 Ready 时，不制造自切换和 preemption。
- Terminated 不再参与选择。

### 2.2 Decision 对象

状态机返回：

- previous index。
- current index。
- switched。
- completed。

硬件层根据 decision 执行 CR3/TSS/frame 切换。把“选谁”与“怎样切”分开，宿主
测试无需模拟 CPU 就能验证轮转公平性。

## 3. PCB

当前 PCB 由 [process_runtime.cpp](../../source/kernel/src/process/process_runtime.cpp)
私有定义，主要拥有：

- scheduler slot 对应身份。
- `UserAddressSpace`：root、entry、映射页记录。
- `ExceptionFrame* savedFrame`。
- `ProcessExecutionResult`。
- v1.0 的 8-slot descriptor table。
- v0.11 文件 handle storage。

固定四槽是因为 v1.0 早期 heap 不能 free。PCB 和四份 Kernel stack 都是
Kernel 静态存储，不从用户地址空间分配。

## 4. 每进程地址空间

### 4.1 为什么不能整棵复制 Kernel 页表

所有进程需要相同 supervisor Kernel 映射，但用户程序和栈必须独立。当前四级
布局利用虚拟地址索引分区：

- PML4[0] 的部分子树：低地址 Kernel identity 和 program window。
- program `0x40000000..0x7FFFFFFF` 位于特定 PDPT slot。
- user stack 位于 PML4[255]。
- Kernel 高半区映射由所有进程共享，U/S=0。

### 4.2 `InitializeProcessRoot`

v1.0 算法：

1. 分配新 PML4。
2. 复制 Kernel PML4 的 supervisor entries。
3. 为低端分配/复制必要 PDPT。
4. 清空 program window 子树。
5. 清空 user stack 所在 PML4 entry。
6. 后续为该进程独立创建用户叶。

相同 ELF 的 `0x40000000` 在两个 CR3 中对应不同 physical frame。

当前 v1.6 的页表 frame 可以通过 direct-map 访问，但共享/私有树的所有权语义
不变。

### 4.3 销毁边界

销毁只递归释放进程拥有的：

- program subtree。
- stack subtree。
- 克隆的低端 PDPT。
- process PML4。

共享 Kernel subtree 不能释放。接口拒绝：

- permanent Kernel root。
- 当前 active CR3。
- 未对齐或零 root。

所以终止当前进程前必须先切回 Kernel CR3或另一个进程 CR3。

## 5. 每进程 Ring 0 栈

v1.0 基线的 `process_memory_layout.hpp` 为每槽静态提供：

```text
4 KiB not-present guard
16 KiB usable Kernel stack
```

当进程在 Ring 3 时发生 IRQ/exception/syscall，CPU 使用当前 TSS.RSP0 切到这份
栈。不同进程的 Kernel frame 不会覆盖同一个 privilege transition stack。

所有 process page table 都共享这些 supervisor 栈映射，因此在 IRQ 中先切 CR3
或返回不同 frame 时，Kernel 仍能访问目标 PCB 的 frame。

该历史文件从 v1.1 起已被动态
[kernel_stack_manager.hpp](../../source/kernel/include/os/kernel/memory/kernel_stack_manager.hpp)
与
[kernel_stack_manager.cpp](../../source/kernel/src/memory/kernel_stack_manager.cpp)
替代。每个栈现在取得六页连续 KVA 所有权：

```text
lower guard | 4 × mapped 4 KiB pages | upper guard
```

四个 mapped pages 分别从 buddy 取得 order-0 物理页；销毁必须先回到永久启动
栈，再按“撤销映射 → 释放物理页 → 释放 KVA”的逆序回收。v1.0 历史源码可用：

```bash
git show 65b0e95:source/kernel/include/os/kernel/process_memory_layout.hpp
git show 65b0e95:source/kernel/src/process_memory_layout.cpp
```

本阶段主体仍讲 v0.9/v1.0 的进程语义；动态 KVA 所有权属于 post-v1.0 增量。

## 6. 初始 176 字节 frame

创建进程时还没有一次真实用户中断。Kernel 直接在该进程 Ring 0 栈顶下方构造
与真实入口完全相同的 `UserPrivilegeFrame`：

- 15 个 GPR 清零，RDI 可放 PID。
- vector/error=0。
- RIP=user entry。
- CS=`0x23`。
- RFLAGS=`0x202`。
- user RSP=`0x7FFFFFFF0000`。
- SS=`0x1B`。

调度启动不需要一条专用“假用户调用”返回路径，只要让公共恢复逻辑把它当作一个
已经保存好的 frame。

## 7. 第一次进入调度

`ExecuteProcesses`：

1. 保存原 IF，关闭中断。
2. 标记 scheduling active。
3. `scheduler.Start` 选择第一个 Ready。
4. 激活其 CR3。
5. 设置 TSS.RSP0 为该进程 Kernel stack top。
6. 调用 `osKernelEnterScheduledProcess(savedFrame)`。

汇编入口先保存外层 Kernel 调用链和非易失寄存器到永久 Kernel 栈，再把 RSP
替换为 PCB frame，恢复 GPR，跳过 vector/error，`IRETQ`。

这份外层调用链只保存一次。中间进程切换不返回 `ExecuteProcesses`。

## 8. PIT 抢占

### 8.1 进入 IRQ0

CPU 和 IRQ stub 已把当前用户现场保存在当前进程 Ring 0 栈：

```text
UserPrivilegeFrame at current RSP
```

C++ handler：

1. 把 frame pointer 保存到 current PCB。
2. scheduler `HandleTimerTick` 增加 tick/run time。
3. 若量子未到，返回原 frame。
4. 若量子到且有 Ready，Running→Ready，目标 Ready→Running。
5. 切换目标 CR3。
6. 更新 TSS.RSP0。
7. 返回目标 PCB savedFrame。

汇编公共 epilogue：

```asm
mov rsp, rax
pop registers
add rsp, 16
iretq
```

因此“上下文切换”没有一个神秘的单独 CPU 指令，它是改变恢复现场、页表根和下一
次 Ring0 栈的组合。

### 8.2 切换顺序

概念顺序：

```text
保存旧 frame
  → 更新调度状态
  → 确认目标 frame 可在共享 Kernel 映射访问
  → CR3=目标
  → TSS.RSP0=目标 Kernel stack top
  → RSP=目标 frame
  → IRETQ
```

如果先释放旧地址空间再切 CR3，CPU 仍可能在已释放页表上取指；如果忘记更新
RSP0，目标下一次 syscall 会压到前一个进程的 Kernel 栈。

## 9. 退出和用户异常

Exit 与用户 fault 共用终止骨架：

1. 记录 exit code 或 vector/error/RIP/CR2。
2. 记录 syscall/tick/dispatch/I/O统计。
3. 关闭该进程拥有的资源——v0.10/v0.11/v1.0逐步增加。
4. scheduler 标记 Terminated 并选择后继。
5. 切到 Kernel root 或目标 root。
6. 释放当前进程用户页和私有页表。
7. 若有后继，设置 TSS.RSP0 并返回其 frame。
8. 若全部完成，恢复 permanent Kernel CR3、默认 RSP0 和外层 Kernel 调用链。

Ring 0 fault 从不经过此回收路径冒充普通进程退出，仍 panic。

## 10. v0.9 与 v1.0 的启动工作负载

v0.9 验收：

- 1 个 smoke。
- 3 个 scheduler worker。

三个 worker 在同址 BSS 上各自做三轮大量递增。若错误共享 physical page，
计数会互相污染。PIT 必须产生真实抢占，最终 frame statistics 回到创建前。

v1.0 正常启动已经演进为：

1. Shell。
2. IPC Producer。
3. IPC Consumer。
4. Scheduler Worker。

调度机制相同，工作负载用于同时覆盖控制台、管道、文件和抢占。

## 11. GetProcessId 与入口加固

v0.9 增加 system call 3。Kernel 不从用户 RDI 信任 PID，而从 current PCB
返回。

每次 system call 还检查：

- 当前 frame 位于当前进程 Kernel stack。
- RIP 的 page 是 U/S、executable、not-writable。
- RSP 位于用户 stack 且是 U/S、writable、NX。
- active CR3 与 PCB root 一致。

这些检查能把 frame/CR3/TSS 配错尽早变成分类失败，而不是在任意后续位置崩溃。

## 12. 资源守恒

创建进程前记录 frame statistics，全部退出后再记录。正常情况下：

```text
before.managed  == after.managed
before.free     == after.free
before.allocated== after.allocated
before.reserved == after.reserved
```

仅检查“free 大概一样多”不足以发现状态错误；完整四类统计能发现 allocated→
reserved 等错误转换。

当前 v1.6 的 managed frames 可覆盖 64 GiB，但相同守恒条件仍成立。

## 13. 测试

### Scheduler 单元/随机

- 初始化、非法 quantum、capacity。
- PID 单调和创建回滚。
- round-robin、单进程不自抢占。
- tick/run/dispatch/preemption 守恒。
- terminate/current index。
- v0.10 后的 Blocked 不变量。
- 4096 组固定种子进程数/量子/tick。

### 地址空间集成

- 相同 virtual address 对应不同 frame。
- Kernel supervisor subtree 共享。
- user program/stack subtree 私有。
- process Kernel stack/guard 不重叠。
- destroy 后 frame 恢复。

### QEMU

- 四个 process 创建和终止精确计数。
- worker progress 和 address-space isolation。
- tick/preemption/dispatch 达到语义下界，不固定具体 TCG 时序值。
- 用户 fault 只终止一个进程。
- 最终 `PROCESS_RESOURCES_RECLAIMED`。

## 14. 常见故障

### 第一次 IRETQ #GP

检查 initial frame 顺序、CS/SS、canonical RIP/RSP 和 RFLAGS。

### 第一次 PIT 后崩溃

检查 IRQ common path 是否保存了 frame、C++ 返回 pointer 是否有效、目标 frame
是否位于共享 Kernel mapping。

### syscall 后写错进程

检查 TSS.RSP0 是否随 CR3/PCB 同步更新，current scheduler index 是否已在
IRETQ 前切换。

### 退出后 frame 泄漏

逐类统计 user leaf、intermediate page tables、PML4 和失败回滚；不要只释放
ELF data pages而遗留 stack 或页表。
