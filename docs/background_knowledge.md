# 背景知识：从宿主机到 x86-64 复位向量

本文建立阅读和开发本项目所需的共同知识基础。它不假定宿主机是 x86-64，也不假定读者已经写过引导程序或内核。

## 1. 我们究竟在构建什么

普通应用程序启动时，操作系统已经替它完成了大量工作：

- 建立虚拟地址空间。
- 加载可执行文件。
- 初始化栈和线程。
- 提供文件、终端、时钟和内存分配接口。
- 初始化 C/C++ 运行时，然后调用 `main`。

操作系统代码面对的环境完全不同。CPU 复位后没有进程、文件系统、系统调用、标准输出，也没有可以依赖的 C++ 运行时。本项目的学习目标，就是把普通程序看不见的这些层逐一实现。

项目最终的控制流是：

```text
CPU 复位
  ↓
自研 ROM 固件
  ↓
自研 Stage 1 / Stage 2
  ↓
ELF64 内核
  ↓
Ring 3 用户程序
  ↓
Shell 与基础命令
```

QEMU 只模拟 CPU、内存和设备。箭头之间的加载、校验、状态切换和数据交接全部由项目代码完成。

## 2. 宿主机和目标机

### 2.1 Host

宿主机是执行编译器、测试程序和 QEMU 的机器。当前开发环境可以是 AArch64，也可以是 x86-64。

宿主机负责：

- 运行 CMake、Clang、LLD 和 NASM。
- 执行不依赖硬件的快速测试。
- 生成 ROM、磁盘和 ELF 文件。
- 运行 QEMU TCG。

### 2.2 Target

目标机是我们正在实现的软件最终运行的环境，固定为 x86-64 PC 硬件模型。

目标代码不能因为宿主机是 AArch64 就生成 AArch64 指令。项目通过：

```text
clang++ --target=x86_64-unknown-none-elf
```

明确要求 Clang 生成 x86-64 ELF 目标文件。构建后再使用 `llvm-readelf` 检查 ELF
头中的 `Machine` 字段，确保它是 `Advanced Micro Devices X86-64`。

这叫交叉编译：编译动作发生在宿主机，生成物面向另一套目标架构和运行环境。

## 3. QEMU TCG 解决了什么

QEMU 有两类容易混淆的职责：

1. 模拟或虚拟化硬件。
2. 附带或加载固件、操作系统镜像。

本项目只使用第一类能力。

TCG 是 QEMU 的动态二进制翻译引擎。它可以把目标 x86-64 指令转换成宿主机指令，因此即使宿主机是 AArch64，也可以运行 x86-64 CPU 模型。

我们允许 QEMU 提供：

- x86-64 CPU。
- 物理内存。
- PC 芯片组和总线。
- 串口、IDE、PIC、PIT、键盘等设备模型。
- GDB 调试接口。

我们不允许 QEMU 或第三方替代：

- ROM 固件。
- 磁盘引导代码。
- 16 位、32 位、64 位模式切换。
- ELF64 内核加载。
- 内核、运行时和驱动。

因此正式运行命令必须显式使用自研 `-bios` 镜像，不能依赖 QEMU 默认寻找的
SeaBIOS 或 OVMF，也不能使用 `-kernel` 绕过加载链。

## 4. CPU 复位后发生什么

### 4.1 复位向量

x86 CPU 复位后会从物理地址 `0xFFFFFFF0` 附近开始取指。这个位置称为复位向量。

复位状态有一个容易忽略的细节：此时 `CS` 的可见选择子、隐藏基址和指令指针共同形成复位地址。它不能简单等同于普通实模式下的 `segment << 4 + offset`。固件通常会在复位向量放置一条近距离可编码的跳转，再进入 ROM 中更完整的初始化代码。

本项目使用 128 KiB ROM：

```text
ROM 起始地址     0xFFFE0000
复位向量         0xFFFFFFF0
4 GiB 边界       0x100000000
```

复位向量位于 ROM 的最后 16 字节区域。`v0.1` 已通过链接脚本、最终二进制
审计和 QEMU 实际执行共同验证这一布局。复位向量字节 `E9 0D F0` 是一个
16 位 near jump：它保留 CS 隐藏基址，把 IP 从下一条指令位置跳到
`0xF000`，最终进入物理地址 `0xFFFFF000`。

### 4.2 初始环境

复位后的环境非常受限：

- 代码从 16 位环境开始。
- 没有可用的 C++ 栈和运行时。
- 中断表、描述符表和页表尚未由我们建立。
- RAM 和设备状态不能按普通应用程序的假设使用。
- 任何输出能力都必须先初始化硬件。

因此最早期代码必须使用少量 NASM Intel 语法汇编。只有建立可靠的栈、明确 ABI
和必要运行时边界后，才进入 freestanding C++20。

## 5. 从 16 位到 64 位

项目会逐步经历三种主要执行模式。

### 5.1 Real Mode

实模式保留早期 x86 的分段寻址模型，默认操作数和地址宽度较小。复位代码和最早期固件在这里执行。

### 5.2 Protected Mode

进入保护模式前需要准备 GDT，并设置 `CR0.PE`。保护模式提供描述符、权限和
32 位执行环境，是进入长模式的中间阶段。

### 5.3 Long Mode

进入 64 位长模式通常需要：

1. 准备至少覆盖当前代码、栈和必要数据的页表。
2. 设置 `CR4.PAE`。
3. 将页表物理地址写入 `CR3`。
4. 设置 `IA32_EFER.LME`。
5. 设置 `CR0.PG` 开启分页。
6. 通过远跳转加载 64 位代码段。

这些步骤有严格顺序，任何一个地址或控制位错误都可能导致异常、三重故障和 CPU
复位。项目不会一次写完整切换，而会为每个状态增加串口标记、GDB 检查点和失败路径。

这条转换链已在 `v0.3 Long Mode` 完成。Stage 1 对 A20、页表和关键控制位
执行写后读回检查，并在 64 位入口输出独立串口里程碑。

## 6. Freestanding C++20 是什么

C++ 标准区分 hosted 和 freestanding 环境。

普通桌面程序处于 hosted 环境，可以假定：

- 程序从标准运行时进入 `main`。
- 标准库和系统调用可用。
- 异常、RTTI、线程局部对象和全局析构得到运行时支持。

内核早期代码属于 freestanding 环境。这并不意味着不能使用现代 C++，而是每项特性都必须确认不会引入未实现的运行时依赖。

当前目标构建关闭：

- 异常。
- RTTI。
- 栈保护。
- 线程安全局部静态初始化。
- `__cxa_atexit` 全局析构注册。
- 位置无关代码。
- x86-64 红区。
- MMX 和 SSE 自动生成。
- 宿主 C++ 标准库头文件。

### 为什么关闭红区

System V AMD64 ABI 允许普通用户程序使用栈指针以下 128 字节的红区。但内核中断可能在任何时刻使用当前栈，如果编译器把临时值放在红区，中断入口可能覆盖它们。因此内核目标使用 `-mno-red-zone`。

### 为什么暂时关闭 SSE

在内核初始化 FPU/SSE 状态和上下文切换策略之前，编译器自动生成 SSE 指令会引入隐藏前置条件。早期目标先使用通用寄存器，等建立明确策略后再决定如何开放。

### 现代 C++ 仍然有价值

freestanding 不等于退回 C 风格。项目仍然优先使用：

- 强类型区分物理地址、虚拟地址和字节数。
- `enum class` 表达有限状态。
- `constexpr` 和编译期检查表达硬件约束。
- RAII 表达中断状态、锁和资源生命周期。
- concepts 约束模板接口。
- 明确返回类型表达错误。

前提是检查生成代码和符号，确认没有隐藏运行时依赖。

## 7. 编译、链接和镜像不是一回事

### 7.1 目标文件

Clang 将每个 `.cpp` 编译为 ELF 可重定位目标文件。目标文件包含机器指令、数据、符号和重定位信息，但通常还不能直接执行。

### 7.2 静态库

`v0.0` 将 `foundation` 目标文件封装为：

```text
libos_foundation_x86_64.a
```

静态库只是目标文件集合。它用于验证：

- 能否生成 x86-64 ELF。
- 是否满足 freestanding 编译限制。
- 是否意外引用外部运行时符号。

它不是 ROM，也不是内核。

### 7.3 链接产物

从 `v0.1` 开始，LLD 根据链接脚本决定：

- 每段代码和数据的虚拟地址与加载地址。
- 复位向量必须落在 ROM 的哪个偏移。
- 哪些符号作为阶段入口。
- 最终 ELF 或二进制镜像如何排列。

### 7.4 ROM 和磁盘镜像

ROM 是 QEMU 映射到固件地址空间的原始字节序列。磁盘镜像是 IDE
设备对外呈现的扇区集合。两者都不是普通宿主机可执行文件。

## 8. 为什么先实现地址类型

操作系统中的很多错误来自“都是整数”：

- 把物理地址当成虚拟地址。
- 把结束地址当成长度。
- 把页号当成字节数。
- 地址加长度发生无符号溢出。
- 一个模块使用闭区间，另一个使用半开区间。

`v0.0` 首先实现：

- `PhysicalAddress`
- `ByteCount`
- `AddressRange`
- `AddressRangeCreationStatus`

地址区间统一采用半开语义：

```text
[begin, end)
```

也就是包含 `begin`，不包含 `end`。半开区间的好处：

- 长度直接等于 `end - begin`。
- 空区间自然表示为 `begin == end`。
- 相邻区间 `[a, b)` 和 `[b, c)` 不重叠。
- 循环边界和内存拷贝长度更容易一致。

创建区间前必须验证 `begin + size` 是否能用 64 位结束地址表示。失败返回
`AddressOverflow`，并保证调用方的输出对象保持不变。

## 9. 为什么需要四层测试

只使用 QEMU 测试所有逻辑会使反馈慢、定位困难；只使用单元测试又无法验证真实硬件交互。因此项目采用四层测试。

### 单元测试

验证单个类型和函数的明确样例、边界与失败路径。

### 集成测试

把多个领域事实组合起来，例如检查 ROM、复位向量、Stage 1 和内核计划加载区间是否冲突。

### 固定种子随机测试

生成大量地址和长度，验证以下性质：

- 所有合法区间都能创建。
- 创建后长度保持不变。
- 非空区间包含首字节和末字节。
- 半开区间不包含结束地址。
- 非空区间与自身重叠。
- 相邻区间不重叠。
- 溢出输入必须被拒绝。
- 创建失败不得修改输出对象。

当前随机测试使用固定种子运行 10,000 组输入，共执行 100,000 次断言。固定种子保证本地和 CI 可以复现相同序列。

### QEMU 系统测试

`v0.0` 的空镜像测试继续保存为硬件环境回归基线。`v0.1` 增加真正的启动测试：
QEMU 从自研 ROM 复位，固件输出 `RESET` 和 `SERIAL_READY` 后进入 HLT。
宿主在两秒预算结束后验证串口协议。

同一份 NASM 源码还能生成故障镜像：第一条日志完成后，固件让发送等待函数看
不到 THRE 就绪状态。轮询到 `0xFFFF` 次上限后返回失败并停机。测试要求
`RESET` 存在且 `SERIAL_READY` 不存在，从而证明错误路径真实可达。

## 13. v0.4 为什么采用两遍 ELF 装载

ELF 是链接器与加载器之间的二进制契约。`PT_LOAD` 不只是“要复制的字节”，
还同时声明文件区间、内存区间、权限、对齐和零初始化尾部。Stage 1 不能因为
文件有 ELF magic 就信任其余字段。

本项目当前把 ELF 暂存到经 E820 验证的 `0x03E00000`，第一遍验证全部程序头：

- 文件偏移和长度没有溢出，且落在精确文件范围。
- `p_filesz <= p_memsz`，内存段非空。
- 当前阶段 `p_vaddr == p_paddr`，并落在低 64 MiB 的加载窗口。
- 段按 4 KiB 对齐，文件偏移和虚拟地址的页内偏移相同。
- 所有加载段可读，不含未知权限位，不同时可写和可执行。
- 任意两个加载段不重叠。
- 固定入口位于可执行加载段。

只有所有程序头都通过，第二遍才复制 `p_filesz`，并清零
`p_memsz - p_filesz`。这种设计的关键不是代码形式，而是副作用边界：不可信
ELF 在验证失败前不能把目标内存改成“装了一半”的状态。

BSS 的历史来源是早期汇编器的 Block Started by Symbol 区域。零初始化对象
不必在磁盘文件中重复保存大量零字节，因此 ELF 允许 `p_memsz` 大于
`p_filesz`。加载器如果不显式清零，C++ 对静态存储期零初始化的语言保证就会
被破坏。本项目用内核 BSS 探针把这条隐含前提变成 QEMU 可见证据。

## 14. BootInfo 与第一次 C++ 交接

进入 64 位模式只表示处理器能执行 64 位指令，不等于已经建立 C++ 运行环境。
Stage 1 需要同时保证：

- RDI 指向有效的 104 字节 BootInfo v2。
- RSP 使用与加载区分离的 64 KiB 栈，并符合 System V AMD64 调用约定。
- 方向标志保持清零，分页仍覆盖入口、数据、栈和串口代码。
- 内核不依赖构造函数、异常、RTTI、标准库或宿主运行时。

BootInfo 的十三个字段全部使用 `uint64_t` 对应的固定宽度 ABI。它记录魔数、版本、
结构大小、原始 ELF 文件位置与长度、入口、加载段数、CR3 根地址、恒等映射
大小、栈顶、物理内存图地址、条目数和条目宽度。内核重新验证这些内容，并独立初始化 COM1；因此控制权交接不是
“跳过去没死”，而是由 `BOOT_INFO_VALID`、`BSS_ZEROED`、`CR3_VALID` 和
`READY` 四个连续证据证明。

## 15. 为什么长模式仍然需要 GDT、TSS 和 IDT

x86-64 长模式弱化了传统分段：代码和数据段的 base/limit 大多不再参与普通
地址计算。但“弱化”不等于删除。CS 仍保存当前特权级和 64 位代码属性；
从用户态进入内核仍需要合法代码段；TSS 仍为特权切换提供 RSP0，并为关键异常
提供 IST；IDT gate 仍引用代码段选择子。

这来自 x86 的兼容演化历史。保护模式先用描述符把内存、特权和任务状态组织在
一起；64 位时代把地址隔离主责交给页表，却保留选择子和门机制，避免彻底重做
中断与特权模型。因此一个教学内核不能因为“不做传统分段”就省掉 GDT。

Stage 1 的 GDT 只解决“怎样进入长模式”。内核自己的 GDT 解决“内核长期使用
哪些代码段、数据段和 TSS”。两者职责不同。v0.5 在 C++ 入口已经可靠后立即
接管描述符表，避免后续内存、中断和用户态建立在加载器私有状态之上。

### 为什么异常需要汇编入口

普通 C++ 函数由调用者按 ABI 放置返回地址和参数；异常由处理器按架构规则压入
RIP、CS、RFLAGS，有时再压错误码，特权切换时还会压旧 RSP 和 SS。它不是一次
普通 `call`。

每个 NASM 桩先把“有无硬件错误码”的差异规范化，再保存通用寄存器、清 DF 并
对齐栈，最后才调用 C++20。返回时必须严格逆序恢复并用 `IRETQ`，普通 `ret`
既不会恢复 CS/RFLAGS，也会把现场解释错。

### fault、trap 和 abort

- fault 通常把保存 RIP 指向故障指令；处理原因后可以重试，例如页不存在。
- trap 通常在指令完成后报告，保存 RIP 指向下一条，例如 `INT3` breakpoint。
- abort 表示严重状态，处理器不保证能够可靠重启，例如双重故障。

因此不能写一个“所有异常都把 RIP 加一”的处理器。当前只允许已知的 `INT3`
自检返回，其余异常 panic。v0.6 虽然已经建立内存所有权，但尚未拥有进程地址
区间、后备对象和回收策略，因此不急于让普通页故障恢复。

### 为什么 panic 必须比普通日志更简单

panic 可能发生在页表、栈、堆、锁或日志模块已经损坏时。如果它再分配内存、
获取锁或执行复杂格式化，就可能重复触发原故障并刷屏。当前 panic 只依赖已经
验证的串口端口、当前异常帧和少数控制寄存器：

- 禁止中断。
- 用单个 BSS 状态位阻止递归。
- 输出向量、错误码、RIP、CS、RFLAGS。
- 页故障额外输出 CR2。
- 进入 HLT 循环。

这不是最终崩溃系统，而是早期内核的最小可信诊断基座。

## 16. 为什么内存管理要同时讨论所有权、翻译和权限

“机器有 64 GiB RAM”不等于 `0..64 GiB` 每个物理地址都能分配。固件或平台需要描述哪些
区间是 RAM、保留区或设备窗口；内核把可用区间按 4 KiB 切成页帧，再记录每帧
处于空闲、动态占用还是启动保留状态。这是物理所有权。

程序产生的是线性地址。x86-64 通过 PML4、PDPT、PD、PT 四级结构查到物理页，
并在每一级累积 present、writable、user 和 NX 权限。这是地址翻译与访问控制。
物理分配器不知道一个页帧映射在哪里，页表也不能独自判断某个物理页是否已经
属于别人，因此两个模块必须分开。

### 为什么采用 `fw_cfg`，却不让 QEMU 替我们做内核

QEMU PC 的 `fw_cfg` 是端口可访问的配置硬件。它提供 `etc/e820` 原始数据，
但不会替来宾解析大端目录、验证长度、排序、处理重叠或分配页面。项目选择它与
选择模拟 UART、IDE 一样：QEMU 只表现设备，软件协议由自研 Stage 1 完成。

传统 BIOS E820 是软件中断服务；本项目没有外部 BIOS，临时借用会破坏完整
启动链。未来若换平台，只需让新的固件后端产生同一种 24 字节规范化内存图，
内核不必知道数据来自 `fw_cfg`、ACPI 还是其他机制。

### 为什么 64 GiB 规格不能写成 64 GiB 常量

QEMU 的 `-m 64G` 是一次机器配置，不是内核 ABI。x86-64 处理器能够放进
页表项的物理地址位数由 `CPUID.80000008H:EAX[7:0]` 报告；平台实际 RAM
来自 E820；内核当前能为物理内存保留多大的连续虚拟窗口又是第三个约束。
受管上限必须取三者最小值。这样同一份代码可以在 64 MiB 回归配置、64 GiB
主配置和未来更大配置上工作，超过当前 64 TiB direct-map 时也会明确截断，
而不是发生地址回绕。

E820 中“最高被描述地址”和“最高可用 RAM 地址”也不是同一个概念。PC 地址
空间包含 PCI、固件和 MMIO 洞；本项目的 64 MiB 配置还会描述延伸到 1 TiB
的高地址保留窗口。如果按最高描述地址计算 PFN 元数据，少量 RAM 会被巨大的
保留洞放大。正确上界取最高 type 1 RAM 完整页末端，保留条目只负责阻止分配。

### 为什么需要高半区物理直映

物理地址是总线和页表使用的编号，不天然是 C++ 可以解引用的虚拟地址。早期
身份映射恰好令两者数值相等，容易诱导代码把
`reinterpret_cast<uint8_t *>(physical_address)` 当成永久接口；一旦页帧位于
4 GiB 以上或低端身份映射被缩小，这个假设立即失效。

direct-map 为普通 RAM 建立稳定关系：

```text
virtual = 0xFFFF888000000000 + physical
```

页表项和 CR3 继续保存物理地址；页表遍历、用户页清零和 ELF 复制需要访问内容
时才执行上述转换。未被 E820 标为 type 1 的洞不建立映射，LAPIC 等设备另用
cache-disabled MMIO 映射。这样“地址翻译”和“页帧所有权”仍是两个独立问题。

### 为什么同时使用 2 MiB 与 4 KiB 页

64 GiB 若全部使用 4 KiB PTE，需要 16777216 个叶项和约 32 MiB 叶页表；
若内部对齐区域使用 2 MiB PDE，只需 32768 个叶项。更少的页表内存和 TLB
覆盖压力适合大范围直映。4 KiB 页仍用于 E820 非对齐边界、权限精细的 Kernel
段、用户页与 guard page。大页不是全面替代小页，而是让“映射粒度”服从用途。

### 为什么 `CR0.WP` 对内核只读页至关重要

页表 RW=0 并不总能约束最高特权代码。x86 的 `CR0.WP` 位决定 supervisor
写访问是否也遵守只读权限。只把 `.rodata` 表项标成只读，却不设置 WP，
Ring 0 仍可能写坏常量。

v0.6 不只读取页表项确认 RW=0，还专门映射一页只读数据并让 Ring 0 写入。
预期 #PF 错误码 `0x3`：P=1 表示映射存在，W/R=1 表示写访问，U/S=0 表示
supervisor。CR2 必须等于测试地址。硬件异常把软件意图升级成处理器执行证据。

### 为什么内存分配器要分层演进

启动期需要少量生命周期覆盖整个内核的对象；此时还没有并发、等待队列、页回收
和进程地址空间。单调分配器只移动一个已用偏移，容易验证对齐、溢出和容量。
缺点是不能释放，所以它不是通用堆。v1.1 先用 buddy 处理连续物理页所有权，
再用边界标记堆处理已经映射区间中的任意字节块；这两个分配器回答的问题不同，
不能因为都叫“分配”就合并。

固定尺寸内核对象又有第三种形状。若每个 64 字节对象都走通用堆，每次仍要
搜索空闲块、携带块头并承担外部碎片。SunOS 在 1980 年代末提出 slab 思路：
把同一类型对象排列在专属后备区中，复用已准备好的槽；后来 Linux 的
SLAB/SLUB 继续扩展了多 slab 状态、per-CPU 快速路径与调试能力。它们的核心
动机不是“另写一个 malloc”，而是利用对象尺寸、对齐和生命周期同构。

本项目当前先实现最小固定容量形式：一个通用堆后备块，块首是活动位图，后面
是等步长槽。活动槽归调用者，空闲槽首 8 字节借作下一空闲索引。位图用于拒绝
重复释放，槽内链让申请/释放保持常数时间；对象全部归还后，整个后备块才能
销毁。它暂不处理多 slab 增长、构造析构、per-CPU 缓存和内存压力回收，因为
这些能力分别依赖 KVA、对象模型和并发语义。按这种顺序，读者可以从测试失败
中明确区分页所有权、字节堆布局和类型槽状态。

### 为什么“页表里没有映射”仍不等于“虚拟地址空闲”

早期实模式和简单身份映射让地址看起来像物理位置；现代分页则把线性地址变成
一种由软件组织、由硬件翻译的命名空间。页表叶项只编码当前翻译与权限：
present=0 时，处理器会产生页故障，却不会告诉我们这一页为何缺席。

同一个 not-present 状态至少可能表示：

- 地址从未分配，可以交给新对象；
- 地址已经属于动态栈的 guard，必须继续缺席；
- 地址已经许诺给一个对象，但物理页尚未准备好；
- 映射刚被撤销，所有者仍在等待其他 CPU 的 TLB 失效；
- 地址永久保留，用于捕获零偏移或布局越界。

因此直接扫描页表寻找零叶项会丢失软件所有权。物理页分配器也无法代替它：
一组非连续物理页可以映射成连续虚拟区间，同一物理页在受控场景又可能出现
多个别名。物理所有权、虚拟区间所有权和翻译关系必须是三套可以交叉验证但不
互相假装的状态。

这种需求在早期 Unix 的内核地址空间还较小时不明显。随着内核模块、动态 I/O
映射和非连续页后备增多，内核需要类似 `vmalloc` 的区域：先保留一段连续虚拟
地址，再逐页接入物理后备。Linux x86-64 也把 direct map 与 vmalloc 区分：
前者按固定偏移访问普通 RAM，后者为动态虚拟连续映射提供命名空间。这里借鉴
的是分层理由，不是调用 Linux 或复制其实现。

### 为什么 32 TiB KVA 不适合逐页位图

32 TiB 包含：

\[
\frac{32 \times 2^{40}}{2^{12}} = 2^{33} = 8589934592
\]

个 4 KiB 页。每页一位需要 \(2^{30}\) 字节，即 1 GiB；如果还要区分保留、
活动和空闲，位数至少翻倍。当前学习内核同时存在的动态区间只有个位数到数百，
按潜在页数付费会让元数据远大于实际内核。

当前实现改为保存有主区间。窗口首尾和相邻有主区间之间天然形成空闲缝隙；
删除一个有主区间后，两侧缝隙自动连成一个更大空闲区，不需要空闲节点合并。
256 个描述符每项 24 字节，只需 6144 字节。扫描、插入和删除是 \(O(N)\)，
但 \(N\) 有明确小上界，完整遍历也更容易证明无重叠和计数守恒。

这不是宣称数组永远优于树。等到并发映射和对象数证明 256 项不够时，可以把
索引替换为平衡树或分片结构；现在提前引入树旋转、节点分配和锁，只会让错误
难以归因。

### 为什么对齐要作用于绝对虚拟页号

假设调用者请求“8 页对齐”。真实要求是虚拟地址低 15 位为零，因为
\(8 \times 4096 = 32768\)。若只把窗口内偏移对齐，窗口基址本身不按 8 页
对齐时，结果仍不满足硬件或对象布局要求。KVA 先把候选地址除以 4096 得到
绝对页号，再按二次幂向上对齐，最后转换回地址。

best-fit 比较可容纳请求的原始空闲缝隙大小，同大小保留低地址。它减少持续
切割大空洞的倾向，但不能消除外部碎片；统计中的最大连续空闲页数因此和总
空闲页数同样重要。

### 为什么 guard 页也必须占有 KVA

保护页的价值正来自“不映射”。若它没有软件所有者，下一次地址搜索就可能把
这页交给别的对象并建立映射，原栈的越界访问将不再触发 #PF。正确的动态栈
形状是：

```text
一个 KVA 所有权区间
┌────────────┬────────────────────────────┬────────────┐
│ lower guard│ mapped stack/data pages    │ upper guard│
│ not-present│ supervisor RW + NX         │ not-present│
└────────────┴────────────────────────────┴────────────┘
```

KVA 负责三段共同不被复用；页表只为中间数据页建立叶项；buddy 只拥有真实
后备页。当前动态内核栈已经按这个形状落地：六页 KVA 区间中，上下各一页
guard，中间四页形成 16 KiB 可用栈。销毁时先撤销映射和 TLB，再归还物理页，
最后释放整个 KVA 区间。这个逆序与构造依赖相反，是后续所有跨层资源事务的
基本模式。

### 为什么四个栈页不要求物理连续

程序看到的 RSP 是虚拟地址，处理器每次访存都经页表把所在虚拟页翻译到对应
物理帧。只要四个虚拟数据页连续，跨页的 push、局部变量和保存帧便具有连续
语义；它们背后的 PFN 可以完全分散。强制申请 order 2 连续块不会让普通栈
访问更快，却会让 Thread 创建受外部物理碎片影响。

DMA 环形缓冲、某些大页或设备描述符可能有真实物理连续约束，内核栈没有。
当前实现因此逐页申请四个 order-0 帧，并在完整校验中证明四帧互不相同。
这也是“虚拟连续”和“物理连续”必须分开学习的直接例子。

### 为什么上下都保留 guard

x86-64 栈按约定向低地址增长，所以 lower guard 能捕获常见的深递归和大局部
变量溢出。但硬件并不禁止代码把 RSP 错设到栈顶以上，也不禁止通过正偏移写
出当前帧；只有 lower guard 会让这类错误进入相邻对象。upper guard 不消耗
物理页，只占一页 KVA 所有权，因此当前布局使用对称边界。

guard 不是完整的内存安全方案。一次跨越整张 guard 页的大跨度错误可能直接
落到更远的合法映射；它提供的是低成本、确定性的邻接越界检测。更强诊断需要
更宽隔离、栈高水位、编译器插桩或地址消毒器类机制。

### 为什么终止栈必须延迟到安全点回收

在系统调用、异常或 IRQ 的 C++ 处理器中，当前局部变量、返回地址和保存现场
都位于当前进程内核栈。把调度状态改为 `Terminated` 只改变软件状态，不会让
CPU 自动换到别的 RSP。若此时撤销栈 PTE，下一次函数返回或局部变量读取就会
在 Ring 0 产生 #PF。

正确路径先选择下一进程并从其保存帧返回用户态，或让汇编恢复调用
`OsKernelEnterScheduledProcess` 前保存的永久启动栈。只有回到 C++ 调度循环，
并读取 RSP 证明它不在任何待销毁栈中，才可以 unmap、清零物理页并释放 KVA。
这种“发布终止状态—稍后 reap”与 Unix 的 zombie 思想不是同一个对象，但
共享一个原则：逻辑退出和物理销毁可能需要不同的安全时刻。

### 为什么共享页表根不能回收最后一张 PDPT

早期分页实现常把“页表项不再 Present”近似成“这张表可以释放”。这只对完整
独占的树成立。x86-64 页表项没有父指针、引用计数或所有者字段；处理器只把
其中的物理地址解释为下一层表。复制一个 PML4 项不会复制其 PDPT、PD 和 PT，
而是产生另一个指向同一子树的硬件引用。

本项目为进程地址空间复制内核高半 PML4 项。内核根撤销 KVA 最后一张叶映射
后，PT 和 PD 只在这条内核分支内使用，可以安全归还；PDPT 却仍可能由已经
创建的进程 PML4 项指向。若仅扫描当前内核根发现分支为空便释放 PDPT，这些
进程根中的父项不会自动清零。物理帧随后可能交给别的对象，而处理器仍会把
新内容当页表解析，结果是最危险的一类 use-after-free。

因此当前管理器显式区分三种根所有权：

```text
Exclusive    整棵树独占，空分支可从 PT 一直回收到 PDPT
KernelShared 高半入口会被进程根借用，只回收 PT 和 PD
Process      只修改并回收自己的用户程序/栈分支
```

这里保留一张共享 PDPT 是所有权协议，不是泄漏。启动仍先执行一次单页“暖机”，
但目的已经变为证明边界：映射创建 PDPT、PD、PT，撤销必须回收低两级并精确
保留一级。随后的四叶 KVA 事务重新创建并回收 PT/PD；整机最终报告两张 PT、
两张 PD、零张 PDPT 被回收，以及一张共享 PDPT 被有意保留。

### 为什么空表检查要比较完整 64 位表项

Present 位只决定处理器当前是否继续页表遍历。操作系统仍可在非 Present 表项
中保存 swap 标识、软件状态或暂存地址；即使本阶段还没有 swap，看到非零项
也不能证明它没有意义。因此回收“除将要解除的子项外为空”的表时，检查的是
其余 511 个原始 64 位值是否为零，而不是只检查 bit 0。

这也解释了撤销操作为什么分为预检和提交。预检先验证整条路径、精确 order-0
页帧所有权、无祖先环和空表条件；任何失败都不碰叶项。提交才清 PTE、执行
一次 `INVLPG`，再从子到父解除并释放空表。否则在检查上级时才发现损坏，
已经清掉的叶映射无法可靠恢复。

映射方向面临对称问题：建立四级路径可能在第三次申请时耗尽内存。只释放最后
一次申请并不够，早先创建的空表和对既有父项 U/S 位的提升也必须撤销。因此
实现记录父项原值与每张新表帧，并在失败时反序恢复。这是数据库事务“先记录、
后提交、逆序回滚”在内核资源生命周期中的一个小型实例。

## 17. 为什么 PIC 已有待处理中断，CPU 仍可能收不到

传统 PC 的 8259A 通过 INTR 把请求送给处理器；后来 APIC 加入后，兼容系统用
“虚拟线模式”把 PIC 输出接到本地 APIC 的 ExtINT 输入。商业 BIOS 通常完成
这段平台设置，但本项目从复位开始没有外部 BIOS。

因此“PIC 重映射 + 开 IRQ0 + STI”隐含了一个并不存在的前置条件。v0.7 的
真实 QEMU 诊断曾同时看到：

- PIT 已产生数百个 IRQ0。
- PIC IRR bit0 已置位，IMR bit0 已清零。
- RFLAGS.IF=1，CPU 正在 HLT。
- IDT 向量 32 已存在，却从未进入。

这说明设备、控制器和 CPU 本身分别“看起来正确”，但它们之间的路由没有建立。
当前单核阶段显式建立 virtual-wire：映射 LAPIC MMIO 页，保持全局启用，
设置 Spurious Interrupt Vector Register 的软件启用位，再把 LVT LINT0
配置为未屏蔽的 ExtINT。PIC 的输出因此经 LAPIC 进入处理器；将来实现
I/O APIC 时再引入重定向表、LAPIC EOI 和目标 CPU 选择。兼容历史不是背景
趣闻，它直接决定初始化序列。

### 为什么中断入口不能直接写成普通 C++ 函数

设备事件没有 C++ 调用者。CPU 只保存 RIP、CS、RFLAGS，PIC 不提供错误码，
普通 ABI 也不保证其余寄存器已保存。汇编桩必须补齐统一帧、清 DF、保存通用
寄存器和修正栈对齐，C++ 才能安全分类 IRQ。返回必须用 `IRETQ`，随后再由
处理器恢复 RFLAGS.IF。

### 为什么时钟中断不应打印每一次 tick

1000 Hz 的串口日志会让 115200 波特 UART 成为系统主要工作：一条几十字节
记录的发送时间远大于 1 ms，下一次 IRQ 又会在输出期间到达。结果既不是好的
日志，也不是好的时钟。ISR 只更新固定宽度计数，低频边界汇总，宿主另以单调
时间标记每条串口行。这把“来宾时间语义”和“测试观察延迟”分开。

### 为什么 QMP 注入仍然满足只让 QEMU 模拟硬件

QMP `sendkey` 相当于测试人员按下虚拟键盘。它让 QEMU 的键盘设备产生扫描码，
不会替来宾读取 `0x60`、发送 PIC EOI、构造 IDT 帧或调用解码器。与测试人员
在图形窗口按键相比，它只是可自动复现的输入方式，而不是引导器或驱动替代品。

## 18. 为什么 Ring 3 不是一次普通函数调用

### 特权级来自三个数字的共同检查

x86 保护模型里经常同时出现 CPL、DPL 和 RPL：

- CPL 是当前代码段选择子的低两位，描述正在执行的特权级。
- DPL 保存在段描述符或门描述符中，描述目标允许的特权边界。
- RPL 是选择子低两位，请求者不能用一个“看起来更高权限”的选择子绕过检查。

数字越小权限越高。内核 CS=`0x08` 的 RPL 为 0；用户 CS=`0x23` 的低两位
为 3。内核不能靠修改一个 C++ 状态变量宣称自己进入用户态，必须让 CPU 通过
`IRETQ` 装载 DPL3 代码段，随后由硬件把 CPL 变成 3。

长模式下，普通代码和数据段不再像 16 位时代那样承担线性地址重定位，但
present、type、DPL 和代码段 L 位仍然生效。分段从“主要地址翻译机制”退到
“特权与执行属性机制”，这是 x86 历史兼容留下的形状。

### 为什么降权帧有五项

同特权级异常只需保存 RIP、CS、RFLAGS；发生 CPL3→CPL0 或反向恢复时还必须
保存/装载栈的 SS 与 RSP。因此首次进入用户态构造：

```text
高地址  SS=0x1B
        RSP=用户栈顶
        RFLAGS=0x202
        CS=0x23
低地址  RIP=ELF 入口
```

`IRETQ` 从低地址方向依次取出状态。`0x202` 中 bit 1 是架构要求的保留位，
IF 让已初始化硬件中断在用户态也能到达；IOPL 仍为 0，所以用户不能直接执行
受保护端口 I/O。

### 为什么系统调用必须先换栈

用户栈属于不可信地址空间，可能指向 guard、只读页或攻击者构造的数据。若内核
一进入就把返回地址和寄存器压在用户栈上，最需要保护的入口反而依赖攻击者。
64 位 TSS 的 RSP0 告诉 CPU：从较低权限进入 Ring 0 时先换到哪个栈。

这个栈也不能是等待用户函数“返回”的原内核栈。系统调用硬件压帧会覆盖原调用
链，exit 再恢复时就可能跳到损坏地址。v0.8 使用独立特权转换栈，并显式保存
进入用户态前的内核 RSP；exit 或异常直接丢弃转换栈，回到那条调用链。

### 页表 U/S 为什么必须逐级传播

x86-64 四级页表的有效权限是路径上各级限制的组合。只给 PT 叶项设置 U/S，
若 PML4E、PDPTE 或 PDE 仍是 supervisor，用户访问依然页故障。反过来，把
中间项设为 user 不会自动泄露内核叶页；最终叶项仍必须允许 user。

页故障错误码可以直接说明硬件判定：

| bit | 名称 | 为 1 的含义 |
| --- | --- | --- |
| 0 | P | 保护冲突；为 0 是 not-present |
| 1 | W/R | 写访问 |
| 2 | U/S | 访问来自 CPL3 |
| 3 | RSVD | 页表保留位非法 |
| 4 | I/D | 取指访问（启用相关能力时） |

v0.8 用户页故障得到 `0x4`：P=0、W/R=0、U/S=1，即用户读未映射地址。
v0.6 内核写保护测试的 `0x3` 则是 present、write、supervisor。两个结果把
同一个 #PF 向量背后的不同原因区分开。

### 为什么 ELF 只是文件契约，不是信任证明

ELF 的程序头告诉加载器“把哪些文件字节放到哪些虚拟地址并赋予什么权限”，
但文件可以恶意或损坏。加载器必须把所有偏移、长度和地址视为不可信 64 位
输入，先检查加法/乘法溢出、文件边界、用户窗口、页对齐、段重叠和 W^X，
最后确认入口落在可执行段。

section header 主要服务链接器和调试器，运行时装载依据是 `PT_LOAD`。v0.8
拒绝未知程序头，是刻意缩小首个用户加载器的语义面；以后支持 TLS、动态链接
或解释器时，应逐项增加协议和测试，不能“遇到不认识的就执行”。

### `INT 0x80` 的历史位置

早期 x86 Unix/Linux 系统常用软件中断进入内核；硬件查 IDT、检查 DPL、保存
返回状态，语义直观但开销较大。后来的 `SYSENTER` 与 AMD64
`SYSCALL/SYSRET` 减少硬件工作以换取速度，也把安全栈、返回地址和标志处理
更多地交给软件。

本项目先用 `INT 0x80`，是因为异常帧、IDT 和 TSS 已经有真实验证，能把新增
变量限制在用户权限与 ABI。调用编号和参数寄存器独立于入口指令，将来增加
`SYSCALL` 时可复用分发层，不需要破坏用户接口。

### 用户指针为什么不能直接解引用

系统调用寄存器来自不可信代码。即使首地址位于用户范围，`address + length`
仍可能溢出，缓冲也可能跨进未映射或 supervisor 页。正确顺序是：

1. 验证非零长度与半开区间无溢出。
2. 验证整个区间位于用户低半地址。
3. 查询涉及的每个叶页并确认 present/U/S。
4. 复制进容量固定的内核缓冲。
5. 内核只处理副本。

v0.9 虽能在用户态抢占多个进程，但系统调用使用 interrupt gate，单核内核
入口期间 IF=0，当前进程地址空间不会被另一个线程解除映射。加入内核抢占或
多线程以后，仍必须通过地址空间锁、页固定或能处理 fault 的复制原语解决
TOCTOU。

## 19. 从“程序”到“进程”：地址空间、现场和时间

进程不是一段正在执行的代码。相同 ELF 可以创建多个进程，代码字节甚至可以
共享；真正使二者成为不同进程的是资源所有权集合：页表根、用户页、内核栈、
保存现场、PID、状态和终止结果。若只有一个函数指针数组而没有这些所有权，
实现的是任务回调，不是受硬件保护的进程。

### 为什么相同虚拟地址能同时属于不同进程

CPU 生成的是虚拟地址。CR3 选择当前四级页表根，所以两个进程都访问
`0x40000000` 时，可以沿不同 PML4/PDPT/PD/PT 路径到达不同物理帧。
这正是地址空间抽象：虚拟地址只在“哪个页表根”上下文中有意义。

v0.9 没有复制整个内核页表。PML4[0] 覆盖的低端 512 GiB 中，PDPT[0]
保存低端内核身份映射，PDPT[1] 覆盖 `0x40000000..0x7fffffff` 用户程序
窗口。每进程复制这一级 PDPT 并清空 [1]，便能共享 supervisor 内核子树，
同时让程序子树独立。用户栈在 PML4[255]，创建时从空项向下分配。

这里保留了 PC/x86 的历史现实：CR3 切换通常意味着 TLB 中非 global 翻译
失效，成本高于只换一个寄存器集合。后续可用 PCID 减少刷新，但必须先拥有
正确的地址空间标识和失效协议；不能为了性能跳过当前清晰边界。

### 为什么每个进程需要内核栈

用户进程被 IRQ0 打断时，CPU 从当前 TSS.RSP0 取得 Ring 0 栈，压入旧
SS、RSP、RFLAGS、CS、RIP；汇编再保存 15 个通用寄存器和 vector/error，
形成 176 字节现场。进程被换出后，这份现场必须一直存活到下一次运行。

若所有进程共用一块转换栈，下一个进程进入系统调用或中断就会覆盖前一个现场。
所以 v0.9 最初为每个 PCB 静态预留 16 KiB Ring 0 栈，并在底部留一页
not-present guard。v1.1 已把它迁移为六页动态 KVA 对象：上下双 guard，
中间四页由独立物理帧后备。上下文切换不仅要写 CR3，还必须在返回用户态前
同步写 TSS.RSP0。

本阶段只保存通用寄存器和硬件返回帧。x87、MMX、SSE、AVX 与扩展状态需要
`FXSAVE/XSAVE` 家族和 CPUID/XCR0 能力协商；在用户程序不使用这些状态前
明确禁止，比假装已经保存更可靠。

### 时间片为什么是策略，IRQ0 为什么只是机制

8254 PIT 周期产生 IRQ0，只提供“时间经过”这个机制。round-robin 决定预算
到期后从当前进程转到下一个 Ready 进程，这是调度策略。把二者分开以后，
纯调度器能在宿主用生成 tick 测试公平性，硬件系统测试只负责证明真实 IRQ
确实能驱动同一决策。

时间片过短会频繁切换 CR3、污染 TLB 和缓存；过长会增加交互延迟。v0.9 选择
4 个约 1 ms tick，是为了在短 QEMU 验收内稳定观察抢占，不是通用桌面系统的
性能结论。日志也不能逐 tick 输出：115200 波特串口发送一行的时间可能超过
整个量子，观测本身会改变被观测调度。

### 终止为什么必须先换回内核 CR3

正在执行的内核入口仍使用当前进程页表。若先释放当前 PML4，下一条取指、栈
访问或返回都会使用已归还帧。正确顺序是先保存结果并选择后继，再激活永久内核
根，最后递归释放进程独占程序/用户栈子树。仍有 Ready 进程时再激活其 CR3；
全部结束时恢复启动调度前的内核调用链。用户地址空间可以在切回内核 CR3 后
立即释放，但当前内核栈必须再等待汇编恢复永久启动 RSP；安全点随后集中回收
所有已终止栈。

资源正确性不能只看 PCB 变成 Terminated。v0.9 在创建前和全部回收后比较
物理页帧 free/allocated/reserved 统计；当前路径还比较 KVA
free/allocated/descriptor 和动态栈 active/creation/destruction/peak 统计。
同一个 worker ELF 的三个 BSS 计数各自从零演进，则从另一方向证明这些物理
帧既独立存在过，也在退出后被统一回收。

## 20. 从“可运行”到“可等待”：同步、条件与 IPC

### 互斥、可见性和等待是三件事

共享环形缓冲需要同时回答三个问题：两个执行流能否同时修改索引；先写入的
字节何时对后取得锁的一方可见；资源不足时进程是否还应占用 CPU。自旋锁解决
前两个问题，Blocked/Ready 状态转换解决第三个问题。把三者都写成一个
`volatile` 标志既没有原子 read-modify-write，也没有跨核 happens-before，
更不会让调度器停止选择等待者。

x86 的内存模型比许多弱序架构强，但编译器仍能重排普通访问，未来移植或加入
SMP 也需要明确契约。本项目锁获取用 acquire，保证临界区内读取不会越过获取；
释放用 release，保证先前写入在另一方成功 acquire 后可见。`PAUSE` 只是优化
自旋等待，不提供互斥或屏障。

### 为什么检查条件与阻塞必须连成一个协议

若读者先发现管道为空，随后释放保护并准备睡眠，生产者可能恰在两步之间写入
和唤醒。此时读者尚未登记为等待者，会永远错过事件。经典解决方法让条件状态、
等待者登记和唤醒遵守同一把锁或同一不可分割调度窗口。

当前系统是单核，`INT 0x80` interrupt gate 进入后 IF=0；Try 返回
`WouldBlock` 后的 Wait 调用再次检查 `ReadCanProgress/WriteCanProgress`，
只有条件仍不满足才把当前 PCB 设为 Blocked。对侧在同一内核执行窗口修改条件
并定向唤醒。SMP 后 IF 只影响本 CPU，必须把“条件检查—入队”放到真正的共享
等待队列锁协议中。

### 有界缓冲为何会产生背压

无限缓冲只是把资源耗尽推迟到内存分配器。有界管道让生产速率超过消费速率时
生产者阻塞，这叫背压。容量为 \(C\)、累计写入为 \(W\)、累计读取为 \(R\)
时，稳定不变量是：
\[
  0 \le W-R \le C,\qquad B=W-R,
\]
其中 \(B\) 是当前缓冲字节数。64 字节容量、31 字节消费块和 256 字节载荷
故意形成不整齐边界，使读写索引多次回绕，测试不会只覆盖一次线性复制。

### 关闭不是销毁，EOF 也不是暂时无数据

空管道有两种不同语义：写端仍存在时，将来可能有数据，读者应等待；写端已经
关闭时，未来不再有数据，读者应得到永久 EOF。对称地，读端关闭后任何写都
无法被消费，应返回 broken pipe。端点关闭改变了等待谓词，所以必须唤醒对侧。

本阶段端点直接归属两个固定验收进程。v0.11 引入文件描述符后，关闭语义将由
引用计数决定：只有最后一个写引用关闭才产生 EOF，只有最后一个读引用关闭才
产生 broken pipe。当前简化没有改变条件本身，只把引用数量固定为一。

### 为什么 Try 和 Wait 分开

系统调用指令已经把返回 RIP 压入内核帧。若一个读调用在内核里睡眠，唤醒后
必须清楚它是“继续完成原操作”还是“告诉用户重新尝试”。本项目选择后者：
Try 只有成功、稳定错误或 `WouldBlock`；Wait 只改变调度资格。高层包装用
循环组合两者，控制流和统计都可直接审计，也不会隐式倒退用户 RIP。

## 21. 为什么资源回收需要状态机、回滚栈和跨层快照

### “调用了 free”不等于“生命周期闭合”

内核对象通常同时占有多类资源。一个动态内核栈看起来只是 16 KiB 内存，实际
创建过程却跨过三个所有权系统：

```text
六页 KVA 软件所有权
  → 四个 order-0 物理页
    → 四张 supervisor RW/NX 叶映射
      → 栈管理器中的一个已提交槽位
```

任何中间步骤失败，都只能释放已经取得的资源，而且必须按相反依赖顺序撤销。
只释放物理页却留下 PTE，会形成指向新所有者数据的陈旧映射；先释放 KVA，
再撤销映射，则另一个调用者可能取得仍然 present 的同一虚拟区间。因此“每个
失败分支都写了几个 release”不是充分证明，关键是依赖关系是否完整、顺序是否
固定、后续代码增加新步骤时是否同步增加补偿动作。

早期 C 内核常用 `goto fail_map`、`goto fail_frame` 一类标签实现展开。它很
直接，但调用点扩大后，标签与资源步骤容易失配。托管语言用垃圾回收处理部分
内存所有权，普通 C++ 可以依赖标准容器和异常展开；freestanding 内核既不能
假定这些运行时存在，也不能把页表、I/O 请求等非内存资源交给垃圾回收。

### `ScopeRollback` 是一个显式小事务

本项目把“已经取得什么”记录为调用方提供的固定动作数组。每完成一个可撤销
步骤，就登记一个函数指针和上下文：

```text
状态：Uninitialized
  │ Initialize(storage)
  ▼
Armed ── TryPush(action) ──► Armed
  │                           │
  │ Commit                    │ TryRollback / 析构
  ▼                           ▼
Committed                 RolledBack
```

固定存储意味着它不会为了记录清理动作再次申请内存，也不会在低内存失败路径
制造第二个失败。回滚从数组尾部向前执行，天然还原获取顺序。一个动作失败时
仍继续执行其余动作，因为“第一项清理失败”不能成为故意泄漏全部其他资源的
理由；最终状态会报告整体失败，让上层决定 panic、隔离对象或留下诊断。

它与完整数据库事务仍有差别：硬件写入和外部设备命令未必可逆，回滚动作本身
也可能失败。因此设计时仍要把不可逆提交放在最后，并保证候选对象在提交前
不对并发读者可见。`ScopeRollback` 消除的是重复、易漏的展开控制流，不会
替代所有权分析。

### 引用计数回答“还有谁拥有”，不回答“对象是否正确”

共享对象不能在任意一个使用者退出时销毁。强引用计数把销毁条件定义为最后
一个所有者释放：

\[
  R > 0,\qquad
  \operatorname{release}(R)=
  \begin{cases}
    (R-1,\ \text{not-last}) & R>1,\\
    (0,\ \text{last})       & R=1.
  \end{cases}
\]

计数到零后拒绝重新获取，防止已经进入销毁协议的对象被“复活”；最大值时拒绝
增加，防止整数回绕把大量所有者误表示为零。失败还必须保持输出参数不变，
否则调用者可能根据一半更新的 `is_last` 销毁仍被引用的对象。

引用计数只证明拥有者数量，不证明对象内部状态、关联页表或等待队列正确，也
不能自动解决环引用。当前 v1.1 是单 BSP 串行基线，因此原语使用普通
`uint64_t`；若现在随意加一个 atomic，只会隐藏尚未确定的 acquire/release、
最后释放、弱引用升级和并发析构协议。v1.4 对象模型建立时，才把这套语义与
锁和原子内存序一起冻结。

### 快照为什么只比较“当前量”

一次成功创建再销毁会让累计创建和累计释放都增加，但当前资源应恢复原值。
泄漏检查因此要区分两类统计：

| 类型 | 例子 | 前后是否应相等 |
| --- | --- | --- |
| 当前所有权 | 活动物理页、KVA 页、活动栈、映射页 | 是 |
| 历史累计 | 成功申请、释放、split、merge、峰值 | 否 |

`ResourceSnapshot` 聚合 26 个当前字段，并先检查管理器内部守恒关系。例如：

\[
\begin{aligned}
F_{\text{accounted}} &=
F_{\text{free}}+F_{\text{allocated}}+F_{\text{reserved}}
\le F_{\text{managed}},\\
F_{\text{unavailable}} &=
F_{\text{managed}}-F_{\text{accounted}},\\
K_{\text{capacity}} &=
K_{\text{free}}+K_{\text{allocated}}+K_{\text{reserved}},\\
S_{\text{kva pages}} &= S_{\text{active}}\times 6,\\
S_{\text{mapped pages}} &= S_{\text{active}}\times 4,\\
S_{\text{guard pages}} &= S_{\text{active}}\times 2.
\end{aligned}
\]

页帧管理上限是地址上限，不是“全部都可分配”的数量。E820 洞、MMIO 与页边界
碎片都保持 `unavailable`；快照不额外占用一个字段，而是从 managed 与三类当前
所有权的差值推导它。64 GiB 规格在 3–4 GiB 附近存在明显 PCI 洞，因此这里
必须使用“小于等于”，不能把地址空间跨度误写成可用 RAM 总数。

如果只比较 frame free 数，一份泄漏和另一份误释放可能恰好互相抵消；如果只
比较栈活动数，陈旧 KVA 描述符或 PTE 也可能被漏掉。跨层快照同时比较这些
视角，并用 64 位差异掩码精确指出首批变化字段。比较函数先写局部候选结果，
只有全部验证成功才修改调用者输出，诊断本身不会交付半份事实。

### 两道真实边界比一个模拟样例更可靠

宿主测试先验证纯状态机和十万事务参考模型，再用真实 frame、buddy、页表、
KVA 与栈管理器组合四个动态栈。目标机还有两道边界：

1. 内存初始化期间创建一个真实双 guard 栈，让外层作用域事务销毁，然后比较
   快照；
2. 四进程运行前拍摄快照，等汇编返回永久内核栈并完成全部安全点回收后再次
   比较。

第一道快速证明基础设施本身可组合，第二道覆盖实际用户 ELF、调度、异常、
文件系统和 IPC 生命周期。256 MiB functional 与 64 GiB capacity 配置运行
同一份实现；前者形成日常阶段门禁，后者额外证明高物理地址和完整容量。这样
“没有泄漏”不再是一句人工观察，而是纯模型、组合测试和真实启动协议共同支持
的可重复结论。

## 22. 建议阅读顺序

第一次进入项目时，建议按以下顺序阅读：

1. `docs/requirements.md`：明确目标和禁止事项。
2. 本文：建立宿主机、目标机、复位与 freestanding 心智模型。
3. `docs/architecture.md`：理解模块边界和依赖方向。
4. `docs/building.md`：亲手完成一次构建。
5. `docs/testing.md`：理解每项测试究竟证明什么。
6. `docs/modules/foundation.md`：阅读第一个基础模块。
7. `docs/modules/firmware.md`：走读 ROM、复位向量和串口契约。
8. `docs/releases/`：按阶段查看实施证据，尤其是 v0.4 的目标机装载链和
   v0.5 的异常控制流、v0.6 的内存所有权/页表权限、v0.7 的硬件 IRQ
   与设备闭环、v0.8 的用户特权边界、v0.9 的进程地址空间与抢占调度，
   v0.10 的同步、阻塞/唤醒和管道 IPC，以及 v1.1 的通用资源生命周期。
9. `books/x86-64-os-from-reset/`：系统阅读硬件、启动和后续内核路线。
10. `docs/roadmap.md`：了解后续知识如何逐层展开。
