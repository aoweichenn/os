# 背景知识：从宿主机到 x86-64 复位向量

本文建立阅读和开发本项目所需的共同知识基础。它不假定宿主机是 x86-64，也不
假定读者已经写过引导程序或内核。

本文适合连续建立全貌；若需要逐主题深入推导，请进入
[七册背景知识专题](learning/background/README.md)。专题把机器/x86 历史、
位与 ABI、工具链/ELF、内存/异常、设备/中断、进程/文件/Shell、测试/调试
分别展开，并从每个 v0.x/v1.x 阶段回链。

## 1. 我们究竟在构建什么

普通应用程序启动时，操作系统已经替它完成了大量工作：

- 建立虚拟地址空间。
- 加载可执行文件。
- 初始化栈和线程。
- 提供文件、终端、时钟和内存分配接口。
- 初始化 C/C++ 运行时，然后调用 `main`。

操作系统代码面对的环境完全不同。CPU 复位后没有进程、文件系统、系统调用、标准输出，也没有可以依赖的 C++ 运行时。本项目的学习目标，就是把普通程序看不见的这些层逐一实现。

项目最终的控制流是：

```text
CPU 复位
  ↓
自研 ROM 固件
  ↓
自研 Stage 1（模式切换与 ELF loader）
  ↓
ELF64 内核
  ↓
Ring 3 用户程序
  ↓
Shell 与基础命令
```

QEMU 只模拟 CPU、内存和设备。箭头之间的加载、校验、状态切换和数据交接全部由项目代码完成。

## 2. 宿主机和目标机

### 2.1 Host

宿主机是执行编译器、测试程序和 QEMU 的机器。当前开发环境可以是 AArch64，也可以是 x86-64。

宿主机负责：

- 运行 CMake、Clang、LLD 和 NASM。
- 执行不依赖硬件的快速测试。
- 生成 ROM、磁盘和 ELF 文件。
- 运行 QEMU TCG。

### 2.2 Target

目标机是我们正在实现的软件最终运行的环境，固定为 x86-64 PC 硬件模型。

目标代码不能因为宿主机是 AArch64 就生成 AArch64 指令。项目通过：

```text
clang++ --target=x86_64-unknown-none-elf
```

明确要求 Clang 生成 x86-64 ELF 目标文件。构建后再使用 `llvm-readelf` 检查 ELF
头中的 `Machine` 字段，确保它是 `Advanced Micro Devices X86-64`。

这叫交叉编译：编译动作发生在宿主机，生成物面向另一套目标架构和运行环境。

## 3. QEMU TCG 解决了什么

QEMU 有两类容易混淆的职责：

1. 模拟或虚拟化硬件。
2. 附带或加载固件、操作系统镜像。

本项目只使用第一类能力。

TCG 是 QEMU 的动态二进制翻译引擎。它可以把目标 x86-64 指令转换成宿主机指令，因此即使宿主机是 AArch64，也可以运行 x86-64 CPU 模型。

我们允许 QEMU 提供：

- x86-64 CPU。
- 物理内存。
- PC 芯片组和总线。
- 串口、IDE、PIC、PIT、键盘等设备模型。
- GDB 调试接口。

我们不允许 QEMU 或第三方替代：

- ROM 固件。
- 磁盘引导代码。
- 16 位、32 位、64 位模式切换。
- ELF64 内核加载。
- 内核、运行时和驱动。

因此正式运行命令必须显式使用自研 `-bios` 镜像，不能依赖 QEMU 默认寻找的
SeaBIOS 或 OVMF，也不能使用 `-kernel` 绕过加载链。

## 4. CPU 复位后发生什么

### 4.1 复位向量

x86 CPU 复位后会从物理地址 `0xFFFFFFF0` 附近开始取指。这个位置称为复位向量。

复位状态有一个容易忽略的细节：此时 `CS` 的可见选择子、隐藏基址和指令指针共同形成复位地址。它不能简单等同于普通实模式下的 `segment << 4 + offset`。固件通常会在复位向量放置一条近距离可编码的跳转，再进入 ROM 中更完整的初始化代码。

本项目使用 128 KiB ROM：

```text
ROM 起始地址     0xFFFE0000
复位向量         0xFFFFFFF0
4 GiB 边界       0x100000000
```

复位向量位于 ROM 的最后 16 字节区域。`v0.1` 已通过链接脚本、最终二进制
审计和 QEMU 实际执行共同验证这一布局。复位向量字节 `E9 0D F0` 是一个
16 位 near jump：它保留 CS 隐藏基址，把 IP 从下一条指令位置跳到
`0xF000`，最终进入物理地址 `0xFFFFF000`。

### 4.2 初始环境

复位后的环境非常受限：

- 代码从 16 位环境开始。
- 没有可用的 C++ 栈和运行时。
- 中断表、描述符表和页表尚未由我们建立。
- RAM 和设备状态不能按普通应用程序的假设使用。
- 任何输出能力都必须先初始化硬件。

因此最早期代码必须使用少量 NASM Intel 语法汇编。只有建立可靠的栈、明确 ABI
和必要运行时边界后，才进入 freestanding C++20。

## 5. 从 16 位到 64 位

项目会逐步经历三种主要执行模式。

### 5.1 Real Mode

实模式保留早期 x86 的分段寻址模型，默认操作数和地址宽度较小。复位代码和最早期固件在这里执行。

### 5.2 Protected Mode

进入保护模式前需要准备 GDT，并设置 `CR0.PE`。保护模式提供描述符、权限和
32 位执行环境，是进入长模式的中间阶段。

### 5.3 Long Mode

进入 64 位长模式通常需要：

1. 准备至少覆盖当前代码、栈和必要数据的页表。
2. 设置 `CR4.PAE`。
3. 将页表物理地址写入 `CR3`。
4. 设置 `IA32_EFER.LME`。
5. 设置 `CR0.PG` 开启分页。
6. 通过远跳转加载 64 位代码段。

这些步骤有严格顺序，任何一个地址或控制位错误都可能导致异常、三重故障和 CPU
复位。项目不会一次写完整切换，而会为每个状态增加串口标记、GDB 检查点和失败路径。

这条转换链已在 `v0.3 Long Mode` 完成。Stage 1 对 A20、页表和关键控制位
执行写后读回检查，并在 64 位入口输出独立串口里程碑。

## 6. Freestanding C++20 是什么

C++ 标准区分 hosted 和 freestanding 环境。

普通桌面程序处于 hosted 环境，可以假定：

- 程序从标准运行时进入 `main`。
- 标准库和系统调用可用。
- 异常、RTTI、线程局部对象和全局析构得到运行时支持。

内核早期代码属于 freestanding 环境。这并不意味着不能使用现代 C++，而是每项特性都必须确认不会引入未实现的运行时依赖。

当前目标构建关闭：

- 异常。
- RTTI。
- 栈保护。
- 线程安全局部静态初始化。
- `__cxa_atexit` 全局析构注册。
- 位置无关代码。
- x86-64 红区。
- MMX 和 SSE 自动生成。
- 宿主 C++ 标准库头文件。

### 为什么关闭红区

System V AMD64 ABI 允许普通用户程序使用栈指针以下 128 字节的红区。但内核中断可能在任何时刻使用当前栈，如果编译器把临时值放在红区，中断入口可能覆盖它们。因此内核目标使用 `-mno-red-zone`。

### 为什么暂时关闭 SSE

在内核初始化 FPU/SSE 状态和上下文切换策略之前，编译器自动生成 SSE 指令会引入隐藏前置条件。早期目标先使用通用寄存器，等建立明确策略后再决定如何开放。

### 现代 C++ 仍然有价值

freestanding 不等于退回 C 风格。项目仍然优先使用：

- 强类型区分物理地址、虚拟地址和字节数。
- `enum class` 表达有限状态。
- `constexpr` 和编译期检查表达硬件约束。
- RAII 表达中断状态、锁和资源生命周期。
- concepts 约束模板接口。
- 明确返回类型表达错误。

前提是检查生成代码和符号，确认没有隐藏运行时依赖。

## 7. 编译、链接和镜像不是一回事

### 7.1 目标文件

Clang 将每个 `.cpp` 编译为 ELF 可重定位目标文件。目标文件包含机器指令、数据、符号和重定位信息，但通常还不能直接执行。

### 7.2 静态库

`v0.0` 将 `foundation` 目标文件封装为：

```text
libos_foundation_x86_64.a
```

静态库只是目标文件集合。它用于验证：

- 能否生成 x86-64 ELF。
- 是否满足 freestanding 编译限制。
- 是否意外引用外部运行时符号。

它不是 ROM，也不是内核。

### 7.3 链接产物

从 `v0.1` 开始，LLD 根据链接脚本决定：

- 每段代码和数据的虚拟地址与加载地址。
- 复位向量必须落在 ROM 的哪个偏移。
- 哪些符号作为阶段入口。
- 最终 ELF 或二进制镜像如何排列。

### 7.4 ROM 和磁盘镜像

ROM 是 QEMU 映射到固件地址空间的原始字节序列。磁盘镜像是 IDE
设备对外呈现的扇区集合。两者都不是普通宿主机可执行文件。

## 8. 为什么先实现地址类型

操作系统中的很多错误来自“都是整数”：

- 把物理地址当成虚拟地址。
- 把结束地址当成长度。
- 把页号当成字节数。
- 地址加长度发生无符号溢出。
- 一个模块使用闭区间，另一个使用半开区间。

`v0.0` 首先实现：

- `PhysicalAddress`
- `ByteCount`
- `AddressRange`
- `AddressRangeCreationStatus`

地址区间统一采用半开语义：

```text
[begin, end)
```

也就是包含 `begin`，不包含 `end`。半开区间的好处：

- 长度直接等于 `end - begin`。
- 空区间自然表示为 `begin == end`。
- 相邻区间 `[a, b)` 和 `[b, c)` 不重叠。
- 循环边界和内存拷贝长度更容易一致。

创建区间前必须验证 `begin + size` 是否能用 64 位结束地址表示。失败返回
`AddressOverflow`，并保证调用方的输出对象保持不变。

## 9. 为什么需要四层测试

只使用 QEMU 测试所有逻辑会使反馈慢、定位困难；只使用单元测试又无法验证真实硬件交互。因此项目采用四层测试。

### 单元测试

验证单个类型和函数的明确样例、边界与失败路径。

### 集成测试

把多个领域事实组合起来，例如检查 ROM、复位向量、Stage 1 和内核计划加载区间是否冲突。

### 固定种子随机测试

生成大量地址和长度，验证以下性质：

- 所有合法区间都能创建。
- 创建后长度保持不变。
- 非空区间包含首字节和末字节。
- 半开区间不包含结束地址。
- 非空区间与自身重叠。
- 相邻区间不重叠。
- 溢出输入必须被拒绝。
- 创建失败不得修改输出对象。

当前随机测试使用固定种子运行 10,000 组输入，共执行 100,000 次断言。固定种子保证本地和 CI 可以复现相同序列。

### QEMU 系统测试

`v0.0` 的空镜像测试继续保存为硬件环境回归基线。`v0.1` 增加真正的启动测试：
QEMU 从自研 ROM 复位，固件输出 `RESET` 和 `SERIAL_READY` 后进入 HLT。
宿主在两秒预算结束后验证串口协议。

同一份 NASM 源码还能生成故障镜像：第一条日志完成后，固件让发送等待函数看
不到 THRE 就绪状态。轮询到 `0xFFFF` 次上限后返回失败并停机。测试要求
`RESET` 存在且 `SERIAL_READY` 不存在，从而证明错误路径真实可达。

## 13. v0.4 为什么采用两遍 ELF 装载

ELF 是链接器与加载器之间的二进制契约。`PT_LOAD` 不只是“要复制的字节”，
还同时声明文件区间、内存区间、权限、对齐和零初始化尾部。Stage 1 不能因为
文件有 ELF magic 就信任其余字段。

本项目当前把 ELF 暂存到经 E820 验证的 `0x03600000`，第一遍验证全部程序头：

- 文件偏移和长度没有溢出，且落在精确文件范围。
- `p_filesz <= p_memsz`，内存段非空。
- 当前阶段 `p_vaddr == p_paddr`，并落在低 64 MiB 的加载窗口。
- 段按 4 KiB 对齐，文件偏移和虚拟地址的页内偏移相同。
- 所有加载段可读，不含未知权限位，不同时可写和可执行。
- 任意两个加载段不重叠。
- 固定入口位于可执行加载段。

只有所有程序头都通过，第二遍才复制 `p_filesz`，并清零
`p_memsz - p_filesz`。这种设计的关键不是代码形式，而是副作用边界：不可信
ELF 在验证失败前不能把目标内存改成“装了一半”的状态。

BSS 的历史来源是早期汇编器的 Block Started by Symbol 区域。零初始化对象
不必在磁盘文件中重复保存大量零字节，因此 ELF 允许 `p_memsz` 大于
`p_filesz`。加载器如果不显式清零，C++ 对静态存储期零初始化的语言保证就会
被破坏。本项目用内核 BSS 探针把这条隐含前提变成 QEMU 可见证据。

## 14. BootInfo 与第一次 C++ 交接

进入 64 位模式只表示处理器能执行 64 位指令，不等于已经建立 C++ 运行环境。
Stage 1 需要同时保证：

- RDI 指向有效的 104 字节 BootInfo v2。
- RSP 使用与加载区分离的 64 KiB 栈，并符合 System V AMD64 调用约定。
- 方向标志保持清零，分页仍覆盖入口、数据、栈和串口代码。
- 内核不依赖构造函数、异常、RTTI、标准库或宿主运行时。

BootInfo 的十三个字段全部使用 `uint64_t` 对应的固定宽度 ABI。它记录魔数、版本、
结构大小、原始 ELF 文件位置与长度、入口、加载段数、CR3 根地址、恒等映射
大小、栈顶、物理内存图地址、条目数和条目宽度。内核重新验证这些内容，并独立初始化 COM1；因此控制权交接不是
“跳过去没死”，而是由 `BOOT_INFO_VALID`、`BSS_ZEROED`、`CR3_VALID` 和
`READY` 四个连续证据证明。

## 15. 为什么长模式仍然需要 GDT、TSS 和 IDT

x86-64 长模式弱化了传统分段：代码和数据段的 base/limit 大多不再参与普通
地址计算。但“弱化”不等于删除。CS 仍保存当前特权级和 64 位代码属性；
从用户态进入内核仍需要合法代码段；TSS 仍为特权切换提供 RSP0，并为关键异常
提供 IST；IDT gate 仍引用代码段选择子。

这来自 x86 的兼容演化历史。保护模式先用描述符把内存、特权和任务状态组织在
一起；64 位时代把地址隔离主责交给页表，却保留选择子和门机制，避免彻底重做
中断与特权模型。因此一个教学内核不能因为“不做传统分段”就省掉 GDT。

Stage 1 的 GDT 只解决“怎样进入长模式”。内核自己的 GDT 解决“内核长期使用
哪些代码段、数据段和 TSS”。两者职责不同。v0.5 在 C++ 入口已经可靠后立即
接管描述符表，避免后续内存、中断和用户态建立在加载器私有状态之上。

### 为什么异常需要汇编入口

普通 C++ 函数由调用者按 ABI 放置返回地址和参数；异常由处理器按架构规则压入
RIP、CS、RFLAGS，有时再压错误码，特权切换时还会压旧 RSP 和 SS。它不是一次
普通 `call`。

每个 NASM 桩先把“有无硬件错误码”的差异规范化，再保存通用寄存器、清 DF 并
对齐栈，最后才调用 C++20。返回时必须严格逆序恢复并用 `IRETQ`，普通 `ret`
既不会恢复 CS/RFLAGS，也会把现场解释错。

### fault、trap 和 abort

- fault 通常把保存 RIP 指向故障指令；处理原因后可以重试，例如页不存在。
- trap 通常在指令完成后报告，保存 RIP 指向下一条，例如 `INT3` breakpoint。
- abort 表示严重状态，处理器不保证能够可靠重启，例如双重故障。

因此不能写一个“所有异常都把 RIP 加一”的处理器。当前只允许已知的 `INT3`
自检返回，其余异常 panic。v0.6 虽然已经建立内存所有权，但尚未拥有进程地址
区间、后备对象和回收策略，因此不急于让普通页故障恢复。

### 为什么 panic 必须比普通日志更简单

panic 可能发生在页表、栈、堆、锁或日志模块已经损坏时。如果它再分配内存、
获取锁或执行复杂格式化，就可能重复触发原故障并刷屏。当前 panic 只依赖已经
验证的串口端口、当前异常帧和少数控制寄存器：

- 禁止中断。
- 用单个 BSS 状态位阻止递归。
- 输出向量、错误码、RIP、CS、RFLAGS。
- 页故障额外输出 CR2。
- 进入 HLT 循环。

这不是最终崩溃系统，而是早期内核的最小可信诊断基座。

## 16. 为什么内存管理要同时讨论所有权、翻译和权限

“机器有 64 GiB RAM”不等于 `0..64 GiB` 每个物理地址都能分配。固件或平台需要描述哪些
区间是 RAM、保留区或设备窗口；内核把可用区间按 4 KiB 切成页帧，再记录每帧
处于空闲、动态占用还是启动保留状态。这是物理所有权。

程序产生的是线性地址。x86-64 通过 PML4、PDPT、PD、PT 四级结构查到物理页，
并在每一级累积 present、writable、user 和 NX 权限。这是地址翻译与访问控制。
物理分配器不知道一个页帧映射在哪里，页表也不能独自判断某个物理页是否已经
属于别人，因此两个模块必须分开。

### 为什么采用 `fw_cfg`，却不让 QEMU 替我们做内核

QEMU PC 的 `fw_cfg` 是端口可访问的配置硬件。它提供 `etc/e820` 原始数据，
但不会替来宾解析大端目录、验证长度、排序、处理重叠或分配页面。项目选择它与
选择模拟 UART、IDE 一样：QEMU 只表现设备，软件协议由自研 Stage 1 完成。

传统 BIOS E820 是软件中断服务；本项目没有外部 BIOS，临时借用会破坏完整
启动链。未来若换平台，只需让新的固件后端产生同一种 24 字节规范化内存图，
内核不必知道数据来自 `fw_cfg`、ACPI 还是其他机制。

### 为什么 64 GiB 规格不能写成 64 GiB 常量

QEMU 的 `-m 64G` 是一次机器配置，不是内核 ABI。x86-64 处理器能够放进
页表项的物理地址位数由 `CPUID.80000008H:EAX[7:0]` 报告；平台实际 RAM
来自 E820；内核当前能为物理内存保留多大的连续虚拟窗口又是第三个约束。
受管上限必须取三者最小值。这样同一份代码可以在 64 MiB 回归配置、64 GiB
主配置和未来更大配置上工作，超过当前 64 TiB direct-map 时也会明确截断，
而不是发生地址回绕。

E820 中“最高被描述地址”和“最高可用 RAM 地址”也不是同一个概念。PC 地址
空间包含 PCI、固件和 MMIO 洞；本项目的 64 MiB 配置还会描述延伸到 1 TiB
的高地址保留窗口。如果按最高描述地址计算 PFN 元数据，少量 RAM 会被巨大的
保留洞放大。正确上界取最高 type 1 RAM 完整页末端，保留条目只负责阻止分配。

### 为什么需要高半区物理直映

物理地址是总线和页表使用的编号，不天然是 C++ 可以解引用的虚拟地址。早期
身份映射恰好令两者数值相等，容易诱导代码把
`reinterpret_cast<uint8_t *>(physical_address)` 当成永久接口；一旦页帧位于
4 GiB 以上或低端身份映射被缩小，这个假设立即失效。

direct-map 为普通 RAM 建立稳定关系：

```text
virtual = 0xFFFF888000000000 + physical
```

页表项和 CR3 继续保存物理地址；页表遍历、用户页清零和 ELF 复制需要访问内容
时才执行上述转换。未被 E820 标为 type 1 的洞不建立映射，LAPIC 等设备另用
cache-disabled MMIO 映射。这样“地址翻译”和“页帧所有权”仍是两个独立问题。

### 为什么同时使用 2 MiB 与 4 KiB 页

64 GiB 若全部使用 4 KiB PTE，需要 16777216 个叶项和约 32 MiB 叶页表；
若内部对齐区域使用 2 MiB PDE，只需 32768 个叶项。更少的页表内存和 TLB
覆盖压力适合大范围直映。4 KiB 页仍用于 E820 非对齐边界、权限精细的 Kernel
段、用户页与 guard page。大页不是全面替代小页，而是让“映射粒度”服从用途。

### 为什么 `CR0.WP` 对内核只读页至关重要

页表 RW=0 并不总能约束最高特权代码。x86 的 `CR0.WP` 位决定 supervisor
写访问是否也遵守只读权限。只把 `.rodata` 表项标成只读，却不设置 WP，
Ring 0 仍可能写坏常量。

v0.6 不只读取页表项确认 RW=0，还专门映射一页只读数据并让 Ring 0 写入。
预期 #PF 错误码 `0x3`：P=1 表示映射存在，W/R=1 表示写访问，U/S=0 表示
supervisor。CR2 必须等于测试地址。硬件异常把软件意图升级成处理器执行证据。

### 为什么内存分配器要分层演进

启动期需要少量生命周期覆盖整个内核的对象；此时还没有并发、等待队列、页回收
和进程地址空间。单调分配器只移动一个已用偏移，容易验证对齐、溢出和容量。
缺点是不能释放，所以它不是通用堆。v1.1 先用 buddy 处理连续物理页所有权，
再用边界标记堆处理已经映射区间中的任意字节块；这两个分配器回答的问题不同，
不能因为都叫“分配”就合并。

固定尺寸内核对象又有第三种形状。若每个 64 字节对象都走通用堆，每次仍要
搜索空闲块、携带块头并承担外部碎片。SunOS 在 1980 年代末提出 slab 思路：
把同一类型对象排列在专属后备区中，复用已准备好的槽；后来 Linux 的
SLAB/SLUB 继续扩展了多 slab 状态、per-CPU 快速路径与调试能力。它们的核心
动机不是“另写一个 malloc”，而是利用对象尺寸、对齐和生命周期同构。

本项目当前先实现最小固定容量形式：一个通用堆后备块，块首是活动位图，后面
是等步长槽。活动槽归调用者，空闲槽首 8 字节借作下一空闲索引。位图用于拒绝
重复释放，槽内链让申请/释放保持常数时间；对象全部归还后，整个后备块才能
销毁。它暂不处理多 slab 增长、构造析构、per-CPU 缓存和内存压力回收，因为
这些能力分别依赖 KVA、对象模型和并发语义。按这种顺序，读者可以从测试失败
中明确区分页所有权、字节堆布局和类型槽状态。

### 为什么“页表里没有映射”仍不等于“虚拟地址空闲”

早期实模式和简单身份映射让地址看起来像物理位置；现代分页则把线性地址变成
一种由软件组织、由硬件翻译的命名空间。页表叶项只编码当前翻译与权限：
present=0 时，处理器会产生页故障，却不会告诉我们这一页为何缺席。

同一个 not-present 状态至少可能表示：

- 地址从未分配，可以交给新对象；
- 地址已经属于动态栈的 guard，必须继续缺席；
- 地址已经许诺给一个对象，但物理页尚未准备好；
- 映射刚被撤销，所有者仍在等待其他 CPU 的 TLB 失效；
- 地址永久保留，用于捕获零偏移或布局越界。

因此直接扫描页表寻找零叶项会丢失软件所有权。物理页分配器也无法代替它：
一组非连续物理页可以映射成连续虚拟区间，同一物理页在受控场景又可能出现
多个别名。物理所有权、虚拟区间所有权和翻译关系必须是三套可以交叉验证但不
互相假装的状态。

这种需求在早期 Unix 的内核地址空间还较小时不明显。随着内核模块、动态 I/O
映射和非连续页后备增多，内核需要类似 `vmalloc` 的区域：先保留一段连续虚拟
地址，再逐页接入物理后备。Linux x86-64 也把 direct map 与 vmalloc 区分：
前者按固定偏移访问普通 RAM，后者为动态虚拟连续映射提供命名空间。这里借鉴
的是分层理由，不是调用 Linux 或复制其实现。

### 为什么 32 TiB KVA 不适合逐页位图

32 TiB 包含：

\[
\frac{32 \times 2^{40}}{2^{12}} = 2^{33} = 8589934592
\]

个 4 KiB 页。每页一位需要 \(2^{30}\) 字节，即 1 GiB；如果还要区分保留、
活动和空闲，位数至少翻倍。当前学习内核同时存在的动态区间只有个位数到数百，
按潜在页数付费会让元数据远大于实际内核。

当前实现改为保存有主区间。窗口首尾和相邻有主区间之间天然形成空闲缝隙；
删除一个有主区间后，两侧缝隙自动连成一个更大空闲区，不需要空闲节点合并。
1024 个描述符每项 24 字节，只需 24576 字节。扫描、插入和删除是 \(O(N)\)，
但 \(N\) 有明确小上界，完整遍历也更容易证明无重叠和计数守恒。

这不是宣称数组永远优于树。v1.1 最初使用 256 项；v1.2 为 512 个 Thread
动态栈把上界提升到 1024 项。等到并发映射和对象数再次证明数组不够时，可以把
索引替换为平衡树或分片结构；现在提前引入树旋转、节点分配和锁，只会让错误
难以归因。

### 为什么对齐要作用于绝对虚拟页号

假设调用者请求“8 页对齐”。真实要求是虚拟地址低 15 位为零，因为
\(8 \times 4096 = 32768\)。若只把窗口内偏移对齐，窗口基址本身不按 8 页
对齐时，结果仍不满足硬件或对象布局要求。KVA 先把候选地址除以 4096 得到
绝对页号，再按二次幂向上对齐，最后转换回地址。

best-fit 比较可容纳请求的原始空闲缝隙大小，同大小保留低地址。它减少持续
切割大空洞的倾向，但不能消除外部碎片；统计中的最大连续空闲页数因此和总
空闲页数同样重要。

### 为什么 guard 页也必须占有 KVA

保护页的价值正来自“不映射”。若它没有软件所有者，下一次地址搜索就可能把
这页交给别的对象并建立映射，原栈的越界访问将不再触发 #PF。正确的动态栈
形状是：

```text
一个 KVA 所有权区间
┌────────────┬────────────────────────────┬────────────┐
│ lower guard│ mapped stack/data pages    │ upper guard│
│ not-present│ supervisor RW + NX         │ not-present│
└────────────┴────────────────────────────┴────────────┘
```

KVA 负责三段共同不被复用；页表只为中间数据页建立叶项；buddy 只拥有真实
后备页。当前动态内核栈已经按这个形状落地：六页 KVA 区间中，上下各一页
guard，中间四页形成 16 KiB 可用栈。销毁时先撤销映射和 TLB，再归还物理页，
最后释放整个 KVA 区间。这个逆序与构造依赖相反，是后续所有跨层资源事务的
基本模式。

### 为什么四个栈页不要求物理连续

程序看到的 RSP 是虚拟地址，处理器每次访存都经页表把所在虚拟页翻译到对应
物理帧。只要四个虚拟数据页连续，跨页的 push、局部变量和保存帧便具有连续
语义；它们背后的 PFN 可以完全分散。强制申请 order 2 连续块不会让普通栈
访问更快，却会让 Thread 创建受外部物理碎片影响。

DMA 环形缓冲、某些大页或设备描述符可能有真实物理连续约束，内核栈没有。
当前实现因此逐页申请四个 order-0 帧，并在完整校验中证明四帧互不相同。
这也是“虚拟连续”和“物理连续”必须分开学习的直接例子。

### 为什么上下都保留 guard

x86-64 栈按约定向低地址增长，所以 lower guard 能捕获常见的深递归和大局部
变量溢出。但硬件并不禁止代码把 RSP 错设到栈顶以上，也不禁止通过正偏移写
出当前帧；只有 lower guard 会让这类错误进入相邻对象。upper guard 不消耗
物理页，只占一页 KVA 所有权，因此当前布局使用对称边界。

guard 不是完整的内存安全方案。一次跨越整张 guard 页的大跨度错误可能直接
落到更远的合法映射；它提供的是低成本、确定性的邻接越界检测。更强诊断需要
更宽隔离、栈高水位、编译器插桩或地址消毒器类机制。

### 为什么终止栈必须延迟到安全点回收

在系统调用、异常或 IRQ 的 C++ 处理器中，当前局部变量、返回地址和保存现场
都位于当前进程内核栈。把调度状态改为 `Terminated` 只改变软件状态，不会让
CPU 自动换到别的 RSP。若此时撤销栈 PTE，下一次函数返回或局部变量读取就会
在 Ring 0 产生 #PF。

正确路径先选择下一进程并从其保存帧返回用户态，或让汇编恢复调用
`OsKernelEnterScheduledProcess` 前保存的永久启动栈。只有回到 C++ 调度循环，
并读取 RSP 证明它不在任何待销毁栈中，才可以 unmap、清零物理页并释放 KVA。
这种“发布终止状态—稍后 reap”与 Unix 的 zombie 思想不是同一个对象，但
共享一个原则：逻辑退出和物理销毁可能需要不同的安全时刻。

### 为什么共享页表根不能回收最后一张 PDPT

早期分页实现常把“页表项不再 Present”近似成“这张表可以释放”。这只对完整
独占的树成立。x86-64 页表项没有父指针、引用计数或所有者字段；处理器只把
其中的物理地址解释为下一层表。复制一个 PML4 项不会复制其 PDPT、PD 和 PT，
而是产生另一个指向同一子树的硬件引用。

本项目为进程地址空间复制内核高半 PML4 项。内核根撤销 KVA 最后一张叶映射
后，PT 和 PD 只在这条内核分支内使用，可以安全归还；PDPT 却仍可能由已经
创建的进程 PML4 项指向。若仅扫描当前内核根发现分支为空便释放 PDPT，这些
进程根中的父项不会自动清零。物理帧随后可能交给别的对象，而处理器仍会把
新内容当页表解析，结果是最危险的一类 use-after-free。

因此当前管理器显式区分三种根所有权：

```text
Exclusive    整棵树独占，空分支可从 PT 一直回收到 PDPT
KernelShared 高半入口会被进程根借用，只回收 PT 和 PD
Process      只修改并回收自己的用户程序/栈分支
```

这里保留一张共享 PDPT 是所有权协议，不是泄漏。启动仍先执行一次单页“暖机”，
但目的已经变为证明边界：映射创建 PDPT、PD、PT，撤销必须回收低两级并精确
保留一级。随后的四叶 KVA 事务重新创建并回收 PT/PD；整机最终报告两张 PT、
两张 PD、零张 PDPT 被回收，以及一张共享 PDPT 被有意保留。

### 为什么空表检查要比较完整 64 位表项

Present 位只决定处理器当前是否继续页表遍历。操作系统仍可在非 Present 表项
中保存 swap 标识、软件状态或暂存地址；即使本阶段还没有 swap，看到非零项
也不能证明它没有意义。因此回收“除将要解除的子项外为空”的表时，检查的是
其余 511 个原始 64 位值是否为零，而不是只检查 bit 0。

这也解释了撤销操作为什么分为预检和提交。预检先验证整条路径、精确 order-0
页帧所有权、无祖先环和空表条件；任何失败都不碰叶项。提交才清 PTE、执行
一次 `INVLPG`，再从子到父解除并释放空表。否则在检查上级时才发现损坏，
已经清掉的叶映射无法可靠恢复。

映射方向面临对称问题：建立四级路径可能在第三次申请时耗尽内存。只释放最后
一次申请并不够，早先创建的空表和对既有父项 U/S 位的提升也必须撤销。因此
实现记录父项原值与每张新表帧，并在失败时反序恢复。这是数据库事务“先记录、
后提交、逆序回滚”在内核资源生命周期中的一个小型实例。

## 17. 为什么 PIC 已有待处理中断，CPU 仍可能收不到

传统 PC 的 8259A 通过 INTR 把请求送给处理器；后来 APIC 加入后，兼容系统用
“虚拟线模式”把 PIC 输出接到本地 APIC 的 ExtINT 输入。商业 BIOS 通常完成
这段平台设置，但本项目从复位开始没有外部 BIOS。

因此“PIC 重映射 + 开 IRQ0 + STI”隐含了一个并不存在的前置条件。v0.7 的
真实 QEMU 诊断曾同时看到：

- PIT 已产生数百个 IRQ0。
- PIC IRR bit0 已置位，IMR bit0 已清零。
- RFLAGS.IF=1，CPU 正在 HLT。
- IDT 向量 32 已存在，却从未进入。

这说明设备、控制器和 CPU 本身分别“看起来正确”，但它们之间的路由没有建立。
当前单核阶段显式建立 virtual-wire：映射 LAPIC MMIO 页，保持全局启用，
设置 Spurious Interrupt Vector Register 的软件启用位，再把 LVT LINT0
配置为未屏蔽的 ExtINT。PIC 的输出因此经 LAPIC 进入处理器；将来实现
I/O APIC 时再引入重定向表、LAPIC EOI 和目标 CPU 选择。兼容历史不是背景
趣闻，它直接决定初始化序列。

### 为什么中断入口不能直接写成普通 C++ 函数

设备事件没有 C++ 调用者。CPU 只保存 RIP、CS、RFLAGS，PIC 不提供错误码，
普通 ABI 也不保证其余寄存器已保存。汇编桩必须补齐统一帧、清 DF、保存通用
寄存器和修正栈对齐，C++ 才能安全分类 IRQ。返回必须用 `IRETQ`，随后再由
处理器恢复 RFLAGS.IF。

### 为什么时钟中断不应打印每一次 tick

1000 Hz 的串口日志会让 115200 波特 UART 成为系统主要工作：一条几十字节
记录的发送时间远大于 1 ms，下一次 IRQ 又会在输出期间到达。结果既不是好的
日志，也不是好的时钟。ISR 只更新固定宽度计数，低频边界汇总，宿主另以单调
时间标记每条串口行。这把“来宾时间语义”和“测试观察延迟”分开。

### 为什么 QMP 注入仍然满足只让 QEMU 模拟硬件

QMP `sendkey` 相当于测试人员按下虚拟键盘。它让 QEMU 的键盘设备产生扫描码，
不会替来宾读取 `0x60`、发送 PIC EOI、构造 IDT 帧或调用解码器。与测试人员
在图形窗口按键相比，它只是可自动复现的输入方式，而不是引导器或驱动替代品。

## 18. 为什么 Ring 3 不是一次普通函数调用

### 特权级来自三个数字的共同检查

x86 保护模型里经常同时出现 CPL、DPL 和 RPL：

- CPL 是当前代码段选择子的低两位，描述正在执行的特权级。
- DPL 保存在段描述符或门描述符中，描述目标允许的特权边界。
- RPL 是选择子低两位，请求者不能用一个“看起来更高权限”的选择子绕过检查。

数字越小权限越高。内核 CS=`0x08` 的 RPL 为 0；用户 CS=`0x23` 的低两位
为 3。内核不能靠修改一个 C++ 状态变量宣称自己进入用户态，必须让 CPU 通过
`IRETQ` 装载 DPL3 代码段，随后由硬件把 CPL 变成 3。

长模式下，普通代码和数据段不再像 16 位时代那样承担线性地址重定位，但
present、type、DPL 和代码段 L 位仍然生效。分段从“主要地址翻译机制”退到
“特权与执行属性机制”，这是 x86 历史兼容留下的形状。

### 为什么降权帧有五项

同特权级异常只需保存 RIP、CS、RFLAGS；发生 CPL3→CPL0 或反向恢复时还必须
保存/装载栈的 SS 与 RSP。因此首次进入用户态构造：

```text
高地址  SS=0x1B
        RSP=用户栈顶
        RFLAGS=0x202
        CS=0x23
低地址  RIP=ELF 入口
```

`IRETQ` 从低地址方向依次取出状态。`0x202` 中 bit 1 是架构要求的保留位，
IF 让已初始化硬件中断在用户态也能到达；IOPL 仍为 0，所以用户不能直接执行
受保护端口 I/O。

### 为什么系统调用必须先换栈

用户栈属于不可信地址空间，可能指向 guard、只读页或攻击者构造的数据。若内核
一进入就把返回地址和寄存器压在用户栈上，最需要保护的入口反而依赖攻击者。
64 位 TSS 的 RSP0 告诉 CPU：从较低权限进入 Ring 0 时先换到哪个栈。

这个栈也不能是等待用户函数“返回”的原内核栈。系统调用硬件压帧会覆盖原调用
链，exit 再恢复时就可能跳到损坏地址。v0.8 使用独立特权转换栈，并显式保存
进入用户态前的内核 RSP；exit 或异常直接丢弃转换栈，回到那条调用链。

### 页表 U/S 为什么必须逐级传播

x86-64 四级页表的有效权限是路径上各级限制的组合。只给 PT 叶项设置 U/S，
若 PML4E、PDPTE 或 PDE 仍是 supervisor，用户访问依然页故障。反过来，把
中间项设为 user 不会自动泄露内核叶页；最终叶项仍必须允许 user。

页故障错误码可以直接说明硬件判定：

| bit | 名称 | 为 1 的含义 |
| --- | --- | --- |
| 0 | P | 保护冲突；为 0 是 not-present |
| 1 | W/R | 写访问 |
| 2 | U/S | 访问来自 CPL3 |
| 3 | RSVD | 页表保留位非法 |
| 4 | I/D | 取指访问（启用相关能力时） |

v0.8 用户页故障得到 `0x4`：P=0、W/R=0、U/S=1，即用户读未映射地址。
v0.6 内核写保护测试的 `0x3` 则是 present、write、supervisor。两个结果把
同一个 #PF 向量背后的不同原因区分开。

### 为什么 ELF 只是文件契约，不是信任证明

ELF 的程序头告诉加载器“把哪些文件字节放到哪些虚拟地址并赋予什么权限”，
但文件可以恶意或损坏。加载器必须把所有偏移、长度和地址视为不可信 64 位
输入，先检查加法/乘法溢出、文件边界、用户窗口、页对齐、段重叠和 W^X，
最后确认入口落在可执行段。

section header 主要服务链接器和调试器，运行时装载依据是 `PT_LOAD`。v0.8
拒绝未知程序头，是刻意缩小首个用户加载器的语义面；以后支持 TLS、动态链接
或解释器时，应逐项增加协议和测试，不能“遇到不认识的就执行”。

### `INT 0x80` 的历史位置

早期 x86 Unix/Linux 系统常用软件中断进入内核；硬件查 IDT、检查 DPL、保存
返回状态，语义直观但开销较大。后来的 `SYSENTER` 与 AMD64
`SYSCALL/SYSRET` 减少硬件工作以换取速度，也把安全栈、返回地址和标志处理
更多地交给软件。

本项目先用 `INT 0x80`，是因为异常帧、IDT 和 TSS 已经有真实验证，能把新增
变量限制在用户权限与 ABI。调用编号和参数寄存器独立于入口指令，将来增加
`SYSCALL` 时可复用分发层，不需要破坏用户接口。

### 用户指针为什么不能直接解引用

系统调用寄存器来自不可信代码。即使首地址位于用户范围，`address + length`
仍可能溢出，缓冲也可能跨进未映射或 supervisor 页。正确顺序是：

1. 验证非零长度与半开区间无溢出。
2. 验证整个区间位于用户低半地址。
3. 查询涉及的每个叶页并确认 present/U/S。
4. 复制进容量固定的内核缓冲。
5. 内核只处理副本。

v0.9 虽能在用户态抢占多个进程，但系统调用使用 interrupt gate，单核内核
入口期间 IF=0，当前进程地址空间不会被另一个线程解除映射。加入内核抢占或
多线程以后，仍必须通过地址空间锁、页固定或能处理 fault 的复制原语解决
TOCTOU。

## 19. 从“程序”到“进程”：地址空间、现场和时间

进程不是一段正在执行的代码。相同 ELF 可以创建多个进程，代码字节甚至可以
共享；真正使二者成为不同进程的是资源所有权集合：页表根、用户页、内核栈、
保存现场、PID、状态和终止结果。若只有一个函数指针数组而没有这些所有权，
实现的是任务回调，不是受硬件保护的进程。

### 为什么相同虚拟地址能同时属于不同进程

CPU 生成的是虚拟地址。CR3 选择当前四级页表根，所以两个进程都访问
`0x40000000` 时，可以沿不同 PML4/PDPT/PD/PT 路径到达不同物理帧。
这正是地址空间抽象：虚拟地址只在“哪个页表根”上下文中有意义。

v0.9 没有复制整个内核页表。PML4[0] 覆盖的低端 512 GiB 中，PDPT[0]
保存低端内核身份映射，PDPT[1] 覆盖 `0x40000000..0x7fffffff` 用户程序
窗口。每进程复制这一级 PDPT 并清空 [1]，便能共享 supervisor 内核子树，
同时让程序子树独立。用户栈在 PML4[255]，创建时从空项向下分配。

这里保留了 PC/x86 的历史现实：CR3 切换通常意味着 TLB 中非 global 翻译
失效，成本高于只换一个寄存器集合。后续可用 PCID 减少刷新，但必须先拥有
正确的地址空间标识和失效协议；不能为了性能跳过当前清晰边界。

### 为什么每个进程需要内核栈

用户进程被 IRQ0 打断时，CPU 从当前 TSS.RSP0 取得 Ring 0 栈，压入旧
SS、RSP、RFLAGS、CS、RIP；汇编再保存 15 个通用寄存器和 vector/error，
形成 176 字节现场。进程被换出后，这份现场必须一直存活到下一次运行。

若所有进程共用一块转换栈，下一个进程进入系统调用或中断就会覆盖前一个现场。
所以 v0.9 最初为每个 PCB 静态预留 16 KiB Ring 0 栈，并在底部留一页
not-present guard。v1.1 已把它迁移为六页动态 KVA 对象：上下双 guard，
中间四页由独立物理帧后备。上下文切换不仅要写 CR3，还必须在返回用户态前
同步写 TSS.RSP0。

v0.9–v1.1 只保存通用寄存器和硬件返回帧；v1.2 已把 x87、MMX、SSE/SSE2
与 MXCSR 纳入每 Thread 的 512 字节 FXSAVE 区。AVX/XSAVE 仍明确禁用，
因为它还需要 CPUID leaf 0xD、XCR0 和可变区域大小协商；“能力不可用”比
“用户偶尔使用但内核不保存”可靠。

### 时间片为什么是策略，IRQ0 为什么只是机制

8254 PIT 周期产生 IRQ0，只提供“时间经过”这个机制。round-robin 决定预算
到期后从当前进程转到下一个 Ready 进程，这是调度策略。把二者分开以后，
纯调度器能在宿主用生成 tick 测试公平性，硬件系统测试只负责证明真实 IRQ
确实能驱动同一决策。

时间片过短会频繁切换 CR3、污染 TLB 和缓存；过长会增加交互延迟。v0.9 选择
4 个约 1 ms tick，是为了在短 QEMU 验收内稳定观察抢占，不是通用桌面系统的
性能结论。日志也不能逐 tick 输出：115200 波特串口发送一行的时间可能超过
整个量子，观测本身会改变被观测调度。

### 终止为什么必须先换回内核 CR3

正在执行的内核入口仍使用当前进程页表。若先释放当前 PML4，下一条取指、栈
访问或返回都会使用已归还帧。正确顺序是先保存结果并选择后继，再激活永久内核
根，最后递归释放进程独占程序/用户栈子树。仍有 Ready 进程时再激活其 CR3；
全部结束时恢复启动调度前的内核调用链。用户地址空间可以在切回内核 CR3 后
立即释放，但当前内核栈必须再等待汇编恢复永久启动 RSP；安全点随后集中回收
所有已终止栈。

资源正确性不能只看 PCB 变成 Terminated。v0.9 在创建前和全部回收后比较
物理页帧 free/allocated/reserved 统计；当前路径还比较 KVA
free/allocated/descriptor 和动态栈 active/creation/destruction/peak 统计。
同一个 worker ELF 的三个 BSS 计数各自从零演进，则从另一方向证明这些物理
帧既独立存在过，也在退出后被统一回收。

## 20. 从“可运行”到“可等待”：同步、条件与 IPC

### 互斥、可见性和等待是三件事

共享环形缓冲需要同时回答三个问题：两个执行流能否同时修改索引；先写入的
字节何时对后取得锁的一方可见；资源不足时进程是否还应占用 CPU。自旋锁解决
前两个问题，Blocked/Ready 状态转换解决第三个问题。把三者都写成一个
`volatile` 标志既没有原子 read-modify-write，也没有跨核 happens-before，
更不会让调度器停止选择等待者。

x86 的内存模型比许多弱序架构强，但编译器仍能重排普通访问，未来移植或加入
SMP 也需要明确契约。本项目锁获取用 acquire，保证临界区内读取不会越过获取；
释放用 release，保证先前写入在另一方成功 acquire 后可见。`PAUSE` 只是优化
自旋等待，不提供互斥或屏障。

### 为什么检查条件与阻塞必须连成一个协议

若读者先发现管道为空，随后释放保护并准备睡眠，生产者可能恰在两步之间写入
和唤醒。此时读者尚未登记为等待者，会永远错过事件。经典解决方法让条件状态、
等待者登记和唤醒遵守同一把锁或同一不可分割调度窗口。

当前系统是单核，`INT 0x80` interrupt gate 进入后 IF=0；Try 返回
`WouldBlock` 后的 Wait 调用再次检查 `ReadCanProgress/WriteCanProgress`，
只有条件仍不满足才把当前 Thread 放入对象的 WaitQueue。对侧在同一
`IrqSaveSpinLock` 提交窗口修改状态并定向唤醒。SMP 后 IF 只影响本 CPU，
仍必须把“条件检查—入队”放到真正的共享对象锁协议中。

### 有界缓冲为何会产生背压

无限缓冲只是把资源耗尽推迟到内存分配器。有界管道让生产速率超过消费速率时
生产者阻塞，这叫背压。容量为 \(C\)、累计写入为 \(W\)、累计读取为 \(R\)
时，稳定不变量是：
\[
  0 \le W-R \le C,\qquad B=W-R,
\]
其中 \(B\) 是当前缓冲字节数。64 字节容量、31 字节消费块和 256 字节载荷
故意形成不整齐边界，使读写索引多次回绕，测试不会只覆盖一次线性复制。

### 关闭不是销毁，EOF 也不是暂时无数据

空管道有两种不同语义：写端仍存在时，将来可能有数据，读者应等待；写端已经
关闭时，未来不再有数据，读者应得到永久 EOF。对称地，读端关闭后任何写都
无法被消费，应返回 broken pipe。端点关闭改变了等待谓词，所以必须唤醒对侧。

本阶段端点直接归属两个固定验收进程。v0.11 引入文件描述符后，关闭语义将由
引用计数决定：只有最后一个写引用关闭才产生 EOF，只有最后一个读引用关闭才
产生 broken pipe。当前简化没有改变条件本身，只把引用数量固定为一。

### 为什么 Try 和 Wait 分开

系统调用指令已经把返回 RIP 压入内核帧。若一个读调用在内核里睡眠，唤醒后
必须清楚它是“继续完成原操作”还是“告诉用户重新尝试”。本项目选择后者：
Try 只有成功、稳定错误或 `WouldBlock`；Wait 只改变调度资格。高层包装用
循环组合两者，控制流和统计都可直接审计，也不会隐式倒退用户 RIP。

## 21. 为什么资源回收需要状态机、回滚栈和跨层快照

### “调用了 free”不等于“生命周期闭合”

内核对象通常同时占有多类资源。一个动态内核栈看起来只是 16 KiB 内存，实际
创建过程却跨过三个所有权系统：

```text
六页 KVA 软件所有权
  → 四个 order-0 物理页
    → 四张 supervisor RW/NX 叶映射
      → 栈管理器中的一个已提交槽位
```

任何中间步骤失败，都只能释放已经取得的资源，而且必须按相反依赖顺序撤销。
只释放物理页却留下 PTE，会形成指向新所有者数据的陈旧映射；先释放 KVA，
再撤销映射，则另一个调用者可能取得仍然 present 的同一虚拟区间。因此“每个
失败分支都写了几个 release”不是充分证明，关键是依赖关系是否完整、顺序是否
固定、后续代码增加新步骤时是否同步增加补偿动作。

早期 C 内核常用 `goto fail_map`、`goto fail_frame` 一类标签实现展开。它很
直接，但调用点扩大后，标签与资源步骤容易失配。托管语言用垃圾回收处理部分
内存所有权，普通 C++ 可以依赖标准容器和异常展开；freestanding 内核既不能
假定这些运行时存在，也不能把页表、I/O 请求等非内存资源交给垃圾回收。

### `ScopeRollback` 是一个显式小事务

本项目把“已经取得什么”记录为调用方提供的固定动作数组。每完成一个可撤销
步骤，就登记一个函数指针和上下文：

```text
状态：Uninitialized
  │ Initialize(storage)
  ▼
Armed ── TryPush(action) ──► Armed
  │                           │
  │ Commit                    │ TryRollback / 析构
  ▼                           ▼
Committed                 RolledBack
```

固定存储意味着它不会为了记录清理动作再次申请内存，也不会在低内存失败路径
制造第二个失败。回滚从数组尾部向前执行，天然还原获取顺序。一个动作失败时
仍继续执行其余动作，因为“第一项清理失败”不能成为故意泄漏全部其他资源的
理由；最终状态会报告整体失败，让上层决定 panic、隔离对象或留下诊断。

它与完整数据库事务仍有差别：硬件写入和外部设备命令未必可逆，回滚动作本身
也可能失败。因此设计时仍要把不可逆提交放在最后，并保证候选对象在提交前
不对并发读者可见。`ScopeRollback` 消除的是重复、易漏的展开控制流，不会
替代所有权分析。

### 引用计数回答“还有谁拥有”，不回答“对象是否正确”

共享对象不能在任意一个使用者退出时销毁。强引用计数把销毁条件定义为最后
一个所有者释放：

\[
  R > 0,\qquad
  \operatorname{release}(R)=
  \begin{cases}
    (R-1,\ \text{not-last}) & R>1,\\
    (0,\ \text{last})       & R=1.
  \end{cases}
\]

计数到零后拒绝重新获取，防止已经进入销毁协议的对象被“复活”；最大值时拒绝
增加，防止整数回绕把大量所有者误表示为零。失败还必须保持输出参数不变，
否则调用者可能根据一半更新的 `is_last` 销毁仍被引用的对象。

引用计数只证明拥有者数量，不证明对象内部状态、关联页表或等待队列正确，也
不能自动解决环引用。当前 v1.11 仍是单 BSP 基线，计数存储使用普通
`uint64_t`，但对象查找与 acquire/release 已在同一管理器锁内提交；最后引用
先把对象从活动集合摘除，再在锁外执行 finalizer。这样冻结了当前并发边界，
却没有伪称已具备 weak reference、无锁升级、SMP 原子引用或循环回收。

### 为什么 Unix 需要“fd”和“打开实例”两层

用户程序看到的 fd 只是当前 Process 内的小整数。早期 Unix 之所以在进程
描述符表之外再维护系统打开文件状态，是因为“名字”和“正在进行的一次打开”
具有不同生命周期：

- `close(3)` 后，整数 3 可以立刻分给另一个文件；
- `dup(3)` 得到另一个整数名字，但两者应共享当前文件偏移；
- 再次 `open(path)` 是新的打开实例，偏移应从头开始；
- `close-on-exec` 只决定某一个整数名字是否跨 exec 保留；
- 读写模式、append 状态和当前偏移属于共享打开实例；
- 管道只有最后一个写引用关闭后，读端才应观察 EOF。

因此关系不是 `fd = file`，而是：

```text
Process FileTable[fd]
    → fd flags
    → strong reference
        → FileDescription
            → file status flags
            → offset
            → underlying file / pipe / console
```

如果 duplicate 时复制 offset，两条路径会各自从旧位置继续，行为等同两个
独立 open；如果 offset 留在 fd 槽内，就无法表达共享。如果把 close-on-exec
放进 FileDescription，又会让修改一个副本意外影响所有引用。这就是 v1.4
必须把两组 flags 放在不同层的原因。

fd 数值复用还产生 ABA 风险：旧 fd 3 关闭后，新对象也可能安装到 fd 3，
甚至 KernelHeap 可能复用同一地址。当前对象 handle 同时记录全局单调
generation；地址相同而 generation 不同仍是另一个对象。generation 不替代
强引用：它负责识别，强引用负责保证对象在操作期间存活。

### 为什么动态 fd 分块不是简单扩大数组

把每 Process 固定数组从 8 扩到 4096 可以通过容量样例，却让所有进程无条件
支付完整空间，并继续把策略限制编码成 C++ 对象形状。分块表每 64 个 fd
申请一次后备：

\[
  \text{allocated bytes}\propto
  \left\lceil\frac{\text{highest touched fd}+1}{64}\right\rceil,
\]

而 hard limit 只是运行时上界。functional 与 capacity 因而可以共享实现，只
选择 256 或 4096。soft limit 可以下降而不销毁已有 fd；它约束新安装策略，
不是对象合法性。

申请分块时不能长期持有 FileTable 锁等待 KernelHeap。实现先记录缺少的 base，
锁外准备候选分块，再锁内复验。若另一路已经提交相同分块，就释放候选；这类
两阶段提交把低内存和未来竞争失败都变成可重复测试的回滚，而不是半插入链表。

### 快照为什么只比较“当前量”

一次成功创建再销毁会让累计创建和累计释放都增加，但当前资源应恢复原值。
泄漏检查因此要区分两类统计：

| 类型 | 例子 | 前后是否应相等 |
| --- | --- | --- |
| 当前所有权 | 活动物理页、KVA 页、活动栈、映射页 | 是 |
| 历史累计 | 成功申请、释放、split、merge、峰值 | 否 |

`ResourceSnapshot` 聚合 26 个当前字段，并先检查管理器内部守恒关系。例如：

\[
\begin{aligned}
F_{\text{accounted}} &=
F_{\text{free}}+F_{\text{allocated}}+F_{\text{reserved}}
\le F_{\text{managed}},\\
F_{\text{unavailable}} &=
F_{\text{managed}}-F_{\text{accounted}},\\
K_{\text{capacity}} &=
K_{\text{free}}+K_{\text{allocated}}+K_{\text{reserved}},\\
S_{\text{kva pages}} &= S_{\text{active}}\times 6,\\
S_{\text{mapped pages}} &= S_{\text{active}}\times 4,\\
S_{\text{guard pages}} &= S_{\text{active}}\times 2.
\end{aligned}
\]

页帧管理上限是地址上限，不是“全部都可分配”的数量。E820 洞、MMIO 与页边界
碎片都保持 `unavailable`；快照不额外占用一个字段，而是从 managed 与三类当前
所有权的差值推导它。64 GiB 规格在 3–4 GiB 附近存在明显 PCI 洞，因此这里
必须使用“小于等于”，不能把地址空间跨度误写成可用 RAM 总数。

如果只比较 frame free 数，一份泄漏和另一份误释放可能恰好互相抵消；如果只
比较栈活动数，陈旧 KVA 描述符或 PTE 也可能被漏掉。跨层快照同时比较这些
视角，并用 64 位差异掩码精确指出首批变化字段。比较函数先写局部候选结果，
只有全部验证成功才修改调用者输出，诊断本身不会交付半份事实。

### 两道真实边界比一个模拟样例更可靠

宿主测试先验证纯状态机和十万事务参考模型，再用真实 frame、buddy、页表、
KVA 与栈管理器组合四个动态栈。目标机还有两道边界：

1. 内存初始化期间创建一个真实双 guard 栈，让外层作用域事务销毁，然后比较
   快照；
2. 四进程运行前拍摄快照，等汇编返回永久内核栈并完成全部安全点回收后再次
   比较。

第一道快速证明基础设施本身可组合，第二道覆盖实际用户 ELF、调度、异常、
文件系统和 IPC 生命周期。256 MiB functional 与 64 GiB capacity 配置运行
同一份实现；前者形成日常阶段门禁，后者额外证明高物理地址和完整容量。这样
“没有泄漏”不再是一句人工观察，而是纯模型、组合测试和真实启动协议共同支持
的可重复结论。

## 22. 为什么 v1.2 必须同时拆 Process/Thread、统一等待并保存 FPU

### “进程”和“线程”为什么在早期系统里常被混写

早期批处理系统中的一个作业通常只有一条执行流，地址空间、打开文件和寄存器
现场天然一一对应。Unix 的 `fork` 又以进程为主要抽象，因此很多教学内核先用
一个 PCB 同时保存 PID、页表、文件和寄存器。它能快速证明保护与切换，却把
两类寿命不同的对象绑在一起：

- Process 回答“哪些执行流共享地址空间、文件和终止关系”；
- Thread 回答“哪份寄存器和栈现在可以取得 CPU”。

一个 Process 有两个 Thread 时，二者共享 CR3 和描述符，却必须拥有不同
RIP/RSP、内核栈、TLS、signal mask 和 FXSAVE 区。调度器若仍选择 Process，
就无法指出究竟恢复哪份 RSP。相反，Thread 退出也不一定能释放地址空间；
只有最后一个 live Thread 离开，Process 才能发布 Zombie 供父进程观察。

因此 v1.2 使用两个状态机，而不是在一个枚举中加入更多状态：

```text
Thread:  Unused → Ready ↔ Running → Blocked → Ready
                           └───────────────→ Exited → Unused

Process: Unused → Alive ──最后一个 live Thread──> Zombie → Unused
```

Exited 是执行现场已经停止但 Thread 对象仍等待安全回收；Zombie 是共享资源
已完成退出、仍保留进程身份和退出信息。两者都不是“内存已经 free”的同义词。

### 为什么 WaitQueue 需要单赢家，而不只是一个 blocked 布尔值

现实等待通常可以由多个事件结束。一次带超时的读既可能因数据到达成功，也可能
因 deadline、signal、关闭或 unmap cancellation 结束。如果每个来源都执行
“把 blocked 改成 ready”，同一 Thread 可能被插入 run queue 两次；两个链
指针随后会形成环或覆盖其他节点。

单赢家协议把完成原因本身当作状态提交：

```text
前置：Blocked，WakeReason=None，仍属于原 WaitQueue
提交：移出队列 → 写唯一 WakeReason → 插入 Ready 尾部
后置：不再属于 WaitQueue，后续完成者只能观察已解决
```

这与 compare-and-swap 的思想相似，但当前单 BSP 通过关中断的调度锁窗口实现。
重要的不是用了哪条原子指令，而是所有完成来源都遵守同一前置条件和唯一提交点。
未来 SMP 会把该协议置于对象锁或原子状态之下，语义不需要重新发明。

等待队列属于“条件可能变化的对象”，不是全局调度器。管道读条件、管道写
条件、控制台输入、Mutex 各有自己的队列；对象关闭才能可靠找到并唤醒所有
相关 waiter。侵入式链接放在 Thread 中，使阻塞不依赖 heap 成功，也让
Validate 可以检查一个 Thread 是否同时错误进入两条队列。

### x87 为什么不是“老旧到可以忽略”

8087 最初是与 8086 配套的可选数值协处理器；后续 x86 把它集成进 CPU，但
保留了八层 x87 寄存器栈、control/status/tag word 等架构状态。MMX 又复用
x87 物理寄存器。SSE 从 Pentium III 引入独立 XMM 和 MXCSR，x86-64 再把
SSE2 作为实用基线并扩展到 XMM15。

这些寄存器不会因为 `IRETQ`、切 CR3 或切内核栈自动变化。若内核只保存通用
寄存器，Thread A 写入 XMM0 后被抢占，Thread B 就能读到 A 的值，既是计算
错误也是跨安全域信息泄漏。即使当前 C++ 用 `-mno-sse2`，用户汇编、编译器
升级或将来的运行时仍可能使用它们，所以必须由内核明确管理能力。

### FXSAVE 区里有什么

64 位模式下 `FXSAVE64` 使用固定 512 字节区域，起始地址至少 16 字节对齐。
核心布局包括：

| 偏移 | 内容 | 长度 |
| ---: | --- | ---: |
| `0x00` | x87 control/status/tag 与 opcode | 8 B |
| `0x08` | x87 instruction/data pointer | 16 B |
| `0x18` | MXCSR 与 MXCSR_MASK | 8 B |
| `0x20` | ST0..ST7/MMX，每槽 16 B | 128 B |
| `0xA0` | XMM0..XMM15，每槽 16 B | 256 B |
| `0x1A0` | 软件可用/保留尾区 | 96 B |

x87 的 80 位值在每个 16 字节槽中保存，不能把它误作八个普通 `double`。
FXSAVE 的简化 tag word 与老式 FSAVE 的完整 tag word 也不同。当前内核不
手工解释这些字段；表格用于审计大小、对齐和测试覆盖，实际保存恢复由硬件
指令完成。

### CR0、CR4 与 CPUID 为什么必须成套配置

`CPUID.01H:EDX` bit 24/25/26 分别报告 FXSR、SSE、SSE2。能力存在并不代表
操作系统已经准备好：

- `CR0.EM=1` 会让 x87 指令陷入仿真，当前必须清零；
- `CR0.TS=1` 会触发 `#NM`，只适用于已经实现惰性切换的内核，当前清零；
- `CR0.MP=1` 使 WAIT/FWAIT 与 TS 语义正确配合；
- `CR0.NE=1` 让 x87 错误经原生异常报告，而不是旧式外部 IRQ13；
- `CR4.OSFXSR=1` 表示 OS 会用 FXSAVE/FXRSTOR 管理扩展现场；
- `CR4.OSXMMEXCPT=1` 允许 SIMD 浮点异常以 `#XM` 报告；
- `CR4.OSXSAVE=0` 明确禁止 XGETBV/XSAVE/AVX 这条尚未管理的状态面。

最后一条尤其重要。AVX 的 YMM 上半部不在 FXSAVE 区中；如果只开放指令却不
保存上半部，XMM 测试看似通过，真实 AVX 数据仍会跨 Thread 泄漏。

### eager 与 lazy 切换的历史取舍

早期浮点运算稀少且 FPU 保存昂贵，内核常在切换时设置 CR0.TS；新 Thread
第一次执行浮点指令触发 `#NM`，内核才保存旧 owner 并恢复新 owner，这叫
lazy FPU switching。它减少不用浮点的切换成本，却引入“CPU 当前 FPU owner”
这一额外状态、异常嵌套、内核浮点禁用和敏感状态清理问题。

现代处理器和虚拟机上的权衡已经不同。本项目更重视可解释性，所以使用 eager：
在抢占、阻塞和退出边界保存当前 Thread，在激活目标 Thread 时恢复。即便时间
片到期后没有真正换人，额外保存也只影响性能，不改变正确性。累计次数在冷路径
输出，热路径不打印。

### 为什么必须用真实用户模式模式测试

只测试 `sizeof(FxSaveArea)==512` 证明不了上下文切换实际调用了两条指令；
只检查 save/restore 计数也证明不了区域属于正确 Thread。因此四个用户程序
安装彼此不同的 XMM0、XMM15、MXCSR、x87 control word 和 ST0：

- XMM0 覆盖常见向量寄存器；
- XMM15 覆盖 64 位模式新增的高寄存器区域；
- MXCSR 证明控制状态也被隔离；
- x87 control word 与 ST0 同时覆盖控制与数据；
- Shell/IPC/worker 分别跨阻塞、唤醒和抢占边界。

每个程序在日志系统调用前后都校验。这样即使输出动作本身污染现场，也无法
误报成功。v1.2 发布时再以 `qemu64,-sse2` 运行同一镜像，证明硬件能力
契约失败时是明确停止，而不是悄悄跳过隔离；v1.3 将这些位并入完整处理器
profile 门禁。

## 23. 为什么 x86-64 原生系统调用需要 CpuLocal、SWAPGS 和返回白名单

### 从软件中断、call gate 到专用快速指令

x86 一直提供多种跨特权级控制转移。保护模式早期可以使用 call gate：GDT/LDT
描述符同时指定目标段、入口偏移、目标特权级和参数复制数量。它通用，却需要
复杂描述符查找，现代操作系统很少把它作为主要系统调用入口。

软件中断更容易复用已有异常基础设施。用户执行 `INT n` 后，CPU 查 IDT gate，
检查 DPL；若从 Ring 3 进入 Ring 0，则读取 TSS.RSP0，换到内核栈并压入
`SS:RSP:RFLAGS:CS:RIP`。Linux 早期 i386 的 `INT 0x80` 因此广为人知。本项目
v0.8–v1.2 也先选它，因为 GDT、IDT、TSS 与 IRET 都已经是异常教学主线的一部分。

随着系统调用频率增加，Intel 引入 SYSENTER/SYSEXIT，AMD 为长模式设计
SYSCALL/SYSRET，Intel 后来也在 64 位模式采用后者。专用指令减少通用门查找，
但把换栈、每 CPU 状态和安全返回策略交给操作系统。它不是“一条更快的
`INT`”，而是一份不同的硬件/软件分工合同。

### SYSCALL 到底自动做了什么

在 64 位模式执行 `SYSCALL` 时，处理器主要完成：

1. 把下一条用户 RIP 放入 RCX；
2. 把用户 RFLAGS 放入 R11；
3. 用 IA32_FMASK 清除当前活动 RFLAGS 的指定位；
4. 从 IA32_STAR 选择 Ring 0 CS/SS；
5. 从 IA32_LSTAR 装入 Ring 0 RIP；
6. 置 CPL=0 并开始执行入口。

它不会：

- 保存通用寄存器；
- 在内存中构造返回帧；
- 从 TSS 读取 RSP0；
- 修改 RSP；
- 自动切换用户和内核 GS base；
- 验证 RCX 中的最终返回地址适合 SYSRET；
- 调用 C++ 函数或理解系统调用号。

所以入口最初拥有“Ring 0 权限 + 用户 RSP”。这是一种危险过渡状态。用户可把
RSP 指向未映射页、只读代码、另一个共享对象或地址空洞；入口若先 `push`，
错误就已经发生。安全顺序必须先获得不依赖用户内存的每 CPU 指针，再从中读取
内核可信栈。

### 为什么 GS 适合保存每 CPU 指针

长模式下，普通数据分段的大多数 base 被忽略，但 FS/GS base 仍是完整 64 位，
并通过 MSR 管理。`SWAPGS` 原子交换 IA32_GS_BASE 与
IA32_KERNEL_GS_BASE，而不需要通用寄存器先保存一个指针：

```text
用户态：
  GS_BASE        = 用户 GS/TLS（当前项目为 0）
  KERNEL_GS_BASE = CpuLocal

SYSCALL 第一条：
  SWAPGS

内核入口：
  GS_BASE        = CpuLocal
  KERNEL_GS_BASE = 用户 GS/TLS
```

此时 `[gs:16]` 可以取得可信入口 RSP。返回用户态前再执行一次 SWAPGS 恢复
两侧。未来用户 TLS 若使用 FS 而不是 GS，这个模型仍成立；关键是用户不能修改
保存在 kernel side 的 CpuLocal 地址。

“两次成对”只是正常局部控制流。若 Thread 在系统调用里退出，内核可能直接
恢复一个更早保存的永久调用栈，绕开普通尾部；此时必须把“已经 swap”当作
显式控制流状态传到非局部恢复桩。看最终 UserContext 的来源无法推断当前硬件
GS 在哪一侧，因为调度器可能已经选择另一个 Thread 的 frame。

### CpuLocal 为什么不是普通全局 current_thread

在单核系统中，全局变量似乎足够，但入口实际需要一组相互约束的状态：

- 当前 Thread 身份；
- 该 Thread 的可信 Ring 0 栈顶；
- IRQ 是否嵌套以及最大嵌套；
- 当前是否位于系统调用中；
- 内核抢占禁止深度；
- IRQ 是否请求返回前调度；
- 原生入口暂存的用户 RSP；
- 返回与安全校验统计。

把它们散落为多个全局变量，很难证明调度切换更新了完整集合。`CpuLocal`
把更新边界变成一个可验证对象；当前只有一个实例，未来每个 CPU 可以各有一个。
TSS.RSP0 与 `CpuLocal.entry_rsp` 看似重复，实际上服务两种不同硬件入口：
interrupt gate 自动读取前者，SYSCALL 汇编读取后者。调度器必须同步写两者。

### STAR 的用户选择子为什么看起来少了 16

IA32_STAR 的低/高字段不是“把最终 CS/SS 原样塞进去”。SYSCALL 使用
STAR[47:32] 作为内核 CS 基值，SS 是 CS+8。64 位 SYSRET 使用
STAR[63:48] 作为基值，再按架构规则得到：

```text
SYSRET SS = base + 8  | 3
SYSRET CS = base + 16 | 3
```

当前 GDT 是 kernel code `0x08`、kernel data `0x10`、user data `0x18`
加 RPL3 得 `0x1B`、user code `0x20` 加 RPL3 得 `0x23`。因此 STAR 的
user base 必须写 `0x10`，完整值形成 `0x0010000800000000`。如果只把
`0x23` 写进高字段，SYSRET 会选择完全不同的描述符。

这也是为什么 GDT 顺序、STAR 纯布局测试和 RDMSR 回读必须共同存在。

### FMASK 清标志不等于丢失用户 RFLAGS

SYSCALL 先把用户 RFLAGS 复制到 R11，再用 IA32_FMASK 清当前 Ring 0 活动
标志。当前 FMASK 清：

| 位 | 原因 |
| ---: | --- |
| TF | 禁止入口第一条后被用户单步陷阱打断 |
| IF | 在可信 frame 与栈形成前禁止可屏蔽 IRQ |
| DF | C++/字符串 ABI 要求向前方向 |
| NT | 不进入遗留嵌套任务语义 |
| AC | 不让用户对齐检查状态泄漏进内核 |

保存到 R11 的原值仍被放入 UserContext。入口随后 `CLD` 只影响内核执行方向，
不会偷偷改写用户现场。因此用户带 DF 进入时，返回验证仍能看见 DF，并选择
能精确恢复该状态的 IRET。

### 为什么 SYSRET 需要白名单

`SYSRETQ` 从 RCX 取 RIP、从 R11 取 RFLAGS，并按 STAR 恢复段。它不从内存
读取五项 IRET frame。问题在于某些非法 RCX/状态会在仍处于 Ring 0 的阶段
触发 #GP；若内核异常路径以为自己在普通用户返回现场中，可能使用错误栈或形成
严重漏洞。历史上的多个内核安全问题都与“在执行 SYSRET 前没有完全规范化用户
控制状态”这一类边界有关。

本项目采用两层集合：

1. 合法用户现场集合：低半规范 RIP/RSP、正确用户段、有效映射、必需
   RFLAGS bit 1，禁止 IOPL/NT/VM/AC/ID 等危险或未支持位；
2. SYSRET 快速集合：合法集合的子集，来源必须为原生 SYSCALL，且不含 DF、
   RF 等当前选择用 IRET 精确恢复的位。

所以返回不是“能 SYSRET 就 SYSRET，否则失败”，而是：

```text
非法现场          -> 不执行返回指令，终止该用户进程
合法快速现场      -> SYSRETQ
合法非快速现场    -> IRETQ
```

规范地址也不等于用户地址。48 位地址的高半规范区属于内核；用户 RIP/RSP
必须落在低半区，并进一步通过实际页表权限检查。

### 为什么要统一 UserContext

INT 0x80、硬件 IRQ 和首次 IRET 已经在内核栈上拥有五项硬件帧；SYSCALL
只有 RCX/R11 和原用户 RSP。若为两条系统调用维护两个 C++ 分发器，参数复制、
阻塞、进程退出、用户地址校验和调度会逐渐分叉。

统一层把“硬件给了什么”转换为“内核保存什么”：

```text
15 general registers
vector + normalized error code
RIP + CS + RFLAGS + RSP + SS
```

固定 176 字节。vector 表示 Initial、HardwareInterrupt、LegacyInterrupt 或
NativeSystemCall。调度器只保存/恢复 UserContext 指针，不需要知道它最初由
哪种指令形成；只有最终返回选择需要查看来源。

### 为什么 IRQ 只设置 need-reschedule

系统调用 C++ 分发器形成可信 frame 后重新 `STI`，因此 PIT/键盘中断可以及时
进入。若 IRQ0 直接在任意 C++ 函数中调用调度器并切换内核栈，原调用链上的
局部对象、锁 guard、返回地址和 GS 状态都可能永远不再按原顺序收束。

当前内核不可抢占的含义不是 Ring 0 永远关中断，而是：

- IRQ 可以打断 Ring 0；
- handler 只处理硬件、唤醒状态并设置请求；
- 真正换用户 frame 只发生在显式阻塞、退出或返回用户态前；
- 返回准备函数消费 `need_reschedule`。

这使“系统调用被 IRQ 打断”和“返回前发生调度”可以分别计数并验证，而不把
每条 IRQ 打成串口日志。

### NMI 为什么不能照搬普通入口

NMI 不受 IF 控制，可能恰好发生在 SYSCALL 已进入 Ring 0、但尚未 SWAPGS，
或已经 SWAPGS、尚未换 RSP 的窗口。普通 handler 若无条件读取 GS，就可能拿到
用户 base；若在当前 RSP 上调用 C++，又可能使用用户栈。

成熟内核会建立 paranoid entry，检查当前 CPL/GS 状态并支持嵌套恢复。本项目
v1.3 先选择最小可证明策略：NMI 使用 TSS.IST2 的独立栈，只写一个固定观察
位并停机，不打印、不取锁、不访问 CpuLocal。它牺牲恢复能力，换来当前阶段
明确的安全边界。

### 这条链如何被证明

纯逻辑测试可以穷举/随机验证 CPUID 位、规范地址、RFLAGS 和 STAR 算术，却
不能证明真实 CPU 使用了这些 MSR。QEMU 正常路径因此必须同时观察：

- MSR 初始化和回读 ready；
- 两条入口对同一调用返回一致；
- 普通原生调用确实从 SYSRET 返回；
- 带 DF 的原生调用确实从 IRET 返回；
- PIT IRQ 真正打断活动系统调用；
- IRQ 请求在返回前被消费并引起调度；
- 可信栈验证覆盖入口，拒绝数为零。

再用 `qemu64,-syscall` 运行同一镜像，missing mask 必须精确包含原生系统调用
位，并在任何用户代码前停止。这样宿主模型、真实指令路径和失败门禁三层证据
共同闭合。

## 24. 为什么 VFS 必须把名字、对象、挂载和打开实例分开

### 从磁盘块到路径，中间缺了哪些概念

磁盘只提供按编号读写的扇区。旧文件系统进一步建立 superblock、bitmap、
inode 和目录项，但用户写下的 `/tmp/session/message` 仍不是一个 inode
number。内核必须回答一串不同问题：

1. 这个路径从哪个根或当前目录开始？
2. 每个 `/` 之间的名字应在哪个目录中查找？
3. `.`、`..` 和重复 `/` 怎样改变遍历？
4. 某个目录上是否挂载了另一个文件系统？
5. 找到对象后，一次 open 的偏移和读写模式保存在哪里？
6. 两个 fd 是共享这次 open，还是各自重新打开？

把这些问题都塞进 `FileSystem::Open(full_path)`，在只有一个根文件系统时似乎
可行；一旦加入 memfs、设备文件系统或新磁盘格式，完整路径就必须被每个后端
重复解析，且不同后端很容易对 `..`、尾斜杠和错误码给出不同答案。

VFS 的本质不是“多写一层抽象类”，而是把命名空间算法从存储格式中拿出来。
后端只回答“在这个目录 vnode 中是否有这个单组件名字”，VFS 决定从哪里开始、
怎样处理特殊组件以及何时跨越挂载点。

### 历史上为什么出现 inode、vnode 与 open file description

Unix 早期文件系统以 inode 表示不含名字的文件元数据；目录项把名字映射到
inode number。名字属于父目录，inode 属于文件系统。于是同一个 inode 可以
有多个名字，重命名目录项也不必搬动文件数据。

当系统需要同时挂载不同文件系统实现时，只写“inode”已经不够，因为 inode
number 1 在每个文件系统中都可以存在。VFS 层因此使用 vnode 一类的通用对象，
把具体文件系统实例与其内部 identifier 组合起来。本项目当前的 vnode 身份
是：

```text
(Superblock address, identifier, generation, NodeType)
```

generation 用来防止将来节点槽位复用后旧引用误认新对象。v1.5 尚无 unlink，
但从第一版就保留代次，避免后续修改所有打开对象形状。

路径找到 vnode 后仍不能把 vnode 直接当 fd。一次打开还具有偏移、读写模式
和状态标志；duplicate 应共享这些状态，两次独立 open 则不共享。这正是 v1.4
已建立的 FileDescription/open file description。v1.5 只把它的底层载荷从
legacy handle 换成 `OpenFile(Path, offset)`。

### 目录项、vnode、Path 和 Mount 分别是什么

四个名字容易混淆：

| 概念 | 保存什么 | 不保存什么 |
| --- | --- | --- |
| 目录项 | 父目录中的名字到子对象映射 | 打开偏移 |
| Vnode | 某后端中的对象身份与类型 | 该对象经哪条挂载路径可见 |
| Path | mount identity 与 vnode | 用户输入的原始字符串 |
| Mount | 父挂载点到子 Superblock 根的连接 | 某个进程的 cwd |

为什么 Path 还要保存 mount？设想同一个文件系统以后被挂到两个位置。vnode
完全相同，但从其中一个位置执行 `..` 应回到该位置的父目录，而不是随机选择
另一个挂载点。即使 v1.5 尚无 bind mount，把 mount identity 放进 Path
仍能冻结正确边界。

### 路径解析是一台有界状态机

路径不是先“规范化成字符串”再一次查表，而是逐组件改变当前 Path：

```text
current = path is absolute ? process.root : process.cwd
for each component:
    empty from repeated "/" -> skip
    "."                    -> keep current
    ".."                   -> MoveToParent(current)
    ordinary name          -> backend.lookup(current, name)
    after lookup           -> FollowMounts(current)
```

这台状态机必须有长度和步数上限。否则攻击者可以让内核在固定内核栈上建立
任意大数组，或让损坏的 mount/parent 链无限循环。本项目使用 4096 字节路径、
255 字节公共组件和 4096 次遍历上限；所有计数是 `uint64_t`，达到边界返回
明确状态。

路径接口同时传地址与长度，不依赖 `'\0'`。这是因为用户缓冲区可能没有终止
符，也可能在终止符前包含内核不愿接受的字节。内核先验证整个用户范围可读，
复制到 4096 字节有界缓冲，再在 Ring 0 中解析。

### `.`、`..` 与根钳制为何不能交给后端字符串处理

`.` 不需要查目录；它只表示当前对象。`..` 却与挂载和 Process root 共同
有关。

普通目录中的 `..` 调用后端 parent。到达某个子 Mount 根时，子后端看到的
parent 通常仍是自身根；真正的命名空间父级在 Mount 对象中。VFS 必须退出
子挂载，找到父文件系统中的 mount point，再取得 mount point 的父目录。

Process root 又可能不是全局 root。安全语义要求在 root 上继续 `..` 仍停在
root，这叫 root clamp。否则将来 chroot 或容器式命名空间会被 `../../..`
逃逸。v1.5 所有 Process 的 root 暂时相同，但 FsContext 已按进程保存，
算法也从第一版执行 clamp。

### 尾斜杠为什么是语义而不是装饰

`/directory/` 的最后一个 `/` 表明最终对象应能作为目录继续遍历。
`/regular-file/` 因此必须返回 NotDirectory。若简单删除所有尾斜杠，
`open("/file/")` 会错误打开普通文件；更危险的是
`open("/missing/", create)` 可能先查找失败，再创建一个普通文件，违背调用者
表达的目录约束。

v1.5 在 Resolve 成功出口检查最终类型；create 分支也在发布节点前单独拒绝
尾斜杠普通文件创建。单元测试同时覆盖已有文件和缺失目标，防止只修成功路径。

### cwd 为什么保存对象而不是字符串

保存字符串看似简单：`chdir("/a/b")` 后把 `/a/b` 复制进 Process。问题是
将来 `/a` 可被重命名，或同一 vnode 可从不同 Mount 到达，缓存字符串就不再
是事实。

FsContext 因而保存 cwd Path。`getcwd` 需要显示时再反向遍历：

1. 从 cwd 调用后端 get-name；
2. 把名字从目标缓冲区尾部向前写；
3. 移动到父 Path；
4. 遇到挂载根时改用父文件系统中的 mount point 名；
5. 到 Process root 后补 `/` 并把结果前移。

反向写能在一个固定缓冲区内完成，不需要递归、动态数组或先知道组件数量。
容量不足时返回 PathTooLong，不返回一条看似合法但被截断的路径。

### memfs 为什么适合先于新磁盘格式出现

如果第一版 VFS 只接一个 legacy 后端，测试通过也可能只是 VFS 恰好顺着旧
接口形状工作。memfs 提供第二个性质不同的后端：

- 没有 ATA、块缓存或磁盘事务；
- 名称可使用完整 255 字节；
- 节点与文件数据来自可回收 KernelHeap；
- sync 是无持久介质的成功边界；
- Destroy 可以直接证明所有内存归还。

同一测试在两个后端运行，才能证明公共契约真正独立于磁盘布局。v1.6 再接入
rootfs v2 时，也可以继续把 memfs 作为语义参考。

memfs 仍不是“无限内存”。每个实例有节点上限和单文件上限；数据从 64 字节
开始二倍增长，并检查乘法与最大值。若实例最大文件只有 17 字节，第一次容量
必须直接取 17，不能因默认初值 64 而越界。集成测试特意使用小于默认增长块的
上限验证这个边界。

### 为什么当前不加入 dentry cache

逐组件 lookup 可能较慢，成熟内核会缓存“父目录 + 名字”的正项和负项。但
缓存会立即引入：

- rename/unlink 后失效；
- negative entry 的过期；
- vnode 与 dentry 引用生命周期；
- mount/unmount 对缓存可见性的影响；
- 并发查找、回收与 RCU；
- 内存压力下 shrink。

v1.5 还没有 rename、unlink 和动态 unmount。此时加入缓存无法完整验证失效
协议，只会让路径错误多一个来源。因此当前明确不缓存；先让两个后端与十万步
参考模型冻结语义，再在有真实修改操作的阶段评估缓存。

### 持久资源为什么不能算作 Process 泄漏

用户在 `/tmp` 写入文件后退出，memfs 文件仍应存在，因为它属于挂载，不属于
某个 Process。若最终快照简单要求 KernelHeap 回到 VFS 建立前的字节数，就会
把正确的持久文件误报为泄漏。

反过来，完全忽略 heap 又会掩盖 FileDescription 或进程栈泄漏。当前做法是
让每个后端报告精确 ResourceUsage：

```text
global resource snapshot
  - registered persistent VFS heap/vnodes
  = process-owned comparison snapshot
```

memfs 自己再通过 Validate 和 Destroy 测试证明登记值真实。分账的关键是
“明确所有者”，不是为了让快照变绿而放宽比较。

### 怎样证明路径实现不是自我验证

单元测试适合精确边界和人为破坏 mount 父链；双后端集成测试适合证明同一
契约；随机测试还需要一个独立模型。

v1.5 的参考模型用宿主 `std::vector<ModelNode>` 保存 identifier、parent、
type、name 和 file bytes。它不调用 memfs 的 parent 或 lookup 来计算预期，
而是自己构造路径、选择节点、枚举子节点并保存文件内容。固定种子执行
100000 步，每一步比较真实 VFS 的状态和模型；失败报告可复现的 step 与 seed。

QEMU 最后证明这些 C++ 逻辑确实经过真实 Ring 3 系统调用、SYSCALL 汇编入口、
Process FsContext、FileTable/FileDescription、VFS 和两个后端。宿主只通过
QMP 逐字输入，不替来宾解析命令或访问文件。

## 25. 从磁盘块到 rootfs v2：历史、硬件与崩溃边界

### 文件系统为什么从“连续字节”演化成 inode

最早的存储可以把一个文件视为连续扇区：起点加长度就足够。它简单，但文件
增长时后面可能已经被别的文件占用；移动整个文件成本高，删除又会制造碎片。
链式分配允许每块指向下一块，却让随机访问必须从头走链，任何断链都可能丢失
后缀。

Unix 的 inode 思路把“目录中的名字”与“文件内容的身份和块索引”分开。
目录项只做名字到 inode 的映射；inode 保存类型、长度、所有权信息和数据块
索引。这样 rename 通常只改变目录边，文件身份不变；多个名字也可以理论上
引用同一个 inode，形成硬链接。

早期 Unix 文件系统使用 direct、single indirect、double indirect，后来又有
triple indirect。直接项让常见小文件无需额外读索引块；多级间接让大文件按需
扩展。ext2 等经典格式沿用了这种容易解释的块树，现代文件系统则常用 extent
描述连续范围。v1.6 选择传统块树，是为了先把逻辑块索引、元数据所有权、
truncate 与 fsck 的因果链完整建立，不代表 extent 不先进。

### 扇区、文件系统块和逻辑块不是一个概念

- ATA sector 是设备传输单位，当前为 512 字节；
- rootfs block 是分配与校验单位，当前也为 512 字节；
- file logical block 是文件 offset 除以 512 后的索引；
- host sparse extent 是宿主文件系统实际保存的一段，不进入来宾 ABI。

它们在当前配置中有相同的 512 字节数值，但职责不同。文件 offset
`offset_bytes` 先分解为：

```text
logical_block = offset_bytes / 512
offset_in_block = offset_bytes % 512
```

RootFileSystem 再把 logical block 解析到 inode 块树中的相对块号，最后加
rootfs 起始 LBA 32768，ATA 驱动才得到设备 LBA。任何一层混用“字节偏移”和
“块编号”都可能把写入送到启动链或盘外，因此各层 API 和常量明确带
`_bytes`、`_block`、`_lba` 语义。

### CPU 到磁盘的真实指令路径

用户态不能执行 ATA `in`/`out`，也不能直接访问 Kernel 地址。以写文件为例：

```text
Ring 3 C++ wrapper
  -> SYSCALL
  -> NASM Intel entry: SWAPGS, trusted stack, UserContext
  -> C++ dispatcher copies user bytes
  -> FileDescription / VFS / RootFileSystem
  -> BlockCache
  -> AtaPioDevice
  -> x86 OUT writes LBA/command, REP OUTSW or looped OUT transfers words
  -> FLUSH CACHE
```

系统调用的第四个参数不能沿用普通 System V 函数调用的 `rcx`，因为
`SYSCALL` 会把返回 RIP 写入 RCX。Linux x86-64 ABI 也选择 `r10` 承载第四
参数；本项目的 rename 因此明确从统一 UserContext 的 `r10` 取得第四项，
再与 `INT 0x80` 路径做等价验证。

Intel 语法中目的操作数在前，例如：

```nasm
mov dx, ATA_COMMAND_PORT
mov al, ATA_WRITE_SECTORS_COMMAND
out dx, al
```

这几条指令只向控制器提交硬件命令。目录查找、inode 分配、CRC 或事务状态都
由 C++20 Kernel 实现，QEMU 不替软件理解。

### 为什么盘面一律显式 little-endian

x86 本身以 little-endian 读写多字节整数，但“当前 CPU 恰好如此”不足以定义
长期格式。盘面明确写 little-endian，Python inspector、未来迁移工具和任何
其他架构宿主都可以按同一规则解码。

直接保存 C++ struct 还会遇到 padding：编译器为了对齐可能在字段之间或结构
尾部加入未命名字节；enum 的底层宽度也可能变化。rootfs 的编码器先把整个
512/320/256 字节对象清零，再按具名 offset 写固定宽度字段，保留区必须为零。
这让“新字段尚未定义”和“磁盘被随机改写”可以区分。

### bitmap 为什么适合固定区域

bitmap 用一位表示一个 inode 或 data block 的分配状态。它的优点是空间固定、
可全盘比较、找空位算法直接；缺点是大规模顺序分配若每次从第 0 位扫描，会
退化为二次成本。

v1.6 保存可回绕 allocation hint：下一次从上次命中之后开始，但 hint 不是
持久事实。即使丢失 hint，扫描 bitmap 仍能得到正确结果。性能状态与正确性
状态分开，是可恢复系统的重要设计习惯。

fsck 不相信 bitmap 本身。它从根目录遍历所有 inode 和块树，重建一张“应该
分配”的 bitmap，再逐位与盘面比较。多一位表示泄漏块，少一位表示两个层次对
同一块所有权理解不同；两者都必须拒绝。

### sparse file 的历史动机

程序常需要一个很大的地址范围，但其中只有少量区域真正有数据，例如数据库
预留区、虚拟磁盘、core 文件或 ELF BSS 映像。若逻辑扩展到 64 MiB 就立即
写 64 MiB 零，不仅慢，也浪费容量。

稀疏文件用“缺少块映射”表示全零 hole。hole 不保存压缩流，随机读仍可直接
定位；写 hole 中的一小段时只分配对应块。安全要求是读 hole 必须主动产生零，
不能把刚从其他文件释放的旧扇区内容暴露给用户。

### unlink 为什么不等于立即释放

成熟 Unix 语义允许：

```text
open("/log")
unlink("/log")
continue writing through the open fd
close(fd) -> finally reclaim inode
```

目录边消失时 inode 的 link count 变为零，但 open-file description 仍拥有
引用。若此时掉电，文件系统还必须知道哪个零链接 inode 需要回收；ext 系列
使用 orphan 机制，journal 也参与保证恢复。

v1.6 尚未建立 orphan list 和 replay，所以打开对象的 unlink/replace 返回
Busy。这是显式阶段边界，不是无意遗漏。直接释放会让现有 fd 指向已复用 inode，
比返回 Busy 更危险。

### rename 为什么是文件系统最难的“小操作”之一

rename 必须同时考虑两个父目录、已有目标、类型、空目录、mount 和祖先环。
若移动目录 `/a` 到 `/a/b/c`，成功后 `/a` 会成为自己的祖先，任何 `..` 或
getcwd 都可能无限循环。实现必须在修改前从 destination parent 沿 parent
链走到根并拒绝 source。

跨文件系统 rename 无法只改两个目录项，因为 inode 和数据块属于不同
Superblock。copy+unlink 又会在中途暴露两个文件或零文件，不等价于原子
rename，所以返回 CrossDevice。

### Dirty/Clean 与 journal 的历史分界

早期 fsck 型文件系统依靠全盘扫描恢复：掉电后检查 bitmap、inode 和目录，
成本随磁盘变大。日志文件系统先把元数据变更写入顺序日志，再写 commit；
启动时只重放有限日志。ordered mode 还要求相关文件数据先落盘，避免新 inode
指向未初始化旧数据。

v1.6 只有 Dirty/Clean：

```text
Clean N -> persist Dirty N -> write/flush changes -> persist Clean N+1
```

它能检测“上次事务没有完整结束”，却没有保存旧值或可重放的新值，因此只能
拒绝挂载。把它称为 journal 会让恢复承诺失真。未来 ordered metadata
journal 必须增加 credit 预留、日志块、commit record、checkpoint、replay
幂等性和逐断电点测试。

### CRC 能做什么，不能做什么

CRC32 擅长发现随机 bit flip、截断和错位写入，计算便宜，适合教学格式。
它不能抵抗故意攻击者：攻击者可修改内容后重新计算 CRC。当前威胁模型是
设备/软件错误检测，不是磁盘加密、签名或防篡改启动。

CRC 也不能替代语义校验。一个校验正确的 inode 仍可能指向另一个 inode 已经
拥有的块；一个校验正确的目录项仍可能制造父链环。因此 Validate/fsck 还要
重建全盘所有权与可达性。

### 测试层为何不能合并

- 格式单元测试证明每个字节偏移和拒绝分支；
- 集成测试证明块树、事务与 VFS 组合；
- 真实容量测试证明 256 MiB bitmap 和 ENOSPC；
- 固定种子随机测试证明长操作序列与两个后端一致；
- QEMU 证明 Ring 3、汇编入口、ATA PIO 和跨进程重启；
- 独立 fsck 证明目标实现之外仍能解释同一介质。

仅在内存设备上通过不能证明 ATA flush；仅在 QEMU 启动成功不能穷举 rename
环或 CRC 偏移；只让 Kernel Validate 自己写出的盘则可能共同带错。多层证据
是不同 oracle 的组合，不是为了堆测试数量。

更完整的实现走读见

[ADR 0033](adr/0033-rootfs-v2-namespace-mutations.md)。

## 26. 从“能运行多个程序”到真正的进程家族

### 为什么固定创建四个程序还不算完整的进程模型

早期阶段由 Kernel 在启动代码中挑选几个内嵌 ELF、创建地址空间并加入
调度器。这足以学习 CR3、Ring 0 栈、抢占和资源回收，却绕开了普通操作系统
必须回答的四个问题：

1. 程序文件由谁命名、从哪里读取？
2. 一个新 Process 是谁创建的，退出状态归谁所有？
3. 旧程序怎样在保持 PID 的同时换成新程序？
4. 父进程先退出时，仍存活或已经 Zombie 的孩子由谁回收？

只在调度器中保存一组 Process 槽无法回答这些问题。调度器关心 Ready、
Running、Blocked 和时间片；父子关系关心“谁能够 wait 谁”和退出状态的
所有权。两套状态相关但不是一回事，所以当前实现用 ThreadScheduler 与
ProcessTree 分别维护，再在运行时事务中同步提交。

### PID1 的历史角色

Unix 进程形成一棵树。最早的用户进程没有普通用户父进程，因此内核赋予它
特殊根身份。现代 Linux 中 PID 1 还承担服务启动、信号策略、关机编排和收养
孤儿等职责；教学内核不需要一次实现完整 init system，但必须先建立最小而
真实的生命周期责任：

- PID 1 唯一，且没有父 Process；
- 普通 Process 必须由一个 Alive 父 Process 创建；
- 普通父进程退出时，孩子重设父进程为 PID 1；
- PID 1 通过 wait 取得每个孩子的退出原因并完成回收；
- PID 1 自身最后退出前，树中不得遗留孩子或 Zombie。

“收养”不是改变孩子的地址空间或调度优先级，只是转移退出状态的回收责任。
若把孤儿直接删除，仍运行的 CPU 现场和内存会失去所有权；若保留已经不存在
的父索引，后续 wait 会引用复用后的错误槽位。稳定 PID 也不能直接等于数组
下标，因为槽位会复用，而身份不能倒退成旧 Process。

### 为什么退出后还要有 Zombie

Process 最后一条 Thread 结束时，其地址空间、内核栈和打开对象可以在安全点
释放，但父进程尚未读取的少量信息仍有所有者：

- PID 与原父 PID；
- 正常退出还是异常终止；
- 有符号退出码；
- 异常向量。

因此 Process 先进入 Zombie。Zombie 不再执行，也不持有普通运行资源，只保存
父进程有权读取的终止记录。父进程 wait 后，记录被复制到用户内存，树项与
调度器槽才变为 Unused。这样“执行资源释放”和“退出信息消费”被分成两个
明确时刻。

若孩子仍 Alive，wait 不能忙循环占用 CPU；当前 Thread 进入 WaitQueue，
孩子退出时定向唤醒父线程。唤醒只表示条件可能改变，用户包装仍会重新发起
wait：期间可能有另一个条件或孩子变化，不能把 wakeup 当作已经取得退出
记录。

### fork、exec 与 spawn 为什么分开理解

经典 Unix 用 `fork()` 复制当前进程，再由孩子用 `exec()` 替换程序映像。
这个组合来自早期 Unix 的简洁进程模型，后来通过写时复制降低实际复制成本。
它也形成 Shell 熟悉的控制流：父 Shell fork，孩子设置 fd/管道后 exec，
父 Shell wait。

当前 v1.11 已有匿名/文件 VMA、只复制调用 Thread 的 COW fork 和外部 Shell
流水线，但尚无
用户多 Thread fork 停世协调，因此先提供：

- spawn：从程序路径直接构造一个全新孩子；
- exec：保持当前 PID 与父子身份，替换当前程序映像；
- wait：消费直接孩子的终止记录。

这里的 spawn 不冒充 fork。它不复制父地址空间，也不继承父 FileTable；
新进程取得独立 FsContext 和标准描述符。这样的阶段划分先把磁盘 ELF、参数
栈、父子树、失败回滚与等待闭合；v1.8 先补齐匿名 VMA 和统一缺页策略，
v1.9 补齐文件页故障与只读共享缓存，v1.10 已在其上实现 COW 和描述符继承。

### exec 为什么必须是候选映像事务

最危险的做法是先销毁旧地址空间，再尝试读取新 ELF。任何路径不存在、ATA
错误、截断程序头、W+X 段、内存不足或参数过大都会让当前 Process 既没有旧
程序，也没有完整新程序。正确顺序是：

```text
旧映像继续有效
  -> 复制路径与参数描述
  -> 打开文件并完成第一遍 ELF 验证
  -> 建立候选页表、映射 PT_LOAD、清零 BSS
  -> 建立候选用户栈和初始现场
  -> 试激活候选 CR3
  -> 原子提交 Process/Thread 记录
  -> 关闭 close-on-exec fd
  -> 回收旧地址空间
  -> 从新 RIP 返回 Ring 3
```

提交点之前失败，只销毁候选对象并返回旧代码；提交点之后出现的不变量错误不能
再作为普通 errno 返回，因为旧映像可能已经回收，当前实现会停机暴露 Kernel
缺陷。`exec` 成功没有“返回 0 到旧调用点”这件事：CPU 下一次回 Ring 3 时，
RIP 已经是新 ELF 入口。

### argc、argv、envp 在硬件上是什么

C++ 的 `char** argv` 最终仍是一组用户虚拟地址。Kernel 不能把自己的指针或
调用者旧地址空间中的指针直接交给新程序，而要把字符串和指针数组都写入候选
用户栈。当前布局从高地址向低地址组织为：

```text
高地址
  参数字符串与环境字符串（各自 NUL 结尾）
  对齐空隙
  envp[0..n-1], nullptr
  argv[0..argc-1], nullptr
  argc
低地址 <- 对齐后的初始 RSP
```

入口寄存器同时得到 `RDI=argc`、`RSI=argv`、`RDX=envp`，使最小
freestanding 入口无需 libc 启动文件也能读取参数。RSP 保持 16 字节对齐，
既满足 AMD64 ABI 的可预期边界，也为以后普通函数调用保留正确栈模型。

参数项与环境项各最多 256 个，字符串连同 NUL 总量最多 128 KiB；当前用户栈
预留 8 MiB，只预提交参数实际覆盖的顶部页。所有计数、地址和加法使用
`uint64_t` 并先检查溢出。限制
不仅防止内存耗尽，也让 Kernel 可以在固定存储中先完成计划，再写候选页。

### 本阶段的证据为什么必须分层

- 单元测试穷举 PID1、父子、Zombie、wait 和参数布局的局部边界；
- 4096 轮集成生命周期证明重设父进程与回收反复执行后恢复空树；
- 固定种子随机测试改变 8192 个孩子的退出顺序，并用独立布局公式比较；
- rootfs 工具测试证明 ELF 字节真的写进嵌套目录并可重新读取；
- QEMU 从自研 ROM 进入真实 Kernel，再经 ATA/VFS 读取 `/sbin/init`，
  真实切换 CR3/RSP、执行 spawn/exec/fork/wait；当前 v1.11 再顺序执行
  VM、fork probe、外部 Shell、重定向和 16 级流水线，并按配置证明 65 或
  88 个 Process 生命周期全部回收。

宿主模型不能证明 x86 页表和系统调用入口；一次 QEMU 成功也不能穷举上千种
退出顺序。只有两者结论一致，才能把“看起来启动了”提升为可回归的生命周期
契约。完整实现走读见
[v1.7 学习章](learning/15-v1.7-pid1-process-tree-exec.md)，设计决策见
[ADR 0034](adr/0034-pid1-process-tree-disk-exec-wait.md)。

## 27. 为什么按需分页必须先有 VMA

页表只告诉处理器“此刻如何翻译”。一个 not-present PTE 不包含缺席原因：
它可能属于尚未触及的匿名区、未来文件页、栈下一页，也可能是 guard 或越界。
如果 Kernel 对任何用户 not-present fault 都分配零页，地址空间隔离会退化为
“访问哪里都能得到内存”。

VMA 增加软件策略层：

```text
VMA = [begin,end) + kind + readable/writable/executable
PTE = present physical frame + current hardware permissions
```

用户 `mmap` 或 `brk` 先建立 VMA。处理器真正访问时把地址写入 CR2，并通过
error code 告诉 Kernel present、write、user、reserved 与 instruction
事实；Kernel 再结合 VMA 决定分配零页、增长栈或终止。成功建立 PTE 后从
异常返回，原指令自动重试。

用户栈还需要保存的 RSP 作为证据。当前只允许 fault page 紧邻 committed
bottom，并与 RSP 位于 64 KiB 邻近范围；永久 guard 完全没有 VMA。这样
“最大栈范围”不是任意写入许可。

撤销时同样要区分 VMA 与 PTE。先 trim/remove/split VMA，再只释放实际驻留
页；最后一个叶项消失时才回收共享的空页表分支。未触及 reservation 没有
frame，不能产生虚构释放。

历史 Unix `brk` 管理连续数据段，`mmap` 后来提供独立区间；用户 allocator
在二者之上管理对象大小。本项目的 `UserHeap` 用 program break 获得页级
容量，再用 boundary header、first-fit、split 与 coalesce 管理 16 字节
对齐块。Kernel 不需要理解用户对象，用户 allocator 也不能越过系统调用直接
修改页表。

完整硬件位、算法和源码顺序见
[v1.8 学习章](learning/16-v1.8-anonymous-vma-demand-paging.md)，设计决策见
[ADR 0035](adr/0035-anonymous-vma-demand-paging-user-heap.md)。

## 28. 为什么 Shell 流水线首先是所有权问题

`a | b | c` 表面是一行文本，内核看到的却是三个 Process、两条字节流和多组
fd 强引用。Unix 让 fd 0/1 成为约定接口，因此 Shell 无需理解 a、b、c 的
内部算法，只需在 fork 与 exec 之间重写孩子的 fd 图。

EOF 来自“所有 writer 引用都已关闭”，不是缓冲区中的特殊字符。只要父 Shell
或无关 child 遗留一个 writer fd，末端 reader 就会永久等待。因此正确顺序是
先创建 Pipe，fork 全部 stage，在 child 中 dup2/close/exec，在 parent 中
关闭全部临时端点，最后 wait 全部孩子。逐 stage 创建后立即 wait 会让大输出
填满 Pipe，而消费者尚未启动，形成必然死锁。

64 KiB Pipe 也不等于创建时占用 64 KiB 物理内存。v1.11 把逻辑环拆成 16 个
4 KiB 槽，首次写入才分配对应页。容量限制约束并发流对象，lazy page 约束真实
内存成本；两者共同存在才能让 64 MiB bootstrap 与 64 GiB capacity 复用同一
实现。

`dup2` 的关键不是“复制整数”，而是让目标 fd 引用同一 FileDescription。
FileTable entry 属于 Process，FileDescription 保存共享状态，Pipe 保存字节与
端点状态。把三层合并会导致关闭一个 fd 就过早 EOF，或多个 fd 错误拥有独立
offset。完整模型和代码走读见
[v1.11 学习章](learning/19-v1.11-unix-io-external-shell.md)。
