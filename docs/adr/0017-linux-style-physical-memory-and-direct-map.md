# ADR 0017：64 GiB 主规格与 Linux 式动态物理内存

## 状态

已接受；64 GiB 动态页帧管理、高半区直映和高内存自检增量已实现。

## 背景

v1.0 的 Stage 1 为进入长模式建立低 64 MiB 恒等映射。v0.6 的内核页帧
分配器直接把这段启动映射当成正式管理上限，并使用固定 4096 字节状态数组。
这一选择适合验证第一套四级页表，却把三个本应独立的概念绑定在一起：

- Stage 1 为继续执行而必须映射的启动窗口；
- QEMU 通过 E820 报告的实际 RAM；
- 内核能够管理和访问的物理地址范围。

在 `-m 64G` 下，QEMU 已经能向自研 Stage 1 交付完整 64 GiB 可用 RAM，
但 v1.0 内核仍把 `MEMORY_MANAGED_BYTES` 截断为 64 MiB。简单修改常量不能
解决问题，因为页表遍历和用户页初始化仍把物理地址直接转换为同值指针；高于
启动恒等映射的帧即使被分配，也不能由内核访问。

## 决策

### 容量与能力分离

正式 QEMU 主规格使用 64 GiB RAM。64 MiB 保留为最小启动和兼容回归配置，
但不再是内核能力上限。

内核必须读取 `CPUID.80000008H:EAX[7:0]` 得到处理器物理地址宽度，再把
以下三个上限取最小值：

1. E820 中最高可用 RAM 页的末端；高地址保留洞不扩大 PFN 状态表；
2. 处理器可表示的物理地址上限；
3. 当前四级内核高半区 direct-map 容量。

64 GiB 只是持续集成和发布验收规格。实现不得用 64 GiB 常量截断 E820，
也不得让分配器容量取决于 QEMU 命令行的已知值。

### 启动映射与正式物理内存分离

Stage 1 继续只建立低 64 MiB 恒等映射。固件、磁盘加载、模式切换和内核
交接均不因正式 RAM 容量扩大而增加不必要的早期页表复杂度。

内核在旧 CR3 下完成以下事务：

1. 验证完整 E820 和处理器物理地址宽度；
2. 在低 64 MiB 可用区中为页帧状态元数据选择连续、页对齐的启动期保留区；
3. 初始化覆盖全部受管物理地址的页帧分配器；
4. 建立新的低端启动映射和高半区 direct-map；
5. 激活新 CR3 后把页表帧访问切换到 direct-map。

元数据大小由受管帧数计算。当前每个 4 KiB 帧仍使用 2 bit 状态，因此
64 GiB RAM 约需要 4 MiB 元数据；实际大小还必须覆盖 E820 中 RAM 洞之前的
物理页号范围。若元数据无法放入启动可访问 RAM，内核必须明确拒绝启动，不能
静默缩小管理范围。

### 高半区物理直映

direct-map 起始地址采用 Linux x86-64 四级布局的
`0xFFFF888000000000`。物理地址 `P` 的普通 RAM 映射地址为：

```text
0xFFFF888000000000 + P
```

当前为 direct-map 保留 64 TiB 虚拟窗口。所有 E820 type 1 RAM 的完整
4 KiB 帧均以 supervisor、RW、NX、普通缓存属性映射：

- 对齐且完整覆盖的内部区间优先使用 2 MiB 页；
- E820 边界和不足 2 MiB 的尾部使用 4 KiB 页；
- 未知、保留和 MMIO 区域不因 direct-map 自动变成普通 RAM；
- LAPIC 等设备继续通过显式 cache-disabled MMIO 映射访问。

direct-map 是物理内存访问机制，不改变页帧所有权。页帧是否可分配仍完全由
E820 类型、启动保留区和分配器状态决定。

### 页表访问与普通地址分离

CR3 和页表项始终保存物理地址。C++ 不再把物理地址直接
`reinterpret_cast` 成指针：

- 新 CR3 激活前，页表帧必须来自启动恒等映射范围；
- 新 CR3 激活后，页表遍历通过 direct-map 得到可解引用虚拟地址；
- 用户页清零、ELF 段复制和高端帧自检同样通过统一转换接口；
- 物理地址宽度、页对齐、加法溢出和 direct-map 窗口必须逐项验证。

### Linux 对齐边界

本决策对齐 Linux 的设计方向，而不宣称 Linux ABI 或实现兼容：

- 对齐 E820/处理器能力驱动的动态容量、高半区 direct-map、启动分配与正式
  分配分层、RAM/MMIO 属性分离和大页优化；
- 当前仍保留低地址内核映像与启动恒等映射；
- 当前正式分页模式仍为四级，LA57 五级分页另行通过启动链 ADR 设计；
- 不复制 Linux 的 `struct page`、伙伴系统、NUMA、内存热插拔或 KASLR。

## 验收

主 QEMU 配置必须以 `-m 64G` 通过完整 v1.0 交互回归，并证明：

- `MEMORY_USABLE_BYTES` 至少为 64 GiB；
- `MEMORY_MANAGED_BYTES` 不再停留在 64 MiB，并覆盖全部 E820 可用 RAM；
- 处理器物理地址宽度、受管最高地址、元数据大小和 direct-map 页数可观测；
- 能从 4 GiB 以上分配一页，经 direct-map 写入和读回两个 64 位模式，再完整
  回收；
- 创建、切换和销毁四个进程后页帧统计仍恢复到基线；
- 64 MiB 最小配置继续启动，且不会错误要求存在 4 GiB 以上 RAM。

主机测试必须覆盖元数据尺寸溢出、E820 洞、启动保留区冲突、2 MiB 对齐边界、
物理地址宽度截断、direct-map 地址溢出和高端帧分配。固定种子随机测试必须
比较页帧状态与参考模型。

## 后果

正面结果：

- 进程、线程、页缓存和 VFS 不再争用固定低 64 MiB；
- 64 GiB 是可重复的真实整机验收，而不是文档中的理论容量；
- 页表与普通物理页共享统一访问规则，为后续按需分页和 COW 提供基础；
- 保留 Stage 1 的小型、可审计启动页表。

代价：

- 内核启动内存事务增加元数据选址和 direct-map 建表失败路径；
- 页表管理器必须同时处理 4 KiB 与 2 MiB 叶项；
- 64 GiB 主配置增加 QEMU 虚拟地址保留量和系统测试启动时间；
- 在完成高半区内核重定位前，低端恒等映射仍是明确保留的过渡机制。
