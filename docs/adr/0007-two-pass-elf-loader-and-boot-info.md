# ADR 0007：两遍 ELF64 装载与固定 BootInfo ABI

- 状态：接受
- 日期：2026-07-24

## 背景

Kernel 磁盘容器只能证明文件被完整读取，不能证明 ELF 声明的目标地址安全。
若 Stage 1 一边遍历程序头一边复制，较早的合法段可能已经覆盖 RAM，而较晚的
非法段才触发失败。此时系统虽然停止，却已破坏加载器、页表或下一次诊断所需
的数据。内核入口还需要知道文件位置、页表和初始栈，不能依赖未记录的寄存器
偶然值。

## 决策

- Stage 1 先把完整 ELF 暂存到低端 RAM，不直接装入目标段。
- 第一遍只验证 ELF 头、程序头表和所有 `PT_LOAD` 的局部与跨段不变量。
- 所有程序头验证成功后，第二遍复制 `p_filesz`，再把
  `[p_filesz, p_memsz)` 清零。
- 初期只接受恒等装载到当前目标窗口的非空加载段；v0.10 将窗口收紧为
  `0x00100000..0x03DFFFFF`，为高地址源暂存区让出不重叠边界。
- 每个加载段必须可读，不能包含未知权限位，且必须满足 W^X。
- 入口固定为 `0x00100000`，并且必须落入可执行加载段。
- Stage 1 在固定物理地址 `0x14000` 构造版本化、定长、仅含 `uint64_t`
  字段的 BootInfo，通过 RDI 传给内核。
- 内核使用独立栈，并在使用 BootInfo 前重新验证其契约。

## 原因

两遍算法把“验证”和“产生副作用”分开，使失败具有事务式边界：要么目标内存
尚未修改，要么所有段都已被证明满足约束。固定宽度 BootInfo 不依赖宿主 ABI
中的 `size_t`、指针宽度或结构体填充猜测，也能通过版本和结构大小演进。

当前采用恒等映射，是为了让 `p_vaddr`、`p_paddr`、复制目标和 CPU 可见地址
一致，先学清 ELF 和交接，再在内存管理阶段引入高半内核映射。

## 未采用方案

- 边验证边复制：实现略短，但失败后目标内存可能只完成一部分。
- 直接从每个磁盘扇区流式写入段：节省暂存区，却显著增加跨扇区 ELF 解析和
  回退复杂度。
- 把 BootInfo 作为若干松散寄存器传递：寄存器数量有限，版本演进困难。
- 直接传递 C++ 指针和平台相关整数：会把当前编译器布局误当作磁盘/启动 ABI。
- 立即装入高半地址：会同时引入非恒等映射、重定位和页表权限，超出 v0.4。

## 后果

- v0.4 最初需要 512 KiB ELF 暂存区和一页加载器临时状态；v0.10 因目标代码
  增长迁移到 `0x03E00000..0x03EFFFFF` 的 1 MiB 暂存区，并在读取前用
  E820 图验证完整 usable 覆盖。
- Stage 1 必须进行程序头两两重叠检查，最坏为二次复杂度；程序头上限 64，
  因此启动阶段成本有明确上界。
- BootInfo 字段变化必须提升版本或定义向后兼容规则。
- BSS 清零、BootInfo 和 CR3 都可以由内核启动日志及系统测试直接验收。
- v0.5 可以在已验证的 C++ 入口上建立内核自己的 GDT、IDT、TSS 与异常路径。
