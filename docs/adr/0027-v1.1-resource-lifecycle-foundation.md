# ADR 0027：用引用计数、作用域回滚与资源快照闭合 v1.1

## 状态

已接受，作为 v1.1 可回收资源基础的阶段收口决策。该决策建立在
[ADR 0020](0020-reclaimable-kernel-heap.md) 至
[ADR 0026](0026-owned-page-table-branch-reclamation.md) 已完成的堆、buddy、
类型缓存、KVA、动态内核栈和页表回收之上，并保持当前四进程执行路径。

## 背景

此前每个资源管理器都能证明自己的局部不变量，但跨资源创建仍有三个空白：

1. 一次操作依次取得 KVA、物理页和页表映射时，调用点必须手写逆序清理；
2. 后续 `FileDescription`、`Vnode` 和共享页需要“最后一个强引用”语义，
   但不能把并发、对象分配和引用计数一次性耦合；
3. 只比较某一类 free counter 会漏掉“总数相同、所有权落在错误层”的问题，
   也会误把累计成功次数当成泄漏。

动态内核栈正好暴露第一项风险。它的创建依赖关系是：

```text
KVA range
  → frame 0 → mapping 0
  → frame 1 → mapping 1
  → frame 2 → mapping 2
  → frame 3 → mapping 3
  → validate → publish
```

任一步失败都必须按严格逆序撤销，而且一个清理动作失败后仍要继续尝试其余
动作。只用一串 `if` 和计数器能够通过当前测试，却会让下一个多资源对象复制
一份稍有不同的错误路径。

另一方面，v1.1 仍是单 BSP、对象模型尚未迁移的阶段。此时直接加入原子引用、
弱引用、RCU 或动态 `KernelObject`，会提前决定 v1.4 的并发和分配策略。
本阶段需要的是可组合的最小语义，而不是最终对象层。

## 决策

### `ScopeRollback` 是外部存储、无分配的补偿事务

`os::foundation::ScopeRollback` 接受调用方提供的固定动作数组。每个动作只由
一个 `noexcept` 函数指针和一个不透明上下文指针组成：

```text
TryPush(A) → TryPush(B) → TryPush(C)
                              │
                 failure ─────┘
                              ↓
                   C → B → A
```

对象状态只有：

- `Uninitialized`：尚未绑定动作存储；
- `Armed`：可以继续注册、提交或显式回滚；
- `Committed`：所有资源所有权已经转移，动作清空；
- `RolledBack`：全部补偿动作成功；
- `RollbackFailed`：所有动作均已尝试，但至少一个失败。

回滚在调用动作前先清除对应槽位，因此失败回调不会被析构路径重复执行。
单个回调失败不短路后续回调，`FailureCount` 汇总全部失败。析构函数只在
`Armed` 状态提供防漏安全网；需要把清理失败传播给上层的路径必须显式调用
`TryRollback`。

动作数组和上下文的生命周期必须覆盖回滚对象。该约束避免隐藏分配、类型擦除
堆对象和异常机制，允许同一实现进入宿主测试和 freestanding Kernel ELF。

动态内核栈创建已经迁移到该事务。九个动作槽对应“一次 KVA 释放”和每个
数据页的“一次帧清零/释放 + 一次撤销映射”。注册顺序与取得顺序一致，因此
失败时自然得到：

```text
最后一页 mapping
  → 最后一页清零并释放 frame
  → …
  → 第一页 mapping
  → 第一页清零并释放 frame
  → KVA range
```

候选栈只有在 guard、映射、权限和所有权校验通过并成功 `Commit` 后才发布到
槽位。

### `ReferenceCounter` 只定义强引用生命周期

`os::foundation::ReferenceCounter` 使用显式 `uint64_t`，不分配内存，也不
隐式采用宿主原子类型。接口语义如下：

| 操作 | 成功条件 | 失败 |
| --- | --- | --- |
| `Start(n)` | 当前为零且 `n > 0` | 零起点或仍有活动引用 |
| `TryAcquire()` | 当前大于零且未到 `UINT64_MAX` | 对象不可用或上溢 |
| `TryRelease(last)` | 当前大于零 | 对象不可用 |

只有从 1 到 0 的转换把 `last` 写为 `true`。失败不得修改输出。归零后不能
通过 `TryAcquire` 复活；只有对象所有者显式 `Start` 才能开启一个新生命周期。

该类当前只允许单 BSP 串行使用，或由调用方在同一把锁内完成“对象查找 +
计数修改”。它不解决 ABA、弱引用、延迟回收或跨 CPU 内存序。v1.4 把它放入
动态对象时，必须同时指定锁归属与对象身份代次；不能因为字段是 64 位就宣称
并发安全。

### `ResourceSnapshot` 只记录当前所有权，不记录累计事件

快照当前跟踪 26 个固定宽度字段：

| 资源层 | 当前字段 |
| --- | --- |
| frame | managed、free、allocated、reserved |
| buddy | active block |
| heap | capacity、consumed、active requested、active allocation |
| KVA | capacity/free/allocated/reserved page、active descriptor/allocation/reservation |
| kernel stack | slot capacity、active stack、mapped page、guard page |
| 扩展槽 | Process、Thread、FileDescription、Vnode、CachePage、BlockRequest |

最后六项在 v1.1 为零，但位位置已经冻结，后续对象层可以接入而不用更改比较
协议。成功申请次数、释放次数、分裂/合并次数和峰值不进入快照，因为它们描述
历史事件；一次完整生命周期之后它们理应增长，不能用于判断当前泄漏。

每个字段映射到一个唯一的 `uint64_t` 差异位。比较前先验证两份快照：

- `free + allocated + reserved <= managed`，且加法无溢出；两者差值是
  E820 保留洞、MMIO 和未对齐边界形成的不可用页；
- buddy 活动块数不超过 allocated frame 数；
- heap 当前占用不超过容量，活动请求字节不超过实际占用；
- KVA `capacity = free + allocated + reserved`，活动对象数不超过描述符数；
- 栈活动数不超过槽容量，mapped/guard 数必须由活动栈数精确推导。

输入无效时比较输出保持不变。有效比较返回变化位掩码和变化字段数；完全匹配
必须同时得到零掩码和零计数。

### 快照进入两个真实生命周期边界

内存初始化完成后，目标内自检执行：

1. 捕获 26 字段基线；
2. 在最后一个栈槽创建真实六页动态内核栈；
3. 把销毁动作注册到一项 `ScopeRollback`；
4. 验证引用计数正常、不可复活和上溢路径；
5. 显式回滚并销毁栈；
6. 再次捕获快照并要求零差异。

因此正常启动累计栈创建/销毁各为五次：一次基础设施自检，加四个真实进程；
峰值仍是四个同时活动的进程栈。

进程运行时在创建任何进程前保存快照，在全部进程退出、地址空间销毁且动态
栈安全点回收后再次比较。差异不为零返回 `ResourceLeakDetected`，不会只依赖
串口宿主检查。

## 测试与验收

- 单元测试覆盖引用生命周期、最后引用、输出保持、上溢、回滚逆序、提交、
  析构安全网、容量耗尽和失败汇总；
- 固定种子 `0x5245534F55524345` 对引用模型和回滚动作组执行 100000 轮；
- 快照单元测试遍历全部 26 个字段位，覆盖守恒失败、输出保持、精确差异和
  完全匹配；
- 集成测试在真实 buddy、页表、KVA 和栈管理器上创建四栈，验证活动快照跨层
  变化，逆序销毁后恢复暖机基线；
- 原动态栈单元、集成和 100000 步随机测试继续通过，证明迁移没有改变成功
  路径或错误语义；
- 具名 256 MiB functional smoke 执行完整四进程、Shell、IPC、文件系统与
  资源快照协议；64 MiB 和 64 GiB 配置继续使用同一实现；
- Kernel ELF 审计必须证明没有异常运行时、隐藏分配或未解析符号。

本决策完成后，完整 CTest 集合为 97 项。

## 被否决的方案

### 继续为每个管理器手写回滚

代码量较少，但动作顺序、短路行为和失败传播会在每个组合对象中重新发明。
动态 Thread、FileDescription 和 VMA 会迅速放大差异。

### 使用异常和 RAII lambda 容器

宿主 C++ 中可读，但目标构建禁用异常和标准库，捕获 lambda 还需要类型擦除或
模板实例化存储。外部固定数组更符合当前可预测内存边界。

### 立即使用原子引用计数

原子加减不能单独解决“先查对象还是先加引用”、对象代次、弱引用和释放时机，
反而会掩盖锁协议尚未定义。v1.2 冻结执行与锁语义、v1.4 引入对象层后再决定
是否需要原子路径。

### 只比较 free frame 数

free 数相同不能证明 KVA 描述符、页表映射、堆活动请求或栈槽已恢复；累计计数
相同又会错误拒绝成功的申请/释放生命周期。跨层当前所有权快照能同时避开两类
误判。

### 在热路径逐项打印资源事件

十万步模型、调度和页故障路径会冲刷串口，并改变时序。目标只在事务完成后输出
有界摘要；详细定位由差异位、宿主模型和调试器承担。

## 后果

- `foundation` 现在除地址类型外，还提供不依赖 Kernel 的生命周期原语；
- Kernel 目标显式链接 freestanding foundation 静态库，宿主模型链接同源
  host 库；
- 动态栈失败回滚不再有私有重复实现；
- v1.2 可以把 Process/Thread 的创建路径建立在同一补偿事务和快照判漏上；
- v1.4 仍负责把引用计数嵌入动态对象，并补充并发、代次和弱引用策略；
- 26 位快照是 v1.1 的诊断协议，不是永久 ABI；字段语义变化必须通过新 ADR
  和测试迁移。
