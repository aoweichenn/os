# ADR 0047：v2 参考机与六个小版本

状态：已接受
日期：2026-08-18

## 背景

v2.0 已冻结为第二周期集成发布。继续把交互、存储、安全和内存压力放进一个
大版本，会让盘面格式、ABI、手机验证和发布证据互相等待，也难以判断某项能力
是否已经完成。

目标运行环境包含 Android 手机上的 Termux/proot。该宿主约有 15.5 GiB
物理内存，但用户要求来宾参考规格固定为 32 GiB RAM 和 128 GiB 存储。

## 决策

1. v2 后续固定为 v2.1 至 v2.6 六个顺序发布：显示与参考机、终端与 Shell、
   128 GiB rootfs v4、本地身份与权限、32 GiB 内存压力、集成冻结。
2. 每个版本只有一个主目标，代码、失败路径、测试、文档、教材、网站和生产
   发布同时闭环；前一版本未发布时不开始下一版本的机制实现。
3. v2.1 参考机使用 32768 MiB RAM。手机验收只要求 QEMU 能建立该来宾并按需
   使用内存，不允许通过启动测试触碰全部 32 GiB；全规模回收、swap 与 OOM
   进入 v2.5。
4. v2.1 启动盘精确为 137438953472 字节，即 268435456 个 512 字节扇区。
   最后一个 LBA 为 `0x0FFFFFFF`，完整覆盖当前 ATA LBA28 地址空间。宿主文件
   必须稀疏；rootfs v2 仍只使用从 LBA 32768 开始的固定 256 MiB 区域。
5. v2.3 只进行一次盘面格式升级，使文件系统使用参考盘容量；v2.1 不伪称
   128 GiB 已经全部成为可分配文件空间。
6. 网络在整个 v2 中都是非目标。SMP、真机 ACPI/PCI/AHCI/NVMe、USB、图形
   桌面和高分辨率 framebuffer 同样不进入这六个版本。

## 原因

128 GiB 恰好是 LBA28 的边界，既能满足当前参考容量，又不要求 v2.1 提前引入
AHCI/NVMe。稀疏镜像只占用实际写入的宿主块，适合手机存储；32 GiB 来宾地址
空间由 QEMU 按需提交，避免把来宾规格误解成宿主必须提供同等空闲物理内存。

版本拆分让 rootfs 格式只改变一次，让权限模型建立在稳定持久元数据之上，
再让 swap、回收和 OOM 使用已经稳定的文件系统与权限边界。

## 后果

- v2.1 的 capacity 运行配置从 v2.0 发布时的 64 GiB 调整为 32 GiB；64 GiB
  纯逻辑与内存可扩展性测试可以保留，但不再是手机参考机。
- 主构建会生成逻辑长度 128 GiB 的多个稀疏故障镜像。复制和同步工具必须
  保留稀疏洞，不能按逻辑长度进行普通字节复制。
- “128 GiB 存储可用”必须等到 v2.3 rootfs v4 验收后才能宣称；v2.1 只冻结
  块设备几何和镜像生成契约。
