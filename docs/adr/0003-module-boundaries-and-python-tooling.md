# ADR 0003：模块目录边界与 Python 宿主工具

- 状态：接受
- 日期：2026-07-24

## 背景

工程基线最初只有一个 `foundation` 实现文件，根 `CMakeLists.txt` 可以直接维护
全部源文件，Shell 也足以串联少量命令。后续将增加固件、引导、处理器机制、平台
设备、内核和用户空间。如果继续集中管理，会让公开接口、私有实现、构建依赖和
测试归属逐渐混在一起。

QEMU 测试还会增加串口捕获、超时、QMP、GDB、失败产物和随机种子。Shell 对结构化
参数、进程生命周期和可测试逻辑的表达能力不足。

## 决策

1. 源码按领域模块组织，每个模块拥有独立 `CMakeLists.txt`。
2. 公开头文件位于 `include/os/<模块>/`，实现和私有头文件位于 `src/`。
3. CMake 只向消费者传递公开包含目录，私有目录不得形成传递依赖。
4. 根 CMake 负责公共策略和模块组合，不维护模块内部源文件清单。
5. 测试先按单元、集成、随机、系统分层，再按被测领域建立目录。
6. 宿主自动化统一使用 Python 3.11+ 标准库。
7. CMake 描述构建图，Ninja 执行构建，CTest 注册测试；Python 只负责调度。
8. Python 启动外部程序时传递参数列表，不使用 `shell=True`。
9. 不为尚未实现的模块预建空目录。
10. 宿主 C++ 测试继续使用显式 `TestContext`，不引入依赖宏注册和宏断言的
    GoogleTest；Python 工具使用标准库 `unittest`，全部测试仍由 CTest 汇总。

## 结果

- 模块公开契约和实现细节具有可由 CMake 检查的物理边界。
- 新模块可以独立定义 host 与 x86-64 freestanding 目标。
- 测试路径能够直接表达测试层和被测领域。
- QEMU、镜像和 ELF 工具拥有可单元测试的 Python 实现。
- 测试代码保持显式控制流，不增加 GoogleTest 外部依赖和宏接口。
- 构建新增 Python 与 Ninja 作为明确宿主依赖。
- Python 不进入目标镜像，操作系统高级语言仍然只有 freestanding C++20。
