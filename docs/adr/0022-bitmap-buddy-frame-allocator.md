# ADR 0022：用双位图伙伴系统管理连续物理页

## 状态

已接受，作为 v1.1 可回收资源基础的第三个完整实现增量。此前两个增量分别是
动态物理内存/direct-map 和可回收 kernel heap。

## 背景

原有 `PhysicalFrameAllocator` 为每个 4 KiB 页帧保存 2 bit 状态，能够区分
unavailable、free、allocated 和 reserved。它已经具备明确的单页所有权、
重复释放拒绝、范围分配与统计，但每次只能取得一页，也不知道相邻空闲页是否能
组成连续块。

后续 KVA、动态内核栈、页表批量后备和某些设备缓冲都需要连续的
\(2^k\) 页。单纯在线性状态数组上扫描连续 free 页存在三个问题：

- 找到连续区间需要反复扫描，释放后也没有可直接复用的块层结构；
- 无法用一个稳定标识记录“本次申请原本是几阶”，错阶释放可能只释放大块的一部分；
- 另挂一套 buddy 而让旧 `Allocate` 继续修改 2-bit 状态，会让两套空闲集合
  立即失同步。

本项目主规格是 64 GiB，代码能力上限由 CPUID、E820 和 64 TiB direct-map
共同决定。不能为每个 PFN 再保存 64 位链表指针：64 GiB 下仅一个指针数组就会
占 128 MiB。分配器还必须在没有 libc、异常、RTTI、全局构造器或自身动态分配
的早期内核中工作。

## 决策

### 保留一个权威分配器

扩展现有 `PhysicalFrameAllocator`，不创建可被旁路的第二个页分配器：

- `Allocate`、`AllocateInRange` 和 `Release` 保持原接口，buddy 启用后把它们
  解释为 order 0 操作；
- 新增 `AllocateBlock`、`AllocateBlockInRange` 和 `ReleaseBlock`，以
  `PhysicalFrameBlock{physical_address, order}` 交付连续块；
- 2-bit 页状态继续回答逐页所有权，buddy 位图回答块的阶和集合成员关系；
- 所有页表、heap 后备页、用户页和进程地址空间继续只依赖这一实例。

宿主早期模型仍可只启用旧的线性单页路径。正式内核必须先完成 E820 初始化和
所有启动保留，再调用 `InitializeBuddy`；从这一刻起，所有分配都走 buddy。

### 阶、对齐与伙伴

order \(k\) 表示 \(2^k\) 个连续 4 KiB 页。块首 PFN 必须满足：

```text
first_pfn mod 2^order = 0
```

同阶块的唯一伙伴由 PFN 的对应位翻转得到：

```text
buddy_block_index = block_index XOR 1
```

只有同阶、完整落入受管范围且当前仍在 free 位图中的伙伴才允许合并。E820 洞、
不完整尾块和 reserved 页天然阻断合并，不能为了形成大块跨越硬件边界。

当前公开最大 order 为 51。它来自 64 位字节地址扣除 12 位页内偏移后的理论
上界；每台机器的实际最大 order 是 `floor(log2(managed_frame_count))`，因此
64 GiB 可用页规模对应 order 24，64 MiB 对应 order 14。

### 双位图元数据

每一阶保存两张位图：

- free 位图：这一阶中哪些完整块是当前空闲集合成员；
- allocated 位图：哪些块首地址以这一阶交付给调用者。

对 \(N\) 个受管 PFN，一组位图的字节数是：

```text
family_bytes =
  Σ(k=0..floor(log2(N))) ceil(ceil(N / 2^k) / 8)

buddy_bytes = 2 × family_bytes
```

总位数小于约 \(4N\)，远小于逐 PFN 的 64 位链表指针。64 GiB 的
16777216 个页需要 8388612 字节精确 buddy 数据；启动选址按页对齐为
8392704 字节。加上原有约 4 MiB 的 2-bit 页状态，总元数据约 12 MiB。

位图由调用者提供连续存储，分配器本身不申请内存。每阶的偏移、长度和空闲块
计数保存在固定 52 元素数组中，不随 RAM 容量扩大。

### 启动事务与保留冻结

内核按以下顺序建立唯一权威状态：

1. 根据 E820、CPUID 和 direct-map 容量计算受管上界；
2. 分别计算页状态和 buddy 精确尺寸，再按页对齐合并为一个元数据区间；
3. 在 Stage 1 可访问的低 64 MiB RAM 中一次性选址，避开低 1 MiB、Kernel
   映像和初始栈；
4. 初始化 2-bit 状态并保留平台、Kernel、栈和完整元数据区；
5. 确认当前没有 allocated 页，再从所有 free PFN 连续段建立 buddy 位图；
6. 初始化页表以及其余内核资源。

`InitializeBuddy` 对每段 free PFN 使用“满足首地址对齐的最大阶”贪心分解，
所以初始集合不会留下本可合并的同阶伙伴。

buddy 启用后，`ReserveRange` 返回
`ReservationAfterBuddyInitialization`。运行期若要撤下普通 RAM，必须另行
设计能够从空闲块中拆出范围、迁移活动页并回滚失败的离线协议，不能悄悄只改
2-bit 状态。

### 分配与失败原子性

申请 order \(r\) 时，从 \(r\) 到实际最大阶依次寻找最小可用源阶。范围接口
要求目标块完整落入调用者提供的页对齐半开区间；源块可以与区间部分相交，但
最终目标块不能越界。

找到源块后先在局部变量中重放全部分裂方向并验证目标，再提交：

1. 从源阶 free 位图移除一个块；
2. 每下降一阶，把未选择的一半放回该阶 free 位图；
3. 在目标阶 allocated 位图登记块首；
4. 把块内所有页状态改为 allocated，并一次提交统计和输出。

没有适合块时返回 `OutOfMemory`，即使总 free 页数足够但因碎片无法形成所需
连续阶也同样如此。无效 order、未对齐范围、越界和溢出拥有独立状态。所有参数
与候选检查在修改位图和输出前完成，普通失败保持状态与输出不变。

### 释放、错阶和合并

`ReleaseBlock` 先验证页对齐、阶对齐、受管边界，以及
`allocated[block.order][block_index]` 精确存在：

- 相同地址被其他阶活动块覆盖时返回 `AllocationOrderMismatch`；
- 没有任何活动块覆盖时返回 `FrameNotAllocated`，包括重复释放和 reserved 页；
- 页状态与活动位图不一致时返回 `CorruptedState`，调用者不得继续假定分配器可靠。

验证成功后清除活动位、把整块页状态改为 free，再逐阶检查 XOR 伙伴。每合并
一次只移除伙伴的 free 位；当前释放块尚未进入 free 位图，因此不会出现一个块
同时属于两阶。最终唯一结果进入最高可合并阶。

### 一致性、统计与日志

`ValidateBuddy` 不申请临时内存，逐阶验证：

- 位图尾部不存在越过完整块数的置位；
- 同一块不能同时 free 和 allocated；
- 任意活动/空闲块都没有已登记的祖先块；
- 同阶空闲伙伴必须已经合并；
- 块内逐页状态与位图身份一致；
- 每阶块计数、加权 free/allocated 页数和 2-bit 统计一致；
- `successful_allocations - releases == active_blocks`。

运行期统计包含元数据字节、最大阶、空闲/活动块数、累计申请/释放、分裂/合并
和当前最大空闲阶。正常启动只输出一次结构化汇总，不逐次记录热路径操作。
QEMU 捕获器仍为每行附加 `[QEMU][T+......ms]`。

### 执行与并发边界

当前 v1.1 仍是单 BSP 串行化路径，分配器内部不获取锁。IRQ、NMI 和 panic
不得调用它。v1.2 冻结 Thread、抢占与锁顺序后，由外层物理内存锁串行化普通
Thread 调用；本 ADR 不提前承诺 IRQ-safe 或 waitable 语义。

## 测试证据

- 单元测试覆盖 64 页精确元数据、缺失/过小存储、已有活动页拒绝初始化、
  最大块分解、递归分裂合并、无效 order、范围失败原子性、错阶、错位、
  reserved 页、重复释放和保留冻结；
- 集成测试构造 1024 页、E820 中洞和低端保留，验证高地址半开范围内 order 5
  连续块，以及 order 0/3/5/6 混合乱序生命周期回到基线；
- 固定种子 `0x425544445936344D` 执行 100000 步随机申请、释放、耗尽和重复
  释放，与逐页布尔参考模型比较，并每 257 步执行完整一致性检查；
- 64 MiB 与 64 GiB QEMU 都实际申请 order 3 的 8 页连续块，经 direct-map
  在首尾页写入两个 64 位模式，再释放、核对页/块统计和完整一致性；
- 64 GiB 用例额外要求 buddy 存储至少 8 MiB、最大阶至少 24、自检块位于
  4 GiB 以上，并继续通过四进程、Shell 和最终资源回收路径；
- Kernel ELF 审计继续拒绝构造器、隐藏运行时分配和未解析运行时符号。

## 备选方案

### 每个空闲块首帧保存链表节点

它接近常见内核实现，扫描更少，但需要在 direct-map 建立前后切换物理页访问
方式，宿主模型还要模拟页内节点。当前位图更容易独立验证，代价是查找需要扫描
对应阶位图。

### 每 PFN 保存 next 指针和 order

实现直接，但 64 GiB 下元数据膨胀到百 MiB 级，不符合教学项目的有界启动目标。

### 只保留 free 位图并相信调用者传回 order

元数据更小，但无法区分正确释放、错阶释放和大块内部指针，会破坏本项目已有的
明确所有权失败语义。

### 完全替换 2-bit 页状态

buddy 位图只描述已登记块，不能单独区分 E820 unavailable、启动 reserved 和
动态 allocated。保留逐页状态让硬件事实、启动所有权和块生命周期各自有明确
职责。

## 后果

正面结果：

- 单页和连续页共享一个权威状态机，现有页表与进程代码无需复制所有权规则；
- 64 GiB 元数据仍有界，并可扩展到 64 TiB direct-map 能表达的 RAM；
- KVA、动态 guard stack 和类型缓存获得可回收连续物理页基础；
- 错阶、错位、重复和保留页释放在提交前被区分。

代价与后续工作：

- 每次块操作仍逐页更新 2-bit 状态，极大块的提交成本与页数线性相关；
- 位图查找不是常数时间，未来可增加每阶非空摘要或 intrusive free list，但不能
  改变公开所有权语义；
- 当前没有 NUMA、zone、每 CPU page list、内存热插拔或并发锁；
- buddy 只管理物理页，不能替代 KVA、kernel heap 或 type cache。
