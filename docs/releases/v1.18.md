# v1.18 发布记录：ABI v2、devfs/procfs 与发布冻结

## 发布结论

v1.18 已完成 v2.0 前最后一个机制开发阶段。现有 69 个系统调用、公共错误
边界、跨 Ring 结构布局和目标 ELF 身份被收束为 ABI v2.0.0；原本只服务
`/dev/console` 的专用后端被替换为职责单一的 devfs；只读 procfs 通过普通
VFS 读取向 Ring 3 提供时间、内存、进程、资源和挂载快照。rootfs 中的用户
工具从 19 个扩展到 32 个，但没有为工具数量新增系统调用。

本阶段仍不使用 BIOS、UEFI、GRUB、Linux syscall、宿主文件系统或第三方
Kernel 组件代替来宾实现。QEMU 只模拟 x86-64 PC、CPU、RAM、ATA、PIC/PIT、
PS/2 和串口硬件；固件、Stage 1、ELF 加载、ABI、VFS、伪文件系统、用户工具
和测试协议均由项目实现。

## ABI v2.0.0 冻结

共享 ABI 新增：

- `version.hpp`：major/minor/patch 为 2.0.0，系统调用号 1--69，公共错误
  区间 -1---57；
- `elf.hpp`：统一 ELF magic、ELF64、小端、`ET_EXEC`、x86-64 machine 和
  program flags；
- `layout.hpp`：以 `static_assert`/`offsetof` 冻结 Pipe、目录项、stat、
  spawn/exec、wait、Thread、signal、文件 mmap、作业事件和终端结构；
- 独立 ABI 单元测试：再检查版本、号值、大小、对齐、字段偏移和 ELF 身份。

Kernel 用户 ELF loader 已消费共享常量，不再维护另一组魔法数字。共享的是
协议事实，不是 parser：Stage 1、Kernel loader 与 Python 产物审计继续作为
不同信任边界的独立实现。

ABI、磁盘、硬件和汇编交接继续只使用固定宽度整数。固定宽度不替代端序、
padding、范围、溢出和用户页权限检查；rootfs 仍逐字段小端编码，syscall
仍先 copy-in/验证，ELF 仍两遍验证后提交。

## devfs

删除 `ConsoleDeviceFileSystem`，新增固定容量 `Devfs`：

- 默认 16 个设备槽；
- 当前注册一个只读字符设备名称 `console`；
- 每项只保存 node id、generation、名称长度、名称和 active；
- 不保存 Terminal、端口或任意驱动指针；
- create/remove/rename/truncate 明确拒绝；
- 注册重名、空名、超长名和容量耗尽在发布新节点前失败；
- open/close、readdir 和拒绝只进入饱和统计，不逐操作刷串口。

用户打开 `/dev/console` 时，VFS/devfs 只解析路径并产生字符设备 vnode，
真正字符流仍由类型化 FileDescription 与 TTY/Terminal 实现。设备命名、
打开对象和驱动行为因此各有唯一所有者。

## procfs

只读 procfs 固定提供：

| 路径 | 内容 |
| --- | --- |
| `/proc/version` | ABI 版本与 `x86_64` |
| `/proc/uptime` | 来宾 PIT 单调纳秒 |
| `/proc/meminfo` | managed/free/allocated 内存字节 |
| `/proc/processes` | 活动 Process/Thread、容量和当前 PID |
| `/proc/resources` | heap、FileDescription、Pipe、vnode、journal commit |
| `/proc/mounts` | VFS mount 数 |

每次 read/stat 采集 15 个 `uint64_t` 快照，在 256 字节局部缓冲中有界格式化，
再执行 offset/short-read/EOF。`stat` 与后续 `read` 可因系统状态变化而得到
不同长度，这是动态伪文件的明确语义。

snapshot provider 调用 memory/process/VFS/journal/time 子系统时不持 procfs
统计锁。统计锁只保护 procfs 自身的 open/read/failure/bytes 计数，避免
`procfs -> VFS/resource -> procfs` 锁环。VFS 资源汇总逐后端 checked-add，
任一失败或溢出都会清空结果，不发布部分快照。

## 32 个用户工具

rootfs 冻结以下独立路径：

```text
help echo cat wc head tee true false pwd ls stat mkdir write touch
rm rmdir mv truncate sync basename dirname cp seq uptime ps free uname
mounts resources sleep kill id
```

新增 13 个工具只组合现有 ABI：

- `basename`/`dirname`：有界用户字符串；
- `cp`：stat/open/read/write/close，打开目标前拒绝同一
  mount/superblock/inode/generation，避免自复制先截断；
- `seq`：有界十进制解析，最多输出 100000 项；
- `uptime`/`ps`/`free`/`uname`/`mounts`/`resources`：读取 procfs；
- `sleep`：检查毫秒到纳秒乘法后使用已有 deadline；
- `kill`：使用已有 signal；
- `id`：读取当前 PID。

`/bin/tool_probe` 在真实 Ring 3 启动中逐个 stat 32 个路径，要求 regular
file、32 个唯一 inode、可读 ELF magic 和全部 fd 关闭，成功才输出
`ELF32_VERIFIED`。256 MiB functional QEMU 再从 Shell 实际执行新增工具。
产物存在和程序可运行因此拥有两类独立证据。

## 测试调度修正

构建图共有 169 项 CTest：

- 145 项宿主单元、集成、随机、产物和源码门禁允许并行；
- 24 项 `os_qemu_*` 共享 `RESOURCE_LOCK os_qemu_system_x86_64`，即使调用者
  使用 `ctest -j20` 也会串行。

冻结前审计发现，并行启动多个 TCG 会让正确的故障用例争抢 CPU，触发墙钟
超时。资源锁把机器约束固化到测试图，不再依赖执行者记忆。修正后没有扩大
用例 timeout，也没有跳过失败用例。

functional QEMU 首次扩展工具覆盖时，串口中已经出现 `tool-basename`，但
验收器错误地把工具输出排在后续作业控制标记之后，导致顺序检查失败。验收
marker 已按真实输入顺序修正；Python 工具测试和 functional QEMU 随后通过。
这一区分保留了真实来宾失败与测试 oracle 错误的证据。

最终源码审计又把 `dirname /alpha//beta/tool` 加入真实来宾输入。第一次执行
暴露了工具只裁剪末尾组件、却没有像 VFS 一样归一化重复分隔符的问题；实现
改为在 4096 字节有界缓冲区内折叠相邻 `/`，重建镜像后的 functional QEMU
通过。该用例防止“内核路径语义正确、用户工具路径语义漂移”进入发布版本。

## 日志和时间

启动新增三个低频边界：

```text
[OS][KERNEL] DEVFS_READY=/dev
[OS][KERNEL] PROCFS_READY=/proc
[OS][KERNEL] ABI_V2_FROZEN
```

单调纳秒。两种时间来源和用途没有混用。

## 已知限制

- ABI v2 是本项目协议，不兼容 Linux syscall/errno/结构；
- 没有动态链接、共享库、能力协商和旧 ABI loader；
- devfs 没有权限、uid/gid、major/minor、注销、热插拔或 udev；
- procfs 没有每 PID 目录、`/proc/self`、符号链接或可写控制项；
- procfs 文本字段没有声明与 Linux 兼容；
- 仍是单 BSP、内核不可抢占，不声称 SMP-safe；
- ATA 仍为 primary master、LBA28、PIO/IRQ14 单飞，没有 DMA/AHCI/NVMe；
- v1.18 冻结已有机制，不把 v2 路线中的 SMP、权限、网络和动态链接视为已完成。
