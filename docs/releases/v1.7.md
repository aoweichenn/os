# v1.7：PID1、进程树与磁盘 ELF spawn/exec/wait

## 阶段结论

v1.7 已把正常启动从“Kernel 内嵌并直接创建若干测试程序”改成真正的用户空间
启动链。QEMU 仍只提供 x86-64 CPU、RAM、IDE、串口、PIT、PIC 和 PS/2
硬件模型；ROM、Stage 1、ATA PIO、rootfs、ELF 加载、用户栈、系统调用、
进程树和 PID1 全部由项目实现。

正常路径现在是：

```text
self-written ROM
  -> self-written Stage 1
  -> freestanding C++20 Kernel
  -> ATA PIO + rootfs v2 + VFS
  -> read /sbin/init as an ordinary file
  -> validate and map ELF64
  -> PID 1 receives argc/argv/envp
  -> PID 1 spawns programs from /bin
  -> exec atomically replaces one process image
  -> wait collects children and adopted orphans
  -> every process/thread/page/fd/VFS context returns to baseline
```

正常 Kernel 不再嵌入 Shell、scheduler worker、pipe producer 或 pipe
consumer。内嵌 ELF 只保留 smoke、用户非法指令和用户页故障三个故障注入
入口；它们是整机失败测试夹具，不是正常启动的程序来源。

## 用户进程 ABI

共享 ABI 新增系统调用 36..38：

| 编号 | 名称 | 成功结果 | 失败保持 |
| ---: | --- | --- | --- |
| 36 | `SpawnProcess` | 新 PID | 父进程和已有子进程不变 |
| 37 | `ExecProcess` | 不返回到旧入口 | 旧地址空间、现场和 fd 继续可用 |
| 38 | `WaitProcess` | 被回收子进程 PID | 非子进程、坏结果地址或运行中子进程不被误回收 |

`ProcessLaunchRequest` 固定为六个 64 位字段：路径地址/长度、参数描述符数组
地址/数量、环境描述符数组地址/数量。每个 `ProcessString` 是 16 字节的
地址与长度；Kernel 不依赖 NUL 扫描来确定用户输入边界。

`ProcessWaitResult` 固定为五个 64 位字段：

- 被回收 PID；
- 执行 wait 的当前父 PID；
- 正常退出或用户异常；
- 64 位有符号退出码；
- 异常向量。

结构尺寸由 `static_assert` 冻结。请求尺寸错误返回 `InvalidArgument`，无法
读取请求结构返回 `InvalidUserMemory`；二者不会被合并成同一个模糊错误。
参数或环境过大返回 `ArgumentListTooLarge`，无可等待子进程返回
`NoChildProcess`。

## 进程树与 Zombie 生命周期

`ProcessTree` 独立保存 PID、父槽位、Alive/Zombie 状态和退出结果。PID 与
调度器槽位仍是两种身份：槽位可以复用，PID 单调增长，wait 对外只接受 PID。

生命周期为：

```text
RegisterInit / RegisterChild
  -> Alive
  -> MarkExited
  -> Zombie
  -> TryWait / CollectInit
  -> Unused slot
```

进程退出时，Thread 先进入 Exited，Process 进入 Zombie；运行时释放用户地址
空间、文件表和 FsContext，但保留最小退出结果。父进程 wait 前先回收已经退出
的 Thread 栈，再从进程树取得一个 Zombie，最后让调度器回收 Process 槽位。
这使“执行资源已经释放”和“父进程尚未取得退出状态”可以同时成立。

非 PID1 父进程退出时，其所有 Alive 或 Zombie 子进程立即重新托管给 PID1。
PID1 必须回收直接子进程和被收养孤儿；仍有子进程时 PID1 不能退出。全部用户
进程结束后，Kernel 使用专用 `CollectInit` 完成最后一个 Zombie 的回收，
因此不存在一个虚构的“PID 0 父进程”。

进程树持续统计 registered、exited、collected、reparented、wait success、
wait block 和 wait no-child，并用 `Validate` 核对：

- PID 唯一且非零；
- PID1 恰好位于唯一 init 槽；
- 每个非 init 项都有可达父项；
- Alive 没有退出结果，Zombie 必须有退出结果；
- active/alive/zombie 与累计注册、退出、回收计数守恒；
- 最终 active、alive 和 zombie 全部为零。

## 从 VFS 分块读取 ELF

v1.7 为用户 ELF 校验器增加 `UserElfReader`：

```text
context + image_size + Read(offset, destination, length)
```

校验器不再要求整个文件先进入连续内核缓冲。第一遍只读取固定 64 字节 ELF
头和每个 56 字节程序头，检查：

- ELF magic、64 位 little-endian、版本、`ET_EXEC` 和 x86-64 machine；
- 程序头表范围、数量和尺寸；
- 只接受 `PT_LOAD`；
- `R` 必须存在，`W+X` 必须拒绝；
- 文件/内存范围、页对齐、重叠、用户地址范围和映射页上限；
- 入口必须落在可执行段内。

只有整份元数据通过后，第二遍才创建候选页表并按页读取 `PT_LOAD` 内容，
余下 BSS 清零，再映射 64 页、256 KiB 的用户栈。任一磁盘短读、VFS 错误、
页分配失败或页映射失败都会逆序销毁候选地址空间。

内存中的故障注入 ELF 继续通过同一个 reader 接口进入相同校验路径，避免
“磁盘 ELF”和“内嵌 ELF”拥有两套安全规则。

## argc、argv 与 envp

参数和环境的公开上限为：

- 参数最多 256 项；
- 环境最多 256 项；
- 字符串内容与每项 NUL 终止符合计最多 128 KiB；
- 初始用户栈为 256 KiB，顶部以下构造布局；
- 初始 RSP 保持 16 字节对齐。

`ProgramArgumentPlan` 先只保存每个字符串的 64 位长度并计算布局，再以 256
字节有界搬运缓冲从旧地址空间分块复制到候选地址空间。大型参数不进入
16 KiB Ring 0 栈。最终布局为：

```text
lower address
  argc
  argv[0..argc-1]
  null
  envp[0..envc-1]
  null
  optional alignment padding
  argument strings with NUL
  environment strings with NUL
higher address
```

用户入口遵循 System V AMD64 的本项目约定：

```text
RDI = argc
RSI = argv
RDX = envp
RSP = aligned initial stack pointer
```

整机测试构造恰好 128 KiB 的参数/环境集合并逐字节验证内容和终止符；再增加
一个终止字节即返回 E2BIG，旧 exec 调用者继续输出证明日志。

## 原子 exec

exec 分成准备、验证和提交三段：

```text
old image remains active
  -> copy bounded path and plan arguments
  -> open ELF through current FsContext
  -> validate metadata
  -> build candidate page table and user stack
  -> activate candidate once as a hardware validity probe
  -> return to old CR3
  -> commit scheduler CR3/RSP metadata
  -> swap runtime ownership
  -> close CLOEXEC descriptors
  -> destroy old address space
  -> install new UserContext and activate candidate CR3
```

提交点之前的任何失败只销毁候选资源。成功后不再执行旧映像；PID、父子关系、
当前 FsContext 和非 CLOEXEC 文件描述符保持不变。v1.4 预先建立的
`FileTable::CloseOnExec` 在本阶段第一次进入真实 exec 成功路径。

当前 exec 只允许单 Thread Process。多线程 exec 的 sibling convergence
属于后续用户线程阶段，不能用“悄悄丢弃其他 Thread”伪造。

## PID1 验收程序

构建工具把普通用户 ELF 离线安装到刚格式化的 rootfs：

```text
/sbin/init
/bin/sh
/bin/smoke
/bin/orphan_parent
/bin/orphan_child
/bin/argument_probe
/bin/exec_probe
/bin/exec_target
/bin/fs_probe
/bin/truncated.elf
```

安装器创建规范中间目录，分配 inode/data bitmap，并能为超过八个直接块的
ELF 构造 single/double/triple 间接树。安装只接受刚格式化的空 rootfs，
重复目标、非法路径、缺失宿主文件、inode 耗尽和块耗尽都明确失败。Kernel
没有新增格式化或“从宿主目录启动”的后门。

PID1 验证自己的 PID、`argv[0]` 和环境后，启动六个直接子进程。测试组合
证明：

- 孤儿父进程先启动子进程再以 23 退出；
- 孤儿子进程以 42 退出并被重新托管、由 PID1 回收；
- 128 KiB 参数和环境逐字节正确；
- 截断 ELF 和 E2BIG exec 失败后旧映像继续运行；
- 成功 exec 保留 PID 并进入新入口；
- 普通磁盘程序可以写入、sync、重读 rootfs 文件；
- Shell 仍经真实 PS/2、系统调用、VFS 和 rootfs 完成命令序列；
- PID1 最后一次 wait 返回 no-child，且没有 Zombie。

## 容量和低内存配置

单个用户 ELF 最多映射 512 个程序页，用户栈固定 64 页。公开限制是安全边界，
不是要求每个程序预分配到上限。

v1.7 正常启动峰值恰好同时拥有八个 Process：PID1、六个直接子进程和一个
被收养孤儿。为使 64 MiB 兼容档也运行完整正常链，bootstrap 容量由 4/4/1
调整为 8 Process、8 Thread、每 Process 1 Thread。256 MiB 与 64 GiB
规格仍分别保持 64/128/32 和 256/512/64。

64 MiB 只是兼容档，不承担高并发压力；但它必须完整运行磁盘 PID1、spawn、
exec、wait、Shell、持久文件和资源回收。64 GiB 主规格继续验证高于 4 GiB
的页帧和全部通用容量实现。

## 日志策略

每个进程只在 spawn、成功 exec、exit、reparent 和成功 wait 的生命周期
边界打印一条聚合日志。不会记录每个参数字节、ELF 页、目录查找或调度 tick，
避免串口输出改变 QEMU TCG 时序。

阶段完成后输出聚合计数：

```text
[OS][KERNEL] PROCESS_TREE_REGISTERED=...
[OS][KERNEL] PROCESS_TREE_EXITED=...
[OS][KERNEL] PROCESS_TREE_COLLECTED=...
[OS][KERNEL] PROCESS_TREE_REPARENTED=...
[OS][KERNEL] PROCESS_TREE_ZOMBIES=0
[OS][KERNEL] PROCESS_TREE_WAIT_SUCCESSES=...
[OS][KERNEL] PROCESS_TREE_WAIT_BLOCKS=...
[OS][KERNEL] PROCESS_TREE_WAIT_NO_CHILD=...
[OS][KERNEL] PROCESS_TREE_VALID
```

来宾继续打印 PIT 单调毫秒；宿主为每行增加 `[QEMU][T+...ms]`。runner 对
总阶段和静默期都设置超时，测试卡死不会留下无限后台 QEMU。

## 阶段边界

v1.7 没有宣称已经具备：

- fork、COW、文件表/FsContext 的 fork 继承；
- 匿名 VMA、按需 ELF、用户 heap 或受控栈增长；
- ELF 文件权限位、动态链接器、共享库或解释器脚本；
- 多线程 exec convergence、ThreadExit 或用户线程；
- 信号、进程组、TTY 作业控制或后台任务；
- dentry/page cache、异步块层或 journal replay。

spawn 当前创建全新的根目录 FsContext 和标准描述符集合；它不是 fork。
当前 ELF 仍是 eager mapping，后续 v1.9 才把文件来源交给 page fault。

下一阶段是 v1.8：建立匿名 VMA、`mmap/munmap/brk`、受控用户栈增长和自研
用户 heap。
