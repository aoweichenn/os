# v1.17 发布记录：ordered metadata journal 与崩溃恢复

## 发布结论

v1.17 已把生产 rootfs 从 Dirty/Clean 拒绝协议升级为格式 3 的 ordered
metadata journal。create、remove、rename、write 与 truncate 的 inode、
位图、间接指针、目录块和 superblock 先进入固定 overlay；相关普通数据稳定
后，系统依次持久化 prepared log、commit、home checkpoint 与 journal 清理。
mount 在读取并信任 home superblock 前恢复。

本阶段不使用宿主文件系统、qcow2 snapshot 或第三方 journal 替代来宾实现。
QEMU 只模拟 x86-64、ATA、PIC/PIT、内存与串口硬件；盘面编码、CRC、credit、
FLUSH 时序、故障注入、replay 和 fsck 均由项目实现。

## 冻结盘面

- rootfs magic：`OSRFV003`，格式版本 3；
- 分区：256 MiB，524288 个 512 B block；
- journal：relative block 4227..4482，共 256 块/128 KiB；
- descriptor：4 块，每块 31 条，共 124 metadata credits；
- payload：最多 124 个完整 512 B metadata block；
- header/descriptor/payload/commit 分层 CRC32；
- sequence：非零 64 位单调值，拒绝耗尽后回绕；
- target：必须在 rootfs 内、不能落入 journal、同一事务不能重复。

编译期断言冻结 payload 末尾、commit block 与 256-block journal 边界。盘面
字段使用显式小端 Store/Load，不依赖 C++ struct padding、宿主端序或平台相关
整数宽度。

## 提交与恢复语义

成功事务的稳定顺序为：

```text
related data home write + FLUSH
  -> header/descriptor/payload + FLUSH
  -> commit + FLUSH
  -> metadata home checkpoint + FLUSH
  -> clear header/commit + FLUSH
```

commit FLUSH 是持久线性化点。它之前断电保留旧 metadata；它之后断电必须
replay 完整新 metadata。checkpoint 写完整块，因此重复 replay 不改变结果。
checkpoint/FLUSH 失败时当前实例冻结，committed journal 不清理，下一 mount
仍能恢复。

commit 前逻辑或 credit 失败会 abort overlay，并恢复 superblock、统计与
allocation hint 快照。释放数据块不会在 metadata commit 前提前清零，避免
旧 inode 在 abort 后指向被主动清空的块。

## 实现范围

- 新增 `RootJournal` 固定容量模块与独立 status/recovery/statistics；
- rootfs Initialize 在 superblock decode 前执行 Recover；
- metadata read 优先查询 transaction overlay；
- inode、inode/data bitmap、pointer block、directory block 和 superblock
  进入 journal；
- 普通数据继续走 BlockCache，commit 前先 sync；
- Create/Remove/Rename/Write/Truncate 的顶层失败统一 abort；
- checkpoint 设备失败冻结 rootfs，remount replay 后可继续；
- Kernel 输出 journal ready、credit capacity 和有界 commit/replay/discard/
  checksum 汇总，不逐块冲刷串口日志；
- Python mkfs/inspect/fsck/bootstrap 与 Kernel 使用相同格式 3 布局，但
  fsck 的可达性 oracle 不复用 Kernel journal parser。

## 测试证据

最终构建图共 164 项 CTest，全部目标均通过。新增：

- `os_kernel_root_journal_unit_tests`：credit、overlay、重复 target、abort、
  commit、prepared discard、坏 header 和坏 committed payload；
- `os_kernel_root_journal_crash_recovery_integration_tests`：1000 个确定性
  Write/Flush crash point；每个恢复结果必须全旧或全新，并再次 Recover
  验证 Clean；
- `os_kernel_root_journal_randomized_tests`：固定种子 100000 步 Begin、
  Stage、Abort、Commit 与非法操作，独立 durable-state oracle。

## 日志证据

QEMU 启动必须观察：

```text
ROOTFS_JOURNAL_READY
ROOTFS_JOURNAL_CREDIT_CAPACITY
```

结束摘要记录 commits、replays、discarded incomplete、checksum failures 和
flushes。事件时间使用来宾 PIT 单调纳秒；runner 的 `[QEMU][T+...]` 只表示
宿主收到串口字节的时间。journal 不打印逐块 stage、CRC 或 replay payload，
避免日志改变 ATA IRQ/PIT 时序。

## 已知限制

- 只保护 metadata，不回滚普通文件旧数据内容；
- 没有 data journal、snapshot、在线扩容或并行 transaction；
- 每事务最多 124 个不同 metadata target；
- 固定单事务、单 BSP，不声称 SMP-safe；
- 没有 `fsync`、`fdatasync`、`msync` 或后台 checkpoint/flusher；
- CRC32 检测随机损坏，不提供恶意介质认证；
- ATA 仍是 primary master、LBA28、PIO 与单飞，没有 DMA/AHCI/NVMe；
- rootfs 工具模块名 `rootfs_v2.py` 为兼容历史入口，实际格式为 3。
