# v1.16 发布记录：IRQ14 块请求与 writeback page cache

## 发布结论

v1.16 已建立可供 Kernel runtime 使用的
`BlockRequestQueue → ATA command → IRQ14/PIT → 唯一完成 → BlockIo wake`
控制流。当前显式 sync 的最终 ATA FLUSH 已走这条真实异步路径；异步 Read
与 Write 命令状态机也已实现，但现有 rootfs 扇区适配器尚未迁移，仍使用
有界同步 PIO。文件页缓存从 clean-only 扩展为
Clean/Dirty/Writeback/Error。完整页 writable `MAP_SHARED` 现可在多个 alias
之间共享修改，经显式 sync 写回文件并等待设备 FLUSH；`MAP_PRIVATE` 修改
仍不回写。

ROM、Stage 1 与 early Kernel 保留有界轮询。QEMU 仍只模拟硬件；请求队列、
IRQ stub/dispatcher、调度、VFS、页缓存、写回和用户探针均由项目自行实现。

## 交付能力

- 64 槽固定存储 BlockRequest FIFO，64 位单调 identifier 与显式 Reap；
- Read、Write、Flush 三种操作，单个 ATA primary in-flight；
- Succeeded、DeviceError、TimedOut、Cancelled 四种冻结结果；
- IRQ14 经 slave IR6、master IRQ2 cascade、LAPIC LINT0 ExtINT 到 vector
  `0x2E`，当前 PIC mask 为 `0xBFF8`；
- IRQ handler 有界处理状态/一个扇区、EOI、定向唤醒和下一请求签发；
- PIT absolute deadline 与 IRQ 单赢家，超时后 ATA software reset；reset
  失败会冻结控制器，队列余项以 DeviceError 有界收敛，不再签发硬件命令；
- `WaitCondition::BlockIo` 与保存/恢复的异步 sync 系统调用结果；
- BlockIo 同时核对 owner Thread 与 64 位请求身份；退出或槽位复用后的迟到
  完成只记为 abandoned，不会唤醒错误 Thread；
- FilePageCache Empty/Clean/Dirty/Writeback/Error 状态与 dirty hard limit；
- Error 页保留、显式重试与不可 clean-LRU 淘汰；
- VFS `WriteAt` 和 UserFileBacking 逐页写回；
- 完整页 writable `MAP_SHARED` 的 write-protect notification；
- sync 前重新写保护 shared PTE，写回后新写可再次标脏；
- unmap、exec 与 exit 在释放可能是最后一个 writable file backing 前强制
  移交尚未写回的页，避免页缓存失去可用 writer；
- fork 保持 FileShared 真共享，FilePrivate 继续 COW；
- rootfs mount generation 在普通数据事务中稳定；
- shared alias 可见、sync 后文件读回与 private 不回写的 Ring 3 探针。

## 状态与失败契约

BlockRequest 只允许：

```text
Unused → Queued → Issued → Completed → Unused
           └──── Cancelled ──────────┘
```

请求完成、设备错误、超时和取消只能有一个结果获胜。Issued 请求不能以普通
取消从队列移除；通用队列中的 Completed 在消费方 Reap 前继续占用槽位。
ATA 适配器会在中断/超时上下文复制冻结结果并立即 Reap，再按
owner+identifier 把结果交给调度器，因此等待 Thread 不直接读取已经复用的
队列槽。容量、非法参数和 identifier 耗尽均在发布新请求前失败。

FilePageCache 只允许：

```text
Empty → Clean → Dirty → Writeback → Clean
                              └────→ Error → Writeback
```

写回失败不会清除 dirty 责任。达到 dirty hard limit 时，shared write fault
在开放 PTE 前失败；不会出现“用户页已经可写，但缓存无法记账”的窗口。

## 测试证据

v1.16 构建图为 161 项 CTest：

- BlockRequest 单元测试覆盖参数、FIFO、单飞、容量、完成、取消、超时、重复
  解析、Reap 与统计；
- BlockRequest 集成测试覆盖 completion/timeout 后下一请求推进；
- 固定种子请求模型执行 100000 步；
- FilePageCache 单元与固定种子 100000 步模型覆盖 dirty limit、Error 保留、
  重试、LRU 与最终守恒；
- PIC/device 集成覆盖 IRQ14 自动开放 master cascade 和 mask `0xBFF8`；
- rootfs 集成冻结 mount generation 稳定与 transaction generation 增长；
- QEMU bootstrap、functional、capacity、persistence 与 failure images
  使用同一目标实现；
- functional probe 验证 writable shared alias、落盘读回和 private 隔离；
- 异步 Flush 验证提交/完成来宾单调时间与 `OTHER_THREAD_PROGRESS=1`。

64 GiB 串行复验还暴露并修复了一个既有作业控制竞态：父 Shell 在 fork 后
发布 foreground PGID 时，尚未运行的 child 仍可能继承 Shell 的 Ctrl-C/Z
handler。现在 Shell 在 fork 前暂时屏蔽这两个信号；child 先恢复默认处置、
加入 PGID，再恢复继承前的 mask。控制信号若落在窗口中只会 pending，解除
mask 时按 child 默认动作处理，不会调用 Shell handler。该修复由同一真实
QMP Ctrl-Z/Ctrl-C 容量路径回归。

远端编译与测试只在验证机的独立临时目录中执行，构建并发上限为 4，并使用
低 CPU/IO 优先级；不修改或终止机器上的其他任务。
宿主测试允许并行，资源敏感的交互式和 64 GiB TCG QEMU 另以单任务有限超时
复验。

## 日志策略

不记录每次 ATA status poll、PIO word、cache hit 或 PIT 检查。低频语义边界
包括：

```text
ATA_IRQ14_READY
ATA_REQUEST_CAPACITY=0x40
FLUSH_SUBMIT_REQUEST
FLUSH_SUBMIT_TIME_NS
COMPLETION_RESULT
COMPLETION_TIME_NS
OTHER_THREAD_PROGRESS
FILE_SHARED_WRITEBACK_VERIFIED
```

请求时间来自来宾 PIT 单调时钟；QEMU runner 的 `[QEMU][T+...ms]` 是宿主
串口到达时间，只用于定位卡住位置。写回只在 sync 边界输出汇总，避免日志
反过来改变 IRQ/调度时序。

## 已知限制

- ATA 仍为 primary master、LBA28、PIO 与单飞；没有 DMA/AHCI/NVMe；
- rootfs 的普通扇区 Read/Write 尚未迁移到 BlockIo；本阶段真正阻塞等待
  IRQ14 的生产消费者是显式 sync 的最终 FLUSH；
- shared writable 只接受完整文件页；
- 本阶段只有显式全局 sync，没有 `msync` 或后台 flusher；
- 持续设备错误会让 Error 页保留并最终产生回压；
- rootfs 仍只有 Dirty/Clean 拒绝协议，没有 journal/replay；
- 单 BSP，不宣称 SMP-safe I/O completion。
