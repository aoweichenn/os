# v1.12：用户 Thread、FS-base TLS 与 private futex

## 阶段结论

v1.12 已完整建立同一 Process 内的用户并发闭环：

```text
Thread runtime maps stack + guard + TLS
  → CreateThread publishes TID and schedulable context
  → FS-base restores per-thread runtime
  → user atomics use private futex on contention
  → ThreadExit publishes value
  → Join reclaims KernelStack, user stack and TLS
```

QEMU 仍只提供 x86-64 CPU、RAM、串口、PIC/PIT、PS/2 与 IDE 硬件模型。线程
运行库、TLS、同步原语、futex 和所有回收均为项目代码。

## 交付内容

- 系统调用 47--53：Create/Exit/Join Thread、SetTLS、GetTID、futex wait/wake；
- 48 字节 `ThreadCreateRequest` 和 16 字节 `ThreadJoinResult`；
- 64 KiB 用户栈、一页低端 guard 和一页 TLS runtime；
- IA32_FS_BASE 随 Thread 切换恢复；
- 单调 AddressSpaceId 与 `(AddressSpaceId, aligned VA)` private futex key；
- 512 entry futex 管理器和原子 compare-and-block；
- `munmap`、`exec`、ProcessExit/异常取消；
- 用户 `Thread`、`Mutex`、`ConditionVariable` 与 `Once`；
- rootfs `/bin/thread_probe` 与三档自适应验收。

## 三档规格与结果

| 档位 | RAM | Process/Thread 容量 | 单 Process Thread | v1.12 验收 |
| --- | ---: | ---: | ---: | --- |
| bootstrap | 64 MiB | 8/8 | 1 | 创建被明确拒绝，单线程降级完成 |
| functional | 256 MiB | 64/128 | 32 | main + 31 worker，下一次创建被拒绝 |
| capacity | 64 GiB | 256/512 | 64 | main + 63 worker，第 65 个 Thread 被拒绝 |

三档均从同一镜像启动。64 GiB 主规格真实管理完整 64 GiB RAM，并在本阶段
完成 64 Thread、TLS/futex/Join 与资源守恒。

## 并发语义

Thread 共享 Process 的 AddressSpace、FileTable、FsContext 和 ProcessTree
身份；每个 Thread 独占 TID、通用/FXSAVE 现场、KernelStack、用户栈、
FS-base TLS、signal mask 预留和等待关系。

普通 ThreadExit 不关闭共享资源。Join 是用户栈/TLS 的回收点；Kernel 先回收
Exited Thread 的 KernelStack 和调度槽，用户运行库再 `munmap` 栈与 TLS。
ProcessExit 和用户异常则终止所有 sibling，关闭 Process 资源并由父 wait
完成最终收集。

`fork` 继续只复制调用 Thread。多线程 `exec` 在候选映像完整成功后取消旧
futex waiter、终止 sibling，并让调用 Thread 接管新映像；候选失败不改变旧
Thread 集合。

## TLS

用户运行时把 `ThreadRuntimeState::self` 放在 FS:0。Kernel 在每次
`ActivateThread` 时写 IA32_FS_BASE；系统调用入口/返回不再写 FS selector，
避免长模式隐藏 base 被覆盖。

整机探针为每个 worker 检查：

- FS:0 指向各自唯一 runtime state；
- runtime TID 与 `GetThreadId` 一致；
- 经 barrier 阻塞、mutex/futex 竞争、系统调用和 PIT 抢占后地址与 TID 不变。

## private futex 与同步原语

wait 在调度器 irq-save 临界区中重新比较 32 位 word，再取得 entry 并入队；
wake 在同一临界区查找、FIFO 唤醒并释放空 entry。相同 VA 只有在同一
AddressSpaceId 内才共享等待队列。

用户态：

- Mutex 用 compare-exchange 快路径和 futex 竞争路径；
- ConditionVariable 用序列号封闭 unlock/wait 竞态；
- Once 用三态原子状态和 wake-all 发布完成。

日志按二次幂节流，只报告 1、2、4、8……次 create/exit/join/wait/wake，不把
每次同步变成串口调度扰动。

## 实现中捕获的问题

整机与生命周期审计发现并修复：

1. 高地址用户栈曾被错误套用 ELF 程序窗口检查，导致合法返回帧被拒绝；
2. `OS_STAGE` 一度仍为 v1.11，PID1 正确拒绝了不一致环境；
3. 子 Thread 曾依赖父 Thread 在 Create 返回后写 TLS TID，存在子先运行竞态；
4. Kernel 曾在 Thread runtime/context 完成前恢复中断，存在半发布 Ready
   Thread；
5. 系统调用入口写 FS selector 会覆盖 IA32_FS_BASE；
6. 直接终止 Blocked sibling 时 WaitQueue wake 账本未计取消；
7. v1.11 的 Process=Thread 和 KernelStack 生命周期公式无法表达用户
   Thread，需要分别统计成功 Thread 与创建失败回滚。

这些问题都不是只读 API 单测能够替代的；需要真实 PIT 抢占、系统调用返回和
整机资源快照共同暴露。

## 阶段边界

v1.12 不宣称：

- SMP、多核 futex 或跨核 IPI；
- futex timeout、absolute deadline 或 wall clock；
- signal handler、异步取消和 robust mutex；
- detached Thread、递归 mutex、读写锁和 barrier；
- pthread/libc ABI；
- TTY、进程组或 job control。

下一阶段 v1.13 在统一 WaitQueue 和现有 PIT tick 上建立单调时间、deadline、
sleep 与 timed wait。
